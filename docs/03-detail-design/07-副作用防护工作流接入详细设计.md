## 2. `ExecutionGuard` 接口

**一个执行入口，内部固定顺序**（这是 arch D1 的落地）：

```cpp
// cppchain —— tool/exec_guard.hpp

namespace cppchain::tool {

// 审批判定：返回 false → 拒绝。why 会塞进 error ToolMessage 回喂。
using Approver = std::function<bool(ToolCall const&, ToolSpec const* spec, std::string& why)>;

// 审计一次判定。decision ∈ {allow, deny, replay, blocked_unknown}
struct AuditRecord {
  std::string ts;            // ISO 时间
  std::string tool;          // 工具名
  std::string args_hash;     // canonical args 的 hash（不落原文，原文在会话日志里）
  std::string decision;      // allow / deny / replay / blocked_unknown
  std::string who;           // host | model（谁发起的这次调用）
  std::string why;           // 人读的缘由
};

class ExecutionGuard {
 public:
  struct Options {
    Approver approver;                          // 空 = 全部放行
    // 防重放。note: 传 journal 就开启防重放；null = 不防（纯审批 + 审计）。
    agent::ToolExecutionJournal* journal = nullptr;
    // 审计目标。不落盘时可用内存计数（离线测试断言）。
    std::function<void(AuditRecord const&)> audit = nullptr;
    bool retry_on_failure = false;              // 透传给 journal 的三态语义
    std::string key_prefix;                     // 多租户隔离
    std::size_t max_parallel_serial = 8;        // batch 内"先串行审批后并行执行"的分批上限
  };

  explicit ExecutionGuard(Options opts) : opts_(std::move(opts)) {}

  // 执行一次工具调用。内部：审批 →（重放命中?）→（登记意图）→ handler →（记结果 + 审计）。
  // spec 允许为空（未知工具）：审批仍走，执行交给 ToolNode 的 unknown 分支。
  [[nodiscard]] message::Message execute(ToolCall const& call, ToolSpec const* spec,
                                         nlohmann::json const& args,
                                         std::string_view who = "model");

  // —— 两步 API（给 c_run_tools 的 batch 场景：先串行 prepare、再并行 run）——
  // prepare：串行段。审批 + 查重 + 登记意图，把本 call 的"放行决定/要重放的结果"定下来。
  struct Prepared { bool approved = false; bool replay = false;
                    message::Message replay_msg; std::string why; };
  [[nodiscard]] Prepared prepare(ToolCall const& call, ToolSpec const* spec,
                                 std::string_view who = "model");
  // run：并行段。只有 prepare 后 approved==true 才调。真执行 or（replay 时）回放已定结果。
  [[nodiscard]] message::Message run(ToolCall const& call, ToolSpec const* spec,
                                     Prepared const& p, nlohmann::json const& args);

  [[nodiscard]] std::size_t denials() const;      // 拒绝次数
  [[nodiscard]] std::size_t replays() const;      // 重放次数
  [[nodiscard]] std::size_t executions() const;   // 真实执行次数
  [[nodiscard]] std::size_t audit_lines() const;  // 内存审计条数（未落盘时）

 private:
  Options opts_;
  // 计数器用 mutex 保护 —— execute 可被 batch 并行调用；计数必须线程安全。
  mutable std::mutex mu_;
  std::size_t denials_ = 0, replays_ = 0, executions_ = 0;
  std::vector<AuditRecord> mem_audit_;
};

}  // namespace cppchain::tool
```

**要点**：
- **审批回调签名与 agent 层不同**：agent 的 `ToolApproval::approve_tool_call(call, why)` 只有 call；
  这里拿到 `spec` 是为了**只读免审**（`spec->read_only` 为真直接放行）与按 `read_only` 分类。
  默认 `Approver` 行为就是把 `ToolApproval`（名单/Decider）包进来；`ToolApproval` **不改**，
  只作为构造 `ExecutionGuard` 时的外部判定器。
- **事务边界**：`execute` 内先 `审批`；审批不通过 → 直接返回 error ToolMessage（循环不打断）、
  审计记 `deny`、计数；审批通过 → `journal->find(key)` 三态：
  - 未见过 → `record_intent`（**执行前落盘**）→ handler → `record_result` → 审计 `allow`；
  - `Completed` → **重放记录结果**、不动盘 → 审计 `replay`；
  - `Intent` → 拒绝并回喂"结果未知，请人工确认" → 审计 `blocked_unknown`；
  - `Failed` → 默认拒绝（可 `retry_on_failure=true` 允许重跑）。

## 3. 关键算法与线程约束

### 3.1 幂等键

复用 `agent::SideEffectGuard::key_for` / `prefixed_key` 同一套逻辑（`ToolCallId` 或
`ToolNameAndArgs` + `key_prefix`）。本期默认 `ToolCallId`（与 agent 层一致）。

### 3.2 Workflow 两个执行点的形状差异 —— 难点在 `c_run_tools`

| 执行点 | tool_call_id 来源 | 并发 | 挂 guard 的方式 |
|---|---|---|---|
| `c_tool`（单工具节点） | `node_id`（**稳定**） | 无（单 handler） | handler 外包一层 `guard->execute(call, spec, args)` |
| `c_run_tools`（batch） | **模型生成的 `call.id`**（不稳定） | `ToolNode` 批内并行 | **先串行审批全部 calls → 再交给并行 handler** |

**`c_run_tools` 的"先串行后并行"是必须的**：
`ExecutionGuard::execute` 内部有 `journal`（FileJournal）读写与计数，它们不是线程安全的；
ToolNode 用 `std::async` 做批内并行（`max_parallel=4`），直接每个线程进 `execute` 会
**并发读写 journal**。方案：在 `c_run_tools` 里**先对整批 calls 逐个做"审批 + 查重/登记意图"**
（此阶段串行、落盘、把每个 call 的决定记到临时数组），然后再把"已登记 & 通过"的批量
`std::async` 到 handler 并行执行。这样：
- 串行段保证 journal/审计只在**单线程**访问；
- 并行段只有 handler 本身（工具是幂等的 or 已登记过，不碰 journal）；
- 结果顺序仍按下标回填（ToolNode 已有该约定）。

实现上更简单：给 `ExecutionGuard` 拆两步 API——`prepare(call, spec) → PrepareResult`（串行段：
审批/查重/登记意图）与 `run(call, prepare, args)`（并行段：真执行/重放）。`execute` 保持为
两步的便捷组合（对 `c_tool` 无并发时可一步用）。

### 3.3 只读免审 & 不记账

`spec->read_only == true` → 审批直接放行、不查 journal、不记审计（`file_read`/`list_dir` 与
读文件相关的操作不留下决策记录 —— 它们不构成风险）。

## 4. `CompileContext` / `CompileOptions` 扩展

```cpp
// workflow/node_type.hpp —— CompileContext 加槽位（footer 最顶）
tool::ExecutionGuard const* guard = nullptr;

// workflow/compiler.hpp —— CompileOptions 加字段
tool::ExecutionGuard const* tool_policy = nullptr;  // 副作用防护；null = 不防护（现状兼容）
```

`compile_workflow` 把 `opts.tool_policy` 填进每个节点的 `CompileContext.guard`。
`c_tool` / `c_run_tools` 两个编译函数拿到非空 `ctx.guard` 才包执行（**null 时行为与现状完全一致**，
保证既有 5 个内置 workflow 与 585 测试不回归）。

## 5. wfr 装配

```cpp
// wfr/main.cpp（伪代码要点）
tool::FileToolsConfig ft_cfg;            // 已有：沙箱根 = 工作区
ft_cfg.root_dir = std::filesystem::absolute(workdir);
registry.add(make_file_read_tool(ft_cfg));    // 已有（只读）
registry.add(make_list_dir_tool(ft_cfg));     // 已有（只读）
registry.add(make_file_write_tool(ft_cfg));   // 新增：read_only=false → 受 guard 管控

// chat 工具集 += file_write
comps.toolsets["chat"] = {"get_weather", "web_search", "file_read", "list_dir", "file_write"};

// 审批策略：白名单回调 —— 只允许写工作区内已 resolve 的路径（沙箱纪律之外，写也限制范围）
tool::ExecutionGuard guard{{
    .approver = [&registry](ToolCall const& call, ToolSpec const* spec, std::string& why) {
        // spec->read_only → true（免审）；名字不在策略名单内 → false
        return tool::file_write_allowed(registry, call, why);  // 新 helper 或内联
    },
    .journal = &journal,           // FileJournal：.wfr/sidefx/{session}.jsonl（跨进程防重放）
    .audit   = audit_sink,         // 追加写 .wfr/audit/{session}.jsonl（原子写 + fail-closed）
}};
// CompileOptions.tool_policy = &guard;
```

审计落地点沿用 `.wfr/` 统一元数据目录纪律（arch 14）。

## 6. 审计记录 Schema

```json
{"ts": "2026-10-11T10:00:00+08:00", "tool": "file_write", "args_hash": "e3b0c442…",
 "decision": "deny", "who": "model", "why": "路径未在白名单内"}
```

- `args_hash`：canonical args 的 SHA-256（树原文在会话日志，audit 不重复存，省空间、防泄露）。
- `decision` 五值闭集：`allow / deny / replay / blocked_unknown / allow_readonly`（只读工具可选记，
  默认不记，见 3.3）。
- 原子写 + fail-closed：与 `FileJournal` 同一纪律（写临时文件 → rename；损坏抛异常不静默降级）。

## 7. 测试计划

### 7.1 单测 `tests/tool/exec_guard_test.cpp`（离线确定性）

| 组 | 覆盖 |
|---|---|
| 审批 | approver 拒绝 → deny + 计数 + error ToolMessage（不抛错）；`spec=null` 未知工具仍走审批 |
| 审批通过 | allow + 真实执行 + 审计 allow |
| 重放 | journal `Completed` → 不动盘、审计 replay、executions 不增 |
| Intent | 拒绝重跑 + 回喂"结果未知" + 审计 blocked_unknown |
| Failed | 默认拒跑；`retry_on_failure=true` 允许重跑 |
| 只读免审 | `spec->read_only=true` → 不经 approver、不查 journal、不审计 |
| 事务边界 | 拒绝路径不走到 executions（problems/03 §5 陷阱的断言化） |
| 线程 | `prepare` 串行段在多 call 下 journal 原子性；`execute` 并发调用计数不丢 |

### 7.2 workflow 集成 `tests/wf/side_effect_workflow_test.cpp`

单张图里 `c_tool` 与 `c_run_tools` 两条执行路各跑一轮：
- `c_tool`（显式 tool 节点，如 `file_write`）：guard deny → 节点产出 error ToolMessage、审计 deny、
  磁盘文件**未创建**（磁盘断言，不看模型说什么）；
- `c_run_tools`（batch，chat 式）：模型调 `file_write` → 审批拦 → `[重放]` 不写盘两次；
- 只读对照：`file_read` 免审、不记账、审计不增行。

### 7.3 真机（wfr，可选本轮结尾做）

- 中危工具演示 + 计数/审计断言（**不做高危工具**：模型自己会拒，中间件没被走到 = 假象）。
- `file_write` 端到端：prompt 里明确要求写 2 次 → 断言：磁盘 1 个文件、审计 1 行 allow、1 行 replay
  （或按策略 deny 的那次不写盘）。
