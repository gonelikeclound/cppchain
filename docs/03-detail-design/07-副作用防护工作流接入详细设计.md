## 2. `ToolSpec::probe` 与 `ProbeResult`

```cpp
// include/cppchain/tool/probe.hpp
namespace cppchain::tool {

enum class ProbeResult {
  Complete,  // 产物存在且完整（如：文件存在、内容签名匹配）
  Partial,   // 产物存在但不完整（如：写一半的残缺文件）
  Absent,    // 产物不存在（副作用没发生过）
  Unknown,   // 无法探测 / probe 自身失败或被中断 → 调用方按 Intent 原义 fail-closed
};

// 便捷 helper：按文件存在性 + 内容签名判定（file_write 的磁盘 probe 就是这么写的）
[[nodiscard]] ProbeResult probe_file(std::filesystem::path const& p,
                                     std::optional<std::string> expected_content,
                                     std::optional<std::size_t> expected_bytes);

}  // namespace cppchain::tool
```

```cpp
// tool.hpp 的 ToolSpec 增字段（保持向后兼容：缺省 nullptr = 无探测能力）
std::function<ProbeResult(nlohmann::json const& args)> probe = nullptr;
```

**`make_file_write_tool` 实现它的 probe**：`probe` 收到 `{path, content, append}` →
`probe_file(resolve_path_in_root(root, path), append? nullopt : content, nullopt)`：
- 文件不存在 → `Absent`；
- 文件存在且内容与本次参数一致 → `Complete`；
- 文件存在但内容不一致 / 比目标短 → `Partial`（追加模式无法只比对，报 `Unknown`→fail-closed，稳妥）。

**probe 铁律**：
1. **只读**——不得有任何写入/副作用（否则 probe 自己进防重放递归）。
2. exec_guard 调用 probe 时**视为非副作用**：不记账、不触发自身探测。
3. probe 抛异常 / 被打断 → 调用方按 `Unknown` 处理（fail-closed，绝不当作 `Absent`）。

## 3. 执行点防护 `ExecutionGuard`（防重放 + 幂等 + 记录）

```cpp
// include/cppchain/tool/exec_guard.hpp
namespace cppchain::tool {

class ExecutionGuard {
 public:
  // 会话日志是事实源：宿主注入"按 tool_call_id+参数 查执行状态"的读接口。
  //   state == 0         → 未开始
  //   state == 1         → 有结果（重放内容在 result 里）
  //   state == 2         → Intent 残留（有发起、无结果）—— 崩溃缺环候选
  using LogProbe = std::function<int(std::string const& tool_call_key)>;

  struct Options {
    LogProbe log_state;                 // 从会话日志重建状态（非空才开启防重放）
    std::function<void(AuditRecord const&)> audit = nullptr;  // 审计 sink（可空）
    bool retry_on_failure = false;      // Failed(有 error 结果) 是否允许重跑
    std::size_t max_parallel_serial = 8;
  };

  // 串行段：状态重建 + probe 判定 + 决定。返回"是否放行执行"。
  struct Prepared {
    bool execute = false;      // true → 真执行 handler；false → 用 report 当结果
    message::Message report;   // 非空时顶端充当 ToolMessage（重放 / 拒跑说明）
    ProbeResult probe_res = ProbeResult::Unknown;
  };
  [[nodiscard]] Prepared prepare(ToolCall const& call, ToolSpec const* spec,
                                 std::string_view who = "model");

  // 并行段：只有 Prepared.execute==true 才调。handler 直跑，不碰日志/审计。
  [[nodiscard]] message::Message run(ToolCall const& call, ToolSpec const* spec,
                                     nlohmann::json const& args);

  // 一次调用完成路径：prepare + run + 记录（单工具节点无并发时用这个一步入口）
  [[nodiscard]] message::Message execute(ToolCall const& call, ToolSpec const* spec,
                                         nlohmann::json const& args,
                                         std::string_view who = "model");

  [[nodiscard]] std::size_t replays() const;
  [[nodiscard]] std::size_t blocked() const;   // Intent→fail-closed 次数
  [[nodiscard]] std::size_t executions() const;
};

}  // namespace cppchain::tool
```

### 3.1 `prepare` 的判定流程（事务边界在此）

```
查 log_state(key)
  · 0（未开始）
      → execute=true（正常执行；执行后主机写会话日志）
  · 1（有结果）
      → execute=false, report=重放日志内容（不动盘）· audit=replay
  · 2（Intent 残留）
      → spec->probe ? probe(args)：
             Complete → execute=false, report="探测到已执行未回执，现状如实报告" · audit=probe_complete
             Partial  → execute=false, report="部分执行，请人工检查" · audit=probe_partial   ← fail-closed
             Absent   → execute=true（当作未开始，安全重跑）· audit=probe_absent
             Unknown  → execute=false, report="结果未知，请人工确认" · audit=blocked          ← fail-closed
        : 无 probe
             → execute=false, report="结果未知，请人工确认" · audit=blocked                    ← fail-closed
```

关键：**只有 `execute=true` 才可能触盘**；`replay/blocked/probe_*` 一律不执行 handler。

### 3.2 幂等键

`tool_call_key = tool_name + "|" + canonical_json(args)`（参数指纹，等价 agent 层
`ToolNameAndArgs`）。因为 run_tools 的模型 `call.id` 不稳定（模型重试换 id），用**参数指纹**
做键比 `ToolCallId` 更符合"防重放"语义；代价是误杀合法重复调用（同参数真调两次）——由
approve/审计把关，工具的 `probe` 也能判真（后台两个都发生→第二次探测 Complete→不重跑，反而对）。

## 4. `approve_tools` 节点（决策层）

```cpp
// node_types.cpp —— c_approve_tools 编译函数（新 kind）
// IR 形状：
//   { "id": "approve", "kind": "approve_tools",
//     "policy": "deny_list|decider"?, "deny": ["file_write", ...],
//     "next": "run", "deny_next": "ask_user"（可选；本期默认同 next + 回喂 error） }
// 运行时逻辑（纯函数，可离线单测）：
//   1. 读 state 最后一条 AI 的 tool_calls
//   2. 逐 call 判定：
//        spec->read_only == true            → approved
//        call.name ∈ deny / decider 拒       → denied（why）；产 error ToolMessage 并入 messages
//        其余                                    → approved
//   3. approved 的 id 列表写入 state（如 messages 的 guard 通道或 results["approve"]）——
//      run_tools 只执行该列表内的 call。
```

- **deny 不吞**：error ToolMessage（`"rejected: <why>"`）直接进消息流，下个节点（含 model）
  能看到；`node.kind` 输出供调试台展示审批轨迹。
- **memo 记忆化**：同指纹拒绝 → 下次不再重复审批（沿 `ToolApproval::MemoPolicy::RememberDeny`），
  会话级；持久化记忆列开放项。
- **read_only 免审**：读类工具不进审批、无决策记录（与防重放侧一致）。

## 5. `run_tools` / `c_tool` 挂 guard（执行层）

### 5.1 `c_run_tools`（batch）——先串行 prepare → 再并行 run

```
for call in state 里 approved_ids ∩ 最后一条 AI 的 tool_calls:
    prepared[call.id] = guard.prepare(call, spec, "model")   // 串行段（单线程访问日志/审计）
for call in approved_ids（execute==true 的子集）:
    run 用 std::async 并行调 guard.run(call, spec, args)    // 并行段（handler 直跑）
把 report（重放/拒跑）与 real_result 全部按原 tool_call_id 顺序回填 ToolMessage →
并入 messages / results / summary
```

### 5.2 `c_tool`（单工具节点）

无并发 → 直接用 `guard.execute(call, spec, args)`（prepare+run+record 一步）。

## 6. 会话日志作为事实源（wfr 侧实现）

- 状态重建 `log_state(key)` 由 wfr 提供：扫 `.wfr/sessions/*.log.jsonl` 尾端，找该
  `tool_name+canonical(args)`：
  - 无 → 0（未开始）
  - 有 ToolMessage（`status=success|error`）→ 1（有结果，重放其内容）
  - 有 AI.tool_calls、无对应 ToolMessage → 2（Intent 残留）
- 精度：尾端扫描 + 内存索引缓冲（长程任务日志大时 O(1) 查）；跨进程重启时重建索引。
- 执行后**写回会话日志**（ToolMessage + 本轮 run）沿用现有 `session_log` 机制——**不另立
  FileJournal**。

开放选择（§9 待定）：索引粒度、是否容忍尾端窗口外的历史（长 Log 方案的完整性对账）。

## 7. 审计记录 Schema

```json
{"ts": "…", "tool": "file_write", "key": "<参数指纹>", "decision":
 "allow|replay|blocked|probe_complete|probe_partial|probe_absent",
 "who": "model", "why": "…"}
```

- `decision` 六值闭集（execute 一栏 + replay 一栏 + 各 fail-closed 一栏 + probe 三栏）。
  与 §3.1 的判定流程一一对应——**审计行数 = 判定真实发生的证据**（验证陷阱纪律的断言对象）。
- 原文不落 audit（`key` 是参数指纹，正文在会话日志）。原子写 + fail-closed 同 `FileJournal` 纪律。

## 8. 测试计划

### 8.1 `tests/tool/exec_guard_test.cpp`（离线确定性）

| 组 | 覆盖 |
|---|---|
| 防重放 | log_state=0 → 执行；=1 → 不执行、report=重放、`executions` 不增 |
| probe 四格 | `Complete`→不重跑+report；`Partial`→fail-closed+report；`Absent`→执行；`Unknown`→fail-closed |
| probe 铁律 | probe 抛出/被打断 → 当 `Unknown`（fail-closed，绝不当作 Absent）；probe 不记账 |
| 只读 | `spec->read_only` → 不进 prepare 判定、无审计行 |
| 事务边界 | 崩溃恢复探针：**模拟"意图登记后 handler 中断"→ 重跑 prepare → 断言不二次执行** |
| 计数线程安全 | `prepare` 多 call 串行段 + `run` 并发下计数不丢 |

### 8.2 `tests/wf/approve_tools_test.cpp`

- deny → error ToolMessage 进流 + 审计 deny；deny 的 call **不**进 run_tools 执行集（磁盘断言文件未创建）。
- read_only 免审无审计行；approve 通过 → run_tools 真执行。
- memo：同参数二次审批 → 不重复判（memo_hits 计数）。

### 8.3 `tests/wf/side_effect_workflow_test.cpp`（集成）

- 单图里 `c_tool` 与 `c_run_tools` 两腿各一轮：防护都生效、审计行数吻合。
- 崩溃恢复端到端：写文件中途模拟中断 → 重启 wfr + 同会话 → 断言文件**只有一个**、
  审计一行 `probe_complete`（或 blocked）。

### 8.4 真机（wfr，可选本轮尾）

中危工具 + 计数/审计/磁盘三断言；高危不用（假象陷阱）。
