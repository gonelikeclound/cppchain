## 2. 接口定义

### 2.1 subagent-as-tool（`agent/subagent.hpp`）

```cpp
namespace cppchain::agent {

// 子代理规格。指针成员一律非拥有 → 生命周期必须长于用它的 ToolRegistry。
struct SubAgentSpec {
  std::string name;                   // 工具名（父视角），如 "ask_math"
  std::string description;            // 擅长什么/怎么用/返回什么（父模型据此决策）
  model::ChatModel* model;            // 与父共享同一实例（非拥有）
  tool::ToolRegistry const* tools;    // 子代理自己的工具集（非拥有，可含其他 subagent → 嵌套）
  AgentOptions options;               // 子循环参数；**system_prompt 即人设**；
                                      //   thread_id 必须为空（见 §2.1 契约③）
  std::vector<std::shared_ptr<Middleware>> middlewares;  // 子代理中间件（审批/压缩等），可选
};

struct SubAgentToolOptions {
  std::string arg_name = "query";     // 唯一入参名
  bool include_trace = true;          // 返回里附 stats 行（iterations/tool_turns/usage）
  bool read_only = false;             // 委派是否视作只读（默认否：子代理内部可能有副作用）
};

// 规格 → 普通 ToolSpec。handler 语义见 §3.1。
tool::ToolSpec make_subagent_tool(SubAgentSpec const& spec, SubAgentToolOptions opts = {});
}
```

### 2.2 Agent → 图节点（`graph/agent_node.hpp`）

```cpp
namespace cppchain::graph {

struct AgentNodeConfig {
  // 从共享 state 提取**本节点**的输入消息（各节点可取不同切片 → 主上下文分槽的前提）
  using InputResolver = std::function<std::vector<message::Message>(Json const& state)>;
  InputResolver input;                // 必填

  std::string output_key;             // 可选：最终答案**文本**写 state[output_key]
                                      //   · 该键的 reducer 决定语义（overwrite / push，见 §4）
  bool append_to_messages = true;     // 可选：最终 AI 消息追加 state.messages（add_messages）
};

// Agent 必须活得比图久（非拥有）。返回一个 NodeFn。
NodeFn as_agent_node(agent::Agent& agent, AgentNodeConfig cfg);
}
```

### 2.3 帮手函数

```cpp
// results 键的"推入"reducer（demo B 用）：left 数组 + right 单条 → append。
// 串行版 orchestrator 用它让每个 worker 只写自己的一条结果，天然按执行顺序排队。
inline state::Reducer push_reducer() {
  return [](state::Json const& left, state::Json const& right) {
    state::Json out = left.is_array() ? left : state::Json::array();
    out.push_back(right);
    return out;
  };
}
```

### 2.4 handoff 约定（简化）

| 层 | 机制 | 说明 |
|----|------|------|
| 图中（demo C） | worker 判定"超出领域" → 返回 `Command{update:{messages:[Human(说明)]}, goto:["supervisor"]}` | M6 原生；触发信号见 §3.3 |
| 子代理内（可选） | 子代理工具表放保留名 `call_supervisor({reason})` | 由 demo C 的 worker 使用，父/包裹层据此打 `handoff` 标记 |

## 3. 数据流

### 3.1 `make_subagent_tool` handler

```
handler(args, ctx):
  query ← tool::arg(args, opts.arg_name)                     // 未知工具/缺参 → error 回喂（沿用 ToolNode 纪律）
  child  ← Agent{*spec.model, *spec.tools, spec.options}     // ① 每次调用**现构**全新子代理
  for mw in spec.middlewares: child.add_middleware(mw)
  msgs  ← [ message::human_message(query) ]                  // ② system_prompt 由 invoke 自动前置
  ret   ← child.invoke(msgs)
  if !ret → 返回 unexpected(ToolError{ret.error()})          // → ToolNode 转 status=error 回喂
  stats ← {iterations: child.iterations(),
           tool_turns: 扫描 child.transcript() 里 tool_calls 总数,
           usage: 抽 ret->usage}                              // 全部来自 child.transcript()，无魔法
  body  ← include_trace ? {answer: ret->text(), stats, handoff:false}
                        : {answer: ret->text()}
  return body
```

**返回不回传子转录**：ToolMessage 只含 `answer + stats`。子代理内部的工具 schema/结果/多轮往返
均不进父 prompt —— 隔离的物理保证，可在 token 上验证（§4.1）。

**现构现用的三重理由**：上下文隔离（无残留历史）；线程安全（并发调用各持一份）；无快照污染
（`Agent::invoke` 仅当 `thread_id` 非空才读写 checkpointer，child 默认 thread_id 为空 → 干净）。

### 3.2 demo B：orchestrator-worker（串行版）图拓扑

**state schema**（`StateSchema::messages_state()` 基础上加一 reducer）：

```cpp
auto schema = state::StateSchema::messages_state();
schema.set_reducer("results", push_reducer());   // tasks 默认 overwrite
```

```
supervisor ── 结构化输出节点（M4，非 as_agent_node）：
              取 messages 末条 Human → StructuredOutput(model, plan_schema).invoke()
              → Command{update:{"tasks": plan}}        ← 任务计划一锤定音，不靠工具回写 state
   │
   ▼  Router（下标对齐——“串行不重排”正是前提）：
   ├─ state.tasks.size() > state.results.size()
   │    → 返回 { tasks[results.size()].worker }        ← 按名命中 worker 节点（enum 限定，见 §4.3）
   └─ 否则 → { "finalize" }
   │
   │
worker_math / worker_news ── as_agent_node：
   │   input    = [human_message( tasks[i].input )]        （i = results.size()，各 worker 对应自己的 i）
   │   output_key = "results"（push → 追加一条答案文本）
   │   append_to_messages = false                          ← 关键：worker 全文不进主线，主上下文保持干净
   │
   ▼
finalize ── as_agent_node：
   input = [human_message("汇总: " + join(results) + 原始提问)]
   append_to_messages = true（最终答复进 messages）→ END
```

**plan_schema 里的 `worker` 用 enum 限定为图里真实存在的节点名** → 拓扑非法在结构层就挡掉
（否则 router 返回未知节点 → `GraphError::UnknownNode`，晚一步且难查）。

### 3.3 demo C：handoff 简化，worker 上交回 supervisor

```
supervisor ── as_agent_node（提问/重新分派的角色）
   │  Router：messages 末条 Human 若带 [handoff] 前缀 → 重新分派给另一 worker；否则按首次分类给 math/news
   ▼
worker_math ── as_agent_node ＋ 包裹层（handoff 检测）：
   · 工具表含调用工具（calculator）**和** call_supervisor（保留名，handler 返回 reason 原文，不真执行）
   · 包裹逻辑（as_agent_node 之后）：
       扫描 worker.transcript() —— 存在任何 Ai 消息带 tool_call name == "call_supervisor"
       → 追加一条 Human("[handoff] " + reason)
         并改 Command{update, goto_nodes = {"supervisor"}}
   ↓ 否则正常 → Router → supervisor →（满意度判断）→ finalize
```

**触发信号是"调用过 call_supervisor"，不是解析文本** —— 确定性，不依赖模型措辞。环的边界靠
`CompileOptions::max_steps` + 重派计数（state 里 `redispatch` 键，达到上限强制 finalize）双保险，
避免"模型反复上交"死循环。

## 4. 关键算法与契约

1. **隔离 = token 会计可验证**：父那一轮的 `input_tokens` ≈ 父自身一档（子代理内部 N 次往返
   不进父 prompt）；子代理的 tool_turns 在 stats 里可见。demo A 对照断言两者同时成立。
2. **并发安全**：子代理 handler 可能与批内其他 tool **并行**（ToolNode max_parallel=4），且共享
   同一个 `ChatModel` 实例 —— 现构子代理只是隔离 transcript，**不隔离传输层**。M2 的 curl_multi
   transport 是否支持并发 invoke 未验证。→ **契约：M8 先用每工具一个 `std::mutex` 串行化子代理
   对共享 model 的调用**（牺牲批内专家并行换安全）；若后续证明 ChatModel 并发安全，去掉互斥升级并行。
3. **results 下标对齐**：push_reducer 按执行序排队；**该对齐以"串行执行 + 不重排"为前提**——
   demo B 无重派（重派是 demo C 单独的小图），因此安全。M10 的 Send fan-out / 重排到来时，
   results 需改 `{task_id, answer}` 形态（已记入 02-arch-design/09 §7）。
4. **有限性**：上图均有 `max_steps`；handoff 有 `redispatch` 上限。模型反复上交 → 强制收口，
   不静默死循环（沿 M6 契约⑤"不返回半成品"）。
5. **副作用透传不豁免**：子代理内部工具仍走**子代理自己的**审批/防重放中间件（Journal 共表）。
   父只审批"委派"动作；委派不豁免子代理内部审批 —— 纵深防御，不是旁路。
