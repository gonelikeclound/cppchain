## 2. 踩坑（按发现顺序，全部已修 + 回归测试）

1. **`std::expected` 的 lambda 返回类型推导**（本项目第 3 次踩）
   `if (!x) return std::unexpected(x.error()); return json(...);` 两句返回类型不一致 → 编译失败。
   → **工具 handler / 任何返回 expected 的 lambda 一律写显式返回类型**。
2. **`Store::size()` 语义错**：返回命名空间个数而非条目数（与调用方预期不符）。
   → 修为条目总数，另加 `namespace_count()`。
3. **`Checkpointer::put` 缺 `next` 参数**：接口只存 values/metadata，导致 `StateSnapshot.next`
   是死字段、恢复时不知道下一步跑谁。→ 接口加 `next`（与 langchain 语义一致），M5 调用点同步。
4. **`END` 被写进快照的 next**：END 不是节点 → 先剔除再落快照，否则污染恢复语义。
5. **`TruncateToolResults` 按字节截断切断 UTF-8 中文** → 序列化成 JSON 抛 `type_error.316`。
   → 截断必须回退到 UTF-8 字符边界（`truncate_utf8`）；demo 的显示截断同理。
6. **Agent 快照只在"工具执行后"写** → **最后一条 AI 回复从未入历史**，续跑时上下文缺一截。
   → 循环结束（终态）也写一次快照；测试相应断言 2 个快照（after_tools + final）。
7. **规范 JSON 的显式 `null`**（M1 的坑在 M5 demo 里再次命中）→ 统一用 `message::opt_string`。

## 3. 真机 demo 暴露的"演示设计"问题（同样是教训）

跑 `examples/agent_loop` 时发现两处**"demo 跑了但没演示到想演示的东西"**：

| 现象 | 根因 | 处理 |
|---|---|---|
| 审批中间件"拒绝次数 0" | `deepseek-chat` **自己就拒绝调用** `delete_file`（模型安全策略），中间件根本没被走到——即使我明确要求"不要征求确认" | 改用**策略禁止但模型愿意调用**的工具（`send_email`），才真正触发审批 |
| 压缩中间件"触发 0 次" | 演示喂了 5 条消息，**没超过阈值 6** | 喂 8 条，触发并观察到真实 LLM 摘要 |

**教训**：验证型 demo 必须**确认被测路径真的被走到**（计数/断言），否则"跑通了"是假象。
这与前面"压缩比 1444x"、"向量 8/8 但动作不对"是同一类问题：**指标与路径都要核对**。

## 4. 验证结论

- `ctest`：**136/136 通过**（message 16 / model 40 / tool 26 / state 21 / graph 10 / agent 10 …）
- demo：**14 个**（新增 `structured_output`、`state_basics`、`graph_basics`、`agent_loop`），
  `./run-demo.sh` 一键全跑
- 真机验证（DeepSeek）：
  - M4：抽取 + classify 正确；**受控对照**两策略均 5/5（推翻了"ToolCall 更准"的过度解读）
  - M7：多步工具调用 2 轮收敛；超长返回截断后模型仍能总结；
    **策略拒绝被模型正确转述**；**LLM 摘要压缩后模型仍记得用户偏好**

## 5. 待办 / 开放点

1. 压缩阈值策略（消息数 → token 估算/上下文占用率）；摘要成本量化（M9）。
2. Agent 尚未暴露为 M6 的图节点（M8 多 agent 编排需要）。
3. 审批的记忆化（同一会话同一工具不重复问）。
4. 并行工具执行已由 M3 ToolNode 支持，但 Agent 目前顺序逐个执行 tool_calls（可改批量）。
