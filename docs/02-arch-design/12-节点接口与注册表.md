# 12 · 节点接口、动态注册与统一日志

> 目标：把 workflow 的**节点**从"编译器里的一堆 `switch` 分支"变成**自包含、可动态注册的单元**，
> 用统一接口 + 工厂查找（内置注册 / 动态库导入），并让**日志成为会话历史的事实来源**。
>
> 依据：M12 落地过程中连续加了两批节点（C 阶段 3 种、D 阶段 2 种），每次都必须在 6 个文件里
> 分别补齐——代价见 §2，那是本文的直接动因。
>
> 状态：设计。**会推翻 M12 D 阶段的落盘实现**（见 §7.3、§8）。

---

## 1. 定位与边界

- **依赖**：M12 已落地的 workflow 层（IR / validator / compiler / 图引擎）。
- **提供**：
  ① 节点类型接口 `NodeType`（JSON ↔ C++ 的契约 + 出边 + 校验 + 编译）；
  ② **符号约定**（`graph_node_<name>_creator`）+ creator descriptor（name/version/context）
     + 注册表：内置集中注册，动态库按 IR 声明的库名 `dlsym` 加载；
  ③ **统一日志规范**（统一外壳 + 来源可区分：引擎写结构事件，节点/宿主可写自有诊断）；
  ④ **history 改为日志的投影**（不再单独落盘）。
- **不做**：节点热插拔（运行中增删）；日志的远程汇聚/轮转（留开放点）；跨 ABI 的异编译器插件。

---

## 2. 问题：加一种节点，要改 6 个文件

实测（`grep NodeKind::` 统计）：

| 指标 | 数值 |
|---|---|
| 涉及文件 | **6 个**（ir / validator / compiler / proactive / features / ir.hpp） |
| `NodeKind::` 分支总数 | **114 处** |
| 其中写成 `switch` | 5 处 —— 编译器用 `-Wswitch` **能**抓到遗漏 |
| **其中写成 if/else 链** | **28 处 —— 编译器完全抓不到** |

第二行是关键：加 `load_history`/`save_history` 时，`-Wswitch` 帮我把 5 个 switch 全列了出来；
但 `VG2`（前向边无环）/ `VG7`（可达性）/ `VG8`（死 label）那几处 if 链**是靠记忆改的**——
漏掉不会编译报错，只会产出错误行为（例如把合法 IR 误报成"死节点"）。

**根因**：节点的"JSON 声明"与"C++ 实现"之间没有绑定，所以每加一种，两边都要在 6 个地方分别补。

---

## 3. 四条要求

1. **每个节点独立**，节点之间不相互依赖。
2. **接口统一，动态查找**：内置节点统一注册，由 `get_graph_node_creator(name)` 出实例；
   节点也可放**动态库**，库导出同一接口，workflow 语法内**显式 import** 后才可用。
3. **所有节点遵循同一套 log 输出规范**（调试与追踪的地基）。
4. **history 不单独 save**，它的事实来源就是 log。

第 1、2 条决定**接口形状**（§4、§5），第 3 条决定**日志规范**（§6），第 4 条决定
**history 的实现方式**（§7）——而且三条互相咬合：日志统一了，history 才可能是它的投影。

## 4. 节点类型接口

### 4.1 `NodeType`

```cpp
// workflow/node_type.hpp —— 一个**节点类型**：把 JSON 声明 ↔ C++ 实现绑在一处
struct NodeType {
  std::string_view kind;                                  // JSON 里 kind 的取值

  // ① 判别：新写法靠 kind 键，历史写法靠"有 goto/expr/tool 键"——由类型自己说
  std::function<bool(Json const&)> matches;

  // ② JSON ↔ 数据（NodeIR 仍是共用槽位，见 §9 Q1）
  std::function<void(NodeIR&, Json const&)> parse;
  std::function<void(Json&, NodeIR const&)> write;

  // ③ **出边** —— 图规则唯一需要知道的东西（本节的重点）
  struct Edge { std::string target; std::string label; bool forward = true; };
  std::function<std::vector<Edge>(NodeIR const&)> edges;

  // ④ 类型专属校验（通用规则由框架按 edges 推导，见 4.2）
  std::function<void(NodeIR const&, ValidatorOptions const&, ValidationErrors&)> validate;

  // ⑤ 编译成图节点
  std::function<void(NodeIR const&, CompileContext&)> compile;
};
```

**为什么是函数表（`std::function`）而不是虚基类**：与既有 `ToolSpec`（数据 + `Handler`）同风格；
类型定义可静态常量初始化，无需为每种节点声明一个类。**虚基类留给 §5 的动态库边界**——
跨 .so 传 `std::function` 不安全，但传抽象接口指针（vtable）在同一工具链下是稳的。

### 4.2 `edges()` 是收敛 28 处 if 链的关键

五条图规则**只需要知道"这节点指向谁、哪些算前向边"**：

| 规则 | 现在 | 之后 |
|---|---|---|
| VG1 目标存在 | 每个 kind 分支各写一遍 | 遍历 `edges()` 统一判 |
| VG2 前向边无环 | `if (kind==Tool) … else if (kind==Expr) …` | 取 `forward==true` 的边统一建图 |
| VG7 可达性 | 同上，且 `on_error.fallback` 特殊处理 | `edges()` 里把 fallback 也作为一条边返回 |
| VG8 死 label | 每个 kind 分支各写一遍 | 任何 `edges()` 的 target 都算"被引用" |
| goto 的回边 | 靠 kind 判断跳过 | `goto` 的边 `forward=false` |

`on_error.fallback` 的处理值得单说：它目前是 tool 专属字段，却参与 VG7 的可达性判定。
把它**渲染成一条边**（`label="on_error.fallback"`）之后，VG7 就完全与节点类型无关了。

### 4.3 规则的三层分类（建议写进规范）

- **通用**（由 `edges()` 驱动，写一次）：VG1 / VG2 / VG7 / VG8
- **类型专属**（各类型自己实现 `validate`）：VN1–VN11、VG9（`load_history` 顺序）
- **全局**（与单个节点无关，框架管）：id 唯一、入口、config 契约（B2/VR4）、组件白名单（VN10）

分清这三层，才不会再把"通用规则"复制到每个类型里——那正是 28 处 if 链的来源。

## 5. 动态注册与动态库导入

### 5.1 符号约定与 creator 接口

**内置节点保持集中注册**（`node_types.cpp` 一张表）：那是**可读性资产**——打开一个文件就能
看到全部节点及其行为；换成自注册后"系统里到底有哪些节点"就不再静态可查。
"零改动"真正值钱的是**第三方扩展**（你无法改核心的场景），所以只对动态库上这套机制。

库与宿主之间只靠**一个符号约定 + 一个 C 结构**耦合：

```cpp
// 库为**每个节点**导出一个符号，名字即约定（<name> 须是合法 C 标识符）
extern "C" const cppchain_node_descriptor* graph_node_<name>_creator(void* host_ctx);

// 版本常量（cppchain 侧）：宿主加载库后**先校验**，不匹配即拒（fail-closed）
inline constexpr int kNodeApiVersion = 1;

// 纯 C 布局（链接规范只作用于函数/变量，不作用于类型）
typedef struct cppchain_node_descriptor {
  const char* name;      // 节点名：须与符号里的 <name> **一致**，宿主校验；不一致直接拒
  int         version;   // 本库编译时的 kNodeApiVersion
  void*       context;   // **库自己的**上下文；宿主原样持有、不解释
  void* (*create)(void* context);              // 由**库**分配
  void  (*destroy)(void* node, void* context); // 由**库**释放
} cppchain_node_descriptor;
```

四个字段各有其存在的理由，缺一个都会咬人：

| 字段 | 为什么需要 |
|---|---|
| `name` | **枚举/按名加载时的自校验**：符号名与声明名不一致（改名漏改）会被立刻发现，而不是"IR 里写 A、实际创建了 B" |
| `version` | **ABI 校验**。插件系统没有版本检查是经典坑：宿主与库的 `NodeType` 布局或 C++ 接口一变，就是静默的内存错乱。不匹配 → 拒绝加载 |
| `context` | **库不该用全局变量**：同一个 `.so` 可能被 `dlopen` 多次、或同时存在多个版本；creator 把自有状态交给宿主代持，`create`/`destroy` 时回传，库就不需要"全局单例"假设 |
| `create`/`destroy` 由库提供 | **跨 `.so` 的 `new`/`delete` 必须配对**：宿主的分配器与库不同就会崩 |

两处 ABI 细节（与上一版相同，仍必须遵守）：

- **`const char*` 而非 `std::string`**：消除字符串 ABI 与名字修饰两个风险。
- **`host_ctx` 是宿主能力的不透明指针**（当前承载 §6.4 的 `NodeLog` 等）；将来往里加能力靠
  `kNodeApiVersion` 递增，而不是改这个签名。
- 传回的 `descriptor` 内部若含 C++ 抽象接口指针（如 `GraphNode*`），仍要求**同工具链**。

### 5.2 加载方式：先 A0，枚举（A1）押后

| | 做法 | 跨平台 | 得到什么 |
|---|---|---|---|
| **A0**（本次做） | 按 IR 声明的节点名 `dlsym(handle, "graph_node_<name>_creator")` | ✅ POSIX `dlsym` / Windows `GetProcAddress` 一个薄 shim | 库侧**无需中心分发函数**：加节点 = 加一个文件 + 一个符号 |
| **A1**（押后） | 扫库自己的 `.dynsym` 枚举 `graph_node_*_creator` | ❌ ELF-only（Mach-O/PE 另写） | `import {lib}` 可省节点名；`--list-nodes` |

**A0 已能拿到"库侧零改动"这个主要收益，且跨平台**；A1 只省掉清单里的节点名，却要吃下
一套 ELF 解析——而且枚举必须**只解 `dlopen` 拿到的 handle 自己的符号表**，
不能用 `dl_iterate_phdr`（它遍历整个进程，会把别的库的同名符号也扫进来）。

### 5.3 import 语法

```jsonc
{
  // 库**必须显式列出**（它是信任单元）；节点名可省（省了就用 A1 枚举）
  "imports": [ { "lib": "./libextra_nodes.so" },
               { "lib": "./libmore.so", "nodes": ["sentiment"] } ],
  "nodes": [ … ]
}
```

- **`nodes` 可选**。省略 = "整库信任"。
  ⚠️ **但 A1 落地前，省略即报错**：「当前构建不支持枚举，请显式列出节点名」——
  语法先定、能力后补，且 **fail-closed**（不静默当作"没有节点"）。
- 声明了 `nodes` 时，逐个 `dlsym`；**取不到 = 校验期拒绝**（不是运行期才发现）。
- 导入的节点与内置节点在 IR 里**用法完全相同**——`kind` 就是它的名字。

### 5.4 符号可见性（最常见的"为什么找不到"）

CMake 默认 `-fvisibility=hidden` 时符号**根本不导出**。库必须显式放开：

```cpp
#define CPPCHAIN_NODE_EXPORT __attribute__((visibility("default")))
extern "C" CPPCHAIN_NODE_EXPORT const cppchain_node_descriptor*
graph_node_<name>_creator(void* host_ctx);
```

或对该 target 设 `-fvisibility=default`。文档与示例 `.so` 都要示范这一点，
否则使用者会卡在"节点明明写了却找不到"。

### 5.5 安全默认

**加载 .so = 任意代码执行。** 与项目一贯的 fail-closed 一致：

> CLI **默认拒绝 import**；要用必须显式 `--allow-import`。加载时把库路径、`kNodeApiVersion`
> 校验结果、以及**发现的节点名**打进日志（§6），保证"这次运行加载了什么"事后可查。
>
> 注意分寸：**库是信任单元**，不是"扫目录发现谁就加载谁"——那样会把显式白名单退化成
> fail-open，与项目一贯纪律相悖。`import` 的**库名**永远显式。

## 6. 统一日志规范

### 6.1 三类来源与分工

日志文件由**多方写入**，但**格式统一、来源可区分**：

| 来源 `source` | 谁写 | 写什么 | 参与 replay？ |
|---|---|---|---|
| `engine` | **框架**（引擎在节点边界） | 节点身份、phases、耗时、状态、**状态增量 `update`** | ✅ **只有它参与** |
| `node` | 节点自己 | 节点内部的诊断（召回了几条、读了哪个文件…） | ❌ 只用于调试/审计 |
| `host` | 宿主（CLI） | 运行参数、加载了哪个 `.so`、放行了哪些节点 | ❌ |

**为什么"状态那部分"必须由引擎写、而"节点诊断"可以节点自己写**：

- **`update` 决定 history**（replay 的输入）。这部分**不能靠节点自觉**——10 个节点之后必然有
  忘返回、字段拼错、漏错误路径的，而代价是历史残缺。故由引擎统一采集。
- **节点自有诊断不参与 replay**，漂移了也不影响事实来源。所以它可以自由写，
  **前提是来源能区分** —— 这正是你这条要求的要点。

> **replay 的铁律：只读 `source == "engine" && phase == "exit"` 的记录。**
> 其余一律不参与状态重建。这条规则让"节点自己写日志"变得**安全**：
> 哪怕节点在日志里塞了 `update` 字段，也不会被应用到状态上。

### 6.2 统一外壳

所有记录共享同一个外壳，用 `source` 区分来源：

```jsonc
{"seq":12,"ts":"2026-10-05T17:05:01.456Z","run":"r-1","source":"engine",
 "node":"think","node_kind":"model", …}
```

| 字段 | 谁有 | 说明 |
|---|---|---|
| `seq` | 全部 | 文件内单调递增（**原子分配**，见 §6.5），replay 的排序键 |
| `ts` / `run` | 全部 | 时间戳 / 本次触发 id |
| **`source`** | 全部 | `engine` / `node` / `host` —— **判别键** |
| `node` / `node_kind` | engine、node | 节点 id 与类型（host 记录可无） |
| `level` | node、host | `debug` / `info` / `warn` / `error` |
| `msg` / `data` | node、host | 人类可读说明 + 任意结构化附加 |
| `phase` / `status` / `ms` / **`update`** | **仅 engine** | 见 §6.3 |

### 6.3 engine 记录（结构性事件）

```jsonc
{"seq":1,"ts":"…","run":"r-1","source":"engine","node":"recall","node_kind":"load_history",
 "phase":"enter"}
{"seq":2,"ts":"…","run":"r-1","source":"engine","node":"recall","node_kind":"load_history",
 "phase":"exit","status":"ok","ms":1,"update":{"messages":[…]}}
{"seq":3,"ts":"…","run":"r-1","source":"engine","node":"think","node_kind":"model",
 "phase":"exit","status":"ok","ms":842,"update":{"messages":[{…ai…}]}}
{"seq":4,"ts":"…","run":"r-1","source":"engine","node":"think","node_kind":"model",
 "phase":"error","status":"error","ms":17,"error":{"kind":"model","msg":"HTTP 429"}}
```

`phase` = `enter` / `exit` / `error`。`enter` + `exit` 都记（而非只记 exit）：
崩溃时"最后一条 `enter` 没有配对的 `exit`"就能**精确定位卡在哪一步**。

### 6.4 node 记录（节点自报）

节点**不自己开文件**，而是用引擎注入的 logger：

```jsonc
{"seq":5,"ts":"…","run":"r-1","source":"node","node":"think","node_kind":"model",
 "level":"info","msg":"完成一次模型调用",
 "data":{"model":"deepseek-chat","finish_reason":"tool_calls","usage":{"in":120,"out":30}}}
{"seq":6,"ts":"…","run":"r-1","source":"node","node":"recall","node_kind":"load_history",
 "level":"warn","msg":"日志末尾有半行，已跳过","data":{"bytes":37}}
```

节点侧接口（编译/运行期注入，不是全局变量——节点仍彼此独立）：

```cpp
struct NodeLog {                       // 引擎实现，注入给节点
  virtual ~NodeLog() = default;
  virtual void log(std::string_view level, std::string_view msg, Json const& data) = 0;
};
```

跨 `.so` 的注意事项与 §5.1 同：传的是**抽象接口指针**（同工具链下 vtable 稳），
且 **host 分配、host 释放**，库不持有其生命周期。

### 6.5 并发

`run_tools` 会**并行**执行工具（M3 的 `ToolNode`，有界并行），节点日志可能并发写：

- `seq` 用**原子递增**分配（保证唯一且单调），
- 文件写入加一把锁（或单写线程 + 队列）。

否则日志会出现 `seq` 重复或**行交织**（两条记录拼在一行）——那会直接毁掉 replay。

### 6.6 append-only 顺带修好了当前的一个脆弱点

现在（D 阶段）的落盘是**每次全量重写整个 JSON**，所以文件一坏就全丢——这正是当初必须写
"损坏就抛异常"（fail-closed）的原因：损坏后除了拒绝启动别无他法。

改成 append-only 之后：

- **崩溃最多损坏最后一行**，前面全部完好
- 解析时**跳过末尾半行并告警**即可（这条告警本身就是一条 `source=node`/`host` 的日志），历史仍可恢复
- 恢复语义从"抛异常拒绝启动"变成"能救回来"

这是一个没预料到的收益：要求 4 顺带把落盘的健壮性提了一档。

## 7. history = 日志的投影

### 7.1 replay 语义

日志里每条 `exit` 事件都带 `update` —— 于是：

```
history = 按 seq 依次 schema.apply(state, update) 之后，取 state.messages
```

**直接复用现成的 reducer（`StateSchema`）**，不需要新机制。附带得到：

- **断点续跑**：replay 到最后一个 `status=ok` 的 seq，从那里继续
- **可审计**：每一步的输入/输出/耗时都在

### 7.2 节点的去留

| 节点 | 去留 | 理由 |
|---|---|---|
| `save_history` | **取消** | 日志已经含了事实，再存一份就是第二个真相源 |
| `load_history` | **保留**（实现换成 replay 投影） | "不必单独 save" ≠ "加载不是节点"；保留它符合"history 是普通节点"的既有决定 |

`load_history` 的实现从"读 history 文件"变成"读本会话日志 → replay → 取 messages 投影"。
它需要 StateSchema 才能 apply，而 schema 在编译期可得，故在 `compile` 时捕获。

### 7.3 与现有落盘的对照

| | 现状（D 阶段） | 本文之后 |
|---|---|---|
| 文件 | `session-<name>.json` | `session-<name>.log.jsonl` |
| 写入 | 每次**全量重写** | **append**（天然只追加） |
| 损坏 | 整文件坏 → 抛异常拒绝启动 | 最多坏最后一行 → 跳过并告警 |
| 事实来源 | history 文件 + （无日志） | **日志**（唯一事实） |
| 模块 | `history_file.hpp/.cpp` | `session_log.hpp/.cpp` |

**不动的东西要守住**：这次是重构 + 扩展，不是改语义。现有 VG*/VN* 的正负用例是安全网 ——
重构后它们应当**逐条仍绿**，否则就是重构引入了行为变化。

## 10. 分阶段实施

| 阶段 | 内容 | 风险 |
|---|---|---|
| **① 抽接口** | `NodeType` + 注册表；ir/validator/compiler 改为按注册表分派；**行为完全不变** | 中：纯重构，靠 365 项测试兜底 |
| **② 图规则通用化** | VG1/VG2/VG7/VG8 改为由 `edges()` 驱动，删掉 28 处 if 链 | 中：正负用例必须逐条仍绿 |
| **③ 日志** | `session_log`（append-only + 半行容忍）+ 引擎在节点边界写 `enter/exit/error` | 低 |
| **④ history 投影** | `load_history` 改为 replay；删 `save_history`；返工 D 阶段的测试与 CLI | 中：**推翻已落地的落盘** |
| **⑤a 动态库（A0）** | 符号约定 + descriptor（name/version/context）+ 版本校验 + `import` 解析 + `--allow-import` + 示例 `.so` | 高：ABI 与安全，需端到端验证 |
| **⑤b 符号枚举（A1）** | 扫本 handle 的 `.dynsym` → `import` 可省节点名 + `--list-nodes` | 中：ELF 细节；押后 |

顺序刻意如此：**① ② 是纯重构，先做且必须零行为变化**；③④ 一起做（日志与投影是一件事）；
⑤ 独立且风险最高，放最后。① 做完就能立刻验证"加一种节点 = 写一个 `NodeType`"，这是本文的核心承诺。

## 12. 开放点

1. **日志轮转与上限**：长会话下 `.log.jsonl` 会一直长。轮转策略与"replay 要不要跨轮转文件"一并设计。
2. **脱敏**：日志含完整对话内容。若将来要共享日志排查，需要脱敏/裁剪。
3. **跨 ABI 插件**：本文限定"同工具链"。真正的跨编译器插件需要纯 C 接口 + 序列化边界，成本高。
4. **日志作为多机事实源**：现在日志是本地的。若要做"跨设备续聊"，它就是天然的同步单元。
