# 12 · 节点接口、动态注册与统一日志

> 目标：把 workflow 的**节点**从"编译器里的一堆 `switch` 分支"变成**自包含、可动态注册的单元**，
> 用统一接口 + 工厂查找（内置注册 / 动态库导入），并让**日志成为会话历史的事实来源**。
>
> 依据：M12 落地过程中连续加了两批节点（C 阶段 3 种、D 阶段 2 种），每次都必须在 6 个文件里
> 分别补齐——代价见 §2，那是本文的直接动因。
>
> 状态：**①–⑤ 全部落地**（全量 384 项测试变绿）。
> ① 注册表、② `edges()` 收敛、③ 统一日志、④ history=日志投影、⑤a 动态库导入（A0 按名
> dlsym）、⑤b 符号枚举（A1 扫本库 `.dynsym`）均已实现 —— 本文五个阶段收口。
> ④ 已推翻 M12 D 阶段的独立落盘（`save_history` 删除、`history_file.*` → `session_log.*`，
> §6.3/§7.1：input 事件 / load_history 省略 update / replay 用固定归约器）。
> ⑤ 的实施定型见 §5：`DynamicNode` 抽象接口、**框架分发一律按名**、幂等导入、
> 宿主 `--export-dynamic` 解析插件未定义引用、A1 读文件不执行（`--list-nodes` 无需放行）。

## 1. 定位与边界

- **依赖**：M12 已落地的 workflow 层（IR / validator / compiler / 图引擎）。
- **提供**：
  ① 节点类型接口 `NodeType`（JSON ↔ C++ 的契约 + 出边 + 校验 + 编译）；
  ② **符号约定**（`graph_node_<name>_creator`）+ creator descriptor（name/version/context）
     + 注册表：内置集中注册，动态库按 IR 声明的库名 `dlsym` 加载；
  ③ **统一日志规范**（统一外壳 + 来源可区分：引擎写结构事件，节点/宿主可写自有诊断）；
  ④ **history 改为日志的投影**（不再单独落盘）。
- **不做**：节点热插拔（运行中增删）；日志的远程汇聚/轮转（留开放点）；跨 ABI 的异编译器插件。

## 2. 问题：加一种节点，要改 6 个文件

实测（`grep NodeKind::`，**重构前**的基线）：

| 指标 | 数值 |
|---|---|
| 涉及文件 | **6 个**（ir / validator / compiler / proactive / features / ir.hpp） |
| `NodeKind::` 分支总数 | **114 处** |
| 其中写成 `switch` | 5 处 —— 编译器用 `-Wswitch` **能**抓到遗漏 |
| **其中写成 if/else 链** | **28 处 —— 编译器完全抓不到** |

第二行是关键：加 `load_history`/`save_history` 时，`-Wswitch` 帮我把 5 个 switch 全列了出来；
但 `VG2`（前向边无环）/ `VG7`（可达性）/ `VG8`（死 label）那几处 if 链**是靠记忆改的**——
漏掉不会编译报错，只会产出错误行为（例如把合法 IR 误报成"死节点"）。

**根因**：节点的"JSON 声明"与"C++ 实现"之间没有绑定，所以每加一种，两边都要在 6 个地方分别补。

**→ ①② 已把这条收口**：分类/解析/序列化/展示/校验 / 编译 / 出边 / 引用全部集中到一张
`NodeType` 表（§4），图结构规则由 `edges()` 统一推导 —— 结构上"加一种节点只改一处"成立
（端到端证明仍未做，见 §11）。

---

## 3. 四条要求

1. **每个节点独立**，节点之间不相互依赖。
2. **接口统一，动态查找**：内置节点统一注册，由 `get_graph_node_creator(name)` 出实例；
   节点也可放**动态库**，库导出同一接口，workflow 语法内**显式 import** 后才可用。
3. **所有节点遵循同一套 log 输出规范**（调试与追踪的地基）。
4. **history 不单独 save**，它的事实来源就是 log。

第 1、2 条决定**接口形状**（§4、§5），第 3 条决定**日志规范**（§6），第 4 条决定
**history 的实现方式**（§7）——而且三条互相咬合：日志统一了，history 才可能是它的投影。

## 4. 节点类型接口

### 4.1 `NodeType`（① 已落地，形状即 `node_type.hpp`）

```cpp
// workflow/node_type.hpp —— 一个**节点类型**：把 JSON 声明 ↔ C++ 实现绑在一处
struct NodeType {
  NodeKind kind;                                    // 内部判别（enumerate，见 ir.hpp）
  std::string_view name;                            // JSON 里 kind 的取值（报错/展示用）

  // ① 判别：显式（kind:"…"）与历史写法（靠 goto/expr/tool 键）都要命中 —— 由类型自己说
  std::function<bool(Json const&)> matches;

  // ② JSON ↔ NodeIR（NodeIR 仍是共用槽位，见 §9 Q1；各类型只管**自己的字段**）
  std::function<void(NodeIR&, Json const&)> parse;
  std::function<void(Json&, NodeIR const&)> write;

  // 一行易读描述（demo 展示用）—— 展示也按表分派，加节点不再改展示 switch
  std::function<std::string(NodeIR const&)> describe;

  // 类型专属校验（VN5–VN11）。上下文**按需注入**：节点只看它要的（ToolRegistry /
  // ComponentRegistry），不把整个 ValidatorOptions 灌进来。
  struct ValidateContext {
    tool::ToolRegistry const* registry = nullptr;
    ComponentRegistry const* components = nullptr;
  };
  using ErrorSink = std::function<void(std::string rule, std::string message)>;
  std::function<void(NodeIR const&, ValidateContext const&, ErrorSink const&)> validate;

  // 把节点编译成图节点。
  struct CompileContext {
    graph::StateGraph& graph;
    tool::ToolRegistry const* registry = nullptr;
    ComponentRegistry const* components = nullptr;
    std::function<std::string(std::string const&)> resolve;  // label/_turn_end/_fail → 图目标名
    std::size_t registered = 0;         // 成功注册的图节点数（供 registered_nodes()）
    std::string error;                  // 非空 = 编译失败，调用方就此中止
  };
  std::function<void(NodeIR const&, CompileContext&)> compile;

  // ③ **出边** —— 通用图规则（VG1/VG2/VG7/VG8）唯一需要知道的东西（本节的重点）
  struct Edge { std::string target; std::string label; bool forward = true; };
  std::function<std::vector<Edge>(NodeIR const&)> edges;

  // 本节点里**可能含引用**的文本片段（parameters 里的字符串 / expr / path+session…）。
  // VR1 的语法检查与 VR 段引用收集**共用这一个钩子**（② 才补上，见 §4.2）。
  std::function<std::vector<std::string>(NodeIR const&)> ref_texts;
};
```

与初版设计的差异（实施中定型，写在这里免得误解）：

- `kind` 是**枚举**而非字符串 —— `NodeKind` 仍是内部判别，注册表里 `name` 才是 JSON 字面量。
- 新增 `describe`（展示归节点）、`ref_texts`（引用钩子）两个成员 —— 分别是 ①a、② 引入的。
- `validate` / `compile` 的上下文从"整个 ValidatorOptions / CompileContext 灌进去"收紧为
  **按需注入的窄上下文**（`ValidateContext` / `CompileContext`），节点看不到用不着的字段。

**为什么是函数表（`std::function`）而不是虚基类**：与既有 `ToolSpec`（数据 + `Handler`）同风格；
类型定义可静态常量初始化，无需为每种节点声明一个类。**虚基类留给 §5 的动态库边界**——
跨 .so 传 `std::function` 不安全，但传抽象接口指针（vtable）在同一工具链下是稳的
（§5 尚未落地，正是它约束了内置表用函数表）。

### 4.2 `edges()` 收敛了图结构规则（② 已落地）

五条通用图规则**只需要知道"这节点指向谁、哪些算前向边"**。改成由 `edges()` 驱动后，
VG1/VG2/VG7/VG8 的实现与节点类型完全无关 —— 加一种节点只需在那张表里把出边写对：

| 规则 | 内容 | 现状 |
|---|---|---|
| VG1 目标存在 | 遍历 `edges()` 判每条边的 target 存在（保留名除外） | ✅ `edges()` 驱动 |
| VG2 前向边无环 | 取 `forward==true` 的边建图（label 替换后 DFS 三色） | ✅ `edges()` 驱动 |
| VG7 可达性 | 从入口沿前向边展开到不动点 | ✅ `edges()` 驱动 |
| VG8 死 label | **任何** `edges()` 的 target 都算"被引用" | ✅ `edges()` 驱动 |
| goto 的回边 | `goto` 的边 `forward=false`，不参与前向环/可达展开 | ✅ `edges()` 驱动 |

各类型的出边（`src/workflow/node_types.cpp`）：

| 类型 | 出边 |
|---|---|
| tool | `next` + **`on_error.fallback`**（两条都算前向边） |
| expr | `then` / `else` |
| goto | `goto_target`，**`forward=false`** —— 回边，循环的唯一来源 |
| model / run_tools / load_history / save_history | `next` |
| route | `cases.*` / `default` |
| label | 无出边 |

**一处有意的语义变化（② 已补测试锁住）**：`on_error.fallback` 现在进前向边集合
（`label="on_error.fallback"`），于是"fallback 指回上游"形成的环会被 **VG2** 检出并拒绝。
改动前它不在集合里（VG2 只按 kind 收 next/then/else/cases），这类环逃过检查 ——
而它正是无限循环的来源。依据是 M11 既有纪律"循环只能通过 label + goto 表达"。
测试：`WfAgentLoop.backward_fallback_cycle_is_now_rejected`。

顺带地，fallback 渲染成一条**前向边**后，VG7 的可达性判定与节点类型无关了
（原先要特判 tool）—— 这正是本节预告的那一点。

**② 顺带查出的真缺口（先证实、再修）**：`find_refs_in_node` 与 VR1 的语法检查**各自按 kind 走、
都只覆盖 Tool/Expr**，于是 `load_history.path`/`session` 里的引用**两边都漏**。后果：
写错 `@config` 键名能一路通过校验（B2 的 config 契约形同虚设），运行期 resolve 成 null、
`as_string` 得到字符串 `"null"`，跑在一个叫 `null` 的目录上。先写断言证实它确实通过校验
（`WfHistoryNodes.config_keys_inside_history_fields_are_validated`），再用**一个统一钩子**
`NodeType::ref_texts` 修掉："本节点里可能含引用的文本片段"，VR1 的语法检查与 VR 段的引用收集
**共用**（原先两处各写一遍，正是漏检的成因）。Tool 递归取 `parameters` 里的字符串、
Expr 取 `expr`、history 取 `path`+`session`。

### 4.3 剩余 `NodeKind::` 的三类关注点（诚实量化）

①② 之后，**图结构规则不再是按 kind 分发的 if 链**。但"消灭 `NodeKind::`"不是目标本身 ——
`src/workflow/validator.cpp` 里仍留着 **16 处**、`compiler.cpp` **3 处**，它们分属三类**别的
关注点**，本就不该进注册表：

| 类别 | 出处 | 说明 |
|---|---|---|
| **结构性约束**（label/goto/on_error 的形态，不在"可插拔节点类型"范畴） | validator 11 处 + compiler 3 处 | label 的续接与目标替换（resolve_labels / resolve_target / 入口 / 编译期"后第一个非 label"）、goto 必须指向 label、fallback 不得指向 goto、死 label/死节点判定里"是不是 label" |
| **编排顺序规则**（跨节点，不属于任何单个节点类型） | validator 3 处 | VG9：load_history 必须在使用 messages 的节点之前（LoadHistory / Model / RunTools 各判一次） |
| **引用语义里"只有 tool 有 result"** | validator 2 处 | VR2 / VR3 依赖 tool 的 `output_schema` —— 这是 tool 语义；引用**收集**本身已收敛到 `ref_texts` |

所以"**28 处 if 链 → 0**"是不准确的说法：**图结构那部分 if 链确实收敛为 `edges()`**，
validator + compiler 共 **19 处** `NodeKind::` 里没有一处是多节点类型分发的 if 链，
剩余这些属上表三类**不同问题**，与"加一种节点要改几处"无关。

分层清楚后，才不会再把"通用规则"复制到每个类型里 —— 那正是原 28 处 if 链的来源。

### 5.1 符号约定与 creator 接口

**内置节点保持集中注册**（`node_types.cpp` 一张表）：那是**可读性资产**——打开一个文件就能
看到全部节点及其行为；换成自注册后"系统里到底有哪些节点"就不再静态可查。
"零改动"真正值钱的是**第三方扩展**（你无法改核心的场景），所以只对动态库上这套机制。

库与宿主之间只靠**一个符号约定 + 一个 C 结构**耦合：

```cpp
// 库为**每个节点**导出一个符号，名字即约定（<name> 须是合法 C 标识符）
extern "C" const cppchain_node_descriptor* graph_node_<name>_creator(void* host_ctx);

// 版本常量（cppchain 侧）：宿主加载库后**先校验**，不匹配即拒（fail-closed）
inline constexpr int kNodeApiVersion = 1;

// 纯 C 布局（链接规范只作用于函数/变量，不作用于类型）
typedef struct cppchain_node_descriptor {
  const char* name;      // 节点名：须与符号里的 <name> **一致**，宿主校验；不一致直接拒
  int         version;   // 本库编译时的 kNodeApiVersion
  void*       context;   // **库自己的**上下文；宿主原样持有、不解释
  void* (*create)(void* context);              // 由**库**分配
  void  (*destroy)(void* node, void* context); // 由**库**释放
} cppchain_node_descriptor;
```

四个字段各有其存在的理由，缺一个都会咬人：

| 字段 | 为什么需要 |
|---|---|
| `name` | **枚举/按名加载时的自校验**：符号名与声明名不一致（改名漏改）会被立刻发现，而不是"IR 里写 A、实际创建了 B" |
| `version` | **ABI 校验**。插件系统没有版本检查是经典坑：宿主与库的 `NodeType` 布局或 C++ 接口一变，就是静默的内存错乱。不匹配 → 拒绝加载 |
| `context` | **库不该用全局变量**：同一个 `.so` 可能被 `dlopen` 多次、或同时存在多个版本；creator 把自有状态交给宿主代持，`create`/`destroy` 时回传，库就不需要"全局单例"假设 |
| `create`/`destroy` 由库提供 | **跨 `.so` 的 `new`/`delete` 必须配对**：宿主的分配器与库不同就会崩 |

两处 ABI 细节（与上一版相同，仍必须遵守）：

- **`const char*` 而非 `std::string`**：消除字符串 ABI 与名字修饰两个风险。
- **`host_ctx` 是宿主能力的不透明指针**（当前承载 §6.4 的 `NodeLog` 等）；将来往里加能力靠
  `kNodeApiVersion` 递增，而不是改这个签名。
- 传回的 `descriptor` 内部若含 C++ 抽象接口指针（如 `GraphNode*`），仍要求**同工具链**。

**⑤a 的实现注记（与初稿的差异，写实）**：

- **库侧实现的是抽象接口 `DynamicNode`**（8 个虚方法：matches/parse/write/describe/edges/
  ref_texts/validate/compile），宿主把它包成 `NodeType` 的函数表适配器 —— std::function 全部在
  **宿主侧**构造，跨 .so 只传 vtable 指针与引用（§4.1 Q2 的"函数表 + 抽象接口"分工兑现）。
- **框架分发一律按名**：`NodeIR` 存 `NodeKind` 之外，新增 `NodeKind::Dynamic` + 按名入口
  `node_type_of_name` / `type_name_of` / `node_type_for_node`；validator / compiler / 展示的
  "取类型"全部改走按名（内置先、导入后）。于是动态节点的 `edges()`/`ref_texts()` 照样喂进
  VG1/VG2/VG7/VG8 与 VR1/VR4 —— **插件的图规则与引用检查与内置节点完全同构**。
  （加 `Dynamic` 枚举值不影响已有结构性判定：label/goto/on_error 仍用 `NodeKind::` 比较。）
- **加载 = 探测后统一提交（fail-closed 原子性）**：`load_workflow_imports` 先把所有库所有节点
  逐个 dlopen/dlsym/校验（任一失败 → 整体失败、一个都不注册），全部通过才逐个注册 —— 不给
  IR 判别留"注册了一半"的半吊子状态。
- **重复导入幂等**：同一宿主反复 import 同一库（多 workflow 共享进程）按"已加载"成功处理，
  不报冲突；与内置同名仍由"名字即键、内置优先"档住。**版本校验就是"改名漏检 + ABI 漂移"
  的第一道闸**：descriptor.name ≠ 符号名、version ≠ `kNodeApiVersion` 都会被立刻拒（测试
  `WfPlugin.name_mismatch_rejected` / `version_mismatch_rejected` 锁住）。
- **插件的符号解析模型 = 经典的"宿主导出"**：`.so` 对 `cc.graph.*` / `message::*` 的引用保持
  **未定义**，宿主可执行文件以 `-Wl,--export-dynamic` 导出自己的符号，dlopen 时由宿主解析。
  因此插件 `.so` 不链接任何 cppchain 静态库（静态库非 `-fPIC` 塞不进 .so）。

### 5.2 加载方式：先 A0，枚举（A1）押后

| | 做法 | 跨平台 | 得到什么 |
|---|---|---|---|
| **A0** ✅ 已实现 | 按 IR 声明的节点名 `dlsym(handle, "graph_node_<name>_creator")` | ✅ POSIX `dlsym` / Windows `GetProcAddress` 一个薄 shim | 库侧**无需中心分发函数**：加节点 = 加一个文件 + 一个符号 |
| **A1** ✅ 已实现 | **读 ELF 文件**扫本库 `.dynsym` 的 `.dynstr`，枚举 `graph_node_*_creator` | ⚠️ ELF-only（Mach-O/PE 另写；暂只支持 ELF64 + little-endian） | `import {lib}` 可省节点名（整库枚举）；`--list-nodes` 只读文件、**不执行库代码**，无需 `--allow-import` |

**A1 的两条技术要点（§5.2 的告诫，写实）**：

- **只扫本库自己的符号**：实现是 `enumerate_plugin_nodes(lib)` —— 重新打开 `.so` 文件、在它自己的
  `.dynsym`/`.dynstr` 里找段节，只收 `graph_node_<name>_creator` 且 **`st_shndx != SHN_UNDEF`**
  （本库**定义**的符号，未定义引用不算）。完全避开 `dl_iterate_phdr` —— 后者遍历整个进程，
  会把别的库的同名符号扫进来。
- **不 dlopen = 不执行代码**：`--list-nodes` 因此是纯检查，不给它设 `--allow-import` 门槛；
  省略 `nodes` 的 `import` 走 A1 枚举后再逐个 A0 加载（枚举只是省掉手工列名）。

**A0 已能拿到"库侧零改动"这个主要收益，且跨平台**；A1 只省掉清单里的节点名，却要吃下
一套 ELF 解析——而且枚举必须**只解 `dlopen` 拿到的 handle 自己的符号表**，
不能用 `dl_iterate_phdr`（它遍历整个进程，会把别的库的同名符号也扫进来）。

### 5.3 import 语法

```jsonc
{
  // 库**必须显式列出**（它是信任单元）；节点名可省（省了就用 A1 枚举）
  "imports": [ { "lib": "./libextra_nodes.so" },
               { "lib": "./libmore.so", "nodes": ["sentiment"] } ],
  "nodes": [ … ]
}
```

- **`nodes` 可选**。省略 = "整库信任"：加载时用 A1 枚举该库的全部 `graph_node_*_creator`
  （`WfPlugin.import_without_nodes_enumerates_and_runs` 锁住）；枚举失败（库读不了 /
  ELF64+LE 之外 / 被 strip）→ **fail-closed**，可改为显式列名。注意列空数组 `[]` ≠ 省略，
  是类型错误，**拒**（`WfPlugin.imports_empty_nodes_rejected_by_loader`）。
- 声明了 `nodes` 时，逐个 `dlsym`；**取不到 = 校验期拒绝**（不是运行期才发现）。
- 导入的节点与内置节点在 IR 里**用法完全相同**——`kind` 就是它的名字。

### 5.4 符号可见性（最常见的"为什么找不到"）

CMake 默认 `-fvisibility=hidden` 时符号**根本不导出**。库必须显式放开：

```cpp
#define CPPCHAIN_NODE_EXPORT __attribute__((visibility("default")))
extern "C" CPPCHAIN_NODE_EXPORT const cppchain_node_descriptor*
graph_node_<name>_creator(void* host_ctx);
```

或对该 target 设 `-fvisibility=default`。文档与示例 `.so` 都要示范这一点，
否则使用者会卡在"节点明明写了却找不到"。

> ✅ 已示范：`tests/plugin_demo/node_demo_plugin.cpp` 用 `CPPCHAIN_NODE_EXPORT`
> 导出 3 个 creator（好的 sentiment、改名漏检的 misnamed、版本过老的 ancient），
> 正好同时演示 `visibility` 与 §5.1 的两个校验。测试 `WfPlugin.*` 点名验证。

### 5.5 安全默认

> ✅ 已实现：CLI `--allow-import` 门 + `load_workflow_imports` 的
> "未放行即拒绝 / 加载内容可经 `host_log` 打进会话日志"。加载 .so = 任意代码执行，默认拒绝。

**加载 .so = 任意代码执行。** 与项目一贯的 fail-closed 一致：

> CLI **默认拒绝 import**；要用必须显式 `--allow-import`。加载时把库路径、`kNodeApiVersion`
> 校验结果、以及**发现的节点名**打进日志（§6），保证"这次运行加载了什么"事后可查。
>
> 注意分寸：**库是信任单元**，不是"扫目录发现谁就加载谁"——那样会把显式白名单退化成
> fail-open，与项目一贯纪律相悖。`import` 的**库名**永远显式。

## 6. 统一日志规范

> **状态：已实现（③）。** `session_log.hpp/.cpp` 落地：append-only `.log.jsonl`、`enter/exit/error`、
> 末尾半行容忍 + 告警（`truncated_lines()`）、seq 在写入锁内分配（文件顺序 == seq 顺序）。
> 引擎在节点边界统一写结构事件（`LoggingStateGraph`，见 §6.3）。节点经注入的 `NodeLog`
> 写 `source=node` 诊断（model / load_history 已示范，见 §6.4）。

### 6.1 三类来源与分工

日志文件由**多方写入**，但**格式统一、来源可区分**：

| 来源 `source` | 谁写 | 写什么 | 参与 replay？ |
|---|---|---|---|
| `engine` | **框架**（引擎在节点边界） | 节点身份、phases、耗时、状态、**状态增量 `update`** | ✅ **只有它参与** |
| `node` | 节点自己 | 节点内部的诊断（召回了几条、读了哪个文件…） | ❌ 只用于调试/审计 |
| `host` | 宿主（CLI） | 运行参数、加载了哪个 `.so`、放行了哪些节点 | ❌ |

**为什么"状态那部分"必须由引擎写、而"节点诊断"可以节点自己写**：

- **`update` 决定 history**（replay 的输入）。这部分**不能靠节点自觉**——10 个节点之后必然有
  忘返回、字段拼错、漏错误路径的，而代价是历史残缺。故由引擎统一采集。
- **节点自有诊断不参与 replay**，漂移了也不影响事实来源。所以它可以自由写，
  **前提是来源能区分** —— 这正是你这条要求的要点。

> **replay 的铁律：只读 `source == "engine" && phase == "exit"` 的记录。**
> 其余一律不参与状态重建。这条规则让"节点自己写日志"变得**安全**：
> 哪怕节点在日志里塞了 `update` 字段，也不会被应用到状态上。

### 6.2 统一外壳

所有记录共享同一个外壳，用 `source` 区分来源：

```jsonc
{"seq":12,"ts":"2026-10-05T17:05:01.456Z","run":"r-1","source":"engine",
 "node":"think","node_kind":"model", …}
```

| 字段 | 谁有 | 说明 |
|---|---|---|
| `seq` | 全部 | 文件内单调递增（**原子分配**，见 §6.5），replay 的排序键 |
| `ts` / `run` | 全部 | 时间戳 / 本次触发 id |
| **`source`** | 全部 | `engine` / `node` / `host` —— **判别键** |
| `node` / `node_kind` | engine、node | 节点 id 与类型（host 记录可无） |
| `level` | node、host | `debug` / `info` / `warn` / `error` |
| `msg` / `data` | node、host | 人类可读说明 + 任意结构化附加 |
| `phase` / `status` / `ms` / **`update`** | **仅 engine** | 见 §6.3 |

### 6.3 engine 记录（结构性事件）

```jsonc
{"seq":1,"ts":"…","run":"r-1","source":"engine","node":"recall","node_kind":"load_history",
 "phase":"enter"}
{"seq":2,"ts":"…","run":"r-1","source":"engine","node":"recall","node_kind":"load_history",
 "phase":"exit","status":"ok","ms":1,"update":{"messages":[…]}}
{"seq":3,"ts":"…","run":"r-1","source":"engine","node":"think","node_kind":"model",
 "phase":"exit","status":"ok","ms":842,"update":{"messages":[{…ai…}]}}
{"seq":4,"ts":"…","run":"r-1","source":"engine","node":"think","node_kind":"model",
 "phase":"error","status":"error","ms":17,"error":{"kind":"model","msg":"HTTP 429"}}
```

`phase` = `enter` / `exit` / `error`。`enter` + `exit` 都记（而非只记 exit）：
崩溃时"最后一条 `enter` 没有配对的 `exit`"就能**精确定位卡在哪一步**。

③ 实现在此基础上又定了三件事（写在这里免得从代码里猜）：

- **错误走 `phase:"error"`**：节点抛异常由边界 wrapper 捕获，落一条
  `{"phase":"error","status":"error","ms":…}`（**无 `update`**）后再向上重抛 ——
  enter 与 error 也配对；replay 只读 `phase=="exit"`，天然跳过。
- **`__input__` 事件**：本轮输入由 `fire_once` 在 run 开头写成引擎事件
  （`node:"__input__"`、`node_kind:"input"`，exit 带 `update:messages`）。宿主输入因此排在
  **历史之后、本 run 节点之前** —— D 阶段"宿主先写进会话文件"不再需要；同时宿主本身
  也写不了带 `update` 的记录（replay 铁律）。下一 run 的 load_history 会自动把它 replay 回来。
- **load_history 的 update 被省略**：它的 update 是更早 `input` + 各节点 `update` 的**回声**，
  写进日志会让 replay 时 `add_messages` 把整段消息再追加一遍（无 id 消息按追加处理）。
  实现上 wrapper 对该 `node_kind` 传 `update=nullopt`（exit 记录仍在，仅无 `update` 键）。

### 6.4 node 记录（节点自报）

节点**不自己开文件**，而是用引擎注入的 logger：

```jsonc
{"seq":5,"ts":"…","run":"r-1","source":"node","node":"think","node_kind":"model",
 "level":"info","msg":"完成一次模型调用",
 "data":{"model":"deepseek-chat","finish_reason":"tool_calls","usage":{"in":120,"out":30}}}
{"seq":6,"ts":"…","run":"r-1","source":"node","node":"recall","node_kind":"load_history",
 "level":"warn","msg":"日志末尾有半行，已跳过","data":{"bytes":37}}
```

节点侧接口（编译/运行期注入，不是全局变量——节点仍彼此独立）：

```cpp
struct NodeLog {                       // 引擎实现（SessionLog），注入给节点
  virtual ~NodeLog() = default;
  virtual void log(std::string_view level, std::string_view msg, Json const& data = {}) = 0;
};
```

实现注记：**注入路径是 `SessionSink`** —— compiler 创建、随每个图节点 wrapper 捕获，`fire_once`
每触发周期写入 `log`（节点运行期经 `sink->nlog()` 拿 logger，null 表示本次不落日志）。
**已埋点示范**：model（"model X 完成一次调用"）、load_history（"replay N messages"）。
run_tools 内部的并行工具**未埋**（那是工具级诊断，留开放点）；`SessionLog` 仍按并发安全实现。

跨 `.so` 的注意事项与 §5.1 同：传的是**抽象接口指针**（同工具链下 vtable 稳），
且 **host 分配、host 释放**，库不持有其生命周期。

### 6.5 并发

`run_tools` 会**并行**执行工具（M3 的 `ToolNode`，有界并行），节点日志可能并发写：

- `seq` 分配与文件写入由**同一把锁**管（`SessionLog::write` 内 `lock_guard`）——
  seq 在锁内递增，等价于"原子分配 + 写锁"，且保证**文件内顺序 == seq 顺序**（不会行交织）；
- 每个记录写后 `flush`（会话规模小，换崩溃安全）。

否则日志会出现 `seq` 重复或**行交织**（两条记录拼在一行）——那会直接毁掉 replay。

### 6.6 append-only 顺带修好了当前的一个脆弱点

现在（D 阶段）的落盘是**每次全量重写整个 JSON**，所以文件一坏就全丢——这正是当初必须写
"损坏就抛异常"（fail-closed）的原因：损坏后除了拒绝启动别无他法。

改成 append-only 之后：

- **崩溃最多损坏最后一行**，前面全部完好
- 解析时**跳过末尾半行并告警**即可，历史仍可恢复
- 恢复语义从"抛异常拒绝启动"变成"能救回来"

这是一个没预料到的收益：要求 4 顺带把落盘的健壮性提了一档。

**（已实现）** `SessionLog` 构造时自动做 §6.6 说的两件事：截掉末尾半行（`truncated_lines()`
计数，测试锁住）、`seq` 从已有记录继续（跨"命令"续写同一会话）。

## 7. history = 日志的投影

> **状态：已实现（④）。** `save_history`/`load_history` 的独立落盘已按本节推翻：
> `save_history` 节点删除、`history_file.*` 重写为 `session_log.*`，D 阶段的测试与 CLI 已同步改。

### 7.1 replay 语义

日志里每条 `exit` 事件都带 `update` —— 于是：

```
history = 按 seq 依次 schema.apply(state, update) 之后，取 state.messages
```

**直接复用现成的 reducer（`StateSchema`）**，不需要新机制。附带得到：

- **断点续跑**：replay 到最后一个 `status=ok` 的 seq，从那里继续
- **可审计**：每一步的输入/输出/耗时都在

④ 的实现在 §7.1 的公式上做了**一处简化**：**用固定的 `StateSchema::messages_state()` 做 replay，**
不再在 `compile` 时捕获 schema。理由：replay 只关心 `messages` 怎么拼，而 messages 通道的契约
在 compile 期恒为 `add_messages`（compiler.cpp 硬设）；`results`/`loop_counts` 的合并归约对
"取 messages"没有影响。因此 `load_history` 运行期只需 `replay_session_messages(path)` 一个函数：
读日志 → 过滤 `source=engine && phase=exit && status=ok` → 逐条 apply → 取 `messages`。
入口在 `session_log.hpp`，只读不写（不会在读取时修复/变更文件）。

> 复述 replay 铁律（§6.1）：**只有 `source=engine && phase=exit && status=ok` 的记录参与。**
> §6.3 的三件事在 replay 里如何体现：`phase:error` 天然不匹配 `exit`；`__input__` 是引擎的
> exit+ok，**参与**（这就是本轮输入进历史的通道）；load_history 那条 exit 没有 `update` 键，
> apply 空更新 = 无操作，不会重复追加。

### 7.2 节点的去留

| 节点 | 去留 | 理由 |
|---|---|---|
| `save_history` | ✅ **已取消** | 日志已经含了事实，再存一份就是第二个真相源 |
| `load_history` | ✅ **保留**（实现已换成 replay 投影） | "不必单独 save" ≠ "加载不是节点"；保留它符合"history 是普通节点"的既有决定 |

`load_history` 的运行期实现：resolve `path`/`session`（可含 `@config` 引用）→
`replay_session_messages(session_path(ws, sess))` 重建 messages → update 进 `messages` 通道。
（编译期无需捕获 schema，见 §7.1。）本轮输入不在 state 里手工拼 —— 它已经是日志里的一条
`__input__` 事件，replay 天然包含，顺序由 seq 保证。

### 7.3 与现有落盘的对照

| | 旧（D 阶段落盘） | 现在（④ 已实现） |
|---|---|---|
| 文件 | `session-<name>.json` | `session-<name>.log.jsonl` |
| 写入 | 每次**全量重写** | **append**（天然只追加） |
| 损坏 | 整文件坏 → 抛异常拒绝启动 | 最多坏最后一行 → 截掉并告警（`truncated_lines()`） |
| 事实来源 | history 文件 + （无日志） | **日志**（唯一事实） |
| 模块 | `history_file.hpp/.cpp`（已删除） | `session_log.hpp/.cpp` |
| 输入进入 state | 宿主先写进会话文件 | 引擎写 `__input__` 事件（§6.3） |

## 12. 开放点

1. **日志轮转与上限**：长会话下 `.log.jsonl` 会一直长。轮转策略与"replay 要不要跨轮转文件"一并设计。
2. **脱敏**：日志含完整对话内容。若将来要共享日志排查，需要脱敏/裁剪。
3. **跨 ABI 插件**：本文限定"同工具链"。真正的跨编译器插件需要纯 C 接口 + 序列化边界，成本高。
4. **日志作为多机事实源**：现在日志是本地的。若要做"跨设备续聊"，它就是天然的同步单元。
