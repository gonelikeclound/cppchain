## 一、一句话定位

**任务 = 一份落盘的档案，每次触发 = 一个批，批内走单批 P-E-V 环，批尾写回档案**。
常驻调度押后（OS cron 归 05 押后清单），但已有一个轻量 `wfr cron`（到期重进本进程跑一轮批）。

## 二、核心心智模型：档案与会话分工

| | 任务档案 `.wfr/tasks/<task>.json` | 会话日志 `.wfr/sessions/*.log.jsonl` |
|---|---|---|
| 管什么 | **计划 + 批进度**（steps/cursor/batch_no/last_summary） | **交互史 + 模型记忆**（replay 投影） |
| 谁写 | `task(end)` 批尾写回 | 每次触发的全部节点事件 |
| 给谁用 | 跨批还原的唯一接口 | 模型"记得之前发生了什么" |
| 会不会因批内变化烂 | 不会（计划稳定） | replay 天然完整 |

**一句话**：档案=计划·批进度，会话=交互史·模型记忆，两者都要、互不替代。
（实证：problems/28 §八.5「续跑契约对照」——删档案失去的只是"计划指针"，模型仍记得发生过什么。）

## 三、数据形态（档案 schema）

```jsonc
// .wfr/tasks/daily-report.json
{
  "task": "daily-report",
  "goal": "每天汇总一条真实新闻并存档，第 3 批出周总结",
  "created": "2026-10-13",
  "steps": [ { "id": "s1", "goal": "查热点写 .out/hot.txt", "deps": [], "status": "done" }, ... ],
  "cursor": 6,           // 全局已完成步数（跨批累积，永不重置）
  "batch_no": 2,         // 已跑批数
  "last_summary": "",    // 上批批间摘要（自由文本，来自末条 AI）
  "strategy": { "on_fail": "retry", "max_auto_rollback": 1 }
}
```

真机样例见 `tmp/pevcmp_b/ws_rc/.wfr/tasks/rc.json`、`tmp/pevcmp_b/ws_lot2/.wfr/tasks/lt1.json`
（后者 `last_summary` 甚至写进了推理块噪音——这正是批③ 交接件要升级的点，见 §九）。

## 四、一条批的运行时路径

```
wfr lot --set task=X [--session X] 一次触发 = 一批
  │
  ▼
recall(load_history; 会话 replay 投影)
  ▼
task begin ──读档案→ state.plan（steps 全清单 + cursor 续上）
  │          ├─无档案→ 用 @config.plan_steps 建档并写盘（created=true, batch_no=1）
  │          ├─时间感注入: 往 messages 加 "📅 第 N 批 @ 今天（+上批摘要）"
  │          └─recheck_prev=on 且非首批 → 游标处插入 audit_prev 复查步
  ▼
loop { max: 批步数+余量 }
  step(announce) → think(model·chat_bash) → route → approve | act(run_tools)
  → judge(verify) → _continue        // 单批 P-E-V 环原封复用
  ▶ 失败: retry ×N → auto_rollback 到首个未满足依赖的步
  ▼
task end ──读 state.plan + 末条 AI 文本 → last_summary → 写回档案
  │        └─另存快照 .history/batch{N}.json（批间修订/fork 的回溯源）
  ▼
final(批间总结·一句) → _turn_end
```

**代码实证**：
- workflow 形态：`share/wfr/workflows/lot.json`（recall → begin → loop{announce/think/route/approve/act/judge} → end → final）。
- `task begin/end` 实现：`src/workflow/node_types.cpp:1824-1949`（`c_task`）——读档还原 L1848-1852、建档 L1862-1878、
  时间感注入 L1908-1912、end 写回 L1925-1942、历史快照 L1940-1942。

## 五、跨批机制五件（长程的"骨架"）

1. **批还原（唯一接口）**：`begin` 读档 → `state.plan = 档案`，cursor 从 `batch_start` 续跑；
   `end` 写回 `cursor += 批内推进`。跨批契约**就是这份文件本身**（每次 fire 用全新 checkpointer +
   独立线程，`tests/wf/lot_task_test.cpp` 屏蔽 replay 干扰）。测试 `WfLot.two_batches_restore_cursor_and_inject_batch_no`。
2. **时间感注入**：`task begin` 把 `📅 第 N 批 @ 今天` 写进上下文 announce
   （DeepSeek-R1 的 `{cur_date}` 同款机制）。真机「日级多日模拟」用 `@config.task_date` 覆盖日期
   （problems/28 §八.2：批1=10-14、批2=10-15，开场"第 2 批 @ 2026-10-15"生效）。
3. **批间摘要**：`end` 捕获**末条 AI 消息全文**（`node_types.cpp:1925-1928`）落 `last_summary`；
   下批 `begin` 以 human 消息 +（可选）`audit_prev` 判据注入。**注意：是自由文本，不是结构化对象**。
4. **批间复查（recheck_prev）**：非首批 + 开关打开时，`begin` 在游标处插入一条 `audit_prev` 判据步
   （L3 模型裁判，criteria = 上批摘要，`node_types.cpp:1884-1900`），不推进 cursor，随批内第一步执行——
   "跨角色复查上批结论是否还成立（时变事实）"的雏形。测试 `WfLot.recheck_prev_inserts_audit_step_with_model_judge`；
   真机判定落 plan_log（problems/28 §八.1）。
5. **批间可改（revision-fork）**：`--set task_revision=N` → 从 `.history/batchN.json`（第 N 批结束快照）
   续，而非最新档案（`node_types.cpp:1836-1847`）= 回到历史批快照岔开重跑。
   测试 `WfLot.revision_forks_back_to_an_earlier_batch_snapshot`（批1→批2→revision=1，末态 cursor4、
   batch1 快照 cursor2 存档保留）。

护栏（problems/28 §三）：begin 缺种子早返（不继续跑坏后续 end）；end 遇空 plan **不覆盖档案**
（revision/history 不受污染，`node_types.cpp:1931-1935`）。

## 六、调度

- **不做 OS cron**，批次由 `wfr cron`（`src/wfr/main.cpp:356-407`）轻量自理：读 `.wfr/cron.json` 的
  `{job: task, every_minutes, last_run}` 表 → 到期**重进本进程** `run_argv(wfr lot ...)` 跑一个批 →
  更新 `last_run`；`--once` 跑一轮即收，`--sleep-secs`/`--max-rounds` 控制节流。
- 真机（problems/28 §四之三）：seed 批（cursor3/batch1）→ `cron --once` → 到期触发批2 → cursor 3→4 · batch 1→2。

## 七、生命周期与自进化接点

- **导出**：`tools/export_task_life.py` 扫 `tasks/*.json` + `sessions/*.log.jsonl` → 每行一条
  `task_archive`（task/cursor/batch_no/last_summary）或 `batch_verdicts`（plan_log 判定集）→ 训练/分析 JSONL。
  这就是 [05 未来专题规划·自进化](../01-discuss/05-未来专题规划.md) 的"运行数据可吃"接点——
  任务锁档 + 每批 verdict 是现成数据源。
- **审计**：batch_verdicts 直接来自 `plan_log`（judge/review 每步判定都落行，`node_types.cpp:1472`、2123-2194），
  回放即复盘。

## 八、与相邻系统的位置

```
单批：  plan → loop{execute→judge} → final        （PEV 环, arch 19）
  ▲ 自然上卷
长程：  task(begin) → [同上单批环] → task(end) → final   （arch 20, wfr-㊿）
多角色： mch = Planner → Executor环 → Reviewer → final   （arch 21, wfr-㊾）
```

- 长程是 **PEV 单批的多轮上卷**（同一环，档案接跨批）；mch 是 **PEV 的角色化**（同一环，身份+输入裁剪分角色）。
- 规划/验证环（`plan`/`verify`/`plan_review`）见 [arch 19](19-复杂任务规划执行验证环设计.md)；
  多 Agent 角色化设计见 [arch 21](21-多Agent角色化PEV设计.md)，计划批③ 交接式合并收口。

## 九、与批③ 的衔接（wfr-㊾ 交接式 A→B 交接件契约）

批③ 的**交接件契约**正好架在三者的接缝上：
- 长程的 `last_summary`（自由文本，甚至混进推理块噪音）→ 升级为**结构化交接件**
  （`done[].artifacts + summary`，随产物引用）；
- mch 的 Executor→Reviewer 接力用它做「A 产出 → B 只读交接件（`input_filter`）续做」。
- 现状确认（探索）：`input_filter` 全仓无实现（仅 docs 对标 OpenAI Codex），既有等价物 =
  `verify review` 相位（rev 只喂 计划+plan_log 判定+判据，不看执行思考，`node_types.cpp:1656-1699`）
  + `refine_history` 规则引擎 + `summarize` LLM 折叠。交接件的输入裁剪可复用这套思路。
