# 25 · P1.5：workflow 声明式配置（config 三形态）

> **来源**：proxyNode 收官时（problems/47 配套调研）明确押后的借鉴项 —— **miclaw-rs `crates/config` 的
> config 三形态机制**（声明区 + `$name` 引用 + `target` 自动应用 + `${workdir}` 运行变量 + 启动即炸校验）。
> 参考仓库 `tmp/miclaw-rs`（实现见 `crates/config/src/lib.rs`）。
> 本档把它按 cppchain 现状适配落地：**在现有「全局 config 表 + `@config.*` 引用」模型上生根**，不引入
> 逐节点 config 对象子系统。

## 一、问题与动机

当前 cppchain 的配置是**宿主手动拼的一张全局表**：

- `fire_once(wf, config)` 把 config 放进 `state["config"]`，节点字段用 `@config.<k>` 引用（refs.hpp §三种引用）。
- 谁是提供了哪些键、缺省值是什么，**workflow 文件自身说不出来** —— 全靠宿主代码（wfr `--set` /
  workspace/session 硬编码、examples 里写死）在外部配齐。`CompileOptions.config_keys` 只是编译期白名单，
  值是运行期才进入。
- proxyNode 之后子 workflow 的 config「同源」共享主表 —— 子 workflow 想有自己独立的配置来源（文件），
  没有表达通道。

**第一问**：一个 workflow 能不能自描述「我需要哪些配置、缺省从哪个文件来、哪些类型节点免声明直接用」，
让配置从宿主代码挪回 workflow 自身，且仍保持编译期 fail-closed（拼错即炸、不运行期变 null 才懵）？

## 二、miclaw-rs 参考（逐条转述）

`crates/config/src/lib.rs`（已 read 全文）：

1. **声明区**：workflow 顶层 `declarations.configs` 集中声明配置来源，节点按名引用：
   ```jsonc
   "declarations": { "configs": [
     { "name": "llm",   "from": "configs/llm.json",   "target": "model" },
     { "name": "tools", "from": "configs/tools.json" }
   ] }
   ```
2. **节点 config 三形态**：
   - **① target(type) 应用**：`target` 命中的类型且节点**自身没写 config** → 自动用该文件（`lib.rs:91`）。
   - **② `$name`/路径**：`"config": "$llm"` 或直接文件路径（顶层字符串 = 路径）。
   - **③ 内联对象 + 字段引用 + `*` 通配继承**：显式键 `$x.y`，未匹配键从 `$z` 整体继承（`lib.rs:162`）。
3. **运行变量**：`${workdir}` / `${sessionId}` / `${runId}` 在 run 创建时**全树字符串替换**（`lib.rs:197`）。
4. **启动即炸校验**（`lib.rs:224`）：`$name` 必须已声明、`target` 必须命中至少一个节点、`from` 必须存在。

## 三、cppchain 适配（核心决策）

cppchain 与 miclaw 的 config 模型**不同向**：miclaw 是「每节点一张 config 对象」，cppchain 是「全局
config 表 + `@config` 引用散落节点字段」。强行做逐节点 config 对象会与现 IR 字段模型打架。**决策：让
声明区成为「全局 config 表」的声明式来源**，三形态映射如下：

| miclaw 形态 | cppchain 落地 | 说明 |
|---|---|---|
| 声明区 `declarations.configs` | IR 顶层 `declarations`（新 `ConfigDecl{name,from,target?}`） | from 相对路径，基准 = `CompileOptions.config_dir` |
| ② `$name` 引用 | `@config.<name>.<子路径>` 命名空间引用 | **refs 扩展多级点分**；单段 `@config.<name>` = 整个文件对象 |
| ① target(type) 自动应用 | 文件**顶层键平铺**注入 config 默认值 | 等价于「该类型节点的默认参数包」；cppchain 的 config 本就全局可见 |
| ③ 内联字段引用 | 节点参数内联 `@config.*` **已是原生** | ✓ 无需新建 |
| ③ `*` 通配继承 | **不迁移** | cppchain 无节点 config 对象、参数显式；强迁违背显式原则 |
| `${workdir}` 等运行变量 | 保留语法 + fire 时全树替换 + resolve_parameter 内联替换 | 新 `RefKind::RunVar`，`${...}` 不再被判引用损坏 |
| 启动即炸校验 | **编译期**：from 存在 + JSON 合法 + target 命中 + `@config.<name>` 已声明 | 沿 VR4 基建，白名单自动并入声明键 |

**合并优先级（fire 时）**：`声明值（缺省） ∪ 宿主 config（顶层键覆盖）` —— 宿主同名字/同键赢；
命名空间键整体覆盖（宿主给了 `config["llm"]` 就整块用宿主的）。**不改** `resolve_parameter` 的宽松语义：
子路径拼错 → 运行期 null（cppchain 一贯哲学），**第一段（name）拼错 → 编译期 VR4 拦**。

**运行变量语义**：`${workdir}` ← `config.workspace`（wfr 宿主必给）、`${sessionId}` ← `config.session`、
`${runId}` ← `config.runId`（宿主显式提供；fire **不自动注入** run 号 —— 一次一 run 的可变值若落入
可见 state，会破坏「串行 vs 并行最终 state 逐键相等」等确定性契约，见 problems/30）。
替换点两处：
(1) fire 时对整个**合并后的 config 树**全树替换（声明文件里的 `${workdir}` 生效）；
(2) `resolve_parameter` 对**节点参数内联**的 `${...}` 替换（不经 config 的直写参数也生效）。
config 缺该键 → 字面量原样保留（不合成 null）。

## 五、边界与遗留

- **子 workflow 的 config**：proxyNode 子 config「同源主表」不变；子自己的声明区按同规则并入（config_dir 下发）。
  子跑 detach 时子 config = 合并后主 config 快照（现行为，不新增语义）。
- **`*` 通配继承不迁移**（理由见上）；如日后出现「参数整体继承」需求再单独立项。
- **运行变量只在值上替换**，不做路径解析/变量嵌套（`${workdir}/${runId}` 这种嵌套串联的字面替换，天然支持）。
- 声明 `target` 的文件 top 键平铺后**全局可见**（不限定只对 target 类型），因为 cppchain 的 config 是全局表；
  「平铺只对 target 类型可见」需要按节点 scope，与全局表模型冲突，不实现。
- `CompileOptions.config_keys`（宿主手写白名单）与声明的并集关系：声明覆盖宿主书写负担，两者可并存
  （宿主未必用的键仍可写；声明未提的键仍靠 config_keys 白名单）。
