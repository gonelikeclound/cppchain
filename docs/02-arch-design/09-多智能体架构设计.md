# 09 · 多智能体架构设计（M8）

> 对应路线图 M8：Subagent/多智能体。参照 langchain/langgraph 的 `ask_expert`（subagent-as-tool）、
> orchestrator-worker（串行版）、handoff（简化）。
> 同时是 `04-problems/05` 的 🔴 卡位「SubAgent / ForkAgent 使用」的落地层。
> 前置：M7 的 `Agent` 已就绪但**尚未暴露为图节点**（本轮补齐）。

## 1. 定位与边界

- **依赖**：M6（`graph::Command`/条件边/编译图）、M7（`Agent` 循环 + `Middleware`）、
  M3（`ToolSpec`/`ToolRegistry`）、M5（`StateSchema`/reducer，`ToolContext` 预留的 `Store`/`StateRef`）。
- **提供**：三种多智能体形态的**最小可运行版**——
  ① subagent-as-tool（ask_expert）；② 串行版 orchestrator-worker（supervisor graph）；
  ③ handoff 简化（控制权回跳）。配套：把 `Agent` 暴露为图节点的 `as_agent_node`。
- **不做**（押后）：

| 不做 | 归属 |
|---|---|
| Send 动态 fan-out（并行委派同一子任务给多个 worker） | M10 |
| 子代理**并行**执行 / 子代理流式 | M10 |
| 完整 `Command(resume)` / interrupt 语义 | M10 |
| 子代理自身持久化记忆（每工具独立 Store 命名空间） | 开放点（M9 评估） |

## 2. 参照：langchain / langgraph 的对应物

- **subagent-as-tool（ask_expert）**：子代理本质是一个**工具**——父模型的工具列表里挂
  `{"name": "ask_expert_<领域>", "description": "擅长…，接受 query 返回答案"}`；
  调用时在**独立的上下文**里跑一个完整 agent 循环，只把**最终答案**（而非子轨迹）带回父上下文。
- **orchestrator-worker**：supervisor 拆任务、worker 各自执行、结果汇总。
  langgraph 靠 `Send(node, state)` 做动态 fan-out；**本次做串行版**：同一时刻只跑一个 worker，
  worker 由一个条件 router 按"队列里下一个待办子任务"选中——不引入 Send。
- **handoff**：langgraph 里是 `Command(goto=PARENT)` / `schema` 让子代理把控制权交回父。
  **简化**：worker 需要澄清/上交时，返回 `Command{update, goto:["supervisor"]}`（M6 原生已支持），
  保留一跳 Human 消息让 supervisor 看到诉求。子代理内部的"上交"用保留工具名 `call_supervisor` 约定。
- **fork 语义提醒（沿用路线图 A2）**：官方 "fork" = checkpoint 时间旅行分叉，**≠** 我们说的"子代理
  委派"。M8 把对照写进 `04-problems/09`，避免两个词在文档里混用。

## 3. 设计

### 3.0 主线设计原则：**主上下文干净是第一优先级**

子代理的价值（langchain 官方口径）＝ 保持主上下文干净。落实成两条硬约束：

1. **隔离**：父看到的是子代理的**最终答案 + 压缩后的 stats 行**，绝不是子转录全文；
   子代理内部的工具 schema / 工具结果 / 多轮往返，都不进父的 prompt（token 上直接可验证）。
2. **可观测而不泄漏**：子代理内部发生了什么，走 `stats` 行（iterations / tool_turns / usage /
   sub-errors）与子代理自己的 transcript 暴露，父模型不需要读它就能配合。

### 3.1 subagent-as-tool（核心抽象）

```cpp
namespace cppchain::agent {

// 子代理规格：描述一个"专家"。全部非拥有指针，生命周期须长于用它的 ToolRegistry。
struct SubAgentSpec {
  std::string name;                 // 工具名（对父可见），如 "ask_research"
  std::string description;          // 工具描述：擅长什么、怎么用、返回什么（父模型以此决策）
  std::string system_prompt;        // 子代理人设（父无关）
  model::ChatModel* model;          // 共享同一模型实例（非拥有）
  tool::ToolRegistry const* tools;  // 子代理自己的工具集（非拥有，可含其他 subagent → 嵌套）
  AgentOptions options;             // max_iterations 等子循环参数
};

struct SubAgentToolOptions {
  std::string arg_name = "query";   // 唯一入参名
  bool include_trace = true;        // 返回里附压缩 stats 行
};

// 规格 → 普通 ToolSpec。handler 每次调用**新建完全干净的子代理**（见契约 ② 线程安全）
tool::ToolSpec make_subagent_tool(SubAgentSpec const& spec, SubAgentToolOptions opts = {});
}
```

**handler 语义**：读 `args[opts.arg_name]` → 依 spec 构造子 Agent → 注入
`system_prompt + [Human(query)]（+ attach_recent 时的父切片）` → `invoke` →
返回 `ToolMessage`，content 为「最终 AI 消息文本 (stats 行)」，status 按子代理成败。

### 3.2 `graph::as_agent_node`（前置补齐：Agent = 图节点）

### 3.3 串行版 orchestrator-worker（supervisor graph）

**state schema（概念）**：主上下文与 worker 内部**分槽隔离**，worker 不碰 `messages`。

```
{
  "messages": [...],   // 主线：supervisor 的委派话术 + finalize 的最终答复只在这
  "tasks": [ {"id":1, "worker":"search", "input":"..."} ],   // supervisor 分解产出
  "results": [ {"task_id":1, "answer":"..."} ],              // worker 逐个回填（不进 messages）
  "next_task": 0                                             // 队列游标
}
```

**图拓扑**（全部是 M6 已有原语，无新增执行机制）：

```
supervisor（结构化输出节点，M4：StructuredOutput.invoke → 一次性把提问拆成任务计划）
   │  plan = {"tasks":[{worker,input},...]} → 写 state.tasks（overwrite；worker 值用 enum 限定为图内真实节点名）
   ▼
├─ 条件边（router）：读 next_task —— 还有未执行子任务? → 返回该任务 .worker 节点名 : "finalize"
│      ↓
│  worker_*（Agent 节点：读 tasks[i].input / 写 results[i]，不进 messages）
│      └─ 条件边：还有任务 → 下一 worker；否则 → finalize
└─ finalize（Agent 节点：读全部 results + 原提问 → 汇总答复 → 写 messages）→ END
```

worker 由 **router 按任务名动态选中**，不需要固定链条——这就是「串行版没有 Send 也能表达
orchestrator-worker」的关键（Send 的横向扇出留 M10，垂直串行是 M6 原生能力）。

### 3.4 handoff 简化

两级，都落已有原语：

1. **图中上交**：worker 发现输入不属于自己 / 需要澄清 → 返回
   `Command{update:{messages:[一条 Human 说明]}, goto:["supervisor"]}`
   （`Command.goto`s 覆盖出边，M6 已实现）。
2. **子代理内上交**：worker 型 subagent 的工具表里放保留名 `call_supervisor({question})`，
   子代理调用它即把"想交给父的问题"放进返回值；`make_subagent_tool` 见到该标记时在
   ToolMessage 里附 `handoff` 标志，父模型据此直接接管（不再当普通答案继续追问）。

## 4. 契约

1. **返回回传只含最终答复**：`make_subagent_tool` 的 ToolMessage 不含子转录；stats 行是
   `iterations / tool_turns / usage / sub_errors` 的**压缩摘要**，不作为父模型的普通输入。
2. **每次调用新建干净子代理**：handler 按 spec 现构现用——因为 `ToolNode` 可并行调用
   （`max_parallel=4`），共享可变子代理必然数据竞争；现构现用同时保证**上下文隔离**与
   **线程安全**。构建成本≈拼指针，可忽略。
3. **副作用透传不豁免**：子代理的工具仍按 M7 中间件审批 / 防重放（`ToolExecutionJournal` 共表），
   父只审批"委派动作"本身，不替代子代理对其内部工具的审批——审批是**纵深**不是**旁路**。
4. **错误语义**：子代理 `ModelError` / 超 `max_iterations` → `status="error"` 的 ToolMessage +
   压缩原因（不抛子转录）；图内 handoff 属控制流，不算错误。
5. **Actor 生命周期**：`Agent`、`ToolRegistry`、`Checkpointer` 均非拥有；`subagent-as-tool`
   里 spec 的指针成员要求与 `ToolRegistry.add()` 相同的纪律——**先注册后使用，勿中途改**。
6. **进程内共享模型**：父子同一个 `ChatModel&`（真机只发一个 provider 连接）；跨进程/独立
   实例留给未来。

## 5. 卡位问题（本层落地）

| 问题 | 落地件 | 验证方式 |
|---|---|---|
| **副作用与子代理**（04-problems/05 🔴） | subagent-as-tool + 审批透传 + 主上下文干净 | demo 里做 **token 会计对照**：子代理内部 N 次工具往返，父那一轮的 input tokens 相对不带子代理时**几乎不变** |
| **fork 语义对照**（路线图 A2） | `04-problems/09` 成稿 | 文档对照：checkpoint 时间旅行 fork ≠ 子代理委派 |

**与 M7 的协同**（04-problems/05 §跨问题观察）：压缩、截断、子代理是同一个问题的三种解法——
都在提高 prompt 信息密度。M8 的"隔离"是**结构性**的一档：父 prompt 里压根不放子代理内部，
比压缩/截断（内容仍躺在对话里）更彻底，但代价是"多一轮委派 + 一次模型往返"。

## 7. 开放点

1. **子代理持久化记忆**：`SubAgentSpec` 是否按专家接 M5 `Store` 命名空间（跨轮记住领域常识）——
   涉及"干净的隔离" vs "专家有长期记忆"的取舍，M9 评估。
2. **attach_recent（父会话切片注入子上下文）**：破坏"绝对干净"，收益/泄漏（token vs 召回）
   需量化——落地前先以严格隔离为准；详细设计（03-detail-design/05 §8）列为开放点。
3. **涉及审批的记忆化**：父对某专家"委派+内部审批"结果会话内记忆化（M9 审批记忆化深化项交叉）。
4. **Send 版 orchestrator**：M10 补 fan-out 后，router 选 worker 从"串行点名"升级为"并行扇出"，
   本节的 `tasks/results` 分槽可原样复用。
