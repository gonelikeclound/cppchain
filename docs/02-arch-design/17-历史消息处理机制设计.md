# 17 · 历史消息处理机制（wfr-㊵）—— 摘要 / 精简 / 长内容裁剪

> 专题：**历史消息处理**。三个方向 —— **摘要**（较早的一段折成一条 LLM 摘要）、
> **精简**（按规则过滤：去思考过程 / 去错误工具轮 / 去检索类调用）、**长内容裁剪**
> （长工具结果、长 AI 回答）。每个方向一个内置 workflow 探索多种做法。
>
> 承接 [15-思考模型推理回传与历史压缩策略](15-思考模型推理回传与历史压缩策略设计.md)：
> 那一篇是**渲染期变换**（`load_history` 的 mode/budget，结果不落盘）；这一篇补上
> **可持久化的派生视图**（op 落进会话日志）。

## 1. 定位与边界

- **在做什么**：把「历史怎么送给模型」从三档固定策略，扩展成**可组合、可持久化、可对比**
  的三类能力。
- **不在做什么**：不改检索、不改工具实现、不做用 LLM 摘要超长单条内容（裁剪只做截断与
  落盘引用两种）。

## 2. 先讲清楚障碍：messages 通道表达不了"折叠"

`state::add_messages`（`src/state/state.cpp:71`）只有两条语义：**追加**，和**同 id 覆盖**。
而 workflow 产出的消息**都不带 id**（`c_model` 写 `Json::array({*r})`、`c_run_tools`、
input 事件都不带）→ "覆盖"路径事实上休眠。于是：

> **"把 18 条历史折成 1 条摘要""删掉 5 组工具轮"——在当前通道下根本表达不出来。**

## 3. 破法：op —— 对累计消息施加的一次操作

在 `add_messages` **开头**加前置判定（数组分支逐字节不变）：

```cpp
if (right.is_object() && right.contains("op") && right["op"].is_string())
  return apply_message_op(left, right);
```

两个 op（封闭词表）：

```jsonc
// 折叠：剥掉头部旧摘要 → 校验 base_size → 保尾部 N 条 → 前置新摘要
{ "op":"fold", "keep_last":4, "base_size":22, "prepend":[<摘要消息的规范 JSON>] }

// 删改：按下标删一批、改一批（计划已由节点算好并固化）
{ "op":"transform", "base_size":22, "drop":[3,4,7], "rewrite":[{"index":9,"message":{…}}] }
```

### 3.1 为什么是 op，而不是"节点直接写回整段数组"

三条决定性理由：

1. **replay 自动一致、零额外注册点**。`replay_session_messages`（`session_log.cpp:263`）用的
   就是同一个 `messages_state()` → 同一个 `add_messages`。扩展函数两处天然同源；**新增
   reducer 就要改两处**——而 wfr-㉙ 的回声抑制正是"两处按 kind 判断"踩过的坑。
2. **一致性是构造性的，不是"重算一遍但愿一样"**。op 里固化了一切所需数据（摘要文本、要删的
   下标、改后的内容），reducer 只做机械应用 → 它是 `left` 的**纯函数** → 日志重放同一条 op
   必然得到同样结果。**规则怎么算、边界怎么选，全在发出 op 的节点里**（那层才有 token 估算、
   工具注册表与 LLM）。
3. **分层依赖不被破坏**。reducer 在 `cppchain_state`，只链 `cppchain_message`；它**不能**
   调 `agent` 的 token/规则，也不能查工具注册表。"节点算计划、reducer 执行"把这一步结构性
   地隔离掉了。

### 3.2 重放一致性论证（归纳）

记 `L_s` = `load_history` 在 seq 点 `s` 执行时对日志做的内部 replay。则：

1. 运行期 `state.messages` **只**由各节点 `update.messages` 贡献（`fire_once` 的 input 事件
   只写日志不入 state）。
2. 运行到 `s` 时 `state.messages = L_s`（定义）。
3. 全量 replay 到记录 `R_s` 结束时的状态 = 对 s 之前全部记录的 apply = `L_s` → **与 2 相等**。
4. 此后每一步 `update.messages` 都被记为 `exit.update`，两处同样 apply。
5. op 分支是 `left` 的纯函数（不读时钟、不调模型、不查注册表）→ 由 3、4，两处 `left` 相同
   → 结果相同。

**∴ 运行期与 replay 不可能分叉。**

### 3.3 会让 replay 分叉的坑（实现里都堵住了）

| 坑 | 说明 | 处置 |
|---|---|---|
| **新节点被加进回声抑制名单** | `compiler.cpp` 有两处按 `kind=="load_history"` 丢弃 update；一旦把 `summarize`/`refine_history` 加进去，op 就不落日志 → replay 静默分叉 | 那两处保持"按 kind 白名单"、代码注释写明纪律、`tests/wf/history_ops_test.cpp` 当哨兵 |
| op 里含不确定量 | 如 reducer 内部现算时间戳 / 随机 artifact 名 | 一律在**节点里算完**写进 op |
| 有节点改了 messages 却不落 update | 只有 load_history（被抑制的恰是"回声"） | 新节点**不加**抑制 |

### 3.4 幂等与防堆叠

- **摘要不堆叠**：摘要消息在 `additional_kwargs` 带 `cppchain_summary` 标记；`fold` 先剥掉
  头部旧摘要再前置新摘要 → **世代交替**。重放两次折叠后仍只有一条摘要。
- **`base_size` 守卫**：op 与"发出它时的那个列表"绑定；apply 时条数不符（重复 apply /
  被人手改过）→ **忽略本次 op**。这把"重复 apply 会退化"从"有界但不严格幂等"变成**显式安全**。
- **孤儿兜底**：保留区不得以 Tool 消息开头（`fold` 里逐条剔除）—— 真实端点会因孤儿
  ToolMessage 直接 400。节点侧另有 `TrimHistory::safe_boundary` 先挡，这是第二道。
- **未知 op / 形状非法 → 原样返回 `left`，不抛异常**：`add_messages` 有三个读者（运行期
  `StateSchema::apply`、replay、`wfr` 末尾打印会话条数），抛异常会把第三个带崩。非法 op
  由发出端的 validator 在**编译期**挡住（fail-closed 放在前面）。

## 4. 两个节点

### 4.1 `summarize`（方向一）

| 参数 | 语义 |
|---|---|
| `when` | `off`（基线档）/ `messages` / `tokens` / `always` |
| `max_msgs` / `max_tokens` | 阈值（超过才折） |
| `keep_last` | 折叠后保最近 N 条（**下限**，见下） |
| `style` | `concise` / `detailed` / `evidence` —— 本方向的核心自变量 |
| `summary_role` | 摘要消息的角色（`system`/`human`/`ai`） |
| `on_fail` | `skip`（默认，**不发 op、保留全量历史**）/ `placeholder` |

- **折叠边界复用 `TrimHistory::safe_boundary`**：保留区不以孤儿 ToolMessage 开头、也不会把
  "Tool 在保留区而它的 AI(tool_calls) 被折掉"。因此 `keep_last` 是**下限**：`keep_last=3`
  实测保 4 条（再切一刀会切开工具组）。
- **失败降级的方向**：`skip` 是默认 —— 没有摘要的折叠会毁上下文，**fail-open（保留全量）才是
  安全方向**。
- **不重复摘要**：头部已有摘要且未超阈值 → `skipped`；下一轮 `load_history` 重放会 apply
  上一轮的 fold op → 模型**不再重算**。真机实测：第 1 次 22→5 条（−71%），第 2 次
  `skipped (below_threshold)`、**零摘要调用**。
- 发布 stats：`action/reason/when/before_msgs/after_msgs/before_tokens/after_tokens/
  summarized_msgs/kept_msgs/keep_last/summary_tokens/style`。

### 4.2 `refine_history`（方向二 + 三）

规则在 `agent/history.{hpp,cpp}` 里做成**纯函数** `plan_history_rules` → 产出
`HistoryRulePlan{drop, rewrite, stats}`，节点再固化成 `transform` op。

| 规则 | 做什么 | 关键边界 |
|---|---|---|
| `drop_reasoning` | 删所有 AI 的 `ReasoningBlock` | 只动 content，**tool_calls 绝不动** |
| `drop_error_tools` | 删"组内工具结果**全是** error"的工具组 | **组粒度，连发起调用的 AI 一起去** —— 只删 Tool 会留下 dangling tool_calls → 400 |
| `drop_category:<c>` | 删"组内每个 Tool 的类别都 == c"的工具组 | 同上；类别经 `tool_call_id` → AI.tool_calls → name → 快照 map；**混类别整组保留** |
| `drop_tool_results` | 删无对应调用的孤儿 Tool（安全网） | 只删孤儿 |
| `clip_tool_results` | 超预算的工具结果 → 截断 + 标注；或落盘引用 | UTF-8 安全（`prefix_within_tokens`/`char_boundary`） |
| `clip_ai_text` | 超预算的**终态** AI 回答 → 截断 + 标注 | **跳过带 tool_calls 的过渡回答**（它的长来自 reasoning 与 args，裁它无益且会断工具组） |

- **规则当集合看**（JSON 里书写顺序不生效），按固定优先级排序 → 计划确定、可测。
- `preset`（minimal / lean / aggressive / clip）∪ 静态 `rules`；`clip_scope` 只门控两条
  clip 规则（切出"只裁 AI 长回答"这类档位）。
- `clip_mode=artifact` 复用抽出来的 `write_tool_artifact`（原 `ArtifactToolResults::after_tool`
  的函数体），落盘目录缺省 `<workspace>/.wfr/artifacts`。注意：**原文仍在日志里**，artifact
  只是给人/给模型的快捷入口，不违反"日志是唯一事实来源"。
- **兑现（wfr-㊶）**：引用行与 `message.artifact` 显示**沙箱根相对**路径（`display_root` = 工作区绝对路径），
  且 wfr loop 的 `chat` 工具集挂只读对 `file_read`/`list_dir`（沙箱根 = 工作区）——模型把引用行里的
  相对路径直接喂 `file_read` 即可读回全文（真机探针读 `"total"` 字段验证过）。`file_write` 是副作用、
  loop 无审批，**不默认挂**。

### 4.3 `ToolSpec::category`

封闭词表 `retrieval | compute | action | model | time | general`（默认 `general`）。
**不进 `to_openai()`** —— 类别是库内分类，不是 function schema 的一部分（真端点对未知字段
敏感，`tool.cpp` 有前车之鉴）。内置归属：`get_weather`/`web_search` → retrieval、
`get_datetime` → time、`calculator` → compute。

**分层纪律**：agent 层的规则引擎不 include 任何 tool 头文件 —— 类别由节点在**编译期**从
`ToolRegistry` 快照成"名字 → 类别"的纯数据传入。`drop_category:` 在 agent 层只校**形状**，
词表由 workflow 的 validator 用 `tool::is_known_category` 校（那里才有 tool 层）。

## 5. 三个内置 workflow 与档位

```
recall(load_history) → <summarize|refine_history> → echo_xxx → loop[…同 chat2…]
```

新节点一律放 **loop 之外**：一个触发器最多产 1 个 op、summarize 不被每轮工具往返反复调用、
`safe_boundary` 不会把刚发生的调用折掉。三个 workflow 的 `system_prompt` 与 chat2 **逐字节
相同**（对照只允许一个自变量）。

| workflow | 档位（`--set`） |
|---|---|
| `hist_sum` | `sum_when` · `sum_style` · `sum_keep_last` · `sum_role` · `sum_on_fail` |
| `hist_rules` | `rule_preset` · `drop_categories` · `rule_clip_scope` · `rule_tool_budget` / `rule_ai_budget` |
| `hist_clip` | `clip_mode` · `clip_scope` · `clip_tool_budget` / `clip_ai_budget` · `artifact_dir` |

## 6. 校验规则

| 规则 | 内容 |
|---|---|
| VN15 | summarize：model 组件存在、next 必填、`when`/`style`/`summary_role`/`on_fail` 字面量走词表、阈值与条数为正整数（写成 `@config.*` 则留给运行期） |
| VN16 | refine_history：`preset`/`clip_scope`/`clip_mode` 词表、规则名与**类别词表**、预算为正整数 |
| VG10 | 历史处理节点必须在 `load_history` **之后**（历史还没投影出来时它无事可做） |
| VG9（扩） | 把 summarize / refine_history 纳入"消费 messages 的消费者" |
| VR2（扩） | 白名单**只加两项**（两者发布 result）；指向 expr 的 `$x.result.f` 仍被拒 |

## 7. 可视化与观测

- 两个节点在调试图上有独立配色（summarize 青、refine_history 橄榄绿）。
- 点节点看 `exit.update` → **op 原文**（`keep_last` / `drop` / `rewrite` 一目了然）。
- echo 节点把 stats 打在终端；`source=node` 诊断带完整 stats JSON（不参与 replay，随便看）。

## 8. 已知取舍

- `fold` **不追求严格幂等**，靠 `base_size` 守卫 + "已折叠且未超阈值则 skip" 从源头避免。
- op 的 `drop` 下标**运行时算好固化** —— 好处是 replay 不必重算（换来可证的一致性），代价是
  op 与"当时的消息列表"绑定。
- 新节点放 loop 外是**建议而非强制**（放 loop 内可选，代价是每轮一个 op）。
