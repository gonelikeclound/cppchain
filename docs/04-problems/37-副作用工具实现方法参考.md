> **定位**：给其它 agent 在本仓库实现"带副作用工具"时作**自包含参考**——可直接复制此文档单独使用。
> **事实基线**：cppchain `main @ d73643d`（2026-10-21），全仓 **763 测试全绿**；
> 主实现见 `tests/plugin_demo/sidefx_notify.cpp`（场景 mock 库）、`tests/wf/sidefx_notify_test.cpp`（31 case）、

> **一句话**：副作用工具 = **声明契约**（read_only/effect_class/approval/probe）挂在工具上，
> 由 **ExecutionGuard**（幂等防重放 + probe 兜底）+ **approve_tools**（前置审批）+ **活动集允许名单**（run 只执行名单内）
> 三道治理接管；"可撤销/可关闭"等业务语义落在**工具域状态机**，guard 不管撤销、只防重复执行。

## 〇、先读这篇：治理全貌（3 分钟）

一条带副作用工具的调用，从模型发出到落地，依次经过：

```
model 发出 tool_call
   │
   ▼
approve_tools（前置审批，state 纯函数）── read_only 免审（直接放行）
   │                                      ├─ deny 名单 → 静态拒绝（error 回喂）
   │                                      └─ approval=NeedHuman → 整节点悬挂（interrupt → 人审 → resume）
   ▼
run_tools  →  活动集允许名单（只执行"本 workflow 声明过"的工具）
   ▼
ExecutionGuard.prepare（每调用）── 串行段，唯一事实源 = 会话日志（三态）:
   │  ├─ 未开始             → 检查 L2 词面门禁 → 放行执行
   │  ├─ completed success  → **replay**（重放日志内容，不真执行）
   │  ├─ completed error    → **blocked**（拒跑，除非 retry_on_failure）
   │  └─ intent 残留(崩溃)  → **probe** 兜底：Complete→replay / Partial→blocked
   │                        / Absent→安全重跑 / Unknown→blocked（fail-closed）
   ▼
ExecutionGuard.run（并行段）→ 真执行 handler → ToolMessage 写回
```

**关键分工**（必须刻进脑子）：
- **guard 只解决"幂等 / 防重放 / 崩溃缺环"**，对"已完成的调用"不做任何下游动作（不撤销、不补偿）。
- **"可撤 / 不可撤 / 可关"是工具域语义**——写在 mock 业务状态机里，或靠"工具集里有没有反向工具"表达。
- **probe 只在"崩溃缺环"（有意图、无结果）时被调**；正常执行完的调用一律 replay 不 probe。
- **重复执行防护的 key** = NameAndArgs（默认）或 ToolCallId；同参数新 id 会命中重放，这正是幂等的意义。

## 一、副作用工具的声明契约（每个副作用工具必须声明 5 个字段）

在 `tool/ToolSpec`（`include/cppchain/tool/tool.hpp`）里：

| 字段 | 类型 | 语义 / 铁律 |
|---|---|---|
| `read_only` | bool | false = 声明"我有副作用"。**只读工具完全免 guard / 免审批**（lookup/prepare/approve 直接放行）|
| `effect_class` | `EffectClass` | `Read / Idempotent / Irreversible`。**read_only=false 必须显式声明**（缺省 Read 会触发启动自检 `effect_class_violations` fail-fast）|
| `approval` | `ToolApprovalLevel` | `Never / Policy / NeedHuman`。NeedHuman 越过静态策略，强制人审（bash 出厂值）|
| `probe` | `std::function<ProbeResult(Json const& args)>` | **崩溃缺环兜底**：判"外部世界是否已发生"。必须**只读**、失败当 Unknown。缺省 nullptr = 无探测 → guard 对 Intent 一律 fail-closed |
| `ttl` | `optional<seconds>` | 结果时效（快照类工具如天气/搜索）。**不参与 guard 决策**（agent 层 StaleStateGuard 消费），别指望它驱动撤销窗口 |

代码骨架（宿主侧静态注册）：

```cpp
tool::ToolSpec spec = make_tool("mock_order_create", "创建订单（幂等）",
    SchemaBuilder().prop("order_id", "string", "", true).build(),
    [world](Json const& args, ToolContext&) -> Res {
      // handler：写 mock 世界（落盘 / 内存状态表 / 真实 API），同参同果
      return Json{{"order_id", args["order_id"]}, {"status", "created"}};
    },
    /*read_only=*/false);
spec.with_effect_class(EffectClass::Idempotent);   // 铁律：免启动自检
spec.probe = [world](Json const& args) -> ProbeResult { // 崩溃缺环才被调
  return world->exists(args["order_id"]) ? ProbeResult::Complete : ProbeResult::Absent;
};
registry.add(std::move(spec));
```

**实测与有效性**：
- 全仓 `effect_class_violations` 自检在 wfr 启动即跑（`src/wfr/main.cpp`），漏声明 → 退 2；
  动态库工具在 fire 后复检（problems/34/35 落地）。
- `tests/tool/effect_class_test.cpp`（3 例）锁定词表与自检行为。
- **有效性结论**：契约自检是"静态声明"防线，成本几乎为零、能挡住"漏声明"这类静默遗漏的
  effect_class 盲区（曾真实发生过：新库 read_only=0 缺声明时 wfr 启动查不到——已用 fire 后复检补上）。

## 二、治理链接入（三处挂载，缺一不可）

### 2.1 ExecutionGuard（执行点防护）
宿主管好一次、挂进 CompileOptions，运行期自动接管 c_run_tools / c_tool 的工具执行点：

```cpp
ExecutionGuard::Options go;
go.log = replay_exec_log_reader(hist_msgs);   // 会话日志 = 事实源
go.audit = [&](tool::AuditRecord const& rec) { /* 审计落盘 */ };
tool::ExecutionGuard guard{std::move(go)};    // 放 main 作用域，活过 compile+全部 fire
CompileOptions opts;
opts.tool_policy = &guard;                    // 关键挂载点
```

决策表（`src/tool/exec_guard.cpp` prepare，文字化后即上面的流程表）。
关键：`key_for(call)` NameAndArgs（默认，参数键序无关）——想测"同参重发"切 key_mode。

**实测与有效性**：`tests/tool/exec_guard_test.cpp`（17 例）+ `side_effect_workflow_test.cpp`（7 例）
断言 `replays()/blocked()/executions()` 计数的**精确值**（如 `completed→replays()==1 && executions()==0`），
非"看起来对"。**有效性结论**：计数断言把 guard 行为钉死，最易回归的点（重放/拒跑）被全覆盖。

### 2.2 approve_tools（前置审批）
放 `run_tools` 之前：`think → approve_tools → run_tools`。state 纯函数，产出 `approved_ids/denied`。

- deny 名单硬拦（先于人审）；read_only 免审。
- `approval=NeedHuman` → **整节点悬挂**：`interrupt`（payload 携待批请求）→ resume `{action:approve}` → 放行。
- **动态工具坑（已修）**：approve 解析 spec 早期只查**内置注册表**，动态 mock 全被当"未知工具"静态拒。
  修复 = `nc.shared_tools` 兜底（`node_types.cpp` c_approve_tools），优先级与 run_tools 对齐。

```cpp
// 校验限界（problems/34 §三 / 35 §三）：deny 名单存在性只查内置表 → mock 名不能写进 deny，
// deny 演示沿用内置名（如 send_notification / file_write）。
```

**实测与有效性**：`approve_tools_test.cpp`（8）+ `approve_tools_interrupt_test.cpp`（6）+ sidefx F1/F2。
F2（`F2_needhuman_dial_suspend_then_approve`）实测：dial 进 interrupt → resume approve → `guard->executions()==1`
（真执行、ring 入库），且悬挂期间 `executions()==0`。
**有效性结论**：批准→执行闭环经悬挂/恢复路径真实验证；修复 approve 共享回退后动态工具全链可跑。

### 2.3 tool_registry 活动集 + run_tools 允许名单（副作用工具的"注册与封锁"）
- workflow 入口放 `tool_registry` 节点（`tools:[{from, type:"so"/"select", load:[工具名]}]`），
  so = 动态库经 `load_dynamic_tools` 加载进**共享表**；select = 仅激活内置（不拷定义）。
- 节点把 `load` 并集发布进 `results.<id>.active_tools`；`model`（think）与 `run_tools`（run）从 context 取。
- **run_tools 允许名单**：非活动名 tool_call → error ToolMessage 回喂，**不执行**（防注入/防误调）。

**实测与有效性**：`tool_registry_select_test.cpp`（12）+ sidefx A 组（5）。
A3（`A3_allowlist_rejects_non_active_tool`）：调 `mock_ghost_tool`（非活动名）→ error「不在本 workflow
的活动工具名单」，guard 未执行。A2：model schema 恰好 == 活动集声明序。
**有效性结论**：活动集闭环（发布→消费→封锁）全链路实测；允许名单把"工具叠加到上下文"约束为
"workflow 自声明过的才算数"。

## 三、handler / mock 库实现：动态库工程模式（跨 DSO 安全）

给副作用工具建独立 `.so`（如 `tests/plugin_demo/sidefx_notify.cpp`），模式：

```cpp
// 1) 只 include tool_plugin.hpp + nlohmann，不链 cppchain；纯 C descriptor + 裸函数指针
#include "cppchain/tool/tool_plugin.hpp"
#include <nlohmann/json.hpp>

// 2) 库内状态表 + 互斥锁（跨调用、可并行；进程期常驻，宿主不 dlclose）
std::mutex g_mu;
std::unordered_map<std::string, int64_t> g_orders;   // 业务世界真相
// ...wechat outbox / sms / calls 各一张表

// 3) 每个工具一个 `tool_<name>_creator` 导出，返回稳定 descriptor
extern "C" CPPCHAIN_TOOL_EXPORT cppchain_tool_descriptor const* tool_mock_order_create_creator(void*) {
  return desc_for("mock_order_create", "mock：下订单（幂等）", R"(...json schema...)",
                  /*read_only=*/0, kToolEffectIdempotent, kToolApprovalPolicy,
                  mock_order_create_run, probe_order);   // handler + probe 都是裸 C fn
}

// 4) desc_for 工厂：必须给每把工具**稳定** descriptor 指针
cppchain_tool_descriptor const* desc_for(...) {
  static std::unordered_map<std::string, cppchain_tool_descriptor> by_name;  // 按名稳定指针
  cppchain_tool_descriptor& d = by_name[name];  // NOT thread_local！
  d = cppchain_tool_descriptor{};  // 逐字段赋值（name/version/context/desc/params/read_only/effect/approval/handler/probe）
  return &d;
}
```

**三个真实坑（都进过雷区，务必抄）**：
1. **`desc_for` 用 `thread_local` → 批量 dlsym 全串成最后一把工具**：
   宿主 `load_dynamic_tools` 逐个 `dlsym→creator()`，同一线程的 thread_local descriptor 被反复覆写，
   pending 里 N 个指针全指最后一个 → 8 个工具全变成同一 handler（sidefx 实测:全部调出
   `mock_clock_forward: seconds 须为正整数`）。**改为按 name 的进程期 static map**（加载阶段宿主串行，无并发）。
   注意 `mock_tools.cpp` 此前只单名加载未暴露，同款潜伏 bug 一并修了。
2. **`approve_tools` 只查内置表 → 动态工具被当"未知工具"拒绝**（见 §2.2，引擎修复）。
3. **run_tools 同批并行 → 状态依赖的调用顺序不可控**（见 §5 串行链）。

**实测与有效性**：
- 最小复现（`load_dynamic_tools` 直调）确认 thread_local 错位：8 工具 handler 全=最后一个 → 修后逐一正确。
- 动态加载真跑：sidefx A4 / tool_registry_select ⑩（`libmock_tools.so` 真 dlopen）。
- **有效性结论**：动态库模式把"mock 世界"与宿主解耦（跨 DSO 只用 C 契约），可被 wfr 真机与测试双路径加载；
  上面三个坑证明"批量加载/审批/并行"是动态副作用工具最容易炸的三处。

## 四、可逆性梯度状态机（"副作用语义"的实现范式）

这是核心——**把"副作用种类"翻译成可测的工具组合**。四种模式（sidefx 库完整实现）：

| 模式 | 例子 | 实现 | guard 关系 |
|---|---|---|---|
| **幂等** | 订单下单 | 同 key 二次 → `status=existing`（不重复入表）| guard 原生协作：同参重发 = replay |
| **窗口可撤** | 微信 | send 记 `sent_at(模拟钟)`；反向工具 revoke 判 `age < 窗口`，出窗 error「已过撤回窗口」| guard 不管撤销；窗口是库状态+handler |
| **不可撤** | 短信 | **只注册 send，无任何反向工具**（D2 断言 schema 无 revoke）| 不可撤 = 工具集层面保证 |
| **任状态可关** | 电话 | 状态机 `ring →(connect) answered →(hangup) hungup`；ring 挂 = 接通前取消、answered 挂 = 接通后关闭 | 状态机拒绝非法转移（如 ended 后再 connect）|

**配套工具**：
- **模拟时钟 `mock_clock_forward`**：`now() = system_clock + offset`，库内 `g_clock_applied[distinct N]` 台账
  保证幂等（同 N 只推一次）。→ **"时间窗口过期"变成确定性输入**，离线可复现，不 sleep。
- **测试隔离控制件 `mock_state_reset`**：清空全部库状态 + 时钟（测试前置调用，隔离跨用例 static）。
- **probe 故障注入档**：id 前缀 `?` → Unknown、`#` → Partial（测 guard 四格 fail-closed 时用）。

**实测与有效性**：
- 窗口：C2 窗口内 revoke success（`revoked`）/ C3 `forward(500s)` 后 revoke error（「已过撤回窗口」）。
- 不可撤：D2 断言 schema 含 "sms" 的工具**只有** `mock_sms_send`；D1 断言 `effect_class==Irreversible`。
- 电话：E2 ring 挂 →「接通前取消」/ E3 connect 后挂 →「接通后关闭」/ E5 ended 后再 connect → error。
- **有效性结论**：模拟时钟是"测时间窗口"的决定性手段（真实时间测试 flaky + sleep 慢；拨钟确定、毫秒级）；
  状态机挡非法转移（ended 后操作 error）经 E5 实测；"不可撤=无反向工具"被 D2 锁定，比在 guard 里
  "禁止撤销"更符合现实（工具集即能力集）。

## 五、测试驱动方法（每种方法的实测数据与有效性）

> 测试骨架照 `tests/wf/sidefx_notify_test.cpp`：Fixture（`builtin` 内置表 + `shared` 共享表 +
> `RecordingModel` 记录 `last_opts` + `ExecutionGuard` + `MemoryCheckpointer`）+
> `reset_sidefx()` 每个 TEST 清库状态。断言**统一走库状态 / guard 计数 / ToolMessage 文本**，
> 不看模型嘴上（problems/03 §5）。

### M1 · guard 计数断言（幂等/防重放/矩阵）
灌 FakeLog（intent/completed 可配），断言 `guard->replays()/blocked()/executions()` 精确值 + 报告内容。
- **实测**：B2（intent+probe Complete → `replays≥1, executions==0`、报告含「已执行」）；
  B5（probe `?`=Unknown → `blocked==1, executions==0`）；F4（`#`=Partial → blocked）。
- **有效性**：★★★★★ 最强——把"行为"钉成"数字"，回归一眼可见；唯一依赖是 guard 计数语义清晰。

### M2 · 收件箱 / 磁盘交叉断言（副作用真假）
副作用工具把结果写假世界（`FakeToolSinks.notifications` / 真实文件），断言"真的没落地"。
- **实测**：F1a（approve deny → 收件箱空 + `executions==0`）；side_effect_workflow_test 同款。
- **有效性**：★★★★★ 防"模型说做了但没真做/真做了但模型没报"的双向撒谎；副作用治理的本质验证。

### M3 · 全链流水线 + 脚本化模型（IR→校验→编译→fire）
每个用例都是完整 `parse → validate → compile_workflow → fire_once`，`RecordingModel` 给预置回复队列。
- **实测**：sidefx 全部 31 例；governance_test 6 例（终态四档）。
- **有效性**：★★★★☆ 覆盖"声明到落地"全链路而非单函数；代价是单例略重，换取端到端可信。

### M4 · probe 矩阵注入
工具 probe 按 id 前缀返回 Unknown/Partial/Complete/Absent，一次跑四种 guard 决策。
- **实测**：B5（Unknown→blocked）/ F4（Partial→blocked）/ B2（Complete→replay）/
  D4 / E4（Complete→replay）/ 库内"对象不存在→Absent→安全重跑"。
- **有效性**：★★★★★ 崩溃缺环兜底的每一条路径都被走实，不留"没测过的分支"。

### M5 · 模拟时钟（时间窗口确定性）
见 §四。**实测**：C3（500s 后 revoke 失败）；G1（forward(60)×2 → 第一次 forwarded、二次 already_applied）。
**有效性**：★★★★★ 时间类测试的"告别 sleep"方案，毫秒级且可复现。

### M6 · 串行链驱动（**避开 run_tools 同批并行竞态**）
`loop{ think → route → act → _continue }`，模型队列每轮一个 tool_call → 每轮执行最后一条 AI 的调用 → 天然串行。
- **为什么必须**：run_tools 对**同一条 AI 消息里的多个 tool_call 是并行执行**（批内并发、结果按下标回填）。
  状态依赖（send→revoke、dial→connect→hangup）同批会竞态——**实测 E5 因此失败**（并行下 connect 可能在挂断前/后执行，结果不确定）→ 全部依赖型 case 改 loop 后稳定通过。
- **有效性**：★★★★★ 不是测试技巧，是**语义正确性**：mock 库 mutex 保线程安全但保不了业务顺序；
  真机由模型自然分步（每轮一个调用），测试用 loop 复刻同一约束。

### M7 · 悬挂 → resume（人审闭环）
NeedHuman 工具验证 interrupt payload → resume approve/reject/坏值三条路径。
- **实测**：F2（resume approve → executions=1、ring 入库）；approve_tools_interrupt_test 6 例
  （reject 回喂 feedback、坏值 fail-closed、read_only 不悬挂、deny 优先于人审）。
- **有效性**：★★★★★ HITL 是"人审副作用"的完整契约，闭环必须逐条路径验证。

### M8 · 动态库真加载 + 活动集断言
`.so` 真 dlopen，断言活动集发布 / schema 曝光 / 允许名单 / 顶替（同名 mock 压内置）。
- **实测**：A1/A2/A4；tool_registry_select ⑩（so+select 混排、`loaded/active_tools` 断言）、⑪（共享表同名顶替）。
- **有效性**：★★★★☆ 验证"声明进 context → 消费取 context"整链；依赖 .so 产物（tests ON 才构建），
  release 需 env/安装布局（边界已记录）。
