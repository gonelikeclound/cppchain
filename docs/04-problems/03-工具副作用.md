# 03 · 工具副作用（Tool Side Effects）

> 对应路线图 M7 卡位问题。数据来自 `examples/agent_loop` 第③段与 `tests/agent/agent_test.cpp`。

---

## 1. 问题场景与产生原因

工具分两类：**只读**（查询、检索、计算）与**有副作用**（写文件、发邮件、付款、删数据、调外部 API）。

副作用带来的问题：
- **不可逆**：删除/发送/付款一旦执行无法撤销；
- **越权**：模型可能被提示注入诱导，或被用户的一句话带偏；
- **难重放**：checkpoint 恢复会**重跑节点**（M6 的恢复语义），若副作用不幂等就会重复执行；
- **难调试**：出错后现场已被改变。

## 2. 常见解决思路

| 思路 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **审批门（HITL）** | 执行前暂停，等人确认/改参数 | 最强保障 | 需要中断/恢复机制；打断自动化 |
| **策略拒绝** | 按规则禁止某类工具/参数（如禁止删除 `/etc`） | 零延迟、确定性 | 规则维护；可能误伤 |
| **只读默认** | 工具声明 `read_only`，写操作显式标注 | 语义清晰 | 仅标记不拦截，需要消费方 |
| **幂等 + 去重键** | 用 `tool_call_id` 作为幂等键，重复调用只生效一次 | 抗重放 | 需要工具侧配合 |
| **dry-run / 预演** | 先返回"将要做什么"，确认后再真执行 | 无中断成本 | 两次往返 |
| **补偿事务** | 记录操作日志，失败后反向补偿 | 可恢复 | 实现复杂，非所有操作可补偿 |
| **审计日志** | 全部工具调用与结果留痕 | 事后可查 | 不阻止损害 |

**关键认识**：这些是**纵深防御**——标记（`read_only`）+ 策略 + 审批 + 幂等，一层都不够。

## 3. langchain / langgraph 的对应做法

- 工具内可 `interrupt()`：执行前暂停，人工确认/改写参数后再 `Command(resume=...)` 继续（官方推荐用于 HITL）。
- `Command(update=..., goto=...)` 让工具能回写状态与控制流（副作用结果可入状态）。
- 注意官方对 `interrupt` 的硬约束：node 会**从头重跑**，所以**副作用必须幂等**。

## 4. 本项目选型与理由

### 4.1 执行前拦截：`ToolApproval`（中间件，`approve_tool_call` 钩子）+ `ToolSpec::read_only` 标记


- **拒绝不抛错**：转成 `status="error"` 的 `ToolMessage` 回喂，模型可换策略或向用户说明——保持循环不中断；
- 两种配置：名单拒绝（`{"delete_file"}`）或回调判定（按参数，如"只允许删 `/tmp` 下的文件"）；
- 完整 `interrupt`（暂停等人）留到 M10，因为它需要 M6 的 interrupt 支持。

### 4.2 执行后防重放：`SideEffectGuard` + `ToolExecutionJournal`（M7 收口补上）

**为什么必须有**：M6 的恢复语义是"回到该步边界**重跑**"，M7 的循环与任何重试叠加，
就可能让**已执行的副作用再执行一次**（重复发邮件/扣款/删除）。这是本层最初最大的隐患。

**三态判定**（幂等键 = `tool_call_id`）：

| 日志状态 | 含义 | 动作 |
|---|---|---|
| 未见过 | 首次 | 登记"意图" → **正常执行** |
| `Completed` | 已成功执行过 | **重放记录的结果**，绝不重跑 |
| `Intent` | 登记了意图但没有结果（执行中崩溃） | **拒绝重跑**，回喂"结果未知，请人工确认" |
| `Failed` | 执行失败（可能部分生效） | 默认**拒绝重跑**；`retry_on_failure=true` 才允许 |

- **只读工具不记账**（重跑查询无害，且不该污染日志）；
- **持久化后端**：`FileJournal`（每次变更**原子落盘**：写临时文件 → `rename`）——
  构造时自动载入，**无需手工 dump/load**；意图在**执行前**就落盘（否则"执行中崩溃"在重启后无法识别）；
  **损坏时 fail-closed 抛异常**（可显式选 `StartEmpty`）——安全机制不能"静默降级为不安全"；
- **多租户隔离**：`SideEffectGuard::Options::key_prefix` 让多个会话安全共用一个日志文件；
- 键模式二选一：`ToolCallId`（默认，语义最明确）或 `ToolNameAndArgs`
  （能抓住"模型重新规划后新 id 同参数"的重复，代价是可能误杀合法的重复调用）。

## 5. Demo 与验证结论

- **单测**（离线）：名单拒绝 → 回喂 error ToolMessage；回调按参数选择性允许 ✓。
- **真机**（`agent_loop` 第③段）：策略禁止 `send_email` → 模型把我们的拒绝原因转述给用户
  （"调用被系统策略拒绝了…需要经过审批流程"）✓。

### ⚠️ 真机暴露的验证陷阱（值得记住）

第一次用 `delete_file` 演示时**拒绝次数为 0**——因为 `deepseek-chat` **自己就拒绝调用**高危工具，
即使我明确要求"不要征求确认"。中间件根本没被走到，demo 却"跑通了"。

→ 教训：**验证型 demo 必须确认被测路径真的被走到**（计数/断言），否则"跑通"是假象。
演示副作用审批要用"策略禁止但模型愿意调用"的中危工具（如发邮件）。

### 5.1 真实内置工具 file_write 的端到端审批（`examples/tools_approval`，离线确定性）

此前审批/防重放演示用的是假工具 `charge`（自增计数）。`file_write` 落地后把它换成
**真实的内置副作用工具**做端到端验证——硬断言全部基于**磁盘状态**（文件在不在、内容对不对），
不看模型嘴上说什么：

| 场景 | 机制 | 断言 |
|---|---|---|
| ① 名单拒绝 | `ToolApproval({"file_write"})` | 拒绝 1 次；`guard.executions()==0`（拒绝不代表执行）；denied.txt **未创建** |
| ② 回调按参数放行 | `Decider` 只允许 `notes/` 前缀 | 合法 `notes/plan.md` 真实写盘且内容 v1；`root.txt` 被拒且未创建 |
| ③ 崩溃重启防重放 | `FileJournal` 复原 → 同 `tool_call_id` 重放 | `replays()==1`/`executions()==0`；同样参数 v2 **没写进去**，文件保持 v1 |
| ④ 只读对照 | `file_read`（read_only=true） | 不进名单、不记账，正常执行 |

**要点**：
- 审批（执行前，`approve_tool_call`）与防重放（执行前 `lookup_tool_result` + 执行后 `record`）是
  **两道独立闸门**：拒绝路径根本不走到 `executions`；重放路径只回放结果不动磁盘。
- callback 的判定能读 `call.args`（已是解析后的 JSON）→ 按参数放行比名单更细（路径白名单）。
- 这正好验证 03 文档 §4.1/4.2 的三态判定在**真实工具**上也成立：铁律是"只读不记账、拒绝不执行、
  重放不动盘"。

### 5.2 防重放验证（`examples/side_effect_guard`，离线确定性）

```
① 首次扣款                    真实执行 1 次    扣款次数 = 1
② 崩溃重启（从落盘日志恢复）    重放 1 次       扣款次数 = 1   ← 没有重复扣款
③ 结果未知（intent 无结果）     阻塞 1 次       扣款次数 = 1   ← 拒绝重跑
```

配套单测 16 项：重放不重复执行、intent 拒跑、failed 默认拒跑/可配置重试、
只读工具不记账、两种键模式对照、日志 JSON round-trip、**跨进程重启后重放**；
以及持久化后端专项：跨实例耐久、**意图即时落盘**、原子写后无残留临时文件且 JSON 合法、
**损坏 fail-closed**（与 `StartEmpty` 选项）、首次运行无文件属正常、**键前缀租户隔离**。

> 修复过程中还抓到一个实现 bug：重放路径也会走 `after_tool`，把带 `[重放]` 前缀的内容
> **再写回日志** → 多次重放会不断累加前缀（内容漂移）。修法：只有**真实执行**才登记待记录键。

## 6. 未解 / 下一步

1. ✅ **持久化后端已补**（`FileJournal`，原子写 + fail-closed + 键前缀隔离）。
   仍未做：SQLite/`Store` 后端（接口已定，可平替）；日志**保留策略**（条目只增不减，长期运行会膨胀）。
2. **键策略选择**：`ToolCallId` vs `ToolNameAndArgs` 的取舍没有银弹，
   需要按工具语义分类（幂等工具 vs 非幂等工具）——目前由使用者决定。
3. **审批的记忆化**未做：同一会话同一工具会被反复询问。
4. **审计日志**未做：现在只有执行日志（intent/result），缺少"谁在何时批准了什么"。
5. `interrupt` 式暂停/恢复（M10）；提示注入下的策略健壮性未测。
