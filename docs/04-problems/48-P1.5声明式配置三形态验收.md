### 关键设计定局

1. **在全局 config 表上生根，不做逐节点 config 对象**：cppchain 的 config 是全局表 + `@config` 引用散落
   节点字段，miclaw 是每节点一张 config 对象。强行引入逐节点对象会与 IR 字段模型打架（arch 25 §三）。
   三形态映射：② `$name` → `@config.<name>.<路径>` 命名空间引用；① target → 文件**顶层键平铺**进
   全局 config 默认值（该类型节点的"默认参数包"，全局可见）；③ 内联字段引用 = 既有 `@config.*`，
   `*` 通配继承不迁移（无节点 config 对象、参数显式原则）。
2. **多级点分只对声明名生效（存量零回归）**：历史 IR 提示词里有 `@config.current.stem`——本义是
   "current 的 stem 字段"，旧解析 = 单段 `@config.current` + 字面量 `.stem`。若一律点分导航，
   `current` 是 JSON 字符串 → 下钻非对象 → 合成 null，提示词当场丢数据。因此 `resolve_ref` 只在
   第一段 ∈ `config["_config_declared"]`（声明名单，fire 合并时写入）时才导航；其余保持旧模板语义。
   `_config_declared` 在**子链里做并集**（父命名空间传下来），不覆盖。
3. **运行变量 `${workdir}`/`${sessionId}`/`${runId}`**：闭词表语法（未知名 → 编译期 VR1 拦，防拼错）；
   `${runId}` **不自动注入** run 号——一次一 run 的可变值若落进可见 state，会破坏「串行 vs 并行
   最终 state 逐键相等」确定性契约（problems/30），故只认宿主显式给的 `config.runId`；较 miclaw 的
   per-run runId 是有意取舍。替换点两处：fire 对合并后 config 树全树替换 + `resolve_parameter` 内联替换。
4. **覆盖优先级**：声明值 = 缺省；宿主 config 顶层键覆盖（命名空间整块覆盖、平铺键逐键覆盖）。
5. **启动即炸（编译期 fail-closed）**：缺 config_dir / from 缺失 / JSON 坏 / 非对象 / target 未命中 /
   未声明第一段（VR4，仅当宿主提供白名单时核对）→ 全部编译期拒，不静默到运行期变 null。

## 四、回归与全仓

- workflow_tests 338 → **349**（+11）；全仓 **861 全绿**（agent 100 / graph 55 / message 20 / model 59 /
  state 43 / tool 226 / webui 9 / workflow 349），零告警语义（唯一告警 = 既有测试对 `CompileOptions`
  聚合初始化缺新字段的 `-Wmissing-field-initializers`，位置语义无移位、非新告警类别可接受）。
- 存量零回归专项：`cgi-workflows/question_execute.json` 的提示词 `@config.current.stem` 等 **不再可能
  被点分解析**（未声明名 → 旧模板语义），CGI 题库工作流不受影响。
- wfr 宿主：`config_dir` = workflow 文件所在目录，内置/自建 workflow 全部行为不变（无声明区时该字段闲置）。

## 五、遗留

- `*` 通配继承不迁移（无节点 config 对象；日后"参数整体继承"需求单独立项）。
- `${runId}` 需要宿主显式给 `config.runId`（fire 不自动注入）——书面记牢的取舍。
- 声明 target 平铺键全局可见（不限定只对 target 类型节点），与全局 config 表模型一致。
- `CompileOptions.config_keys`（宿主手写白名单）与声明区并存：声明覆盖书写负担，宿主未列的新键仍靠白名单。
