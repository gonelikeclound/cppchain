## 逐项说明

### 1. 大批量工具查找 → `04-problems/01`
- **结论**：关键词检索（含 CJK 2-gram + IDF）是零依赖基线；向量检索修复了跨语言/同义改写；
  但**压缩比不是目标**——我们踩过"检索返回 0 个工具却被当成 1444x 优化"的坑，也踩过
  "8/8 但动作不对"的指标定义坑。
- **下一步**：混合召回（关键词 ∪ 向量 → 去重 → 可选 LLM 精排）+ **动作级评测集**。

### 2. 超长工具返回 → `04-problems/02`
- **结论**：截断省的是"每轮重复"的钱；UTF-8 边界必须处理（否则 JSON 序列化直接抛异常）。
- **下一步**：启用 `ToolMessage::artifact`（完整结果落盘 + prompt 只放引用）——M1 已留字段。

### 3. 工具副作用 → `04-problems/03`
- **结论**：拒绝要**回喂而非抛错**（模型能自愈/解释）；标记 + 策略 + 审批是纵深防御。
- **下一步**：幂等键（`tool_call_id` 去重）——M6 恢复与 M7 循环都可能导致**副作用重放**，这是当前最大的隐患。

### 4. 上下文压缩 → `04-problems/04`
- **结论**：线性增长可用阈值压缩压成有界；LLM 摘要在真机上保住了关键要点。
- **下一步**：按 token/占用率触发；量化摘要成本与信息损失。

### 5. SubAgent / ForkAgent → 未开始（M8）
- 计划形态：`subagent-as-tool`（把子代理包成工具）、orchestrator-worker、handoff。
- **前置**：M7 的 Agent 还没暴露成 M6 的图节点；`Store` 的命名空间隔离机制已就绪（M5）。

## 跨问题的横向观察

1. **"小 demo + 计数断言"是必需品，不是奢侈品**：三次踩坑（0 工具、动作不对、路径没走到）都源于
   "跑通了" ≠ "验证了"。→ 已定为评测纪律：**任何检索/中间件实验都要确认被测路径被走到**。
2. **压缩、截断、子代理是同一个问题的三种解法**：都在回答"如何让 prompt 里的信息密度更高"。
   M8 的子代理隔离与 M7 的中间件压缩应当协同设计，而不是各自为政。
3. **有损操作必须可观测**：截断标注了字节数、压缩留了摘要与触发计数、拒绝回喂了原因——
   凡是"丢信息"的动作都要留下痕迹，否则问题会以"模型变笨了"的形式出现，难以归因。
