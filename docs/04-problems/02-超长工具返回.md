# 02 · 超长工具返回（Long Tool Response）

> 对应路线图 M7 卡位问题。数据来自 `examples/context_budget`（实验 A）与 `examples/agent_loop`。
> 复现：`./run-demo.sh context_budget agent_loop`

---

## 1. 问题场景与产生原因

工具返回的内容会**原样进入下一次请求的 prompt**，而且——关键在于——**在它被压缩或丢弃之前，每一轮都要重新计费一次**。

实测（`context_budget` 实验 A，真实 usage）：

| 工具输出字节 | prompt 增量 token | tok/字节 |
|---|---|---|
| 1,000 | +241 | 0.241 |
| 4,000 | +833 | 0.208 |
| 16,000 | +3,185 | 0.199 |

（中文为主的文本约 5 字节/token。）典型触发场景：读文件、查数据库、搜索、抓网页、`ls -R`、日志。

**危害**：① 直接挤占上下文窗口；② 一次 16KB 输出 ≈ 3.2k token，若后续还有 10 轮工具往返，等于**重复付费 10 次**；
③ 长噪声还会稀释模型的注意力（"lost in the middle"）。

## 2. 常见解决思路

| 思路 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **头部截断** | 超过 N 字节截断并标注 | 零成本、确定性强 | 可能切断关键信息（截断点之后的内容永远看不到） |
| **摘要式压缩** | 用模型把长结果压成摘要 | 保留语义 | 多一次模型调用；有信息损失 |
| **结构化摘取** | 工具本身只返回需要的字段（投影） | 最省、最准 | 需要按工具设计，泛化差 |
| **分页/游标** | 返回前 N 条 + 游标，让模型按需再取 | 可继续深挖 | 多轮往返 |
| **落盘 + 引用** | 完整结果写文件/存储，prompt 里只放路径和摘要 | prompt 极省、原文可回溯 | 需要存储与二次读取工具 |
| **流式丢弃** | 流式输出时边收边丢（只留统计） | 内存省 | 信息直接丢失 |

**关键认识**：截断省的不是"一次性"的钱，而是**每轮重复**的钱——这才是它真正的价值。

## 3. langchain / langgraph 的对应做法

- `ToolNode` **没有内置截断**：工具结果原样进 `ToolMessage`。
- `ToolMessage` 有一个 **`artifact` 字段**（存放不适合进 prompt 的完整结果）。本项目已启用：
  M9 的 `ArtifactToolResults`（`include/cppchain/agent/artifact.hpp`）把超预算全文落盘、inline 换成
  "头部 + 路径 + 规模"引用行；wfr 侧另有**渲染期** artifact 模式（`problems/19`，含沙箱相对路径回读）。
- 官方在 Harness 层（Deep Agents）用**虚拟文件系统 + 子代理**来隔离大输出：工具结果写文件，主上下文只拿引用。
- 检索式解法（grep / BM25 / 向量）在两头都只有零散工具或外部依赖，**没有"按需打开一份大文档"的统一抽象**——这正是本仓库 longdoc 与本节「追加」要补的位置。

## 4. 本项目选型与理由

`TruncateToolResults`（中间件，`after_tool` 钩子）：

- **UTF-8 安全**：按字节截断会切断中文（实测触发 `type_error.316`，见 `03-detail-design/04` §2），实现回退到字符边界；
- **显式标注**被截断的字节数，并在文案里提示"如需完整内容请缩小查询范围"——把选择权交回模型。

## 5. Demo 与验证结论

- **单测**（离线）：500 字节输出 → 被截到 <500 且含"已截断"标注；中文边界不产生非法 UTF-8。
- **真机**（`agent_loop` 第②段）：`search_docs` 返回 ~3KB → 截到 500 字节 → 模型仍能正确总结（"返回了若干片段，因过长已截断"），
  即**截断未破坏可用性**，只是丢了细节。

## 6. 未解 / 下一步

1. **摘要式截断**未做：现在是无脑头部截断；对"结论在后半段"的结果会丢关键信息。
2. ✅ `ToolMessage::artifact` 已启用（M9 `ArtifactToolResults`；wfr 渲染期 artifact 模式见
   `problems/19`）。**剩余**：工具结果**自动句柄化**——`fetch_url`/`web_search` 等仍只在历史处理时
   才落盘，执行当时不主动落盘。
3. ✅ **截断阈值**已有 token 预算模式（`TruncateToolResults::max_tokens`，M9）；但
   `history::HistoryRuleParams` 的 `tool_budget=200` / `ai_budget=400` 仍是拍的值，未按任务动态化。
4. 截断对**任务成功率**的影响未量化（需要任务级评测集，M9）。
5. **七法没有统一抽象与评测**：翻页 / 落盘回读 / grep / 结构化提取 / BM25 / 向量 / 采样
   各自散落在工具、longdoc、历史规则里，没有"按问题形态路由"的编排——见下节「追加」。

## 追加（2026-10-27）· 全景：超长工具返回没有单一解法，只有混合路由

> 本节回答两个问题：① 超长工具返回"完整解法"长什么样；② 已有 longdoc（arch 28）在这张图里站哪。
> 结论先说：**没有单一手段能同时做到"不漏、不贵、不假"**。现实解法是把七种手段按"对答案位置的
> 先验强度"排序，配上一个预算兜底——**混合路由**才是解法，任何单法是它的一个特例。

### 7.0 成本模型：优化的单位是"每轮留在上下文里的 token"

一条工具结果的生命周期成本 = **大小 × 剩余轮数**（见 §1 实测：16KB ≈ 3.2k tok/轮，10 轮 = 3.2 万）。
所以"把结果变小"只是次要目标；**"让结果根本不进上下文、需要时再取局部"**才是主战场。
由此定下三条原则：

1. **取全但不进上下文**（落盘/翻页/索引）优于"截断后放进上下文"；
2. **先定位、后加载**：用确定性/统计/语义信号把候选缩到预算内，再读原文；
3. **预算轴永远兜底**：定位失败（没命中/没结构/没索引）时必须退回到截断/摘要/丢弃，并**显式标注失真**。

### 7.1 三轴模型：取全 / 定位 / 预算

```
             ┌─ A 取全（保证"拿得到全部"，但不全进上下文）───────────────┐
             │   ① 翻页：file_read(offset, max_chars) 顺序读全            │
             │   ② 句柄化：大结果落盘 → 引用行 → file_read 回读           │
             │   （longdoc：索引 units.path + offset/bytes 按块读）        │
             └────────────────────────────┬─────────────────────────────┘
                                          ▼
             ┌─ B 定位（把"该看的那段"缩进预算；先验由强到弱）────────────┐
             │   ③ grep / 正则 —— 我知道要找的**字面**                     │
             │   ④ 结构化提取 —— 我知道**结构/键路径**（md/xml/json/yaml） │
             │   ⑤ BM25 词法检索 —— 问题词与正文**词面重叠**               │
             │   ⑥ 向量检索 —— **语义相近**但词面不同                      │
             │   ⑦ 采样跳读 —— 没有先验，用**空间分布**赌覆盖率（前/中/后） │
             └────────────────────────────┬─────────────────────────────┘
                                          ▼
             ┌─ C 预算（B 不可用/没命中时的兜底）────────────────────────┐
             │   截断（头部/N tok）、摘要（占位/LLM/evidence）、凭据行、  │
             │   丢弃、上下文隔离（subagent）                             │
             └──────────────────────────────────────────────────────────┘
```

**轴 A 与轴 B 的区别**：A 管"能不能拿到全部"，B 管"这一轮只拿哪一段"。A 无失真但占轮数；
B 省 token 但**每种 B 都带一个先验假设**——先验错了就漏。轴 C 是"先验全错/全无"时的止损。

### 7.2 七法逐项分析（① ② 属取全轴，③~⑦ 属定位轴）

| # | 方法 | 它假设你知道什么 | 失真 / 风险 | 仓库现状（2026-10-27） |
|---|---|---|---|---|
| ① | **翻页 + max_chars** | 知道"读到哪里了"，且答案可按顺序扫到 | 无内容失真，但**轮数×上下文**双增；模型可能不翻 | **已具备（S1）**：`file_read` 支持 `offset`（字节起点，自动对齐 UTF-8 边界）+ `max_chars`（默认 4000 / 上限 8000），返回 `next_offset`（非空即后面还有）；旧调用零回归 |
| ② | **全文落盘 + 引用行 + 回读** | 存在可回读的文件/读取工具 | 零失真，代价是"两跳"（先拿引用再读）；落盘失败要显式降级 | **已具备（S3）**：`run_tools` 执行时**自动句柄化**（`@config.tool_result_artifact` 开启；缺省落 `<workspace>/.wfr/artifacts/tool`），inline 换成"头部 + 路径 + 规模"，`message.artifact` 同步；配合 `file_read` 回读。历史处理侧另有 `ArtifactToolResults` / `clip_mode=artifact` 兜底（`problems/19`） |
| ③ | **grep / 正则**（确定性定位） | 知道目标**字面**（或可构造正则） | 词面不匹配 → **全漏**（同义、变形、分块边界）；不能把"没命中"当"不存在" | **已有（S2）**：`file_grep`（只读）沙箱内递归按行正则，返回 `{path,line,text}`，`max_matches`/单行截断兜底；二进制与超大文件跳过并计数；只描述里明确"没命中 ≠ 不存在" |
| ④ | **结构化提取**（md/xml/json/yaml） | 知道**文档模式与键路径** | 解析失败/嵌套猜错；格式一变就退化 | **已有（S4）**：`file_extract` 支持 JSON Pointer/点路径、YAML 点键路径、Markdown 标题（含中文章节）、XML 元素路径；解析失败 fail-closed，找不到 selector 返回目录提示 |
| ⑤ | **BM25 式词法检索** | 问题词与正文**词面重叠** | 中文分词是上限；longdoc 的键级 IDF **无 TF、无文档长度归一**，不是严格 BM25 | **部分**：longdoc 关键词臂（`keys` 倒排 + IDF 加权 + 归一，`problems/57`）；只作用于 longdoc 索引，不是任意文件 |
| ⑥ | **向量检索** | **语义相近**、词面可不同 | 不可解释；**依赖摘要质量**（blurb 差则向量差）；长文本表示被截断 | **有**：longdoc 向量臂（blurb 嵌入 + 余弦 × `vector_weight=0.5` 混合，`problems/59`）；真机验证骨架质量前提成立（`problems/60`） |
| ⑦ | **采样跳读**（前/中/后） | **没有先验**，赌答案分布 | 覆盖率**不可证**：可能恰好跳过答案，且模型不知道跳过了什么；不适用于"有没有/全不全"类问题 | **已有（S5）**：`file_sample` 返回 head/middle/tail 三段（UTF-8 安全、带 offset），并在 `note` 里明确"不保证覆盖全文"；小文件整份返回。longdoc 的每单元 blurb 是"分层采样"，两者互补 |

**跨轴兜底（已有）**：`TruncateToolResults`（字节 / token 预算、UTF-8 安全、标注截断量）、
`ArtifactToolResults`（落盘）、历史规则 `clip_tool_results`/`clip_ai_text`（`tool_budget`/`ai_budget`，
`truncate`/`artifact` 两模式）、摘要风格三档（concise/detailed/evidence，基线 full，`problems/16`）、
`drop_round` vs `keep_evidence`（保凭据，`problems/14`）、subagent 上下文隔离（`problems/09`）。

### 7.3 路由：按"问题形态"选方法（先验从强到弱）

| 问题形态 | 首选 | 兜底 | 为什么 |
|---|---|---|---|
| "我知道要找的词/串"（错误码、人名、配置键） | ③ grep/正则 | ② 落盘 + 人工/模型细读 | 确定性最高，一轮出结果 |
| "我知道文档结构"（第几章、JSON 路径、YAML 键） | ④ 结构化提取 | ③ grep → ⑤ BM25 | 不猜内容，只走路径 |
| "我知道主题词，但表述不确定" | ⑤ BM25 | ⑥ 向量 | 词面重叠概率高 |
| "只有语义描述"（"讲的是谁和谁的恩怨"） | ⑥ 向量 | ⑤ BM25 → ⑦ 采样 | 词面可能完全不重合 |
| "要全局观/主题/风格"（"这本小说讲了什么"） | ⑦ 采样 + 摘要（或 longdoc blurb） | ⑤/⑥ 检索代表段 | 不需要精确命中，要覆盖 |
| "按顺序读完全文"（审阅/校对/逐条核对） | ① 翻页 | ② 落盘 + 分页读 | 顺序性无法替代 |
| "没有任何先验" | ⑦ 采样 → ② 落盘细读 | ① 翻页 | 先便宜地看轮廓，再决定 |

**混合不是把七个工具都塞给模型**：工具描述本身占 prompt（问题 [01](01-大批量工具查找.md) 的
"工具太多"同源），而且模型面对七个选择容易挑错。正确姿势是 **harness 侧路由/编排**：
按上表选 1~2 个，把结果统一成"片段 + 出处"格式；③ 没命中时自动升级到 ⑤/⑥，最后用采样兜底。

### 7.4 与 longdoc 的关系：同一套七法，两个"时相"

**longdoc 不是七法之外的第八种，而是把七法在"建索引时"一次性用掉**：

| 七法 | longdoc 中的对应物 | 差异 |
|---|---|---|
| ① 翻页 | 索引 v2 的 `units[].offset/bytes`，retrieve 只读 `[offset, offset+bytes)` | 不是给模型的翻页工具，而是**按块深读**的内部机制 |
| ② 落盘 + 回读 | `longdoc.index.json` + `root` 原文目录 + 路径引用 | 索引本身就是"指针缓存"；原文不搬运 |
| ③ grep | `keys` 倒排（模型抽取的专名/主题，双向子串匹配） | 是**预抽取的键**，不是任意正则；模型没抽出的键就查不到 |
| ④ 结构化提取 | `unit_of=chapter`（标题行切块）+ `title` | 只覆盖中文小说式标题；无 json/yaml/xml |
| ⑤ BM25 | 关键词臂：`keys` 倒排 + IDF 加权 + 归一 | 键级、无 TF/长度归一；中文分词=整段一 token + 子串兜底 |
| ⑥ 向量 | blurb 嵌入 + 余弦，与关键词按权重混合 | 依赖 blurb 质量（`problems/60` 已验证） |
| ⑦ 采样 | **每单元一条 blurb**（分层采样） | 覆盖可证；但没有"前/中/后跳读"这种无先验采样 |

**两种时相**：

- **预索引（longdoc）**：语料固定、问题多样 → 建索引一次，查询时只读命中块。实测（`problems/57`）：
  蜀山 42 块 / 497KB，三问共读 **68,792 字节 = 全量的 13.83%**（≈13.8k token，对比全量 ≈99k token）；
  单问平均约 4.6%——**"少读也能答对"已被证明**。
- **在线（工具返回）**：语料一次性、无索引 → 只能现取现定位，七法按 7.3 路由。

**缺的那块拼图**：两者之间没有统一抽象。现状是 longdoc 有自己的节点与索引格式，工具返回有自己的
截断/落盘，**"一份任意大文档（文件/URL/工具结果）"没有共同的句柄**。补齐后的形态应是：

```
DocumentHandle { id, path|url, size, structure?, index? }
  ├─ page(offset, n)        // ①
  ├─ grep(regex)            // ③
  ├─ extract(json_path|yaml_key|xpath|heading)  // ④
  ├─ bm25(query) / vector(query)  // ⑤⑥（有索引时）
  └─ sample(head|mid|tail)  // ⑦
```

- 在线侧：超过 N token 的工具结果 **自动句柄化**（落盘 + 引用行 + 上述能力）；
- 预索引侧：longdoc 索引就是句柄的**持久化索引**，retrieve 变成 `handle.bm25/vector + page`；
- 预算轴（C）始终外包给 `TruncateToolResults`/历史规则/摘要，句柄只负责"定位与取段"。

### 7.5 评测方案（先分析评估，再落实）

**语料（与 longdoc 共用，保证可比）**：

| 语料 | 形态 | 考什么 | 答案可确定性断言？ |
|---|---|---|---|
| 蜀山 42 块 / 497KB（已有） | 长中文叙事，单文件多章 | ⑤⑥ 语义/词法、④ 章节 | ✅（问题-单元已标注，`problems/57/58`） |
| 长日志（10~50MB） | 纯文本、行结构 | ③ grep、① 翻页 | ✅（构造时埋唯一串） |
| JSON / YAML 配置（KB~MB） | 嵌套键 | ④ 结构化 | ✅（键路径已知） |
| 长网页（fetch 正文） | 异质、噪声多 | ② 落盘 + ③⑤⑥⑦ | ✅（埋入唯一事实） |

**任务四族 × 七法矩阵**（每题标注"答案在原文的哪个字节区间"，这是 Read@budget 的前提）：

1. **定点事实**："X 的值是多少"——答案唯一、字面或键可定位；
2. **跨段关联**："A 和 B 什么关系"——需 2~3 段；
3. **全局概括**："讲了什么/有哪些主题"——无单点答案；
4. **完整性/核对**："一共有几条/有没有提到 Y"——最怕假阴性。

**指标（必须分开统计，否则会误判）**：

| 指标 | 定义 | 为什么重要 |
|---|---|---|
| **Read@budget** | 答案所在片段是否进入上下文（Recall） | 区分"方法不行"与"模型没用好" |
| **Precision** | 进入上下文的 token 中与答案相关的比例 | 省不省 |
| **input tokens / 任务** | 真实 usage | 成本主指标（截断/剥离的 token 也要计，见 `problems/19`） |
| **工具轮数 / 延迟** | 轨迹计数 | 翻页/回读的隐性成本 |
| **成功率** | 确定性断言或 LLM 判分 | 最终目标 |
| **引用正确率** | 回答里的引用是否真含答案 | 防"引用了但没读" |
| **漏读率 vs 利用率** | 答案存在但没取到 / 取到了但没用 | **分开**：前者是方法问题，后者是模型问题 |

**方法**：离线确定性桩（工具调用次数/轨迹可断言，答案位置已知）+ 真机小样本（DeepSeek-flash，
验证"模型会不会用"）；每臂必须断言"路径真的被走到"（否则就是 `problems/03` 的验证陷阱）。

### 7.6 落地顺序（切片，每步带验收，评测贯穿）

| 切片 | 内容 | 状态 |

### 7.6.1 统一评测结果（2026-10-27 · `examples/file_retrieval_eval`，离线确定性）

语料：log.txt（4000 行）· report.md（40 节）· config.json（200 项填充）· app.yaml（1500 项填充）·
feed.xml（20 条目）· novel.txt（60 章）。每题预置答案位置；hit = 答案进入返回文本（Read@budget 的确定性版）；
calls = 工具轮数；B = 返回字节数。

| 任务（问题形态） | grep | extract | sample | paging | 混合路由 |
|---|---|---|---|---|---|
| T1 日志错误码（已知字面） | **✓ 1 轮/62B** | — | ✗ 1200B | ✓ 29 轮/232KB | grep ✓ |
| T2 JSON 端口（已知结构） | ✓ 1/12B | **✓ 1/4B** | ✗ 1199B | ✓ 1/8KB | extract ✓ |
| T3 YAML 端口（已知结构） | ✓ 1/71B | **✓ 1/3B** | ✓ 1200B | ✓ 1/8KB | extract ✓ |
| T4 XML 标题（已知结构） | ✓ 1/89B | **✓ 1/24B** | ✗ 1198B | ✓ 1/1617B | extract ✓ |
| T5 报告章节（已知标题） | ✓ 1/59B | **✓ 1/1049B** | ✗ 1197B | ✓ 5/39.5KB | extract ✓ |
| T6 小说章节（中文标题） | ✓ 1/45B | **✓ 1/1823B** | ✗ 1196B | ✓ 3/24KB | extract ✓ |
| T7 结局（无先验） | — | — | **✓ 1196B** | ✓ 14/106.5KB | sample ✓ |
| T8 最后一行（完整性） | — | — | ✓ 1200B | **✓ 45/355.6KB** | paging ✓ |

**方法汇总**（仅适用任务）：grep 6/6 命中 · 平均 1.0 轮 / **56B**；extract 5/5 · 1.0 / **581B**；
sample 3/8 · 1.0 / 1198B；paging 8/8 · **12.4 轮 / 96.9KB**；混合路由 8/8。

**五条结论**：

1. **已知字面 → grep**：56B vs 翻页 96.9KB，约 1700×；这是"确定性定位"的真实价值。
2. **已知结构 → extract**：1 轮、几百字节，且**不要求答案字面出现在命中行**（T2 4B vs grep 12B）；
   结构类问题应优先于 grep。
3. **采样只中 3/8**：命中的都是"答案恰在首/尾窗口"（T3/T7/T8）；中段答案（T1/T4/T5/T6）全漏
   ——采样能改变"看没看到"，**不能证明"有没有"**，必须带不可证声明。
4. **翻页 8/8 全覆盖**，但平均 12.4 轮 / 96.9KB，T8 达 45 轮 / 355KB——它买的是**完整性与顺序性**，
   不是便宜。
5. **混合路由 8/8**：按问题形态选 1 法，代价就是所选方法的代价；没有"全便宜"的单一选择。

**本台边界**：① 只测"答案是否进入返回文本"，不测模型利用率/最终正确率（需真机判分，§7.5）；
② ⑤ BM25 / ⑥ 向量不在本台重跑——longdoc 验收已给实测（蜀山三问读入 **13.83%**，problems/57·59·60），
本台语料刻意保留为"结构/字面可确定性判定"的任务。

### 7.6.2 S6 运行时路由（`file_context` 节点）

评测台证明了"什么形态该用哪法"；S6 把这张表变成运行时决策：

| 件 | 实现 |
|---|---|
| **节点** | `file_context`（`NodeKind::FileContext`）：读最后一条 Human → 选法 → 执行只读工具 → 片段写 `state[system_context]`（model 自动带上）→ 证据写 `results.<id>` |
| **判定** | 结构（JSON Pointer / 点路径 / 中文章节 / Section N）→ `file_extract`；引号字面或代码 token（`0x9F3A`、`code=…`）→ `file_grep`；全局词（总结/讲了什么/结局）→ `file_sample`；完整性词但无字面 → 不预取（交模型规划，采样不能作兜底） |
| **升级阶梯** | extract 未命中 → grep（选择器原文）→ sample；grep 未命中 → sample；每步写 attempt（tool/detail/hit/bytes） |
| **预算** | `budget_chars`（默认 2000）+ `max_files`（默认 5）；超预算截断并标 `…[路由预算已满]` + `budget_hit=true` |
| **配置** | `@config.file_route = {enabled, budget_chars?, max_files?}` 或 wfr 平铺 `--set file_route=on`；**默认关 → 零回归** |
| **接线** | `share/wfr/workflows/chat.json` / `chat2.json`：`recall → files(file_context) → think(带工具) → route → act → final(无工具)`——与真机评测的 **hybrid 预算版**同构：**≤1 轮工具 + 强制收口**；每个用户提问路由一次。默认 `file_route` 关（`--set file_route=on` 开预取）；多轮工具探索交给 `lot` 等专用 workflow |
| **测试** | `tests/wf/file_context_test.cpp` 8 例：默认关、字面→grep、指针→extract、miss 升级链、全局→sample、引号字面、预算截断、无信号 noop |

**顺带修的真 bug**：`file_grep` 原先会递归进 `.wfr/`（会话日志里正存着用户提问）——
路由一搜就把"自己的问题"当成命中。现在 `.wfr` / `.git` 默认不进搜索面（`GrepSkipsRuntimeDirs` 锁定）。

**真机评测（2026-10-27 · `examples/file_route_live`，DeepSeek-flash）**

7 题：6 题有路由信号（JSON 指针 / YAML 键路径 / 代码字面 / 章节 / 引号字面 / 结尾采样）+
1 题**路由盲区**（"app.yaml 里 host 的值是什么"——没有结构/字面/全局信号，`file_context` 不预取，
只能靠工具兜底）。三臂：

| 臂 | 做法 | 正确 | 模型工具调用 | 总 token |
|---|---|---|---|---|
| **route** | `file_context` 预取 → model 单次作答（不给工具） | **6/6**（盲区题按设计失败） | **0** | **2,223** |
| **hybrid·预算版** | 预取 → 带工具答一次（≤1 轮）→ **强制收口**（无工具再答一次） | **7/7** | **1**（只在盲区题） | 14,639 |
| **base** | 只给工具、循环自己决定（max 4） | 6/7 | 16 | 39,331 |

**hybrid·预算版的结构**（不变式，不靠提示词自觉）：

```
recall → files(file_context) → first(model, tools) 
   ├─ 文本 → _turn_end
   └─ tool_calls → act(run_tools) → final(model, 无工具) → _turn_end
```

没有 loop：**至多一轮工具**，工具用完必有一次"最终作答"机会——所以不会出现 base 那种
"调 4 轮工具后空答"。

- **盲区题被兜底救回**：route 无素材 → "没找到"；hybrid 调 1 次 `file_extract` → 收口答
  `localhost`；base 也能答（1 轮）。这正是"兜底但不失控"要的行为；
- **成本**：hybrid ≈ route 的 6.6×（工具 schema + 两次模型调用），但只有 base 的 37%；
- **base 仍然会空答**（本题集里"引号字面"再次 4 轮后返回空）——自由越多，越需要"何时停"的纪律；
- 结论：**默认 route（预取单次）**；需要兜底时用 **hybrid 预算版（结构限轮 + 强制收口）**；
  base 只适合作对照，不适合作默认。

**模板落地 smoke（2026-10-27，chat / chat2 已改为预算版结构）**：

| 场景 | 模板 | 期望路径 | 实测 |
|---|---|---|---|
| 有路由信号（YAML 键路径） | chat | 预取 → 直接答（0 工具） | ✓ `443`，0 次工具 |
| 路由盲区（host 的值） | chat | 0 素材 → 模型调 1 次 `file_grep` → final 收口 | ✓ `localhost`，1 次工具 |
| 有路由信号（JSON 指针） | chat2 | 预取 → 直接答 | ✓ `8443`，0 次工具 |

**两个真机才发现、都已修的问题**：

1. **利用率失败**：route 臂 YAML 题素材里明明有 `443`，模型却说"未给出具体值"——因为片段只有裸值。
   注入格式改成「**提取结果：**\n443」后同题 **3/3 命中**；
2. **工具诱惑**：hybrid 最初是"提示词约束"（素材有答案就别调工具），但模型仍会反复调（引号题 4 轮空答）。
   最终改成**结构约束**（≤1 轮工具 + 强制收口）：hybrid 从 5/6 升到 **7/7**、工具调用 10→1、
   token 32.7k→14.6k——**提示词管不住的，用图结构管**。

**验收方法**：每个切片先跑 §7.5 的离线矩阵（同任务集、同指标），S6 再上真机小样本；
只有 Read@budget 与成功率同时达标才算"方法成立"，否则回到路由表调整。

### 7.7 风险与陷阱

1. **工具太多**：七个工具的描述本身占 prompt，且模型选择困难（[01](01-大批量工具查找.md)）——
   按会话开关/路由，不默认全开；
2. **grep 全漏**：词面不匹配时"没命中 ≠ 不存在"，必须有升级路径（⑤/⑥/⑦），且回答里如实说"没搜到；
3. **采样不可证**：不能用于"有没有/全不全"类问题，否则会产出自信的假阴性；
4. **向量依赖摘要质量**：blurb 差则向量差（`problems/60` 的前提），别把向量当兜底真相；
5. **截断/摘要是失真操作**：必须标注"原文多少、保留多少、怎么拿全文"，否则模型会不知道自己缺什么；
6. **评测陷阱**：模型没调用工具 ≠ 方法无效；必须看工具轨迹与真实 usage（[03](03-工具副作用.md)、
   [19](19-历史处理补测与统计口径修复.md) 的教训同源）。
