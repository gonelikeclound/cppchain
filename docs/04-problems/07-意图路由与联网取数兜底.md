# 07 · 意图路由与联网取数兜底保证

> 新增问题域（M7 收口后）。核心命题：**"要不要联网、且联网真的发生"不能靠模型自觉**——
> harness 必须一分为二地兜住：(a) **意图判定**（什么时候该外源取数）与 (b) **取数保证**（判定后必然真取）。
> 数据来自 `examples/research_chat`（真机：DeepSeek 对话 + feedcoop web_search + 天气实时源）。

---

## 1. 问题场景与产生原因

单 Agent **连续聊天**里，模型面对"资料查询类"问题有两种偷懒方式：

1. **凭记忆/过时印象作答** —— 不调用任何工具，直接给"自信的错误答案"；
2. **假装联网** —— 声称"据最新消息"，实际没有取数的动作。

这是模型幻觉的高发区，且**不会报错**——跟 [[06-状态时效性]] 一样属于"安静地错"。

拆解后是两个独立的子问题：

| # | 子问题 | 病症 | 后果 |
|---|--------|------|------|
| 1 | **意图判定**：这条消息到底是需要外源资料的 research，还是能凭常识/记忆答的 casual？ | 该联网的问题走了 no-tool 路径 | 错答（用旧印象） |
| 2 | **取数保证**：判定为 research 后，模型"要调工具" ≠ "真的取到了数" | 模型调了工具但失败、或干脆不调 | 错答（编造） |

只解决子问题 1 不够：模型可能在 research 轮"自觉"调了工具但端点失败、或直接跳过取数凭记忆作答。
只解决子问题 2 也不够：每个问题都强制联网，闲聊轮被白白拖慢烧钱。

**根因**：把"取数"这个**正确性保证**委托给了模型的自觉——agentic loop 本身没有"必须成功取数"的约束。

## 2. 常见解决思路

| 思路 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **提示词约定** | system prompt 写"资料问题必须调用搜索" | 零框架成本 | 不可靠（模型常无视；尤其当它自认记得答案时） |
| **每轮全挂工具 + 模型自选** | 不给意图判定，所有轮次都挂全部工具 | 结构简单 | 闲聊轮也被拖入工具决策；模型仍可能不调 |
| **意图路由 + 按意图授工具集** | 路由节点把消息分两类，casual 轮**不挂任何工具**、research 轮挂全部外源工具 | 意图判定独立；闲聊零工具开销；工具集按需收窄 | 路由本身有误判代价；仍不能保证"模型真的取数" |
| **`tool_choice` 强制** | research 轮强制模型必须调用某工具 | 保证有调用动作 | 只约束"调了"，约束不了"调成功了"；且"必须调"会让模型在结果失败时也硬答 |
| **harness 兜底**（本 demo） | 轮后判定"本轮是否有成功的外源取数"，无 → harness 直接执行 web_search，再让模型仅凭检索结果重答 | **构造性保证取数发生**，不依赖模型自觉 | 多一次额外取数成本；兜底又是要"通用检索"这一种口径 |

**关键认识**：`tool_choice` 和"挂工具"都只能提高"调用概率"，**兜底是唯一能给出"取数发生"硬保证的手段**；
而它要与意图路由配合，否则只会无差别地在每个轮次多烧一次检索。

## 3. langchain / langgraph 的对应做法

- **意图判定**：LangGraph 常见"router node"（分类节点）决定后续走哪个子图——本项目把这一点做成
  **结构化输出路由**（`StructuredOutput`，见 [05-structured-output 架构设计](../02-arch-design/05-structured-output架构设计.md)），
  分类本身不进会话记忆。
- **工具集按意图授**：复用同一 `ToolRegistry`，casual 与 research 各持一份（前者为空、后者为全部外部数据源）。
- **取数保证**：**官方没有内置**——agent 循环中模型"调了工具又失败"或"根本没调"时，LangChain 默认就让它
  凭上下文接着答。这与「工具检索」「状态时效性」一样，属于**应用层空白带**，本 demo 是补这个洞的最小样板。

## 4. 本项目选型与理由

三层，对应 `01-discuss/04-架构模式清单.md` 的 **Router + Skill**：

1. **意图只分两类（casual / research）**，不做按工具的分类——否则以后每加一个工具就要加一个意图标签。
   分类依据是"是否需要**外部最新/精确资料**"，天气、新闻、数据、事实核实归 research；闲聊、记忆问答、常识归 casual。
2. **research 轮挂"全部外部数据源"工具集**（现在 = `web_search` + `get_weather` + `arxiv_search` + `fetch_url`）。加新工具直接
   `reg_research.add(...)`，路由器与后续判定**都不用改**。
3. **harness 兜底（本 demo 的看点）**：research 轮完成后，遍历注册表**整表**，判定本轮新增切片里
   是否有**成功执行**过的任意外源工具：
   - 有 → 放行（模型自发）；
   - 无 → harness 直接执行 `web_search`（通用检索兜底），同 thread 续跑，让模型**仅凭检索结果重答**
     （上一条凭记忆的回答留在历史里，被显式纠正）。
   - 判定只看**本轮新增切片**——历史轮的成功取数不算数（防"上一轮的旧天气糊弄本轮新资料"，呼应
     [[06-状态时效性]] 的切片口径）。
   - 注意区分：保证的是"**取数真的发生**"，成功与否单列——若端点不可用（如 401），本轮如实记为
     「未取到有效结果」，不把失败包装成成功。

## 5. Demo 与验证结论（`examples/research_chat`，真机，2026-09-25 双路径）

剧本 6 轮，同一 `thread_id` + `MemoryCheckpointer`（复用 history_agent 的多轮记忆机制）：
闲聊 → 天气(专用实时源) → 联网检索(LLM 进展) → **记忆考核** → 联网核实(珠峰海拔) → 收尾。

### 5.1 主路径：模型自发取数（`run-demo.sh research_chat`，20.8s）

| 轮 | 用户输入 | 意图 | 本轮工具行为 |
|----|----------|------|--------------|
| 1 | 闲聊开场 | casual | ∅（不挂工具） |
| 2 | 上海明天天气 | research | 自发 `get_weather` ×1 |
| 3 | 2025 LLM 进展（联网查） | research | 自发 `web_search` ×2 |
| 4 | 刚才问的是哪个城市天气？ | **casual** | ∅（凭记忆答出"上海"，记忆考核命中） |
| 5 | 珠峰精确海拔（需外部核实） | research | 自发 `web_search` ×1 |
| 6 | 收尾寒暄 | casual | ∅ |

- **harness 兜底 0 次**——模型每轮 research 都自觉联网；意图二分 3/3 全对（记忆考核轮正确不联网）。
- 统计：`get_weather ×1 | web_search ×3`，unretrieved **0**。
- 连续记忆：首轮消息数 `2→4→8→13→15→19`（单调递增，同一 thread 历史累积）。
- 断言：连续记忆递增 ✓ | research 检索保证达成 ✓ → **全部通过，exit 0**。

### 5.2 兜底路径：强制零外源（`RESEARCH_CHAT_FORCE_BACKSTOP=1 ./run-demo.sh -n research_chat`，14.6s）

强制每轮 research **跳过自由尝试**，直接走"零外源 → harness 兜底"分支：

| 轮 | 意图 | 外部取数 |
|----|------|----------|
| 2（天气） | research | ⚠ 零外源 → 兜底 web_search，**成功**，凭检索结果（天气网/中国天气网）重答 |
| 3（LLM 进展） | research | ⚠ 零外源 → 兜底 web_search，**成功**，按结果归纳主线 |
| 5（珠峰海拔） | research | ⚠ 零外源 → 兜底 web_search，**成功**，答出官方 8848.86 米并附来源 |

- `harness 兜底尝试 ×3，全部成功`，unretrieved **0**；记忆仍递增 `2→4→6→8→10→12`。
- 断言全 ✓ → **全部通过，exit 0**。

### 5.3 两条路径共同验证的主张

1. **检索保证是构造性的**（`unretrieved == 0` 在两条路径都成立）：判定遍历注册表整表，
   不针对某个工具名写死——未来 add 新工具，路由器与兜底判定都不用改。
2. **意图路由独立于取数保证**：casual 轮零工具零检索开销，research 轮兜底才介入；两侧各自闭环。
3. **记忆考核轮正确归 casual**：轮 4 是"纯记忆问答"，路由没误判成 research（那会白白烧一轮检索）。
4. DeepSeek（企业代理 MITM，需 `~/.geo/corp-ca.pem`）+ feedcoop search 全程正常。

### 5.4 运行注意

- **必须经 `run-demo.sh` 运行**（它 source `~/opt/gcc16/env.sh`）——二进制依赖 libstdc++
  `GLIBCXX_3.4.35`，直接裸跑会 `version 'GLIBCXX_3.4.35' not found`。
- 无 LLM 密钥时 demo 退化为**工具直连自检**（`get_weather`/`web_search` 各打一发即退）；
  隐式可被 `RESEARCH_CHAT_DIRECT=1` 强制。

## 6. 未解 / 下一步

1. **兜底口径只有一种（通用 web_search）**：强制路径下天气这类"专用源"问题也由通用检索兜底作答
   （5.2 轮 2 实测仍答对了，但丢了 `get_weather` 的实时结构化数据）。改进方向：兜底时按"本轮被授予工具集"
   里**优先级最高的可用源**挑，而不是写死 web_search。
2. **意图误判代价不对称**：casual 误判成 research → 白跑一轮检索（浪费）；research 误判成 casual →
   **丧失取数保证**（本轮不经过兜底）。当前靠路由提示词 + 结构化输出降低误判率，没有误判回退——可以把
   casual 轮也加一条"模型若意识到需要外源可自行声明"的逃生口。
3. **兜底重答一次性**：harness 兜底后只让模型重答一次，若重答仍与检索结果矛盾，没有二次纠正。
4. **检索结果质量未量化**：demo 只断言"取数发生"，没评估检索命中质量；与 [[01-大批量工具查找]] 的
   「评测局限」同理，只有人工抽查。
5. **与压缩的交叉**：本 demo 记忆无截断；若叠加 `TrimHistory`，兜底注入的检索结果如何随压缩折叠、
   会不会被清掉，尚未验证（对应 [[04-上下文压缩]] 的交叉矩阵还没覆盖 research 轮）。
## 7. 复跑与端点兼容修复（2026-10-27）

**复跑发现的问题**：意图路由**每轮 HTTP 400** → 全部按 casual 处理 → research 0 轮；
而原断言只看 `unretrieved == 0`，在 research=0 时**空真通过**（典型的"验证陷阱"）。

两个端点兼容坑（DeepSeek thinking 模式 / `deepseek-flash`）：

1. **`response_format=json_object` 要求提示词里出现小写 `json`**——结构化输出的提示词原来只有大写
   "JSON"，端点直接 400：`Prompt must contain the word 'json'`；
2. **thinking 模式不支持强制 `tool_choice`**（`"Thinking mode does not support this tool_choice"`，
   `required` 也不行）——`StructuredOutput` 默认的 ToolCall 策略在该模型上整体失效。

**修复**（`src/model/structured.cpp`）：

- JsonObject 提示词显式带小写 `json`；
- ToolCall 被端点以 400 / `tool_choice` 拒绝时，**自动降级 JsonObject 重试一次**（不占 schema 重试次数）；
- demo 增加防空真断言：`research 真被走到 = n_research > 0 && total_hits > 0`，全 casual 直接判失败。

**复跑结果**（`deepseek-flash` + feedcoop）：

| 路径 | 意图分布 | 成功外源取数 | harness 兜底 | unretrieved | 连续记忆 |
|---|---|---|---|---|---|
| 主路径（模型自发） | casual 3 / research 5 | 11 次 | 0 | 0 | 2→4→8→18→20→25→41→45 |
| `RESEARCH_CHAT_FORCE_BACKSTOP=1` | casual 3 / research 5 | 8 次 | **5 次全成功** | 0 | 2→4→8→13→15→17→26→30 |

两条路径 `exit 0`，且 research 轮与实际取数都非零——本次是**真通过**，不是空转。

## 8. P0 会话单飞锁（2026-10-27）

**问题**（"上一个 query 没完成，下一个就来了"）：wfr 一次调用 = 一个进程同步跑完；
同一 session 再发一条 → 两个进程同时读写
`<ws>/.wfr/sessions/session-<name>.log.jsonl`。`SessionLog` 只有**进程内** mutex，
`seq` 在构造时从旧文件最大值续编——两个进程会拿到同一个起点，产生**重复 seq + 行交织**，
replay 顺序不再确定。（WebUI 侧也没有排队/插话/取消：设计档 UI-07 明确"不做"。）

### 8.1 实现（P0：拒绝 / 等待 / stale 回收）

| 件 | 内容 |
|---|---|
| 锁文件 | `<ws>/.wfr/sessions/session-<name>.lock`，内容 `{pid, run, started_epoch}` |
| 原子获取 | 临时文件写全内容 → `link(tmp, lock)`；`link` 原子且已存在即失败（不会读到半截锁） |
| stale 回收 | 持有者 `kill(pid,0)=ESRCH`（进程已死）或锁内容损坏 → 自动删除并重试（最多 3 次） |
| 释放 | 仅当锁内 `pid == 本进程 pid` 才删除（防误删新持有者）；wfr 用 RAII 覆盖所有 return 路径 |
| 默认策略 | **busy 直接拒绝**（fail-closed，exit 2）：`会话 'x' 正被另一轮查询占用（pid=… run=…）` |
| `--wait` | 轮询等待（200ms × ≤3000 次 = 10 分钟），获锁后照常执行 |
| 作用域 | 按 **session** 隔离：不同 session 互不影响；cron 父进程不持锁（子进程各自获取） |

代码：`include/cppchain/workflow/session_lock.hpp`、`src/workflow/session_lock.cpp`；
wfr 入口在 cron 分支之后、定位 workflow 之前获取（`src/wfr/main.cpp`）。

### 8.2 验证

- 单测 `WfSessionLock` 6 例：二次获取 Busy（带 pid/run）、释放后可再取、死 pid 回收、
  损坏锁回收、不同 session 独立、只删自己 pid 的锁；
- 真机并发：先起一轮 `wfr chat`，等锁文件出现后再起同一 session → 第二个进程
  `exit 2` + 明确的占用提示；
- `--wait`：第二个进程打印"等待中"，第一轮结束后自动获锁并正常完成（exit 0）；
- 第一轮结束后锁文件消失（RAII 释放）；全仓 `ctest` **1017 绿**。

### 8.3 边界与下一步

- **P0 不含"取消当前轮"**：本轮只能等它跑完（或外部 kill）；kill 后残留锁由 stale 回收，
  会话日志保留已完成的节点记录（语义 = "发生过什么"，副作用由 ExecutionGuard 兜底）。
- **P1 需要**：节点边界的取消钩子（graph 目前未接 `CancelToken`）+ `POST /cancel` /
  `<session>.cancel` 标记 + 前端"取消"按钮 + 取消档 `_cancelled` 落账。
- **P2**：排队策略与"插话"（新 query 打断并接续）——语义最复杂，先不做。
- WebUI 目前把 busy 错误原样回显即可（CGI 子进程 stderr），尚未做前端禁用/排队提示。

## 9. P1 取消当前轮（2026-10-27）

**目标**：运行中的 query 可以被取消，且取消是**可查的终态**，而不是硬杀进程。

### 9.1 机制（节点边界取消）

| 件 | 内容 |
|---|---|
| 引擎钩子 | `graph::InvokeOptions::should_stop`（`std::function<bool()>`）：**每个节点执行前**检查；true → 不再跑后续节点，返回 `GraphError::Kind::Cancelled`（已完成节点的 update 保留在 state/snapshot） |
| 工作流层 | `FireOptions::should_stop` 透传；`WorkflowError::Kind::Cancelled` 区分"取消"与"运行错误" |
| 触发源 1 | **SIGINT / SIGTERM**：handler 只做 `atomic<bool>` 置位；wfr 在每个节点边界看到即取消（`Ctrl-C` 不再硬杀） |
| 触发源 2 | **取消标记** `<ws>/.wfr/sessions/session-<name>.cancel`（`{pid, run, requested_epoch}`）：wfr 必须匹配自己的 pid 才认，读到后**消费删除**（不影响下一轮） |
| CLI | `wfr cancel [--workdir DIR] [--session NAME] [--no-wait]`：读锁拿 pid/run → 写标记；默认轮询等锁释放（≤30s） |
| 收尾 | 写会话日志 `__cancelled__`（kind=`cancel`, status=`cancelled`，replay 忽略 error 记录）；锁由 RAII 释放；退出码 **130**（128+SIGINT 惯例） |
| Web | CGI `?action=cancel&ws=&s=` → 写标记并返回 `{ok, cancelled, pid, run}`；前端运行中显示「停止」按钮；`--stream` 通道在取消时发 `{"type":"cancelled"}` 事件 |

### 9.2 验证

- `Graph.should_stop_cancels_at_node_boundary`：钩子第 2 次返回 true → 节点 a 执行、b/c 不执行，返回 `Cancelled`；
- `WfSessionLock.cancel_marker_roundtrip`：标记写/读/清除；
- 真机 CLI：`wfr cancel --session p1test` → 运行中的 wfr 打印"已取消"、**exit 130**、锁文件消失、会话日志末尾有 `__cancelled__` 记录；
- 真机 SIGINT：对 wfr 进程发 `kill -INT` → 同样 exit 130 + 收尾记录；
- CGI：`QUERY_STRING='action=cancel&ws=…&s=…'` → `{"cancelled":true,…}`，对应 wfr 退出 130；无运行中查询时返回 `cancelled:false`；
- 全仓 `ctest` **1019 绿**。

### 9.3 边界

- **只在节点边界生效**：取消请求到达时如果正在跑一次长模型调用/长工具，需要等它返回；不做 token 级中断（那要 transport 层取消 + 节点内检查点）。
- 取消是"停止取值/写状态"，**不回滚已发生的副作用**（仍由 ExecutionGuard/probe 负责）。
- 队列/插话（新 query 打断并接续）仍是 **P2**；当前语义是"取消当前轮，用户再发一条"。

### 9.4 用例清单（哪些是自动化的）

| 层 | 用例 | 类型 |
|---|---|---|
| 引擎钩子 | `Graph.should_stop_cancels_at_node_boundary`（a 执行、b/c 不执行，返回 Cancelled） | gtest |
| 工作流接线 | `WfFireCancel.stops_before_next_node_and_keeps_completed_log`（取消点后无 node_end，日志只含 e1） | gtest |
| 工作流接线 | `WfFireCancel.no_cancel_runs_all_nodes`（钩子恒 false → 三节点全跑） | gtest |

## 10. P2 插话（2026-10-27）：新 query 来了，取消当前轮并接管

**语义**（`--on-busy`，默认 `reject`）：

| 策略 | 行为 |
|---|---|
| `reject` | 直接拒绝（exit 2），提示持有者 pid/run |
| `wait`（`--wait` 别名） | 轮询等锁（≤600s），当前轮结束后自己跑 |
| **`interject`（插话）** | 读锁拿 holder → 写 `<session>.cancel` 定向取消 → 轮询等锁 → **接管会话跑新 query**；完成/取消后锁由 RAII 释放 |

实现要点：
- 插话方写取消标记时**目标 pid = 当前持有者**；持有者只在 `should_stop` 里认"自己的 pid"，所以不会误伤；
- 持有者取消后 exit 130、写 `__cancelled__`、释放锁；插话方随即获锁继续；
- 接管后清理**目标不是本进程**的陈旧取消标记（holder 若在消费前自然结束，标记不该影响下一轮）；
- 新 query 用**自己进程**的 workflow/`--set`（同一 session、不同 workflow 也可）。

**Web 交互**：
- 运行中「发送」按钮保持可用；同一 session 再发送 = 插话（前端 abort 旧流 → 新请求带 `on_busy=interject`）；
- 旧流的 `finally` 用 `streamSeq` 防止清掉新流的忙碌态；「停止」仍是纯取消（不发送新消息）；
- CGI `action=chat` 透传 `on_busy=<reject|wait|interject>`。

**验证**：`WfInterjectE2E.new_query_interjects_and_takes_over`（spawn wfr + `slow_sleep(3s)`）：
第一轮运行中被第二轮 `--on-busy=interject` 插话 → 第一轮 exit **130**、第二轮 exit **0**；
会话日志含 `act`（第一轮慢节点已执行）、`__cancelled__`（取消留痕）、`e`（第二轮 wf_quick 已跑），
不含 `after`（第一轮取消点之后未执行）；锁最终释放。全仓 `ctest` **1027 绿**。

**边界（P2 未覆盖）**：
- **排队**：单进程时代只有拒绝/等待/插话；**会话 C/S 见 §11**（服务端 FIFO 串行处理请求，但没有优先级/公平调度与"第 N 位"提示）；
- 插话是"取消式"的：第一轮已完成的副作用不回滚（ExecutionGuard 负责幂等/防重放）；
- 多客户端同时插话由会话锁串行化，后到者可能再次插话（语义 = 最新者赢），没有公平队列。

## 11. P2b 会话 C/S（FIFO 服务端/客户端，2026-10-28）

把"同 session 的多个 wfr 进程"从**抢锁/取消**升级为**会话内 C/S**：谁先到谁是服务端，
后来者投递 query，服务端串行执行并回传结果。

### 11.1 模型与参数

| 参数 | 语义 |
|---|---|
| `--lock-session` | 启动或连接。**没有活服务端** → 本进程成为服务端（持会话锁 + 建 FIFO）；已有活服务端 → 自动作为客户端投递 |
| `--as-server` | 强制服务端且**常驻**（本轮 query 跑完后继续服务；`--server-idle-timeout N` 空闲 N 秒退出，0=常驻）；已有服务端 → 报错 |
| `--as-client` | 强制客户端（必须有活服务端），只投递、不取锁、不执行 workflow |
| `--post` | 配合客户端：**只投递不等待**（fire-and-forget），立即退出 |
| `--no-session-lock` | 内部：服务端的子进程跳过取锁（锁在服务端手里） |

默认（`--lock-session` 非 `--as-server`）行为：先跑自己的 query，然后处理 500ms 内到达的请求，
空闲后退出并清理 FIFO/登记/锁。

### 11.2 通道与协议

```
FIFO        <ws>/.wfr/sessions/session-<name>.fifo
服务端登记  <ws>/.wfr/sessions/session-<name>.server.json  {pid, workflow, started_epoch}
回包 FIFO   <ws>/.wfr/sessions/session-<name>.<pid>.<seq>.reply（客户端创建）
```

- **请求**（一行 JSON）：`{id, query, reply, stream, sets}`；`reply=""` 即 `--post`；
- **回包**（一行一个 JSON）：`{"type":"out","line":"<子进程 stdout 行>"}` … `{"type":"end","exit":N,"cancelled":bool}`；
- 客户端 `--stream` 时 `line` 是 wfr 的 NDJSON 事件（CGI 原样转发即可），否则是人类可读输出。

### 11.3 执行与取消

- 服务端**为每轮 query spawn 一个普通 wfr 子进程**（`--no-session-lock`），复用现有执行路径
  （历史 replay、工具、审批、终态记录都不变）；服务端把子进程 stdout 逐行 relay 到回包 FIFO；
- **取消传播**：`wfr cancel` 的锁持有者是服务端 → 标记指向服务端 pid；服务端在 relay 轮询里
  看到标记（或 SIGINT/SIGTERM）→ 对子进程发 **SIGTERM** → 子进程按 P1 在节点边界优雅取消
  （exit 130、写 `__cancelled__`）→ 服务端回 `end{exit:130,cancelled:true}`；
- 服务端收到 SIGTERM → 转发子进程 + 清理 FIFO/登记/锁后退出。

### 11.4 Web 接入

CGI `action=chat` 在启动 wfr 前检查 `session_server_alive(ws,s)`：有服务端 → 追加 `--as-client`
（带 `--stream`），事件流由服务端 relay 回来；没有服务端 → 维持原来的"每次一个独立 wfr"。

### 11.5 验证（全自动）

| 用例 | 内容 |
|---|---|
| `WfSessionChannel.paths_and_server_info_roundtrip` | 路径/登记读写清除 |
| `WfSessionChannel.fifo_line_roundtrip` | FIFO 行读写/超时 |
| `WfSessionChannel.server_client_roundtrip_and_post` | 服务端常驻 + 同步客户端（输出 relay）+ `--stream` 事件 + `--post` 不等待 + SIGTERM 清理 |
| `WfCancelViaServerE2E.cancel_targets_server_and_propagates_to_child` | 服务端跑 `slow_sleep(3s)` 子进程，`wfr cancel` 打服务端 → 子进程 exit 130 + `__cancelled__`，服务端继续存活，`after` 未执行 |

全仓 `ctest` **1031 绿**。

### 11.6 边界

- **服务端串行**：请求按到达顺序排队（P2c 起有 `queued{position}` 回执与队列入队），但没有公平调度/优先级；
- **服务端绑定一个 workflow**：客户端请求使用服务端启动时的 workflow（请求里的 `sets` 可覆盖配置）；
- 服务端模式下子进程 stdin `/dev/null`：需要人工审批的流程请用 `--set approve_policy=…`；
- **无持久队列**：请求在 FIFO 内核缓冲/服务端内存里，服务端崩溃即丢；重启后由下一个
  `--lock-session` 进程接手（stale FIFO/登记由 `server_alive` + 覆盖写处理）；
- 回包 FIFO 路径含 pid+seq，客户端退出即删；异常退出可能残留空 `.reply` 文件（可安全忽略）。

## 12. P2c 队列回执 / 请求级 workflow / stop（2026-10-28）

P2b 的服务端是"读一条、跑一条"，客户端在 FIFO 里干等、看不到位置。P2c 把服务端做成
**带内存队列的串行执行器**：

### 12.1 队列与位置回执

- 服务端单独一个**读线程**：从 FIFO 收请求 → 入内存 `deque` → 立即向客户端回
  `{"type":"queued","position":N}`（N = 队内等待序号，不含正在执行的那条）；
- 主线程按 FIFO 串行 `cs_dispatch`（每轮一个子进程）；跑完回 `{"type":"end",exit}`；
- 队列上限 `--server-max-queue N`（默认 32）：满 → 回 `{"type":"error","msg":"queue full"}`；
- 客户端把 `queued` 显示为「排队第 N 位…」；**`--stream` 模式不打印**（避免污染 NDJSON 事件流）；
- 自己命令行带的 query 作为队首（local 任务），因此客户端看到的 position 天然把"服务端自己的
  正在跑的 query"排除在外（语义 = 你前面还有几个在排队）。

### 12.2 请求级 workflow

请求体新增 `workflow` 字段：服务端默认用自己的 workflow，客户端可以指定（如 `wfr wf_slow … --as-client`）；
`sets` 仍逐请求覆盖。于是同一个会话服务端可以交替跑不同 workflow（各自子进程）。

### 12.3 `wfr stop`

```bash
wfr stop --workdir ws --session s
```

有服务端 → `SIGTERM` 服务端（它会转发子进程、清理 FIFO/登记/锁）；没有服务端但有进行中的
普通查询 → `SIGTERM` 锁持有者（P1 节点边界优雅取消）。最多等 10s，打印是否完全退出。

### 12.4 验证

- `WfSessionChannel.queue_position_and_per_request_workflow`（≈3.5s）：
  - 服务端 `--as-server`（wf_quick，无自身 query）；
  - 客户端 A 指定 `wf_slow` 发慢请求（3s），等服务端进入 `act`；
  - 客户端 B 发快请求 → 输出含「排队第 1 位」+ 慢请求完成后拿到 `hello from child`；
  - `wfr stop` 停服务端，FIFO/登记/锁全部清理；
- `server_client_roundtrip_and_post` 的收尾也改为 `wfr stop` 并断言「已停止」；
- 全仓 `ctest` **1032 绿**。

### 12.5 边界

- 队列是**内存态**：服务端崩溃即丢；没有持久 spool；
- 仅 FIFO 先到先服务，无优先级/公平调度；position 只表示"队内等待序号"；
- 服务端仍**串行**（一次只跑一个子进程）；并行需要多 worker（未做）；
- 请求级 workflow 是本地信任面（客户端可指定任意可查找 workflow）。

### 12.6 `cancel --request <id>`（2026-10-28）

- 客户端可用 `--request-id ID` 指定请求标识（缺省 `<pid>-0`）；
- `wfr cancel --request ID` 通过服务端 FIFO 发控制消息 `{"type":"cancel","request":ID}`：
  - **排队中**：服务端直接从队列摘除，向该请求回包 FIFO 写
    `{"type":"end","exit":130,"cancelled":true}` → 客户端立即退出 130（不会被执行）；
  - **执行中**：服务端置 `cancel_current`，relay 轮询里对子进程 SIGTERM → 子进程按 P1
    节点边界取消（130 + `__cancelled__`）→ 回包 end；
  - 未找到：静默忽略（可能已完成）。
- 用例：`WfSessionChannel.cancel_queued_request_by_id`（排队中被摘除、慢请求不受影响）、
  `cancel_running_request_by_id`（执行中被 SIGTERM、日志有 `__cancelled__`）。

## 13. 人工审批通道 `--approve`（2026-10-28）

服务端模式下子进程 stdin 是 `/dev/null`，原有的人审悬挂无法交互。按三层优先级解决：

| 优先级 | 来源 | 说明 |
|---|---|---|
| **1** | `--approve <unix socket>` | 显式通道：子进程在审批点连接 socket，发 `{"kind":"approve_request","node","payload"}`，等一行 `{"action":"approve|reject|abort","feedback"}` |
| **2** | 客户端 | 服务端未指定 `--approve` 时，自己建内部 socket 并把请求转给**发起该 query 的客户端**（回包 FIFO 事件 `{"type":"approve","request","node","payload"}`）；客户端读 stdin 决定，通过 FIFO 控制消息 `approve_response` 回传 |
| **3** | stdin | 客户端不可交互（`--stream`/EOF）或 120s 无应答 → 服务端回退自己的 stdin；EOF → **reject**（fail-closed） |

实现要点：

- 子进程 `--approve` 连接失败 → 回退自己的 stdin（非 C/S 场景行为不变）；
- 服务端 `--approve` 直接透传给子进程（外部审批人自己 listen）；否则服务端建
  `<session>.approve.sock` 做中转（accept → 转发客户端 → 等 `approve_response` → 写回子进程）；
- 审批通道失败/超时/坏值一律 fail-closed（reject/abort）；
- `approve_tools` 与 `plan_review` 两类悬挂都走同一通道（plan_review 动作映射为
  continue / rollback_to / abort）。

**验证**（`WfApproveChannel` 4 例）：

| 用例 | 断言 |
|---|---|
| `approve_over_socket_executes_tool` | mock approver 收到 `approve_request`，批准后只读工具执行成功 |
| `reject_over_socket_blocks_tool` | 拒绝后工具 message=error（不执行） |
| `server_passes_approve_channel_to_child` | 服务端 `--approve` 透传子进程，客户端请求同样被批准执行 |
| `client_unavailable_falls_back_to_server_stdin` | `--stream` 客户端自动回退；服务端 stdin EOF → reject（工具 error） |

全仓 `ctest` **1038 绿**。

**边界**：Web 前端尚无审批 UI（`--stream` 客户端自动走回退）；审批通道是 UNIX socket
（本机/同命名空间），跨机器需自行转发；客户端交互审批只支持终端 stdin。

## 15. Web 审批 UI（2026-10-28）

后端协议（§13）不变，把"客户端"换成浏览器：

```
server 审批中转 ──approve 事件──▶ 客户端 wfr --stream ──stdout──▶ CGI ──NDJSON──▶ 浏览器
       ▲                                                                          │
       └──────── approve_response（server FIFO）◀── CGI action=approve ◀── 按钮 ──┘
```

### 15.1 链路

1. **客户端（--stream）**：收到 `{"type":"approve", request, node, payload}` 时**原样转发**
   到 stdout（不再自动 fallback），继续等 `end`；
2. **CGI**：`chat` 透传事件；新增 `?action=approve&ws=&s=&request=&decision=&feedback=`
   → 校验决定 ∈ approve/reject/abort/fallback → 写服务端 FIFO
   `{"type":"approve_response","request","action","feedback"}`（要求该会话有活服务端）；
3. **前端**：`renderStreamEvent` 识别 `approve` → `renderApproval()` 渲染节点/calls 与
   「批准 / 拒绝 / 中止」按钮；点击调 `raw("approve", …)`，按钮随即禁用并提示"审批已提交"；
4. **服务端**：审批中转线程收到 `approve_response` → 唤醒 → 把决定写回子进程；
   120s 无应答或客户端不可用 → 回退服务端 stdin（§13 三层优先级）。

### 15.2 验证

| 用例 | 断言 |
|---|---|
| `WfApproveChannel.web_stream_forwards_event_and_approve_decision` | `--stream` 客户端输出含 `{"type":"approve",…}` 并等待；外部发 approve → 工具执行成功 |
| `WfApproveChannel.web_stream_fallback_goes_to_server_stdin` | 外部发 fallback → 服务端 stdin（测试为 `/dev/null`）→ reject，工具 error |
| `WfSessionChannel.cgi_approve_action_forwards_control` | CGI `action=approve` 返回 `{"ok":true}`；无服务端 → 明确报错 |

### 15.3 使用前提与边界

- 审批 UI 只在**该会话有常驻服务端**时出现（CGI 才会以 `--as-client --stream` 连服务端）；
  没有服务端的普通 wfr 仍走 stdin，Web 看不到 approve 事件。
- 浏览器交互路径未做自动化（无 headless 浏览器）；已覆盖到"事件转发 + 控制消息回传"。
- 页面刷新/断线后旧按钮失效（request 已结束或 120s 超时回退），服务端对未知 request 静默忽略。
- 审批决定文本（reject 理由）UI 暂未提供输入框，固定为空（协议已支持 feedback）。

## 16. 上一轮未完成：内置到 env 层（2026-10-28）

**原则**：query 保持原样（不改写、不加前缀）；"上一轮被打断"是**会话状态**，放进 context 节点的
`【当前环境】` 块，模型结合历史自行判断新消息是追问 / 新话题 / 纠正。

### 16.1 实现

| 件 | 内容 |
|---|---|
| 日志判定 | `session_last_run_cancelled(ws, session)`：取日志**最后一条记录所属 run**，看该 run 是否出现过 `__cancelled__` 节点记录（P1 优雅取消的终态） |
| context 节点 | `【当前环境】` 默认键由 `{now, host}` 扩为 `{now, host, prev_round}`；`prev_round` **无需模板配置**：按 `@config.workspace/session` 自动判定，命中则值为 `未完成（被新消息打断）`，否则跳过 |
| chat / chat2 | 各加一个 `context` 节点（`recall → env → files → think`）；系统提示词补一句：出现 `prev_round: 未完成` 时，先判断新消息关系，不要假设上一轮结论成立 |
| system_context | `context` 与 `file_context` 改为**追加**已有片段（原先整键覆盖，env 会被 files 覆盖） |
| file_context | 检测到上一轮未完成 → **跳过预取**（最后一条 Human 可能是"那明天呢"这类碎片，硬查无意义），交给模型带工具处理 |

### 16.2 验证

| 用例 | 断言 |
|---|---|
| `WfSessionState.last_run_cancelled_detects_tail_terminal` | 空日志 false；正常结束 false；`__cancelled__` 结尾 true |
| `context_env_injects_prev_round_builtin` | 取消后新轮 env 含 `prev_round: 未完成（被新消息打断）` |
| `context_env_omits_prev_round_when_normal` | 正常日志不出现该键 |
| `file_context_skips_prefetch_after_interrupted_round` | 上一轮取消 → `results.files.action=skipped`、无预取片段 |
| `file_context_runs_normally_without_interruption` | 正常轮仍照常预取（action=route） |

全仓 `ctest` **1045 绿**；真机 chat smoke 通过（9 节点，`443` 正常）。

### 16.3 边界

- 只识别**优雅取消**（有 `__cancelled__` 记录）；`kill -9`/崩溃无终态 → 识别不到；
- env 是**每轮快照**，不跨轮累积；首轮无日志 → 无该键；
- 带 `prev_round` 时一律跳过预取（不区分追问/无关）——基线选择，宁可让模型多查一次；
- **不做三分类**：追问/无关/矛盾交给模型按照 env 信号 + 历史自行判断；若真机证明判断不稳，
  再考虑加轻量关系路由（不改变 env 语义）；
- 审批悬挂期间的 interject 打断：**已在 §18 补齐**（取消感知的审批等待）。

## 17. E2E 用例补全（2026-10-28）

补齐之前评估出的两个 E2E 缺口（真实进程、无 LLM）：

| 用例 | 拓扑 | 断言 |
|---|---|---|
| `WfInterjectE2E.next_round_env_sees_prev_round` | wfr A（`slow_sleep 3s`）+ wfr B `--on-busy=interject`，B 的 workflow 为 `recall → context` | A 被取消（130）；B 的 env 节点 exit update 里 `system_context` 含 `prev_round: 未完成（被新消息打断）` |
| `WfSessionChannel.idle_timeout_exits_and_cleans` | server `--as-server --server-idle-timeout 1` | ≤2s 自动退出、FIFO/登记/锁清理、exit 0 |
| `WfSessionChannel.stale_server_registration_is_taken_over` | 预置死 pid 的 `server.json` + 残留 FIFO → 启动新 server | `server_alive=false`；新 server 覆盖登记；客户端正常往返 |
| `WfSessionChannel.queue_positions_increment_and_full_errors` | server `--server-max-queue 2` + 慢请求 + 两个排队客户端 + 第三个 | 两个排队者分别收到「排队第 1/2 位」；第三个收到 `queue full` 并 exit 1 |

**顺带修的一个真 bug（E2E 抓出来的）**：host 若在写本轮 `__input__` **之后**再扫日志，
"最后一条 run"就是本轮自己 → `prev_round` 永远为 false。现在：
- wfr 在**写 `__input__` 之前**算好 `@config.prev_round`；
- `context` / `file_context` 优先读 `@config.prev_round`，没有宿主时才回退到扫日志
  （单测/嵌入式场景）。

全仓 `ctest` **1049 绿**（约 39s；E2E 用例含真实 3s 慢节点）。

## 18. 剩余 E2E 补全：SIGINT / 审批等待取消 / 交互审批（2026-10-28）

（浏览器端按用户要求不做。）

### 18.1 审批等待可取消（实现）

之前审批悬挂时 SIGTERM 打不断等待：`--approve` 通道的读是阻塞 poll、stdin 的 `getline` 也不看取消标志。
现在：

- `ask_approval_channel` 改为 **200ms 轮询**读，每轮检查 `g_cancel_requested`；命中即返回 nullopt，
  调用方转 `handle_cancelled()`（exit 130 + `__cancelled__`）；
- 新增 `read_stdin_line_cancellable()`：`poll(STDIN, 200ms)` + 逐字符读，取消时返回 `Cancelled`；
  审批两类分支（approve_tools / plan_review）都改用它；
- 服务端审批中转在 `stop_reader`（服务端退出）时**不再回退 stdin、不再写已关闭的子进程 socket**。

**顺带修的一个真 bug**：向已关闭的子进程 socket 写审批决定会触发 **SIGPIPE** 杀掉服务端（exit 141），
且清理不执行 → `wfr stop` 白等 10s。现在 wfr 启动即 `SIGPIPE=SIG_IGN`，写失败按 EPIPE 处理。

### 18.2 新增 E2E 用例（4 例）

| 用例 | 拓扑 | 断言 |
|---|---|---|
| `WfCancelE2E.sigint_cancels_running_query` | 运行中的 `wfr`（slow_sleep 3s）+ `kill -INT` | exit 130、`__cancelled__`、锁释放 |
| `WfApproveChannel.cancel_during_approval_wait` | 子进程卡在 `--approve`（mock 只收不答）+ SIGTERM | ≤1s 取消（exit 130 + `__cancelled__`，工具未执行） |
| `WfApproveChannel.server_cancel_during_approval_wait` | server + `--stream` 客户端进入审批等待 → `wfr cancel` | 客户端 130、服务端存活、可正常 stop（修复前要 11s，现 ~1.3s） |
| `WfApproveChannel.client_interactive_approval_via_stdin` | server + 非 stream 客户端，stdin 预写 `approve\n`（pipe） | 客户端读 stdin → approve_response → 工具执行成功 |

全仓 `ctest` **1053 绿**（约 45s，含多个真实 3s 慢节点）。
