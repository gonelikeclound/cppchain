# 04 · 上下文压缩（Context Compression）

> 对应路线图 M7 卡位问题。数据来自 `examples/context_budget`（实验 B）与 `examples/agent_loop` 第④段。

---

## 1. 问题场景与产生原因

对话历史在每一轮都要**整体重发**给模型，于是：

- 成本随轮数**线性增长**（实测下表的"不压缩"列）；
- 长工具输出会把这个斜率放大（见 `02-超长工具返回`：16KB ≈ 3.2k token/轮）；
- 最终撞上上下文窗口上限，**硬失败**（不是变慢，是报错）。

实测（`context_budget` 实验 B，8 轮短对话，真实 usage 的 input_tokens）：

| 轮次 | 不压缩 | 压缩后（TrimHistory 阈值 6） |
|---|---|---|
| 1 | 38 | 35 |
| 4 | 107 | 110 |
| 6 | 153 | 113 |
| 8 | **199** | **113** |

压缩触发 5 次后，prompt 稳定在 ~113 token，**线性增长被压成有界**。

## 2. 常见解决思路

| 思路 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **窗口截断** | 只保留最近 N 条 | 零成本 | 早期信息直接丢失 |
| **摘要压缩** | 把旧消息压成摘要 | 保留语义要点 | 多一次调用；有损；摘要本身也占 token |
| **关键信息外置** | 把事实写进长期记忆（Store），历史只留索引 | 可跨会话复用 | 需要"写什么"的判断（hot path vs background） |
| **同 id 改写** | 用 reducer 覆盖式改写历史里的某条消息 | 不改变消息数，语义可控 | 需要消息 id 与 reducer 支持 |
| **上下文隔离** | 子代理/subagent 在独立上下文里干活，只回传结论 | 主上下文最干净 | 需要多智能体编排（M8） |
| **分线程** | 按主题/任务开新 thread | 天然隔离 | 会话连续性变差 |

## 3. langchain / langgraph 的对应做法

- 提供 `trim_messages` / `filter_messages` / `merge_message_runs` 三个消息级工具（本项目 M1 时把它们列为"M7 占位"，**尚未落地**）。
- `add_messages` reducer 支持**按 id 覆盖**——压缩中间件改写历史的标准手法（我们 M5 已实现）。
- Harness 层（Deep Agents）把"自动上下文压缩 + 虚拟文件系统 + subagents"作为卖点：**压缩与上下文隔离是同一个问题的两种解法**。

## 4. 本项目选型与理由

`TrimHistory`（中间件，`before_model` 钩子）：

- **阈值触发**（消息数超过 `max_messages` 才动手）——避免每次都压；
- **保留系统提示 + 最近 N 条**，中间段折叠；
- **可插拔摘要器**：不给摘要器 → 丢弃 + 占位说明（零成本）；给摘要器 → 调模型生成摘要（真压缩）；
- 依赖 M5 的 `add_messages`/`StateSchema`，压缩后的历史仍可正常归约与快照。

## 5. Demo 与验证结论

- **单测**（离线）：超阈值触发压缩、请求里出现 `[历史摘要]`、自定义摘要器生效 ✓。
- **真机**（`agent_loop` 第④段）：8 条"请记住我喜欢简洁的回答" → 压缩触发 1 次，
  摘要为"用户偏好简洁的回答。"，**压缩后模型仍然记得该偏好**（最终回答确认）✓ —— 说明有损压缩保住了要点。

### ⚠️ 数据必须诚实说明的两点

1. 上表**只统计主循环的 prompt token，未计入摘要调用的开销**（每次压缩多一次模型调用）。
   压缩是否"划算"取决于：被折叠的历史有多长、摘要调用有多贵。短对话下可能不划算。
2. 演示一开始"压缩触发 0 次"——因为我喂的消息数没超过阈值（5 ≤ 6）。
   与 `03-工具副作用` 的陷阱同源：**必须确认被测路径真的被走到**。

### 5.4 压缩 × 时效（交叉验证，`examples/stale_state` C 段）

单独看两个机制都"验证过"了，但**机制之间的相互作用**才是最容易出事的地方。本段做 3+1 路对照
（预置一段含"1 小时前的余额结果"的历史，TTL=3s，触发压缩后再问余额）：

| 策略 | 工具调用 | 观察 |
|---|---|---|
| Fold + 占位摘要 | 1 次 | 摘要把旧值**删掉**了 → 模型只能重查 |
| Fold + LLM 摘要 | 1 次 | 同上（本次摘要未保住旧值） |
| **Preserve** | **0 次** | 守卫成功标注"已过期" → 模型**向用户报告过期**而非重取 |
| **Drop** | 1 次 | 整组丢弃 + 明示"请重新查询" → **结构上迫使重取** ✓ |

**机制层面的结论（与模型随机性无关）**：
- **Fold 会丢掉时效元数据** → `StaleStateGuard` 再也看不到它（信息损失不可逆）；
- **Preserve 保住元数据** → 守卫能标注过期，但「标注」≠「模型必定重取」——需要更强策略（见 06 §6）；
- **Drop 结构性迫使重取**（值没了 + 明确指示），代价是彻底丢失历史值。

⚠️ **本次未复现「用旧值作答」**：模型较自觉 + system prompt 明确要求用最新结果。
风险并非不存在，只是需要更弱的前提（弱模型 / 不强调时效的提示词 / 摘要里旧值显得权威）；
且**每次运行模型行为不同**（同一策略在不同运行里 0 次/1 次都出现过）——评估时效类机制不能只看单次结果。

### 5.5 顺带修掉的真 bug：折叠边界会切断工具调用组

`TrimHistory` 原本把 `[keep_from, drop_count)` 整段折掉，**边界可能落在 AI(tool_calls) 与其
ToolMessage 之间** → 保留区出现**孤儿 ToolMessage** → 真实端点直接 400
（这类问题离线测试发现不了：`validate_sequence` 是我们的自检，而假 transport 不校验协议）。

→ 新增 `TrimHistory::safe_boundary()`：边界左移到"不撕裂工具调用组"的安全点；
配套 2 项测试断言折叠后 `validate_sequence` 仍通过、且保留区不以 ToolMessage 开头。

## 6. 未解 / 下一步

1. **触发策略**：现在按消息条数；应改为按 token 估算 / 上下文占用率（M9）。
2. **成本量化**：摘要调用的 token 与延迟没测（本表未含）。
3. **信息损失评估**：压缩后任务成功率是否下降，需要任务级评测集（M9）。
4. `trim_messages`/`filter_messages`/`merge_message_runs` 三个消息级工具未实现（M1 时列为此处占位）。
5. **子代理式上下文隔离**（M8）——与压缩互补的解法，尚未实现。

## 追加（wfr-㉙）：压缩的**历史形态**维度

上面几节压缩的是"条数/token"，问的是"压多少"；wfr-㉙ 补的是另一个轴：**压成什么形状**。
同一个 token 预算下，历史形态不同，模型的自我一致性完全不同。

| 形态 | 做什么 | 效果 |
|---|---|---|
| `full` | 不压 | 基线 |
| `drop_round` | 工具轮整组删（连 assistant 的 tool_calls 一起） | 省得最多，但**模型可能判定自己的历史答案"无凭据"**并重查/加免责声明 |
| `keep_evidence` | 只删 reasoning + 改写超预算的工具返回为"凭据行" | 保住"我确实查过"的最小凭据；实测模型会**读凭据行并据此作答** |

结论：**压缩不该只按体积算，还要保住"结论的凭据"**。把工具结果整条删掉省下的 token，
往往会以"重查一次"或"加一句不可靠声明"的形式还回去。实测数字、探针脚本与反例见
[14-wfr-chat2思考历史对比落地与验收记录](14-wfr-chat2思考历史对比落地与验收记录.md)，
实现见 [02-arch-design/15](../02-arch-design/15-思考模型推理回传与历史压缩策略设计.md)。

## 追加（wfr-㊵）：从"渲染期变换"到"可持久化的派生视图"

上面几节与本篇末尾那节讲的是**压缩多少 / 压成什么形状**，都是渲染期变换（不落盘，
每次触发重算）。wfr-㊵ 补上另一半：把摘要与规则化的精简/裁剪做成**写进会话日志的 op** ——
于是重跑不必重算（真机实测第二次触发 `skipped`、零摘要调用）、replay 与运行期一致、
调试台能看到 op 原文。三方向的完整对照见
[16-历史消息处理专题](16-历史消息处理专题.md)，机制见
[02-arch-design/17](../02-arch-design/17-历史消息处理机制设计.md)。
