## 1. 落地了什么

| 分层 | 交付 |
|---|---|
| **state** | `Packet{node, optional<Json> state}`；`StateSnapshot::next` 与 `put()` 签名升为包队列；落盘 v1→v2，**load 兼容旧字符串数组**（旧快照直接读，不迁移不丢弃） |
| **graph** | invoke 重写为**四态包队列**（普通单路径 = 全局状态包特例，行为逐位等价）；Streaming（`InvokeOptions.sink/mode` + `NodeContext.emit`）、Interrupt（`interrupt()` + resume + 2 新错误档）、Send（`Command.sends` + 独立包 + reducer 归约） |
| **workflow** | `FireOptions.stream` 把图事件通道注入 `fire_once`；`LoggingStateGraph` wrapper 在 stream 模式下**让位**（双源互斥）+ 正确重抛 `InterruptSignal`（不误记 error）；`project_stream_to_log` 投影适配器；`session_log.engine_interrupt`（replay 铁律不变） |
| **demo** | `m10_streaming` / `m10_interrupt` / `m10_send`（纯离线，链接 `cppchain_graph`） |

## 2. 关键决策（与文档 13 对应）

1. **单执行通道**：不加第二个 `stream()` 执行路径；事件、恢复、中断、扇出都走在
   `invoke` 的同一个包队列里（`CompiledGraph::stream()` 只是便捷收集）。
2. **包队列追加而非替换**：M6 的 `current = *next` 会让 Send 的第二个包被丢弃 ——
   修复为**追加到队尾**（super-step 语义）。这是本次引擎改造**唯一的语义变化**，
   且只影响「一次路由产出多个目标」的场景（普通图无差异）。
3. **Interrupt 异常驱动**：`InterruptSignal` 不继承 `std::exception`（防节点泛捕获误吞）；
   重跑包**保留原包局部输入视图**（一度漏掉，被 `Send.resume_after_partial_super_step`
   抓出修复：`key 'item' not found`）。
4. **幂等契约明确化**：interrupt 之前的副作用必然重复（测试断言 before×2 / after×1），
   不是引擎提供幂等，是节点约定 —— 与 LangGraph 语义一致，写进 docs/13 §5 + demo 输出。
5. **workflow 双源互斥**：默认 wrapper 写结构日志；`FireOptions.stream` 非空时 wrapper 让位、
   由宿主用 `project_stream_to_log` 从事件通道落地 —— 防止同一节点被记两遍（测试锁住）。

## 3. 度量与验收

**graph 层（`tests/graph/`，+21）**
- Streaming：边界事件序列 + seq 单调、Snapshot 开关、delta 转发（Deltas 收 / Updates 不收）、
  零 sink 与旧 invoke 行为等价、异常吐 `node_end{ok:false}`。
- Interrupt：悬挂返回完整 state + writes 落 payload、resume 重跑返回注入值 + **副作用计数
  before×2/after×1**、无 resume 保持挂、已跑完带 resume → `ResumeNotInterrupted`、
  无 cp → `InterruptUnavailable`、`catch(std::exception)` 拦不到 InterruptSignal、
  新 FileCheckpointer 实例跨进程重建 `last_interrupt()`。
- Send：fan-out + reducer 归约（顺序确定性 a→b）、局部输入视图（worker 看不到全局键）、
  send 目标未知报错、goto 优先于 sends、send 覆盖静态边、多级扇出（2 mgr × 2 worker = 4 包）、
  checkpoint 的 `next` 以包形式承载、super-step 内第二个包悬挂 → 恢复后**剩余包先跑、中断节点重跑**
  （顺序 `w:a → w:c → w:b`）。

**workflow 层（`tests/wf/m10_runtime_test.cpp`，+4）**
- `fire_once` 全模式收集（每节点 node_start/node_end/values = 3 事件）；stream 模式 wrapper
  让位（日志无节点结构事件、input 事件仍在）；`project_stream_to_log` 信封映射（enter/exit/error/
  interrupt 与 seq 单调）；interrupt 记录不参与 replay（replay 铁律只读 exit+ok）。

**全仓**：411/411 全绿（386 既有 + 25 新增）、零编译告警。

**demo ×3（离线，`./run-demo.sh -n m10_streaming|m10_interrupt|m10_send`）**
- `m10_streaming`：14 个事件的时间线，delta 的 seq 与引擎事件单调相接（修的 seq 分配 bug）。
- `m10_interrupt`：第 1 次触发悬挂（before=1/after=0）→（模拟外部审批）→ 第 2 次 resume
  重跑（before=2/after=1，decision 写入、approved/shipped=true）。
- `m10_send`：3 个 worker 顺序执行（4 步含 orchestrator），results 归约完整。

## 4. 明确的边界与后续留意

- **时间旅行 / fork 押后**：存储（全链快照 + list + 按 id get_tuple + parent 链）已就绪，
  缺「从任意 checkpoint 重建并 invoke」的图层入口。
- **真并行押后**：包与队列结构已按可并行设计；线程池 + Send 的 barrier（worker 归拢到
  汇聚节点）一并设计时再补 —— 本轮 worker 无出边自然收，归约在共享 state 上累积。
- **`c_model` 流式留开放**：默认仍走阻塞 `invoke`；模型层 `stream` 与 delta 事件通道已就绪，
  切流 = 改 `node_types.cpp` 一处 + 需要可流式测试模型基建。
- **Send × workflow IR 未接**：每包独立局部输入对 IR 的 `$_`/`@config` 是新的解析面，单独评估。
- **resume 单活跃中断**：index = 悬挂节点名；并行多中断按 index 分发押后。
- **max_steps 语义**：改为按包计数（一个 super-step 的 N 个包耗 N 步）；对既有线性/条件图无差异。

## 5. 学到的一手东西（避免再踩）

- **`current = *next` 是"整条替换"不是"追加"** —— 这台引擎从未真正支持多目标执行；
  Send 翻开这个死角时，第一个版本把第二个 worker 包丢了（results 只有 1 条）。
  教训：加"多实例同一队列"语义时，先确认既有实现是替换还是追加。
- **悬挂重跑包必须背原包的局部输入**：重跑包重建为 `Packet{node}` 会丢 Send 包的局部 state
  （恢复后 `key 'item' not found`）。重跑不是"再跑一次节点"，是"再跑**这个包**"。
- **nlohmann + C++ 的类型坑在测试里反复出现**：`Json` → `optional<Json>` 的 braced-init 是
  两次用户定义转换（编译失败），需要显式 `std::optional<Json>{...}`；Message → JSON 需 include
  `message/serializer.hpp`（ADL 序列化不自动可见）。这些在写测试时比写实现更容易踩到。
