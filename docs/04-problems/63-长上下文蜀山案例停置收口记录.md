## 一、案例回顾（要点）

用《蜀山剑侠传》（还珠楼主，公有领域；中文维基文库 309 回全可取、源码 11.8MB）验证
「分块 → 局部理解 → 跨块实体对齐 → 归约」的超长文本理解管线：

- 工具：`tools/fetch_shushan.py`（仓库内、不进编译）。**双视图落盘**：`raw/` 带回目标题头
  （人读/对账）、`blocks/` 纯正文 + 中性命名（喂模型，**零先验纪律**：提示词不含书名/回数/
  人物/作者任何与被处理内容相关的信息）。
- 子集验收（2026-10-17）**走通**：3 回 11664 字 → 3 块 → C2 双链局部 6 步 + 全局归约，
  6+1 JSON 全落盘、0 fail-closed、10 名跨片段人物归并；同日挖出 3 个真问题并修复 2 个
  （`file_read` 字符/字节语义 bug、LLM 长生成超时 `LLM_TIMEOUT_MS`）。完整原文见 git `7c00431`。

## 三、停置决定（本次计入文档的结论）

1. **蜀山真机对照两批停置、不续跑**：语料与两批残留原样保留（不清理）。随 2026-10-25 longdoc
   移交（蜀山降格为测试物），两批对照不再续跑；管线走通性此前已由 3 回子集验收证明，跨片段/
   关系质量由 longdoc 主线继续承接。
2. **梗概方案拍板不做**：曾设想把蜀山缩成 1/10~1/20 概要再分析——讨论后放弃。估算 30 回
   ≈40~50 万 token、全量≈500 万 token，**卡点不是 token 量**，而是**要保人物名录就得在梗概里
   内嵌名册，等于丢细节**；权衡后否决，**勿再提**。
3. **机制移交 longdoc、蜀山降格为测试物**：2026-10-25 起主线转向与语料无关的通用 longdoc
   机制（problems/57→58/59/60/61 持续演进），蜀山 42 块仅作验证数据。**停置的是「蜀山长上下文
   对照 + 梗概」这条线，不是 longdoc 机制本身。**

## 四、遗留与重启入口

若长上下文按原样重启，从以下条目续（**梗概方案勿再提**）：

1. `text.hpp::utf8_truncate` 仍为**字节计数**（2026-10-31 实核，`include/cppchain/tool/text.hpp`
   `utf8_truncate`，fetch_url/arxiv 的使用者）——与 file_read 的**码点计数**不一致，**两实现待统一**。
2. C1（单链）vs C2（双链）、rolling vs tree 归约对照——需更多块（10~30 回量级）才有统计意义。
3. 残留批次 `tmp/cmp`、`tmp/cmp2`：或清理、或各自 `run_all.sh` 续跑。
4. 全量 309 回：按原设计交给长程任务（wfr cron + task 档案）分批、批间状态保留——未启动。
