# 01 · 大批量工具查找（Tool Retrieval）

> `04-problems/` 首篇。对应路线图 M3 的卡位问题。
> 结论基于 `examples/tools_retrieval` 的**实测数据**（可复现：`./build/dev/examples/tools_retrieval`）。

---

## 1. 问题场景与产生原因

工具调用要把工具的 **JSON Schema** 放进请求（`tools` 字段）。工具少时没问题；一旦工具库变大：

| 症状 | 原因 |
|---|---|
| **请求体/费用线性膨胀** | 每个工具的 name + description + parameters 都要进 prompt，N 个工具就是 N 份 |
| **模型选错工具 / 幻觉工具名** | 候选项越多，区分度越低；相近工具（`get_weather` vs `get_weather_forecast`）互相干扰 |
| **上下文被挤占** | 工具 schema 与对话历史、系统提示争抢同一个上下文窗口 |

实测（工具名+描述+参数，混合中英文，按 3.5 字节/token 估算）：

| 工具数 N | 全量 schema | 估算 token |
|---|---|---|
| 10 | 3.0 KB | ~875 |
| 100 | 30 KB | ~8,775 |
| **1000** | **308 KB** | **~88,000** |
| 5000 | 1.5 MB | ~441,000 |

> N=1000 时，光工具定义就吃掉 **~88k token** —— 这已经超过多数模型的上下文预算。

## 2. 常见解决思路（横向对比）

| 思路 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **全量注入** | 所有 schema 直接进 prompt | 零实现成本、召回 100% | 规模一大就不可用（上表） |
| **关键词检索** | 用 query 对 name/description 打分，取 top-k | 零依赖、可解释、快、无需外部服务 | 同义改写/跨语言/纯语义相似会漏召回 |
| **向量检索（embedding）** | 工具描述预先 embed，query embed 后取近邻 | 语义泛化强、跨语言好 | 需 embedding 端点/模型、需维护索引、可解释性差 |
| **分层/命名空间** | 工具分组（域），先让模型选域再取该域工具 | 结构清晰、可解释 | 需要人工维护分类；域多时退化为同样问题 |
| **tool_search 元工具** | 把"搜索工具"本身做成工具，模型运行时按需检索 | 完全按需、上下文占用最小 | 多一轮往返；模型需学会用检索 |
| **MCP / 动态工具** | 工具由外部服务按需提供 | 解耦、生态化 | 引入协议与部署复杂度 |

**关键认识**：这些不是互斥的。工程上常见组合是 **分层（粗筛）→ 关键词/向量（细筛）→ top-k 注入**，必要时叠加 `tool_search`。

## 3. langchain / langgraph 的对应做法

- langchain 本身**没有内置工具检索**：`bind_tools(tools)` 默认就是全量注入。
- 其生态做法是让用户自行在 `bind_tools` 之前过滤工具列表（检索属**应用层**职责）。
- 官方在 **Harness 层（Deep Agents）**才提供更激进的方案：subagents（把工具集拆给子代理）+ 预置工具集，本质上是用**上下文隔离**替代检索。
- 换言之：**"工具检索"在 langchain 里是空白带**——我们要自己设计的部分。

## 4. 本项目选型与理由

**可插拔 `ToolSelector` 接口**，三种实现：

```
ToolSelector（接口）
├─ AllToolsSelector     全量：小集合基线（也是"不检索"的对照组）
├─ KeywordSelector      关键词 + IDF 加权（默认，零依赖）
└─ EmbeddingSelector    预留（待 embedding 端点接入）
```

**为什么关键词起步**：符合"从底向上、先跑通再演进"；零依赖（无需 embedding 服务）；**可解释**（能回答"为什么选中这个工具"）；并且它是后续向量检索的**对照组基线**——没有基线就无法证明向量检索真的更好。

**关键词评分的三条规则**（`KeywordSelector`）：
1. **可检索文本 = 工具名 + 描述 + 参数名 + 参数描述**（工具语义大量藏在参数里）
2. **CJK 用 2-gram**（单字切分噪声太大："天气"必须是一个 token，而不是"天"+"气"）
3. **IDF 加权**：token 权重 `log(1 + N/df)`

## 5. Demo 设计与验证结论

### 5.1 体积（`examples/tools_retrieval` A 段）

查询 `"weather 天气"`，检索 top-8：

| N | 全量 | top-8 检索 | 节省 |
|---|---|---|---|
| 10 | 3.0 KB | 305 B | 10x |
| 100 | 30 KB | 2.4 KB | 12x |
| **1000** | **308 KB** | **2.5 KB** | **125x** |
| 5000 | 1.5 MB | 2.5 KB | 626x |

**检索耗时**：N=1000 时 ~16 ms/次（单线程朴素实现，可接受）；N=5000 ~83 ms（该优化了，见 §6）。

### 5.2 质量（B 段）—— 只看压缩比会骗人

> ⚠️ 实验过程中我们**先踩了这个坑**：初版检索对中文查询全军覆没（返回 0 个工具），
> 于是"压缩比 1444x"看起来极漂亮——**它其实是把正确答案排除了**。
> 教训：检索必须同时报 **precision / recall**，压缩比单独看毫无意义。

修复两处后（参数描述纳入检索 + CJK 2-gram），再叠加 IDF：

| 查询 | 无 IDF | 有 IDF |
|---|---|---|
| "查询天气 weather" | 1.00 / 1.00 | 1.00 / 1.00 |
| "发送邮件 email" | 1.00 / 1.00 | 1.00 / 1.00 |
| **"get stock price"** | **0.38 / 0.38** | **1.00 / 1.00** |
| "删除文件 file" | 1.00 / 1.00 | 1.00 / 1.00 |
| "translate text" | 1.00 / 1.00 | 1.00 / 1.00 |

（precision@8 / recall@8，N=1000）

**IDF 的作用**：`"get"` 在 1/6 的工具名里出现（高频 → 低权重），`"stock"` 只在 1/10 里出现（稀有 → 高权重）。
无 IDF 时 50 个 `get_*` 工具靠 "get" 挤掉真正相关的 `stock_*`。

### 5.3 已知短板（尚未解决，留给后续实验）

| 短板 | 例子 | 需要什么 |
|---|---|---|
| **同义改写** | 查询"查天气" ↔ 工具描述"weather" | embedding 或同义词表 |
| **跨语言** | 查询中文 ↔ 工具全英文 | embedding（多语言模型） |
| **纯语义相似** | "帮我看看明天要不要带伞" ↔ `get_weather` | embedding |
| **模型选错工具**（未测） | 检索对了但模型仍选错 | 需端到端评测（M7 agent 循环后） |

## 6. 后续优化方向

1. **EmbeddingSelector**：接入 embedding 端点（DeepSeek 无 embedding API，需换 provider 或本地模型）→ 与关键词做**对照实验**（这正是本项目的实验方法）。
2. **性能**：当前 `select()` 是 O(N) 全表扫描 + 每次重建 df；N≥5000 时可预建倒排索引或缓存 df。
3. **`tool_search` 元工具**：让模型在运行时自行检索（对超大工具库更友好）——与"检索后注入"做 A/B 对比。
4. **分层命名空间**：域 → 工具的粗筛，可与关键词检索叠加。
5. **注入策略**：top-k 的 k 如何定？固定 k vs 分数阈值 vs 按 token 预算裁剪（与"上下文压缩"问题域交界）。
