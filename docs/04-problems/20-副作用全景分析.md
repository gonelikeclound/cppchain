# 20 · 副作用全景分析（wfr 审批专题 · 开篇）

> **这份是什么**：工具副作用域在**当前代码库**的完整盘点——能力清单、执行通道差异、
> 遗留开口、与未来专题的血缘。它是「文件工具 + 副作用」专题（wfr 线继承者）的**研究前置**：
> 先看清现状与断层，再设计 wfr 审批怎么挂、`file_write` 怎么进 loop。
> 机制历史见 [03-工具副作用](03-工具副作用.md)；本篇是它的**全景版**，结论以本篇为准。

---

## 一、结论先行

副作用防护在**库的 `Agent` 循环通道**里已是一套完整纵深（审批 + 记忆化 + 防重放 + 持久化 +
只读标记），但**在 wfr 命令行（Workflow 图）通道完全是裸奔**——工具节点 `tn.run(calls)`
直跑，中间件一个都没有。`file_write` 挂不进去，根因就在这里（`src/wfr/main.cpp` 注册处
明确写道：要挂得先接审批）。

## 二、两道执行通道的防护差异

| 环节 | `Agent` 循环通道（库/examples） | `Workflow` 图通道（wfr 命令行） |
|---|---|---|
| 工具执行 | 中间件链：审批 → 防重放 → `node.run` → 后处理 | 工具节点 `tn.run(calls)` **直跑** |
| 审批 | ✅ `ToolApproval`（名单/回调 + `read_only` 免审） | ❌ 无 |
| 审批记忆化 | ✅ M9（`RememberDeny/All/Off` + FIFO + 只读免审） | ❌ 无 |
| 防重放 | ✅ `SideEffectGuard` + Journal 三态 | ❌ 无 |
| 持久化 | ✅ `FileJournal`（原子写 / fail-closed / 键前缀租户隔离） | ❌ 无 |
| 审计 | ❌ 都没有 | ❌ |

## 三、现有能力盘点（assets）

- **只读标记**：`ToolSpec::read_only`（默认 true，写工具显式 false）；`ToolApproval` 配
  registry 后对只读工具**免审**（`approval_memo_test` 覆盖）。
- **审批**：名单拒绝 / 回调按参（`call.args` 已是解析后 JSON，能读路径白名单）；拒绝转
  `status="error"` 的 ToolMessage 回喂，不抛错、不打断循环。
- **记忆化**：fingerprint = `name|canonical_json(args)`；`RememberDeny` 默认只记**拒绝**
  （放行是副作用敞口，每次仍审）——设计本意正确。
- **防重放三态**：未见过→执行；`Completed`→重放记录结果、不动盘；`Intent`→拒绝重跑并回喂
  "结果未知，请人工确认"；`Failed`→默认拒跑、可配重试。只读不记账。
- **持久化**：`FileJournal`，意图在**执行前**落盘（崩溃重启才能认出"执行到一半"）；
  损坏 **fail-closed** 抛异常，不静默降级为不安全；键前缀隔离多租户。
- **HITL 原语**：M10 graph 原生 `interrupt`/`resume`（真暂停，事务语义）+ proactive CLI 的
  `ask_user` 澄清菜单均已存在——"人到场"的原语不缺，缺的是把它接到工具审批上。

## 五、真正的断层（按处置优先级）

1. **wfr loop 审批 + 防重放缺失**（`file_write` 挂不进来的直接原因）——需要把 agent 层的
   `ToolApproval` / 防重放逻辑（或新的轻量中间件）接进 **Workflow 工具执行路径**（`tool_node`）。
2. **审计日志缺失**：现在是"执行日志"（intent/result），没有"谁在何时批准了什么"。
   这是「复杂任务 · 可记录/可回溯/结果可置信」专题的地基——**可置信 = 决策有据可查**。
3. **记忆化不持久**：`ToolApproval.memo` 是内存 FIFO，重启即失，与 `FileJournal` 的持久化
   能力不配套；"这工具这参数会议室已批过"没有落盘，长程任务（数天）会重复打扰。
4. **键策略悬空**：`ToolNameAndArgs` 会误杀合法重复调用，需要 `ToolSpec` 上的**幂等性语义**
   （哪些工具可安全重跑）支撑选键——这同时是「结果不飘移」的前提。
5. **保留策略 / Store 后端**：长程任务（数天/数月/数年）的底座，`FileJournal` 纯追加会膨胀。

## 六、与已立项五个专题的血缘

| 未来专题 | 与副作用域的关系 | 依赖哪块 |
|---|---|---|
| **复杂任务** · 可记录/可回溯/可置信 | 审计日志 = 可置信的另一半；审批决策留痕 = 回溯的依凭 | 断层 2 |
| **长程任务** · 多次分批运行/结果不飘移 | 防重放 + 持久化 + 保留策略正是它的底座；"批"之间不能漂 | 断层 3/4/5 |
| **多 Agent 协调** | 子代理并行写同一文件 = 副作用冲突；审批要能跨代理协商 | 断层 1/2 |
| **Agent 自进化（RSI）** | 审计日志是复盘素材（谁批的、为什么拒、失败在哪） | 断层 2 |
| **长上下文** · 目标不飘移 | 审批决策记忆化跨会话复用，降重复打扰 | 断层 3 |

**所以"文件工具 + 副作用"不是孤立一步——它是专题 2/3/4/5 的共同地基，越早做越值。**

## 七、下一步（本专题）

1. 设计 wfr 工具执行路径接审批：工作是 `ToolNode` → 需要审批钩子与日志钩子（复用或轻量复制
   agent 层的 `ToolApproval` / `SideEffectGuard` 语义；注意 workflow 通道没有 `Middleware` 链，
   是打到 tool 执行点上的）。
2. 把 `ToolApproval` 的记忆化接到 `FileJournal`（持久化记忆，替代内存 FIFO 或作为其背书）。
3. `file_write` 挂进 wfr `chat` 工具集（带审批）、`file_read`/`list_dir` 维持只读免审。
4. 审计留痕（决策 + 结果）作为同一专题的可选件，先做最小版：`{ts, tool, args, decision, who, why}`。
5. 用 problems/03 §5 的教训做真机验证：必须确认**被测路径真的被走到**（拒绝/放行计数 + 磁盘断言），
   避免"模型自己拒绝高危工具 → 中间件没走到却以为跑通"的假象。
