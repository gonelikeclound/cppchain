# 09 · 子代理与副作用隔离（M8 收口）

> M8（Subagent/多智能体）的问题卡收口。三个真机 demo（`examples/subagent_ask_expert`、
> `subagent_workers`、`subagent_handoff`）验证了：**子代理把复杂任务隔离在独立上下文里**，
> 并把副作用审批的边界讲清楚（**审批是纵深，不是旁路**）。本卡顺带落实路线图 A2 的
> **fork 语义对照**，避免"子代理委派"与 checkpoint 时间旅行 fork 在文档里混用。

---

## 1. 问题场景与产生原因

- **主上下文膨胀**：一个 agent 既负责总览又处理所有子任务时，各子任务的工具 schema、中间结果、
  多轮往返全都堆进同一条 prompt。M7 的压缩/截断是"内容仍在对话里"的缓解；**子代理是结构性一档**：
  子任务整体搬进独立上下文，主上下文只收一条 compact 结果。
- **副作用边界模糊**：一旦把执行委派给子代理，"审批由谁负责"变得暧昧——父审批委派，
  子代理内部还动不动自己的工具？处理不好会变成：父只审委派、子代理内部工具随意执行（旁路），
  或父子双重审批冗余。
- **术语污染**：langchain 官方 "fork" 特指 checkpoint 时间旅行分叉；社区口语又常拿它指
  "子代理委派"。两者语义完全不同，搅在一起会让实现讨论失真。

## 2. 常见解决思路（横向对比）

| 思路 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| 单 agent + 中间件压缩 | 压缩/截断高密度信息（M7） | 简单 | 内容仍留在 prompt，只是"少而旧" |
| **subagent-as-tool（ask_expert）** | 子任务 → 独立 agent 循环 → 只回最终答案 | 主上下文干净是**结构性保证**；专家可以各配各的工具/人设 | 多一轮委派往返；成本 = 父+子两段 |
| orchestrator-worker | supervisor 拆任务分派给 worker | 角色职责清晰、可编排 | 需多 agent 管理；Send 并行版更重 |
| handoff | worker 上交控制权给主管 | 灵活、可纠错 | 需吞吐上限防死循环 |

## 3. langchain / langgraph 中的对应做法

- **subgraph-as-tool**：子代理 = 子图，包成工具；调用即子图独立运行，只回最终结果（ask_expert 官方形态）。
- **orchestrator-worker**：官方用 `Send(node, state)` 动态 fan-out；无 Send 的版本就是 supervisor 循环串行委派。
- **handoff**：官方 `Command(goto=..., graph=PARENT)` / `schema` 上交；简化版用 `Command.goto` + 保留工具名。
- **fork ≠ 委派（路线图 A2）**：官方 "fork" = 在某个 checkpoint 上**分叉出替代时间线**（时间旅行）
  ——盘问"假如当时不同做会怎样"；子代理委派是**同一时间线上的并行/分层的执行**。对照表见 §6。

## 4. 本项目选型与理由

三形态全部落在**既有插槽**上（`ToolSpec.handler` / `graph::NodeFn`），核心是两件新增：
`agent::make_subagent_tool`（subagent-as-tool）与 `graph::as_agent_node`（Agent 暴露为图节点）。

| 形态 | 落点 | 关键机制 |
|------|------|---------|
| ask_expert | `make_subagent_tool`：每次调用**现构干净子代理** | 返回 `answer + stats`，子转录不进父 prompt；共享 ChatModel 按实例串行化 |
| orchestrator（串行） | supervisor（M4 结构化输出拆任务）→ 条件 router 点选 worker → finalize | **no-Send**：results 用 push reducer 下标对齐 = 执行序；worker 不回写 messages |
| handoff（简化） | worker 包 `Command{goto:["supervisor"]}` | 触发信号 = 转录里出现了 `call_supervisor`（确定性，不解析措辞）；redispatch 上限兜底 |
| 副作用边界 | 子代理自己的中间件照常审批；父只审委派 | **审批是纵深不是旁路** |

## 5. Demo 验证结论（真机，DeepSeek，2026-09-26）

### 5.1 `subagent_ask_expert`：主上下文干净 + 副作用透传

**场景 ① 委派计算**——父把 `123*4567` 整体交给子代理：

- 父转录只 4 条（[system, human, ai(委派), tool(子代理结果)]）→ 最终答复；
  子代理内部 `tool_turns=1`（calculator 往返）发生在它自己的上下文。
- **token 会计**：父最后一轮 input=**539** tokens；子代理内部 usage `input=566`——
  子代理的工作量**没有**进父的上下文。隔离是结构性的，不是"运气好"。
- 真实细节：模型第一次把参数传错（`{"string": …}`）→ 工具回喂
  `missing required argument: 'query'` → 模型自愈改传 `{"query": …}`。
  —— 顺带验证了 **M7 的 error 回喂纪律在子代理委派场景同样生效**。

**场景 ② 副作用透传**——父让子代理发邮件：

- 子代理内部的 `send_email` 被子代理自己的 `ToolApproval` 拒绝，**denials=1**；
  父转录里看不到"被拒"的回喂（那是子代理的上下文）。
- 结论写进设计（02-arch-design/09 §4.3）：父审批"委派"动作，**不豁免**子代理内部审批。
  若两者都要审（危险工具），是父审委派 + 子代理审细节的**纵深叠加**。

### 5.2 `subagent_workers`：串行 orchestrator（no-Send）

- supervisor（M4 结构化输出）把"星期几 + 12*13"拆成 2 个任务；router 按 `results.size()`
  串行点选 `worker_math` → `worker_news`；各 worker 用 calculator / get_datetime 取真实结果。
- **主线 messages 只有 [用户提问, finalize 汇总]** —— worker 全文（含工具结果）只留在各自的
  transcript 与 `state.results`，主上下文干净在**图层面**就成立。
- results 顺序 = tasks 顺序（下标对齐，串行不重排的前提成立）。

### 5.3 `subagent_handoff`：上交 + 上限兜底

- 数学题：worker 直解（`answered=true`）→ 收尾。
- 天气题：worker_math（数学专家）判领域不符 → **调用 `call_supervisor`** → 包裹层检测到 →
  `[handoff]` 消息进入会话 + `redispatch=1` + `Command{goto:["supervisor"]}` → 主管重新分派 →
  再次上交 → `redispatch=2` 达上限 → finalize 兜底答复（"无法获取实时天气"）。
- 确定性：触发信号是转录里出现 `call_supervisor` 这个**保留工具名**，不解析模型措辞；
  即使粒度改变（这轮没触发上交），`answered` 兜底也会走收尾——演示不会假死。

## 6. fork 语义对照（路线图 A2 落实）

| 维度 | 官方 "fork"（checkpoint 时间旅行） | 我们的 "子代理委派" |
|------|----------------------------------|--------------------|
| 本质 | **同一执行的多条替代时间线**（在某 checkpoint 分叉探索"另一种做法"） | 同一时间线上的**分层委派**（主→子独立执行） |
| 机制 | checkpoint + `Command(resume)` / 分叉记录 | subgraph-as-tool / orchestrator / handoff |
| 关系 | 与 M10 的时间旅行共振 | 与 M8 的 subagent 形态共振 |
| 混用后果 | 把"并行子代理"当成"分叉时间线" → 实现错位 | 把"时间旅行回顾"当委派 → 语义失真 |

**约束**：本项目文档/代码里，"委派"一律说 subagent / 委派 / handoff；"fork" 仅在讲 checkpoint
时间旅行时使用（M10 落地时再展开）。
