# 06 · 状态时效性（Stale State）

> 新增问题域（M7 收口后加入）。核心命题：**某些系统状态必须实时获取，不能凭上下文里的历史结果推断**。
> 数据来自 `examples/stale_state`（真机 A/B 对照）与 `tests/agent/stale_test.cpp`。

---

## 1. 问题场景与产生原因

有些状态天然易变：**余额、库存、价格、任务进度、文件内容、服务健康、当前时间**。
而对话历史里的工具结果是一个**快照**——模型却倾向于把它当现状。

三条失效路径：

| # | 路径 | 说明 |
|---|---|---|
| 1 | **历史结果被当现状用** | 上下文里有"余额 101"，模型直接回答，不再调用工具（实测见 §5） |
| 2 | **压缩把时效抹掉** | 摘要把"余额 101（10:00 观测）"压成"余额 101"，**时间戳丢失** → 更危险，因为失效变得不可见 |
| 3 | **框架缓存/去重引入的陈旧** | 任何结果缓存（包括我们的执行日志）在 TTL 之后都可能返回旧值 |

**危害**：给出**自信的错误答案**（用户无法察觉）；在自动化流程里可能触发基于旧状态的错误动作
（按旧余额下单、按旧库存发货）。这类错误不会报错，只会"安静地错"。

**根因**：模型**不知道自己看到的是什么时候的快照**——上下文里没有时间维度。

### 1.1 什么是「易变信息」（本文的判定口径）

上面用的"易变"不是修辞，本文与相关文档（[04](04-上下文压缩.md) §5.4、`TrimHistory` 的
`VolatilePolicy`）里它是一个有明确定义的工程概念，分三层说清：

**① 语义层——什么叫易变**：取值会随外部世界推进而变化，**同一问题在不同时刻的正确答案不同**，
所以历史里的值是"某时刻的观测快照"，不能当现状。正例：余额、库存、价格、订单/任务状态、
文件内容、服务健康、当前时间、天气。反例（非易变）：百科词条、数学常数、历史事件、
已归档文档——问一百次答案都一样，查一次可以一直用。

**② 工程层——系统怎么认（唯一判据，不靠猜内容）**：在本项目里，「易变信息」**≡ 带时效元数据的
工具结果**，即 `ToolMessage.additional_kwargs` 同时含 `observed_at` 与 `ttl_seconds`
（`freshness::has_metadata`，`include/cppchain/agent/freshness.hpp`）。链路只有一条：

```
工具声明 ToolSpec::ttl（留空 = 不过期）
  → StaleStateGuard::lookup_tool_result 登记 tool_call_id → ttl
  → StaleStateGuard::after_tool 执行后写 observed_at + ttl_seconds 进 additional_kwargs
  → 读者：StaleStateGuard::before_model（标注过期）、TrimHistory（压缩时分流）
```

由此可得三条推论：**没声明 ttl 的工具，结果不算易变信息**；**没挂 `StaleStateGuard` 时没有任何
元数据**，下游按"全是普通消息"处理；**易变与否是工具作者的责任**，框架不根据内容文字推断（模型自己
在文本里写"截至 12:00"不构成元数据，不算）。

**③ 组的口径——压缩时怎么算一组**：`TrimHistory` 以**工具调用组**为单位处置，一组 = 一条
`AI(tool_calls)` + 紧随其后的连续 `ToolMessage`；组内**任一**结果带上述元数据，整组即"易变组"
（同去同留，不拆组——拆开会留下孤儿 `ToolMessage`，真实端点直接 400）。分组与分流逻辑见
`src/agent/agent.cpp`，策略差异与四路实测见 [04](04-上下文压缩.md) §5.4。

**边界**：非工具来源（State/Store 里手写的易变字段）不在覆盖内，见 §6 第 5 条；TTL 取多少由工具
作者按业务拍，见 §6 第 3 条。

## 2. 常见解决思路

| 思路 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **结果自带观测时间** | 工具返回里写"截至 12:00:03，余额=101" | 零框架成本；模型可自行判断 | 依赖模型自觉 |
| **TTL + 框架失效标注** | 结果记录观测时间；超过 TTL 后改写为"已过期，需重新获取" | 框架保证；不依赖模型自觉 | 需工具声明 TTL；需处理"改写 vs 删除" |
| **回答前强制刷新** | 回答涉及易变状态的问题前，强制重取 | 最强保证 | 成本高、打断流程、需要判断"哪些问题涉及易变状态" |
| **易变工具不缓存** | 只读工具每次都真执行，绝不缓存结果 | 简单、消除路径 3 | 解决不了路径 1（模型不调用） |
| **状态外置 + 每轮刷新** | 易变状态放 State/Store，由框架每轮刷新 | 单一事实来源 | 需要框架级支持与状态建模 |
| **提示词约定** | system prompt 里要求"必须重新查询" | 零成本 | 不可靠（实测：无守卫时模型照样用旧值） |

**关键认识**：路径 1 与 2 都源于"**时间信息不在上下文里**"。所以最小可行的解法是
**把时间放回上下文**（观测时间戳）+ **到点替模型判断**（框架失效标注）。

## 3. langchain / langgraph 的对应做法

- `ToolMessage` 有 `additional_kwargs` / `artifact` 可挂任意元数据（本项目 M1 保留了 `additional_kwargs`，
  本次正好用它承载观测时间与 TTL）。
- **官方没有内置 TTL/失效机制**——与「工具检索」一样属于**应用层空白带**。
- 相关但不相同：LangChain 的 `Cache`（请求级缓存，有 TTL）解决的是"同样的请求别重复花钱"，
  不是"上下文里的结果过期了要提示模型"。前者是**成本**问题，后者是**正确性**问题。
- checkpointer 恢复出的状态"是上次运行时的状态"——官方文档也提醒持久化状态需自行判断时效。

## 4. 本项目选型与理由

两层：

1. **工具声明时效**：`ToolSpec::ttl`（`std::optional<std::chrono::seconds>`，留空 = 不过期）。
   这是工具自身的属性（余额 3 秒、库存 30 秒、百科条目永不过期），放在工具声明最自然。
2. **中间件执行策略**：`StaleStateGuard`
   - `after_tool`：把**观测时间戳**（+ TTL）写进 `additional_kwargs` → 随序列化/**快照存活**；
   - `before_model`：扫描过期结果 → **改写成"已过期"警示**（而不是删除）。

**为什么改写而不是删除**：
- M1 的协议不变式要求 `tool_calls` 必须有对应 `ToolMessage`，删掉会破坏闭环；
- 把旧值换成显式警示比留着旧值更安全——模型不会再拿它当现状（同时保留原值供参考）。

**可注入时钟**：测试用假时钟保证确定性（真机用系统时钟）。

## 5. Demo 与验证结论

### 5.1 真机 A/B 对照（`examples/stale_state`，工具 TTL=3s，等待 4s）

```
A 无守卫：第1轮 工具调用 1 次 → 余额 101
          等待 4 秒
          第2轮 工具调用 0 次 → 回答「101 元」        ← 直接用历史值作答（病症复现）

B 有守卫：第1轮 工具调用 1 次 → 余额 102
          等待 4 秒（过期标注生效）
          第2轮 工具调用 1 次 → 回答「103 元」        ← 重新取数，拿到最新值
```

（工具每次返回不同值，因此"有没有重新查"可从答案直接读出。）

### 5.2 离线单测（7 项）

新鲜不改写 / 过期改写含警示语 / 改写成幂等（多次调用不重复包裹）/
**保留 `tool_call_id` 使协议仍闭环** / 无 TTL 工具不受影响 / **时间戳随序列化往返存活** /
端到端确认过期标注真的进入了发给模型的 prompt。

### 5.3 途中发现的真机专属坑

写 demo 时用空对象 `{}` 当无参工具的 `parameters` → 真实端点 400：

```
Invalid schema for function 'get_balance': schema must be a JSON Schema of 'type: "object"', got 'type: null'.
```

**离线测试发现不了**（`FakeTransport` 不校验 schema）。已在 `ToolSpec::to_openai()` 做**归一化**
（补齐 `type`/`properties`，不覆盖用户内容）+ 2 项回归测试。→ 教训：**schema 合法性只有真端点是裁判**。

## 6. 未解 / 下一步

1. ✅ **与压缩的冲突已处理**（`TrimHistory::VolatilePolicy`）：
   - `Fold`（默认）—— 一起折叠，**时效元数据随之丢失**（原行为，最危险）；
   - `Preserve` —— 易变结果的整组保留原文 → 守卫仍能标注过期（实测：模型会向用户报告过期，但**不一定重取**）；
   - `Drop` —— 整组丢弃 + 明示"需要时请重新查询" → **结构上迫使重取**（实测 ✓）。
   详见 `04-problems/04` §5.4（含"本次未复现用旧值作答"的如实说明）。
   **仍未解**：若要求"必须重取"，需要更强策略（如回答前强制刷新），目前只是提示模型。
2. **强制刷新**未做（与第 1 项的遗留同源）：目前是"提示模型重取"，若模型不理会仍会答旧值。
3. **TTL 取值**：现在由工具作者拍（3 秒/30 秒/永不过期）；应按状态变化频率与业务容忍度制定。
4. **时钟偏移**：本地时钟回拨/快照来自其他机器时，`observed_at` 可能不可比（当前实现把负 age 当新鲜）。
5. **非工具来源的状态**：State/Store 里的易变字段同样会陈旧，本中间件不覆盖。
6. **注入攻击面**：攻击者可借"伪造时间戳"诱导模型认为数据新鲜——需要签名或由框架独占写入时间戳（我们已是后者）。
