## 1. 长上下文：目标不飘移，多目标讨论可切换

**动机**：现有压缩（[04-problems/04](../04-problems/04-上下文压缩.md)、wfr 历史处理）解决的是
**体积**——token/条数裁剪、摘要折叠；但"体积压下来"不等于"意图保住"。长会话里模型会
逐渐忘掉最初目标（目标漂移），或同时谈多个问题却在中间窜线（多目标切换）。
压缩为什么造成漂移、多目标讨论怎么可切换，是这一题的落点。

**现有垫底**：
- 历史处理三方向（摘要/精简/裁剪）与 op 语义：`wfr-㊵`（[problems/16](../04-problems/16-历史消息处理专题.md)）
- 真机对照证明「事实」不丢、「凭据」取决于 style：problems/16 §五
- 思考模型的历史形态三档（wfr-㉙，problems/14）

**第一问**：漂移的根源是"摘要把目标陈述折掉了"，还是"目标没有一个独立通道、
和普通聊天混在一条 messages 里"？多目标讨论可切换是否天然需要一个显式的"目标/话题"状态？

## 2. 复杂任务：规划 → 执行，可记录、可回溯、结果可置信

**动机**：单轮 ReAct 对复杂任务爱即兴发挥（走一步看一步）。要的是**计划先行、按计划执行**：
每一步从哪来、依据了什么、结果怎么出来的要可查（**可回溯**）；结论要和证据对上
（**结果可置信**）。这里的"可置信"已有一个真机底座：problems/16 §五的对照证明
差别在**凭据**（工具名/参数/来源）而不在事实——背书能力是要花 token 买的。

**现有垫底**：
- 主动智能 Workflow：`M11`（problems/11、12）+ wfr 命令运行器 / loop 容器 / 调试台
- `summarize` / `refine_history` 节点把"计划"当纯数据产（wfr-㊵）
- 会话日志 JSONL 是**唯一事实来源**，replay 可逐轮复盘（wfr 系列一以贯之）

**第一问**：规划放在**人写的 workflow** 还是**模型自己生成的计划**（然后落到图上）？
可回溯的最小粒度是什么——一步一个工具调用，还是节点级？

> 📎 **已落一个具体专题建档**（2026-10-12）：[07-复杂任务规划执行验证环](07-复杂任务规划执行验证环.md)
> ——把本条的「规划 → 执行」再加**验证**，并补两级能力：**可中断**（步骤边界 interrupt 悬挂）、
> **可撤回/回退**（定点回退到第 K 步 / 整计划丢弃边界）。现有垫底盘点与第一问见 07。

## 3. 长程任务：持续数天/数月/数年的任务

**动机**：跨进程、跨重启、多次分批运行；中途改需求、改参数；结论在时间轴上不能飘
（**结果不飘移**），同时要能感知"现在是哪天"（**可感受时间变化**）。这是 wfr 会话日志
（只增不改）与 interrupt/resume 自然延伸出的问题域。

**现有垫底**：
- Checkpointer（内存五方法接口）+ Store 接口已定死，SQLite 换实现不换接口（discuss/03 B0）
- M10 的 interrupt / Send / **时间旅行 fork**：problems/13
- 会话日志「条目只增不减」——但**保留策略**（长期运行膨胀）正是 problems/03 遗留的未做项

**第一问**：跨重启恢复的最小契约是"replay 日志"，还是需要显式 checkpoint？
「结果不飘移」（同输入、不同天同输出）与「感受时间变化」（如实让模型知道日期变了）
如何同时成立而不打架（锚定一个、另一个就冲突）？

## 4. 多 Agent 任务：多 Agent 协调

**动机**：M8 已有多智能体三形态（subagent-as-tool / orchestrator-worker 串行 /
handoff 简化），但有"分工"不等于有"协调"——任务分派、共享状态、进度同步、
冲突消解（两个子代理写同一处）、结果汇总，这些还没成型。

**现有垫底**：
- M8 多智能体 + fork 语义对照：problems/09
- M10 Send 动态 fan-out、时间旅行（fork 后改挽互不影响）
- 交互的"HITL"原语（提问/澄清/审批）已经在 proactive CLI 里有雏形

**第一问**：协调中心是**长在对话里**（orchestrator 自己读共享状态），还是
**显式 orchestration 协议**（状态/消息在子代理间直接路由）？子代理并行写共享状态需要什么防线？

## 5. Agent 自进化（RSI）

**动机**：让 Agent 从**自身的运行记录**里学习——复盘失败案例、改进提示词、调整工具用法、
甚至生成新 workflow，形成自我改进的闭环。整个 wfr 线都是现成素材：会话日志存了
每轮思考/工具/统计，有调试台、有回放、有"唯一事实来源"纪律。

**现有垫底**：
- wfr 会话日志 JSONL（思考 💭 / 工具 🔧 / stats 全员落盘）
- replay 一致性（折的原文仍在日志里可复盘）
- 规则引擎产出"计划"当纯数据（wfr-㊵）——"改进"也可以用同一套数据通道表达

**第一问**：最小的自进化闭环是什么——从「复盘失败会话 → 产出规则/提示词变更 →
回归验证（585 测试 + 真机对照）」起步？进化产物是改人读的 workflow，还是改机器读的规则？
