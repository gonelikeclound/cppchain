## 二、逐家提取（要点 + 源）

### 2.1 deepseek-harness（必选）
- **任务生命周期**：Session = 追加式类型化 `SessionEvent` 日志（**模型可见即已入日志，上下文永远从日志派生**）；step = 一次模型请求+工具；turn = 0..N step（闭环于"无所亏欠"）。工具执行管线 `tools/pre-execute → execute → post-execute` + **单调 Guard（只收窄不放行）**。
- **规划**：三件可组合物（无强 schema）——Plan Mode（软提示+出口工具，**限制交给沙箱/审批**，与计划状态解耦）、Goal（状态机 + CAS revision）、todo（整表替换）。**plan-review 是 user-questions 的一等 `intent`**，Approve/Keep planning 用显式标签。
- **验证**：**全仓库无 judge/scorer/pass@N**。验收 = 人工计划审查 + 审批（`ApprovalPolicy ask|never`，非 allowed-once 一律当拒绝 = fail-closed）+ auto-review（实验性，执行前让模型审动作分级）+ workspace-changes（每 turn 前后 git 树 diff）作为**给人审的账**。PTC 失败错误语义专为"回喂模型自纠"设计。
- **可中断**：AbortSignal 全局贯穿（tool/subagent/PTC/workflow）；ask_user **timed 模式**（超时返回 pending，迟到答案作新 turn）；interrupt_agent；jobs（kill-with-reason）。
- **可回退**：**没有 undo**。核心是 `session-checkpoint-policy` 的**三屏障**（模型请求前 / 顶层工具副作用前 / 步骤边界前落盘）+ 恢复时被打断的工具给 **TOOL_OUTCOME_UNKNOWN、绝不自动重试**（"durable execution intent, not exactly-once effects"）；回退 = resume + **turn 边界 fork（seed+seedLength）** + git 账本。官方 SAFETY 明言沙箱/审批只降险不保证隔离。
- 源：`docs/architecture.md`（turn flow）· `docs/persistence-catalog.md` · `docs/subsystems/{plan,approval,tools,sandbox,ptc-runtime,subagent,user-questions,session,deliverables}.md` · `packages/session/session-checkpoint-policy/README.md` · `packages/experimental/{auto-review,tool-ralph}/README.md`

### 2.2 LangGraph
- **规划**：plan-and-execute 教程（Planner→Executor→RePlanner + `should_end` 条件边；**计划 = `List[str]` 落 shared state，已完成步骤 = `past_steps: Annotated[list, operator.add]` reducer 追加**）；2026-01 教程从 docs 移除但 git 历史可查；官方现主推 orchestrator-worker（`Sections` + `Send` 并行派发 + 聚合）。
- **执行**：subgraph 作 subagent（compile(checkpointer) 三档：None 继承父图可用 interrupt / True per-thread / False 纯函数）；super-step 边界落 checkpoint + pending writes 容错；**节点重跑从函数体开头、副作用重打 → 要求幂等**（idempotency key / upsert / read-before-write）。
- **验证**：无 verifier 原语；官方三姿势 = evaluator-optimizer（LLM judge 出 Feedback，条件边回环到 pass）/ HITL 验收节点 / 已完成标记。清空累积标记要显式 `Overwrite`（`[]` 不清）。
- **可中断**：静态 `interrupt_before/after`（仅调试）vs 动态 `interrupt(payload)+Command(resume)`（主推，HITL approve/reject 标准模式）。**硬规则**：别 try/except interrupt、一节点一 interrupt（禁止条件跳过/while 内 interrupt）、payload JSON 可序列化、**interrupt 之前的副作用必须幂等**。
- **可回退**：时间旅行 `get_state_history`（按倒序列出 checkpoint）+ **fork = `update_state` 把某步设回去**——**不删历史、只开新分支**；`as_node` 可让图"以为某节点已跑过"。**官方明确不做副作用回退**，只靠幂等设计 + 外部兜底。
- 源：`docs.langchain.com/oss/python/langgraph/{interrupts,use-time-travel,checkpointers,graph-api,workflows-agents,use-subgraphs,fault-tolerance}` · plan-and-execute 教程（git 历史）· `github.com/langchain-ai/langgraph`

### 2.3 OpenAI Codex + Agents SDK
- **规划**：Codex `/plan` 会话模式 + **`update_plan` 工具**（步骤四态、带 explanation 可中途改写、渲染给用户）——**无强制确认门**（无 `--require-plan`）；`codex exec` 无 plan 子命令。SDK 无内置 planner；文档分 LLM 编排 / 代码编排（后者可写"任务 agent → 评估 agent → 不过重跑"循环）。
- **执行**：Codex 工具集 = shell / **apply_patch（唯一编辑途径）** / web_search / exec / fork / MCP；`codex exec` 非交互（`--json` / `--output-schema` / `--worktree` 隔离 / resume / fork / review 子命令）；交互态每工具调用走 exec policy 门控。SDK = Runner loop + handoffs（input_filter 交接脱敏）+ sessions（SQLite/Redis…）+ durable execution 集成。
- **验证**：Codex = **自跑测试/lint（"Validating your work"）** + apply_patch 严格 parser + **`git apply --check` preflight** + **`--output-schema` JSON Schema 严格校验** + `codex review`；**无内建 CI/acceptance 运行器**。SDK = output guardrail（tripwire，剔除被拒最终输出落脱敏占位）+ structured `output_type` + `error_handlers`。
- **可中断**：`approval_policy = untrusted|on-request|granular|never` + 审批 UI（approve/deny/approve-with-prefix/approve-for-session）+ `auto_review`（guardian_subagent：子代理按风险决策框架批/拒）+ sandbox 三档（read-only/workspace-write/danger-full-access）；SDK `needs_approval` → `result.interruptions` → `RunState.to_state/approve/reject` → 续跑，**RunState 可序列化跨进程恢复**（鉴权/防重放清单）。
- **可回退**：Codex **backtrack**（选早期 prompt 就地编辑，会话回退到该点前重放）+ resume/fork 会话 + `--worktree` 整棵可丢弃 + patch 审批逐项 deny（deny 不进工作树）+ `codex apply` 的 diff 应用前闸；**Codex 不自动 git commit**（checkpoint 责任在用户/CI）。SDK `session.pop_item()` 撤销单条 + `create_branch_from_turn(n)` 分支。
- 源：`github.com/openai/codex`（`base_instructions/default.md`·`config_types.rs`·`exec/src/cli.rs`·`app_backtrack.rs`·`apply-patch`）· `openai.github.io/openai-agents-python/{agents,running-agents,guardrails,handoffs,sessions,human_in_the_loop,multi-agent}`

### 2.4 OpenHands
- **规划**：Planning Agent **只创建计划、禁止执行**，产物 = `.agents_tmp/PLAN.md`（固定结构 OBJECTIVE/CONTEXT SUMMARY/APPROACH/IMPLEMENTATION STEPS/TESTING），只授权 `planning_file_editor` 工具；**确认 = 前端 Build 按钮** → 切 code 模式按 PLAN.md 执行。
- **执行**：reasoning-action loop（`agent.step()` 单步），事件状态机含 `WAITING_FOR_CONFIRMATION`、`PauseEvent`；sandbox Docker（默认）/Process/Remote。
- **验证**：**Critic 验证器**（agent 完成即预测成功概率 0~1；`Enable Iterative Refinement` 时总分<60% 或单 issue≥75% → 自动发回重做，最多 3 轮）——**少数显式后置评分器**；另有 QA-changes agent 实跑软件产出 PASS/FAIL/PARTIAL（含证据）；GitHub issue-to-PR 预置含 "Runs tests to verify"。
- **可中断**：确认三档（AlwaysConfirm/NeverConfirm/ConfirmRisky + threshold/confirm_unknown）+ `respond_to_confirmation`（accept/reason）+ `conversation.pause()/run()` + `reject_pending_actions("理由")`。
- **可回退**：**无官方一键 undo**；git 历史 + `openhands --resume` 持久化（`base_state.json` + events）+ pause 打断组成。
- 源：`docs.openhands.dev/sdk/arch/*` · `openhands/usage/agent-canvas/critic` · `qa-changes` · SDK `confirmation_policy.py` · GitHub 源码（`plan-file.ts`·`use-handle-build-plan-click.ts`·`respond-to-confirmation`）

### 2.5 Gemini CLI
- **规划**：Plan Mode（只读研究环，白名单工具 + ask_user + 写 `.md` 计划到 `~/.gemini/tmp/<project>/<session>/plans/`）；**两段式审批**：ask_user 非正式对齐 → PLAN 文件 → 用户 `Ctrl+X` 外部编辑 → 正式批准（"Yes, automatically accept edits" / "Yes, manually accept edits"）→ **批准即退出 Plan Mode 开始执行**；Pro→Flash 型号路由；`write_todos` 子计划（Ctrl+T 全览、可 skip/cancel）。
- **执行**：approval 模式 `default|auto_edit|plan|yolo`（auto_edit 自动放行 replace/write_file，其余询问）；run_shell_command 需人工确认（可交互/后台）；非交互 `-p/--prompt` + `--output-format json`。
- **验证**：无内置自愈重试；验证失败以 **exit code（0/1/42/53，53=turn limit）** / JSON error 事件暴露给上层；`--mode one_shot` 已从现行文档移除。
- **可中断/可回退**：**checkpointing（默认关）** —— 每次批准文件修改类工具前，在**影子 git 仓库**（`~/.gemini/history/<project_hash>`，不影响用户仓库）+ 对话历史 + 原工具调用上打点；**`/restore [tool_call_id]`** 回滚到某工具执行前（文件+对话+重新提出原调用）；`/rewind`（Esc Esc）可仅对话/仅代码/两者；`/restore` 需先开 checkpointing、`/rewind` 不动 shell 工具改的改动。
- 源：`geminicli.com/docs/cli/{plan-mode,checkpointing,rewind,sandbox,headless}` · `docs/reference/{commands,configuration,tools}` · `github.com/google-gemini/gemini-cli`

## 三、跨框架收敛出的共识（可作为设计的「背书清单」）

1. **计划要过人类确认关**（deepseek plan-review / OpenHands Build / Gemini 批准 → 执行；Codex 偏软渲染）——「规划 → 人确认 → 执行」是主流骨架。
2. **验证没有「确定性产物断言」的先例**：deepseek 明说无 judge；LangGraph 用 LLM evaluator；Codex/SDK/Gemini 靠自跑测试、output schema、guardrail、exit code；OpenHands Critic 是 LLM 后置评分。**`ToolSpec::probe`（只读产物状态断言）是 cppchain 的差异化空白点**。
3. **可中断 = 审批/HITL + 恢复续跑 + 持久化**，且硬约束跨框架一致：**一节点一 interrupt、payload JSON 可序列化、interrupt 前的副作用必须幂等**（LangGraph 明示 / deepseek 三屏障 + TOOL_OUTCOME_UNKNOWN）。
4. **可回退统一拆成两层，且都不做「命令反做」**：状态/任务层回退（fork/backtrack/update_state 开新分支、不改历史）人人有；**副作用层回退只有 Gemini 做了文件级 restore**，其余靠 git/沙箱/幂等兜底。
5. **执行都以沙箱/审批为护栏底座**（三家 sandbox 三态 + fail-closed），任务级环只管"组织"，不动护栏。

## 四、对 arch 19（wfr-㊹）的落点复查

| arch 19 定论 | 复查结论 |
|---|---|
| ① 验证：每步 probe-first + human 边界，LLM judge 首版不做 | ✅ **背书 + 差异化确认**：无一家做确定性产物断言，probe 是我们的空白点；LLM judge 各家的做法（LangGraph evaluator / OpenHands Critic ≤3 轮）正好是我们「下一版」的模板 |
| ② 回退两级、不做命令反做 | ✅ **背书**：与四家一致（Gemini 是唯一文件级例外，但需开 checkpointing = 默认不做）；「指针回 K + 标记 + 痕迹保留」= LangGraph fork / Codex backtrack 同款 |
| ③ 中断落点 = 步骤边界、resume 三态 | ✅ **背书**：对齐 approve/HITL 主流；补一条硬约束落实：**副作用必须放在步骤边界的「执行前」中断点之后**（LangGraph "interrupt 前要幂等" + deepseek 三屏障） |
| ④ 计划 = state 数据 + plan 节点产出 | ✅ **背书**：LangGraph「计划落 state + 已完成标记 reducer」是同一姿势；OpenHands/Gemini 用文件是另一形态（我们选数据以保可回放审计） |
| ⑤ 重规划 = 环内一等动作 | ✅ **背书**：LangGraph RePlanner / OpenHands Critic 自动重做 / Codex update_plan 中途改写 全支持「计划可变/重规划」 |

**两点修正/强化（写回 arch 19）**：
- **人确认关默认开**：跨框架共识是"计划过确认关"（deepseek/OpenHands/Gemini 都是硬门）——`plan_review` 由 arch 19 的「可选节点」强化为**默认确认门**（`strategy` 可关，如无人值守 retry 链）。
- **verify 判据再补一档「输出 schema」**：Codex `--output-schema` / SDK `output_type` 说明"结构化输出校验"是确定性验证的另一档；arch 19 的 `verify` 除 `probe`/`human` 外，**预留 `schema`（JSON Schema 校验步骤产物）**，首版可实现 probe + schema，扩展 human。
