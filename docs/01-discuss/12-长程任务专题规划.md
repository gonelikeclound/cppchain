# 12 · 长程任务专题规划（🟡 待启动 · 建档）

> **定位**：05 未来专题 #3「长程任务」的深化建档。上一题（wfr-㊹ PEV 三级验证，见 01-discuss/11）
> 把"**单批内**的规划→执行→验证 + 中断 + 回退"做完了；本题补上"**跨批**"——同一任务**多次分批运行**、
> 结论在时间轴上**不飘移**、且**可感受时间变化**。沿用流程：本建档 →（启动时）五框架对照 → arch → demo → problems 验收。
> 状态：🟡 已记录、待启动（先立「第一批问」，不实现）。

## 一、动机：两处被现实戳中的信号

1. **A1 全量（28 份合同）直接被 LLM 端点超时踢掉**（900s×2 次，problems/26）——"一次跑完"对大任务不可靠，
   更稳的形态就是**分批：每批做一部分、能续跑**。
2. **"结果不飘移"的感性体验**（wfr-㊵、problems/16/17/18 常讲）：Agent 在长会话里会忘最初目标、或被新一轮
   输入带偏。跨"天"级时间轴，这个风险更大——需要把"任务本身"与"某一次运行"解耦。

## 二、两级心智模型（贯穿设计）

- **单批**（一次 wfr 触发）= 已有 PEV 环：`plan → loop{announce, model, run_tools, verify(judge)} → final`，
  步骤边界可中断续审（plan_review）、失败自动回退依赖步（on_fail=rollback_deps，A1）。
- **长程** = 同一任务**跨多批**：每批仍走 PEV，但批间要保持——任务计划/进展（存哪）、上下文（会话续跑）、
  时间感（今天几号/第几批）、可控漂移（计划可否改、怎么改）。

## 三、期望能力（三支柱 + 两使能）

| 能力 | 含义 |
|---|---|
| **分批续跑** | 任务 = 持久计划；每次触发做"本轮批目标"（计划子集/进展点），跑完自动停；下次触发从上次进展继续 |
| **结果不飘移** | 任务目标/已完成步骤/批间约定在时间轴上稳定（计划是唯一界，不在 batch 里重构）；已有步骤结果可复核（verify 可跨批复用） |
| **感受时间变化** | 模型上下文注入当期日期/批号（DeepSeek-R1 的 `{cur_date}` 同款）；批间"上轮结论 vs 本轮现实"显式声明 |
| 使能① 续跑契约 | 会话日志 replay（现行）为最小契草；**显式 checkpoint（Store/SQLite）** 是否必要 = 5.《01》第一问 |
| 使能② 到点再跑 | 定时/定期触发（wfr trigger=schedule 已在 IR，但 **cron 常驻调度是押后项**）——长程真需要"每早 8 点跑一批" |

## 四、现有垫底（比 05 版厚得多，直接可接）

- **PEV 环 + 中断/回退**：`pev_*` workflows、`plan_review`（继续/回退/中止续审）、`strategy.on_fail=rollback_deps`（批内自愈）—— problems/24/25
- **会话续跑 replay**：wfr 下次触发读 `.wfr/sessions/<s>.log.jsonl`，模型可见全部历史（= 长程的"记忆"）
- **时间旅行 fork**（M10 problems/13）：改需求/回退到过去某点的底座（跨批因何改动的"撤销"）
- **M10 interrupt + checkpointer + resume**（挂续机制现成，跨进程）
- **`plan`/`verify` 数据化**（state.plan / plan_log）：任务结构是可审计、可回放的数据
- **外部工具面**（office-docs）：长程里各种格式产物跨批可解析
- **A1 教训**（problems/26）：批是解法，超时是现实；批次间产物落盘（verify 可探）天然是"跨批手账"

## 五、第一问（启动切入点，5 条）

1. **任务的持久形态**：任务 = 一个 `state.plan` 走查存盘（跨批 append 批进度），还是"plan + 每批子计划"两层？
   plan 要不要 JSON 落盘到工作区（如 `.wfr/tasks/<task>.plan.json`）而非只活在会话？
2. **批的边界与推进**：一批怎么决定"做多少"（按步数/按预算/按目标完成）？批尾把 `plan.cursor/批进度` 写盘；
   下批从哪恢复（replay 重建 plan vs 直接读任务文件）？
3. **续跑契约**：最小契约为 replay 是否够（05 第一问）；显式 batch checkpoint（独立于 M10 的会话级）何时必须？
4. **感受时间的注入口径**：上下文加 `{date, batch, task 摘要}` 的节点（接在 load_history 后）？批间"上批结论 vs 现实变化"要不要 L3 judge 复查？
5. **调度**：先不依赖 cron（押后），用**手工分批触发**做 demo 验证；触发编排（trigger schedule）留二期。

## 六、验收预想（按项目基调）

- `lot`（long-horizon task）demo：一个任务拆 2~3 批跑，每批 separately; 批间无超时；终批汇总；
  断言：任务计划批间稳定（plan 未漂移）、已完成步骤跨批可见、模型知道"今天/第几批"；
  再给一批"改需求"（时间旅行 fork 回过去改）拉一个对照。
- 全仓全绿 + problems/NN 验收记录。

## 七、边界与不做的

- 本建档只做**规划**（第一问），不实现。
- 不做：常驻 daemon / 真实日历轮询（cron 押后）；不做"自动跨批睡眠等待"（批间由宿主/人触发）。
- 与 #5 Agent 自进化的接点：长程的"任务档案 + 批记录 + 结果"正是自进化要吃的运行记录——先不做。
