# 03 · 案例推演集：13 个 case 与它们暴露的七个缺口

> 日期：2026-10-29
> 目的：**不继续写设计，改用 case 反证设计。** 每写完一条 case 就问一次"按现在的设计，它会怎么走？哪里走不通？"
> 使用方法：逐条推演，走不通的地方就地改设计；走通了就补验收口径。

---

## 0. 为什么先搞 case

设计文档很容易自洽，case 不会配合。写这 13 条的过程中，**发现了七个设计缺口**（§13），
其中两个是我在 `02` 里明确写下的机制所无法解决的。这比再写一遍设计更有价值。

case 分五组：任务式（C1–C3）、常驻式（C4–C6）、能力状态机（C7–C8）、图演化（C9–C11）、元层面（C12–C13）。

---

## A. 任务式（query 驱动）

### C1｜基准：装个安装包

**场景**：用户："把下载目录里最新的安装包装上。" 目录里有 40 个文件，最新是个 80 MB 的 apk。

**预期走法**：任务 T1 → `P1 找文件`（program）→ `P2 校验签名`（program）→ `A1 判断要不要用户确认`（AgentLoop）
→ 若需确认 → `H1 ask_human`（pivot）→ `P3 安装`（program）。共 4~5 个节点。

**压力点**：**委派开销**。同样的事 ReAct 一次工具调用就能干完，SA 要 1 次编排 + 1 次 AgentLoop + 2 次 program。

**风险**：这是 SA 最可能被"太笨重"击倒的 case。**如果小任务上 SA 的成本高于 ReAct，架构在 80% 的日常场景里是负收益。**
→ 需要"单节点快通道"：一个 Program 节点内部串行做多步，SA 只建 1 个节点。

### C2｜可逆长任务被中途取消

**场景**：装 2 GB 应用，30 秒后用户说"算了"。

**预期走法**：`cancel_node(P_install)` → `cancel_requested` → 安装器停止 → 节点上报 Cancelled
→ SA 醒来 → 加 `P_clean`（清理残留）→ 断言 `no_partial_install`。

**压力点**：SA 在 cancel 之后**立刻**建清理节点，而 `P_install` 可能还没真停。两者会打架（清理时安装器还在写）。

**缺口 G-a**：**"取消完成"必须是一个可等待的数据源**。清理节点的 `inputs` 要能依赖
`P_install.state == cancelled`，而不是依赖"SA 发了取消指令"。当前契约只有 `deps`（control 前驱），
无法表达"等某个节点的终止事件"。

### C3｜不可逆动作 + pivot

**场景**："给张三发条消息说明天不去了。"发出后用户说"发错了"。

**预期走法**：`P_send` 声明 `compensable: false` → 路径上必须有 `H1 ask_human`（pivot）
→ 发出后用户反悔 → 善后不是"撤销"，而是"补一条更正"（语义补偿，非物理回滚）。

**压力点**：**"撤回"不存在时，compensator 表达成"补救动作"**。契约里写 `compensator: "send_correction"`，
但怎么验证它有效？

**风险**：这类"语义补偿"的断言必须写成**最终序列**：`张三收到的消息序列 == [原消息, 更正消息]`。
否则补偿只能"自称做了"。→ 断言必须能描述外部世界的**终态**，不只是"我调用了 compensator"。

## B. 常驻式（事件驱动）

### C4｜长期订阅 + 去重

**场景**：常驻任务 `T_sub`："下载目录出现 .apk 就装。"一天 12 次，其中 3 次是同一版本重复下载。

**预期走法**：L0 命中订阅 → L1a 写 inbox 不唤醒 → "要装"需改图 → L1b 批量唤醒 → SA 建安装子图。

**压力点**：**幂等**。同一版本重复下载不该重复安装。

**缺口 G-c**：**缺幂等键**。`add_node` 与 `spawn_task` 都没有 idempotency key。
必须有 `dedup_key`（如 `(install, pkg, version)`），相同 key 的第二次 add 是 no-op 而非新增节点。

### C5｜多源事件关联

**场景**：`电量<20%` ∧ `时间>18:00` ∧ `在回家路上` → 提前开省电。三个事件在 15 分钟内陆续到达。

**预期走法**：不是"来一个改一次图"，而是**窗口内聚合后再判断**。

**压力点**：L1b 只有"批量合并"（同一 tick 内的事件），**没有"情境关联"语义**——谁和谁属于同一件事。

**缺口 G-d**：**需要事件关联窗口**（correlation key + window）。
否则三个事件各触发一次思考，而且**每次看到的信息都不完整**（第一 tick 只见电量，第二 tick 只见时间）。

### C6｜事件洪水

**场景**：一夜产生 5 000 个系统事件（通知/电量/网络/传感器），真正值得关注的 3 个。

**预期走法**：L0 丢弃 ~4 900，L1a 增强若干，L1b 唤醒 3 次。模型调用数 = 3 + tick 数。

**压力点**：**L0 的过滤规则从哪来？** 规则是纯函数（好），但规则本身是"编排层的配置"，
属于 SA 的产出 → 又需要记账、又需要被验证。且**规则错了会静默丢事件**——漏报比误报危险得多。

**缺口 G-e**：**L0 需要漏报审计**：定期抽样被丢弃的事件，人工/模型确认"没有丢掉重要的"。
这条不做，常驻模式就是在赌过滤器永远正确。

## C. 能力状态机（FSM 层）

### C7｜打电话（最复杂的一条）

**场景**："给妈妈打电话问她晚上来不来吃饭。"拨号 → 振铃 → 拒接一次 → 重拨 → 接通 → 对话中用户改口
"算了，发个微信就行" → 挂断 → 建成消息节点。

**预期走法**：图上一个节点 `N_call`，内部 FSM：`Dialing → Ringing → Connected → Talking → Ended`；
拒接走 `Failed`，重试由 SA 在里程碑上决定（或 FSM 内部重试一次并上报）；
用户改口 → `cancel_node(N_call)` → 通话中 cancel 是 **compensable**（`compensator=hang_up`）→ 挂断 → 建消息节点。

**压力点**：三个都很难 ——
① 里程碑词汇表（`ringing` / `rejected` / `connected` / `hungup`）决定 SA 能不能"看见"这通电话；
② FSM 每个状态都要有取消出口（`Talking` 状态下 cancel = 挂断）；
③ 通话中 SA 不能逐帧观测，只能在里程碑上醒来。

**缺口 G-b（最重要）**：**节点必须区分"等完成"和"等打断"**。
`02` 的 `waits` 只说了"节点在等什么事件"，但没区分：
- **等完成**：这个事件让节点走向终态（如 `call.completed`）
- **等打断**：这个事件要在任何时刻都能被响应（如用户改口、更紧急的任务插入）

**"用户改口"是最高频的真实场景**，它要求 FSM 节点在 `Talking` 状态下也能接收外部指令。
这在 statechart 里是**正交区域**（对话区 + 控制区），而不是一个额外的 waits。
→ 契约需要 `interrupts`（可与任何状态并发的事件集合），且这些事件必须能映射到状态机里的转移。

### C8｜并发任务抢对话

**场景**：C7 通话进行中，另一个任务 T2（下载完成）需要 SA 决策。

**预期走法**：T2 的 L1b 事件进 tick 队列 → SA 醒来处理 T2 的 patch → 通话节点不受影响继续跑。

**压力点**：SA 处理 T2 时，上下文里必须有通话的 digest，否则**可能误删通话节点或重复派任务**。

**风险**：L1 digest 里必须显式包含"活跃节点的不可打断性"，否则并发编排会互相踩。
→ digest 字段要加 `protected_nodes`（不可取消/不可重复的节点）。

## D. 图演化

### C9｜异步续体（下载经典例）

**场景**：派 Program 节点下载 500 MB，约 3 分钟。期间 SA 静默。完成后要"校验 → 解压 → 安装"。

**预期走法**：下载节点 `waits: progress | done`；进度事件**不唤醒**（L1a），完成事件唤醒（L1b）→ SA 加三节点。

**压力点**：等待期零 token（验证 §5.1 预算）；且"下载完成"与"用户取消"可能同时到达。

**风险**：需要 **per-task 事件因果序**（revision 单调 + 事件序）。若取消事件的序在完成之后，
SA 不应再建后续节点。当前设计只说了"per-key 串行"，但没定义"SA 读到的事件序"与"patch 顺序"的一致性。

### C10｜卡死 → 善后（验证 D4）

**场景**：第三方安装器忽略 SIGTERM，卡在 `Cancelling` 90 秒，进程进入不可中断状态。

**预期走法**：
```
request(5s) → grace(30s) → force(SIGKILL 无效) → abandon
   → 资源账本显示持有 /dev/xxx + 一个文件锁
   → Reaper 派清理任务 T_cleanup（不依赖 SA）
   → 对账：安装实际到 60% → 隔离(quarantined) → 释放锁 → needs_human（半装需人确认）
   → 回写原任务终态：Aborted + cleaned/quarantined + 1 个 abandoned
```

**压力点**：**整条 D4 链路**，特别是"清理任务不依赖 SA"这一点。

**风险**：清理任务的"对账"是**唯一被允许读世界的地方**。
这打破了"SA 不执行"的纯洁性——但清理任务不是 SA，所以原则不被破坏。
需要明确：清理任务可以用 Program/AgentLoop 节点，但**不得改写已完成节点的产出**（Q12）。

### C11｜结构性死锁

**场景**：SA 把 A 的 `waits` 设成 `event.X`，而图里没有 X 的生产者（X 来自另一个已失败的任务）。

**预期走法**：V2 在提交前算出"无生产者"→ 拒绝 patch → 重试 1 次 → 仍失败 → `stuck` → 升级。

**压力点**：**死锁检测的完备性**。如果 `waits` 允许任意谓词（如"等一个表达式的值为真"），
活性判定就**不可判定**，V2 只能退化成"尽力而为"。

**缺口 G-f（理论硬洞）**：**`waits` 必须限制到封闭的事件类型集合 + 结构化匹配**（如 `type == X ∧ field.y == 3`），
才能静态判定。这是"表达能力 vs 可验证性"的取舍，**必须显式决定**——
一旦允许自由谓词，`02` 里"结构性死锁可静态判定"这条卖点立即作废。

## E. 元层面

### C12｜SA 自己出问题

**场景**：某任务连续 5 次 patch 验证失败；或预算耗尽；或 L1 已满 50 条仍在增长。

**预期走法**：`stuck` → 冻结图 + 记录原因 → 升级；预算耗尽 → `Aborted`；L1 满 → 淘汰 + 归档。

**压力点**：**"SA 卡住时谁在管事"**。

**缺口 G-g**：需要 **任务级 janitor**（与 Reaper 不同：Reaper 管**节点**，janitor 管**任务**）。
否则一个 stuck 任务会永久占着 `running` 名额，最终拖垮准入。

### C13｜任务爆炸与去重

**场景**：一次网络抖动产生 50 个相同事件，触发 50 个相同任务。

**预期走法**：`spawn_task` 带 dedup key → 只建 1 个；其余合并为该任务的新事件。

**缺口 G-c（同 C4）**：同 G-c，任务创建也需要幂等键。

## 13. 写 case 发现的七个缺口

| # | 缺口 | 暴露于 | 严重度 | 对 `02` 的影响 |
|---|---|---|---|---|
| **G-a** | "取消完成"不是可等待的数据源 | C2 | 高 | `deps` 需支持 `state` 型前驱 |
| **G-b** | 节点未区分"等完成"与"等打断" | C7 | **最高** | 需加 `interrupts`，并映射到 FSM 转移 |
| **G-c** | 缺幂等键（任务级 + 节点级） | C4/C13 | 高 | `spawn_task` / `add_node` 需 `dedup_key` |
| **G-d** | 缺事件关联窗口 | C5 | 中 | L1b 需 correlation key + window |
| **G-e** | L0 规则的来源与漏报审计 | C6 | **最高** | 需规则版本化 + 抽样审计 |
| **G-f** | `waits` 若允许自由谓词则活性不可判定 | C11 | **最高** | 必须限制为封闭类型 + 结构化匹配 |
| **G-g** | 缺任务级 janitor（Reaper 只管节点） | C12 | 中 | 需第二个确定性守护者 |

**其中最要紧的三个（G-b / G-e / G-f）都不是"补个字段"能解决的**，它们各自要求一条硬决定：

- **G-b**：状态机节点必须支持**并发控制区**（用户改口要能在任何状态下生效）——这是 statechart 的正交区域，
  不是加一个事件类型就行。
- **G-e**：过滤器是**唯一的静默丢弃点**，必须像对待删除操作一样对待它（审计、可回滚、可解释）。
- **G-f**：要不要保留"任意谓词"的表达力？要，则失去静态死锁检测；不要，则编排能力受限。
  **这是一次性的取舍，选了就锁死。**

## 14. 建议的推演顺序

按"最能推翻设计"排序，建议先推这三条：

1. **C7 打电话** —— 同时压 FSM、中断、里程碑词汇表、并发区。它如果走不通，能力层就立不住。
2. **C6 事件洪水** —— 同时压 L0 规则、漏报审计、成本模型。它如果走不通，常驻模式就立不住。
3. **C11 死锁** —— 一次性决定编排语言的表达力上限。它如果走不通，静态验证整条卖点作废。

C1 虽然最"平庸"，但它是**商业上最重要**的一条：如果小任务上 SA 比 ReAct 贵，这套架构就没有落地价值，
必须设计"退化成单节点 ReAct"的快速通道。
