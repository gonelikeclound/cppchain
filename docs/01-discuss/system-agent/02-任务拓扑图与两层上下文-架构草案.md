## 0. 一句话模型

> **SA 不做任务，SA 编排队列：它把每个任务表达成一张可变拓扑图，图上的节点独立运行；
> SA 平时静默，靠事件醒来，每醒一次只做一轮「思考 → 调整图 → 验证」，然后回到静默。**

这条定位带来一个关键推论：**SA 的动作只作用于图，图外的世界只由节点改变**。
SA 没有能力直接执行领域动作——这不是权限裁剪，而是这套架构能自洽的前提（§7）。

---

## 1. 核心模型：五个对象

| 对象 | 定义 | 是否持久化 |
|---|---|---|
| **Task** | 一个任务 = 一张拓扑图 + 一份任务日志 + 一套订阅 | 是 |
| **Graph** | 可变有向图；活跃节点集合 + 边 | 是（= fold(patch 事件)） |
| **Node** | 图上一个可独立运行的执行单元，三类（§3） | 是（含状态与输出槽） |
| **Event** | 外部世界的事实（系统事件 / 节点里程碑 / 用户输入） | 是（唯一真相） |
| **Patch** | SA 对图的一次编辑事务（§5.2） | 是（可重放，**不重新问 SA**） |

**不变量 I0（记账）**：图的一切演化都只能通过 `Patch` 表达，且每个 Patch 带 `base_revision`。
回放 = 重放 Patch 序列，不重新推理。**这是"重启可恢复"的唯一依据**——否则可变图的演化就是不可重建的。

### 1.1 正交两层：任务层 vs 能力层

```
任务层   拓扑图（做什么 / 先后 / 并行 / 依赖）        ← 本稿主体，可静态检查、可编辑、可审计
            │  一个节点可以是一台状态机的宿主
            ↓
能力层   FSM / statechart（一个动作内部怎么演化）       ← 拨号→振铃→接通→挂断
```

**这不是二选一。** 一通电话 = 拓扑图上的**一个节点**，节点内部是一台 FSM。
FSM 的每次跃迁产出一个**里程碑事件**汇给 SA；SA 从不逐帧观测 FSM 内部。

## 2. 两种运行模式，同一个引擎

| | 模式 A：**任务式** | 模式 B：**常驻式** |
|---|---|---|
| 入口 | 用户一个 query | 系统事件流 |
| 起点 | 生成一张图并启动 | 触发规则 → 生成任务 |
| 结束 | 任务终态 | **不结束**（SA 本身永不退出） |
| 主要风险 | 编排质量 | **成本、去重、洪水** |

**统一方式：SA 永不结束；只有任务有生命周期。** 模式 A 只是"由一个用户事件初始化了一个任务"的特例。
这直接消解了 §2 的一个潜在歧义——**"图空"结束的是一个任务，不是 SA**。

### 2.1 任务生命周期

```
pending ──admit──> running ──┬─> waiting（等事件，不占资源）
   ▲                         ├─> done
   │                         ├─> failed
   └───(容量不足回退)──────── ├─> cancelled
                             └─> idle（长期存活、只在订阅命中时被唤醒）
```

- `pending` 隐含**准入控制**：并发任务数、每任务预算必须有上限（否则常驻模式必然失控）。
- **准入策略建议做成确定性的**（优先级 / 公平性 / 配额），SA 只能请求调优先级，不能自己决定准入——
  否则准入本身就要一次模型调用，且不可审计。
- `idle` 是常驻模式的关键状态：一个长期任务（如"盯着这个下载目录"）永远不 `done`，只在订阅命中时短暂 `running`。

## 3. 节点：三类、九项契约

### 3.1 三类节点

| 类型 | 执行者 | 运行时长 | 汇报 | 中断 |
|---|---|---|---|---|
| **Program** | 进程/后台作业 | 长（可数分钟~数小时） | 关键**里程碑**（声明式，非 stdout 全量） | 杀进程（graceful → SIGKILL） |
| **AgentLoop** | 一次 LLM turn（可多步工具） | 中（数秒~数分钟） | **一次结果** + 过程里程碑 | abort 请求 + 在途工具合成结果 |
| **SubGraph** | 子拓扑图 | 长 | 子图终态 + 关键里程碑 | 向下递归 + 级联 |

三者对 SA 是**同一个接口**（图上的一个节点，上报同一套里程碑）。差异只在内部执行器——这是让 SA 不必关心节点内部的关键。

### 3.2 节点契约（九项）

| 字段 | 作用 | 缺失的后果 |
|---|---|---|
| `kind` | Program / AgentLoop / SubGraph | 运行时不知道该用哪个执行器 |
| `deps` | control 前驱 + **join 语义**（all/any/quorum） | 就绪判定无定义，图无法执行 |
| `inputs` | data 边：引用上游哪个输出槽 | 节点拿不到数据，只能读全局——破坏隔离 |
| `milestones` | **声明的里程碑词汇表**（类型 + 载荷 schema） | 无归约依据，等于把原始日志灌进上下文 |
| `waits` | 在等什么事件（类型 + 匹配 + **超时**） | **"静默"与"挂死"无法区分**（见 §6.2） |
| `reversibility` | `{cancelable, compensable, compensator}` | 取消不可逆动作会制造脏状态（见 §8.6） |
| `budget` | 时间 / token / 步数 | 常驻模式下成本失控 |
| `assertion` | 完成时交出的**可校验断言**，而非自报 OK | 图空 ≠ 完成（见 §6.1） |
| `resources` | **资源账本声明**：进程 / 连接 / 设备 / 文件锁 / 预约（acquire→release） | 善后只能靠猜（见 §8.7） |

> **`milestones` 是观测归约的落点**：节点只能上报词汇表内的事件。词汇表之外的东西一律不进 SA 的上下文。
> 这一条把调研里"事件不能直接进对话"变成了**类型系统层面的强制**，而不是 prompt 约定。

## 4. 上下文架构：两层 + 瞬时装配

### 4.1 为什么不能是历史递增

SA 同时跑很多任务，且**永不结束**。如果上下文是"对话历史 append"，那么：

- 常驻模式下历史**只增不减**，必然撞上 compaction 的墙；
- 任务之间互相污染（A 的失败描述出现在 B 的上下文里）；
- KV cache 前缀反复失效。

所以上下文必须**按需装配**，而不是累积。核心公式：

```
任务一次"醒来"看到的上下文 =
    任务章程（稳定前缀：目标 / 契约 / 词汇表）
  ⊕ L1 快照（其他任务的状态摘要，只取相关的）
  ⊕ 本任务的 digest（折叠自该任务事件日志）
  ⊕ 触发本次醒来的事件
  ⊕ 订阅命中的增量（自上次醒来以来）
```

这是一个**投影**，不是历史。信息没有丢——它躺在任务的**事件日志**里，只是不进上下文。
（这正是调研里那条：`state = fold(events)`，对话历史只是投影。）

### 4.2 第一层（L1）：任务表

**L1 = 全体任务的 digest 表**，是 SA 唯一常驻的东西。

每个任务维持一条 **digest**（≤ 若干十字）：

```
{ task_id, 一句话目标, phase(pending/running/waiting/idle/done/failed),
  当前图规模(活跃节点数), 最近里程碑, 阻塞点(在等什么), 上次醒来的 revision }
```

**L1 的致命风险：它自己也会膨胀。** 常驻模式跑一天，可能有几百个任务——L1 变成新的无界历史，问题原地递归。
必须有的机制：

| 机制 | 说明 |
|---|---|
| **硬上限** | L1 只保留 N 条（建议 20~50），超出按优先级淘汰 |
| **优先级** | `阻塞在 SA 上` > `刚活跃` > `running` > `waiting` > `idle` > `done(近期)` |
| **归档** | 淘汰的 digest 进"归档索引"，SA 可按需 `query_task(id)` 取回（一次工具调用，非常驻） |
| **不做全量摘要** | 不要试图"总结所有任务"——那是又一次 LLM 调用，且信息有损 |

**谁写 digest（这条容易漏，但很关键）**：digest **必须由运行时从任务事件日志 fold 出来**，
**节点不得自己写摘要**。节点只能通过声明式 `milestones` 影响 digest 的内容。

理由：若节点能自由写摘要，它就能用一句话操纵 SA 的编排决策——这是 **prompt injection 的编排层版本**，
而且它比注入到对话更危险，因为它直接改的是"编排者相信什么"。
同一原则已经在 §6.1 出现（节点交断言，SA 只读断言结果）：**被编排者不能编辑编排者对自己的认知。**

### 4.3 第二层（L2）：单任务上下文

- L2 **不是常驻会话**，而是**每次醒来时装配出来的瞬时上下文**（公式见 §4.1）。
- L2 的稳定前缀 = 任务章程 + 节点契约 + 里程碑词汇表 → 这部分**跨醒来不变**，可复用 KV cache。
- L2 的易变后缀 = digest 增量 + 触发事件 + 订阅命中 → 每次不同（这是无法避免的）。
- 任务一旦进入 `waiting` / `idle`，**L2 上下文整体丢弃**，只留 digest 与日志。等待期零 token。

### 4.4 订阅：两个方向的语义

用户明确要求"对关注的任务或主题进行订阅跟踪，上层变化也通知进来"，以及"L1 认为某变化值得某任务关注，也会推消息"。
这是**两条独立的通路**，不能混：

| 通路 | 谁发起 | 语义 | 可靠性要求 |
|---|---|---|---|
| **声明式订阅（下→上）** | 任务自己声明 | `subscribe(predicate)`：任务 id / 事件类型 / 主题 key | **纯函数匹配**，必须可审计、可解释"为什么这条推给了它" |
| **推送（上→下）** | L1 判断 | `push(task_id, fact)`：L1 认为"这件事你得知道" | 需要判断依据，**必须有理由字段**，否则无法回归 |

两条都要落到 `send(target × wakeup)` 这个既有原语上（`inject` = 只丰富下次醒来；`followup` = 唤醒）。

### 4.5 事件三级路由（成本控制的核心）

**这是常驻模式下能不能活下来的分界线。** 事件绝不能"每条都让 SA 想一次"。

```
事件到达
  │
  ├─[L0 纯函数过滤]  不匹配任何订阅 ──> 丢弃（零成本，可计数）
  │
  ├─[L1a 任务增强]  命中某任务订阅 ──> 写进该任务 inbox，**不唤醒**
  │
  └─[L1b 编排唤醒]  需要改图 ──> 进 SA 的 tick 队列，**批量合并后**一次思考
```

- **L0 / L1a 必须是纯函数**。"这事值不值得关注"如果每次都问模型，常驻模式的成本就无法收敛。
  模型只处理**歧义项**（L1b 内部仍可再做一次确定性筛选）。
- **L1b 必须批量 + 限频**：一个 tick 可以合并 N 个事件，"思考"一次。
  → 建议：**每任务每 tick 至多一次模型调用**，tick 间隔与合并窗口可配。
- 丢弃与合并没有任何成本，这让成本只与**值得编排的事件数**成正比，而不是与系统事件总数成正比。

## 5. 低轮次循环：思考 → 调整图 → 验证

### 5.1 单次处理的有界预算

用户要求"不阻塞、低轮次"。把它写成可验收的预算：

| 维度 | 上限 | 理由 |
|---|---|---|
| 每 tick 的思考轮数 | **1**（不允许在同一个 tick 内反复自我修正） | 防"想不完" |
| 每 tick 的 patch 数 | K（建议 8~16） | 防"改爆炸" |
| 每 tick 的模型调用 | **1** | 成本可预测 |
| 验证失败重试 | **1**（第二次仍失败 → `stuck` 升级） | 防死循环 |
| 事件处理总时长 | 有硬超时 | 一个 tick 卡住不能拖垮 SA |

**关键：`stuck` 必须有出口。** 验证连续失败、或 SA 无法给出合法 patch 时，任务进入 `stuck`（不是"一直重试"），
按策略升级给人 / 降级到"冻结当前图 + 记录原因"。**没有这一条，静默会变成黑洞。**

### 5.2 Patch 原语：封闭集

编辑能力收敛到很小的封闭动词集，便于审计、校验与回放：

```
add_node(spec)        cancel_node(id, reason)
rewire(from, to)      bind_input(node_id, slot, source)
set_budget(node_id, budget)
```

**不要允许任意图重写。** 封闭集带来两个好处：①每个动词都能配一条验证规则；②回放时不必解释"SA 当时在想什么"。

兼容性检查：`base_revision` 不匹配 → 拒绝并重取（乐观并发），**两个 SA 实例不会打架**。

### 5.3 验证清单（`验证` 这一步到底验什么）

| # | 检查 | 失败含义 |
|---|---|---|
| V1 | **结构**：无悬空边、无不可达节点、join 可满足 | patch 本身有错 |
| V2 | **活性**：每个存活节点的 `waits` 都有存活生产者，或已设超时 | **结构性死锁**（见 §6.2） |
| V3 | **收敛**：无环形依赖、重试有界 | 图不会终止 |
| V4 | **预算**：新增节点不超任务预算 | 成本失控 |
| V5 | **副作用**：不可补偿动作的每条路径都经过 `pivot` | 埋下不可收拾的脏状态 |
| V6 | **断言**：每个叶子节点都有 `assertion` | 完成不可验证 |
| V7 | **原子性**：图空判定 = 无活跃节点 ∧ 无在途 patch ∧ 无待投递事件 | 误判完成（见 §6.1） |

**验证必须是纯函数、可拒绝、可单测。** 它是 SA 的"编译器"，不是又一次模型调用——
否则"验证"就退化成"模型再看看"，等于没有验证。

### 5.4 提交语义

- **验证通过才提交**：`revision += 1`，patch 落日志。验证失败则**整体回滚**（不是部分应用）。
- **no-op 是合法结果**：多数事件不需要改图。no-op 必须被低成本记录（不要为"没改"付一次完整思考的代价）。
- **每个 patch 记 `trigger_event_id`**：任何一次改图都能回答"你当时因为什么改的"，这是可回溯性的基础。

## 6. 终止、死锁、挂死

### 6.1 图空 ≠ 完成

图空有三种成因，语义完全不同：

| 成因 | 正确语义 |
|---|---|
| 所有节点正常完成且断言通过 | **Completed** |
| 节点被 cancel / SA 误删，导致"自己把活删光了" | **Failed（自杀式完成）** |
| 边断了，图非空但永久不动 | **挂死**（连"空"都到不了） |

**终态必须三态**：`Completed / Incomplete / Aborted`，判定条件：

```
Completed  = 无活跃节点 ∧ 无在途 patch ∧ 无待投递事件 ∧ 全部断言通过
Incomplete = 无活跃节点 ∧ 存在断言失败/未验证项   → 触发一次 SA 咨询（有限次）
Aborted    = 外部取消 / 超时 / 预算耗尽
且有节点被 abandon 时，终态必须附带「善后结论」：cleaned / quarantined / needs_human，以及被放弃节点数。
**"完成"里若藏着未善后的孤儿，那个完成就是假的。**
```

### 6.2 结构性死锁：显式图独有的能力

隐式 ReAct 循环里"卡住"只能靠超时发现。显式图可以**静态判定**：

> 若某存活节点在等事件类型 T，而所有存活节点中不存在 T 的生产者（且无外部订阅源），则**必然永不推进**。

这条在 V2 就能算出来，**画图即可查**。这是"把控制流变成数据"最有力的回报，建议做成第一等能力
（同时对 `waits` 缺失的节点直接判死——这也解释了为什么 `waits` 是契约必填项）。

配合两类超时：**事件超时**（等太久了）与**无进展超时**（活着但什么都没发生）。

### 6.3 挂死的可观测性

SA 静默意味着**外部无法从"没有输出"推断出任何信息**。所以必须主动暴露：

- 每任务一条 `liveness` 心跳（由运行时产出，不经过模型，零 token）：图规模、最近事件、等待时长、tick 数；
- `pending`/`waiting` 的累计时长要能被查询；
- 常驻模式需要一个"任务看板"——否则跑一夜之后没人知道发生了什么。

## 7. SA 的工具面：只有编排动词

### 7.1 内置工具清单

用户明确："SA 只有核心的内置工具，其他全部是任务委派"。具体化为两类：

**写（编排动词，只作用于图）**

| 工具 | 说明 |
|---|---|
| `patch_graph(task_id, patches[], base_revision)` | 唯一的图编辑入口（§5.2 的封闭集） |
| `spawn_task(goal, contract)` / `kill_task(id, reason)` | 任务生命周期 |
| `push_to_task(task_id, fact, reason)` | 上→下推送（§4.4） |
| `ask_human(question)` | 唯一的人类交互点 |

**读（只读观测，不改变世界）**

| 工具 | 说明 |
|---|---|
| `query_task(id)` | 取回被归档的 digest、日志片段、图快照 |
| `list_tasks(filter)` | 查询超出 L1 上限的任务 |
| `get_node_output(node_id, path?)` | 读节点输出槽（受 `milestones` 词汇表约束） |

### 7.2 不变式 I1：SA 的动作只作用于图

**可验收**：SA 的工具 schema 中不存在任何改变外部世界（文件、网络、设备、账号）的动词。
这条不只是安全边界，更是**架构自洽**的要求：

- 若 SA 能直接执行，则"图"不再是唯一真相，回放就无法重建状态；
- 若 SA 能直接执行，则预算/权限就无法按任务隔离；
- 若 SA 能直接执行，SA 的上下文就必须包含执行细节 → 回到 ReAct 的老路。

**推论**：连"读文件"这种小事也必须是一个 Program 节点。
代价是委派开销，收益是 SA 的上下文永远只有**编排层信息**。

### 7.3 委派机制的代价

| 代价 | 缓解 |
|---|---|
| 简单动作也要建节点 | 提供"瞬时节点"：Program 节点可在同一次 patch 内 add→complete，不进入活跃图 |
| 每节点有调度开销 | 瞬时节点走同步快路径，不落盘为图事件（只落任务日志） |
| 编排粒度过细 | 节点可以粗（一个节点做十件事），SA 不必拆到原子操作 |

## 8. 中断与退出保证（回应"取消了却退不出"）

这是一个真问题，而且是个**已知的工程陷阱**：DSH 自己的 job 运行时在 README 里就承认
"A silently ineffective cancel can stall teardown"——`cancel` 返回了，但生产者没有 `done`，
运行时无法区分"慢停"和"卡死"。

### 8.1 为什么会"取消了还退不出"

| 根因 | 表现 |
|---|---|
| 取消是**协作式**的 | 节点只在检查点看信号，卡在系统调用里就永远看不到 |
| 节点在等**不可中断的 I/O** | 内核态阻塞，信号收不到 |
| 节点的取消路径本身也在等 | 取消逻辑里又发起了新的等待（典型递归陷阱） |
| **状态机节点处于无法响应的状态** | FSM 在某个子状态里没有定义"取消"的出口 |
| SubGraph 只取消了根，没级联 | 子节点还在跑，父节点"已完成" |

### 8.2 四级升级（必须全部实现，缺一级就有僵尸）

| 级 | 动作 | 失败后 |
|---|---|---|
| **1. request** | 投递 `cancel_requested` 事件，节点协作退出 | 超时 → 2 |
| **2. grace** | 关闭新工作入口（停止 spawn / 停止接新子任务），给最多 G 秒 | 超时 → 3 |
| **3. force** | 强制终止执行器（abort LLM 请求 / SIGKILL 进程 / 递归取消子图） | 无法终止 → 4 |
| **4. abandon** | 标记 `Abandoned{at, reason, known_effects}`，**从活跃图移除**，记入任务日志，**并触发善后交接**（§8.7） | — |

**关键：第 4 级是必须存在的。** 没有"放弃"这个显式状态，就一定会出现"图上有个永远不结束的节点"。
放弃不等于假装成功：它会把节点标记为**非权威**，并把它**已声明的副作用**交给补偿/对账流程（§8.6）。

### 8.3 各类节点的中断点（必须在契约里声明）

| 节点类型 | 中断点 | 强制终止手段 |
|---|---|---|
| Program | 作业契约：`cancel(reason)` 幂等 + `done` 必达 | 杀进程组（先 TERM 后 KILL） |
| AgentLoop | 模型请求可 abort；**已发出但未返回的工具调用要合成结果**（DSH 的做法：未派发的调用配 `ABORTED_BEFORE_DISPATCH`） | abort 信号 + 合成结果 |
| SubGraph | 递归取消所有活跃子节点，等其终止 | 子图的四级升级 |
| **FSM 宿主节点** | **每个状态都必须定义 `Cancel` 出口**（否则就是"无法退出"的根因） | 强制回到 `Cancelled` 终态；**走到 abandon 则交善后（§8.7）** |

**FSM 那条是重点**：状态机的强项是"知道自己处于什么状态"，所以**取消的响应性也随之可判定**——
每个状态声明"能否立即取消 / 需要几步 / 有无补偿"，可以在**静态检查阶段**验证"所有状态都有取消路径"（V5 的扩展）。

### 8.4 中断也是一次图编辑

取消节点会留下悬空边与失效依赖，所以：

```
取消请求 → 节点进入 Cancelling → 终止/放弃 → 产出 Cancelled 事件
                                                    ↓
                                    SA 被唤醒（或确定性规则自动处理）
                                                    ↓
                                        rewire / 标记下游 Skipped
                                                    ↓
                                          走 patch + 验证（V1/V2）
```

**不要绕过 patch 直接改图**。取消是最高频的图变更，如果它绕过记账，图就无法回放。

### 8.5 僵尸节点的可观测性

运行时必须维护 `Cancelling` 停留时长，并暴露：

- `cancelling_ms`：超过阈值即告警（"这个节点正在变成僵尸"）；
- `cancel_attempts`：四级升级实际走到第几级；
- `abandoned` 计数：任务终态里必须显示"有几个节点是被放弃的"——否则"完成"是假的。

### 8.6 不可逆动作：补偿，而不是取消

若节点已发出**不可逆**动作（已拨出电话、已发送消息、已删除文件），"取消"是**错的**：

- 节点契约声明 `{cancelable: false, compensable: true, compensator: "hang_up"}`；
- 取消时执行**补偿**而不是终止，并把补偿本身作为子节点加入图中（`Compensating` 是一个**可持久化的子状态机**）；
- 完全不可补偿的动作，其路径上必须有 **`pivot`**（人机确认点），V5 验证这一点。

### 8.7 善后：把"退不出"交给专门的退出清理任务

> 决策：节点走到 `abandon` 之后，**不再指望它自己退出**，而是派一个**专门的清理任务**做善后。

这个决定把"退出保证"从"要求节点守规矩"变成"系统承认节点会赖着不走，并为此准备了收尸队"。
我认为这是全稿最重要的一处转向——因为**协作式取消永远不可能 100% 成功**，
任何声称"我们的取消一定能成功"的设计，最后都会以僵尸节点收场。

#### 触发者必须是运行时，不是 SA

**这是本节的硬约束。** 善后任务若由 SA 来派，就会出现"SA 卡住 → 没人派善后"的死锁，
而"卡住"恰恰是最需要善后的时刻。

```
节点卡住 → 四级升级 → abandon
              ↓（运行时判定，纯规则，零模型）
        Reaper（运行时子系统）
              ↓
        生成清理任务（Task，有自己的拓扑图）
              ↓
        对账 → 补偿 → 隔离 → 出证据
              ↓
        回写原任务终态 + push 给原任务/SA
```

**Reaper 是确定性的**：`abandon(node)` / `cancelling_ms > 阈值` / `孤儿资源账本非空` 这三类条件命中即派任务。
SA 可以 `query` 善后结果，但**不能阻止也不能替代**它。

#### 善后任务做什么（顺序不能乱）

| 步 | 动作 | 为什么必须在这个位置 |
|---|---|---|
| **1. 对账** | 查外部世界的**真实**状态（唯一允许"读世界"的地方） | 节点自报的状态不可信，只有对账是证据 |
| **2. 补偿** | 执行 `compensator`；补偿必须**幂等** | 先对账再补偿：避免"其实没事却去补偿"造成二次伤害 |
| **3. 释放** | 按 `resources` 账本释放进程/连接/设备/锁/预约 | 没有账本只能靠考古（见下） |
| **4. 隔离** | 无法确认干净的东西标记 `quarantined`，禁止后续任务触碰 | 宁可隔离也不假装干净 |
| **5. 出证据** | 产出 `reconcile_report`：发现了什么、做了什麼、还剩什么 | 这是终态"完成"能不能成立的前提 |
| **6. 上报** | 必要性：`needs_human`（不可自动善后）→ `ask_human` | 兜底出口 |

#### 资源账本：善后的前提，不是可选

节点必须**声明并记账它持有的资源**（这就是契约里新增的 `resources` 一项）：

```
acquire(resource_id, kind, meta) → 记账
release(resource_id)             → 销账
abandon 时 → 账本即"待释放清单"
```

**没有资源账本，善后就是考古**：只能猜"它可能开了一个进程"。有了账本，善后是查表。
（这与 workspace 里 `miclaw副作用治理-账本票据回收站设计.md` 的"账本 + 票据 + 回收站"是同一套东西，
可以直接复用那套设计，不必另起。）

#### 防递归：清理任务也会卡住

清理任务本身是普通任务，因此它也可能 abandon。**如果它可以再派清理任务，就会无限递归。**

- **深度上限 = 1**：清理任务不再派出清理任务；
- 清理任务到达上限仍失败 → 任务进入 **`NeedsHuman`** 终态 + 高优先级告警，**不再自动重试**；
- 清理任务的资源与副作用同样入账（否则会制造第二层孤儿）；
- 清理任务**豁免准入配额**（这是系统任务，不能被"并发满了"挡在门外），但**有独立预算上限**（防它在清理里再烧一笔大钱）。

#### 与不可变性的关系

**善后任务不得修改已完成节点的产出**，只能隔离或标记。否则"可回溯性"被破坏：
历史被改写，回放就不再成立。善后只能**追加结论**，不能**改写事实**。

## 9. 与 DSH 的映射

| 本设计 | DSH 现成件 | 缺口 |
|---|---|---|
| Program 节点执行 | `ctx.jobs`（句柄 + 增量输出 + `cancel`/`done` + 归属隔离） | 里程碑事件（只有终态） |
| AgentLoop 节点 | agent turn / `subagent`（含 abort + 合成结果） | 中途里程碑上报 |
| 节点完成 → 唤醒任务 | `send(target × wakeup)`（busy→inject / idle→followup） | 生产者粒度是"job 终态" |
| L2 任务日志持久化 | session 事件日志 | 需要"每任务一条日志"而非"一 agent 一条" |
| 图状态持久化 + 冷恢复 | `schedule` 的做法（持久事件 + fold + live 时补跑） | 需照抄该范式 |
| Patch 记账与回放 | session 的可重建事件流 | 需定义 patch 事件类型 |
| 取消四级升级 | `ctx.jobs` 的 `stopping` | 缺 abandon 与级联 |
| Reaper / 善后任务 | `ctx.jobs` 的 teardown + 孤儿告警（官方原话："warns that work may be orphaned instead of deadlocking"） | **把"承认孤儿"升级为"派任务处理孤儿"** |
| 资源账本 | 无 | 需新建（可复用 miclaw 的账本/票据/回收站设计） |
| SA 宿主 | 插件形态（`agent-loop` 是唯一循环，不可 fork） | **Graph Runtime 需要新建** |

**结论：真正要新建的只有一个东西——Graph Runtime（图状态 + patch 记账 + 验证 + tick 调度），
其余全部是复用。** 这与调研的结论一致：异步与持久化的零件齐备，缺的是"显式迁移表 + 记账咨询"这一层。

## 11. 与调研结论的对照

**已被一手证据支持的部分：**

| 设计选择 | 依据 |
|---|---|
| 等待卸载（静默零 token） | 主流 durable 执行全部把等待从算力上摘下（§2 ⑤） |
| 事件日志是唯一真相、上下文是投影 | 事件溯源 + `state = fold(events)`（01 §5） |
| 状态不放在模型里 | Belief-State Engine：部署态 LLM agent 是无 belief 的 history-conditioned policy |
| 编排层零模型调用 | ADK「without consulting an AI model」、LangGraph Workflows/Agents 二分 |
| per-key 串行 | Restate virtual object / DBOS queue key（同一任务的事件严格串行） |
| 补偿而非取消 | Saga + pivot 提交点 |
| FSM 作为能力层 | HEXIS（skill→EFSM，+16.2pp）、SPlanner（EFSM 规划，+28.8pp） |
| 可校验断言而非自报 | 高可信第③支柱「结果真实性」；LlamaIndex/ADK 的 at-least-once 教训 |

**没有论文背书、只能靠工程自证的部分（必须用可执行验收立信）：**

1. **层次 + 并发状态图 + 快照 + Saga 的 LLM 系统性工作** —— 未找到；
2. **actor mailbox 串行化解决 agent 事件乱序** —— 未找到；
3. **Saga/补偿与 agent 副作用回滚的正式工作** —— 未找到；
4. **观测归约（事件→上下文的事前准入）** —— 业界只有事后压缩，无人公开讲过策略；
5. **多层上下文的 L1 有界性** —— 就是本项目最可能翻车的地方，需要用压测数字说话；
6. **"收尸队"式善后（Reaper + 清理任务）** —— 业界做法是**记录孤儿并告警**
   （DSH 原文："warns that work may be orphaned instead of deadlocking"），
   **没有找到把"孤儿"升级为"专门任务去收拾"的公开设计**。这块要么我们首创，要么就得自己写验收。

> 注意第 6 条的性质：它不是学术空白，而是**工程空白**。好处是没人能说我们错；
> 坏处是**没有最佳实践兜底**，只能靠 crash-only 测试和故障注入来证明。

> 这五块恰好是本设计的重量级部分。**它们没有论文可抄，所以验收必须自己写。**
