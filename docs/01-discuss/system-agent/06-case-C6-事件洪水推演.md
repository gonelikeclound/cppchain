# 06 · C6 事件洪水：常驻模式的生死线

> 日期：2026-10-29
> 对象：[`03`](./03-案例推演集.md) C6
> 结论：走通了，**但推翻了 `02` §4.5 的一条断言**（"L0/L1a 必须是纯函数"过强），
> 并发现常驻模式的最大风险不是成本而是**打扰**。

---

## 0. 场景

一台手机，一夜（8 小时，待机 + 轻使用）产生的事件流：

| 来源 | 数量 | 特征 |
|---|---|---|
| 传感器（加速度/光线/接近/步数） | ~2 000 | 高频、无意义、**不该到达 SA** |
| 通知更新（微信/邮件/推送） | ~800 | 中频、**语义相关** |
| 位置变化 | ~400 | 中频、需窗口关联 |
| 网络状态（WiFi/蜂窝/信号强度） | ~300 | 中频、多数无关 |
| 应用前后台切换 | ~200 | 中频、弱相关 |
| 媒体播放状态 | ~100 | 低频 |
| 屏幕开关/解锁 | ~80 | 低频、强相关（人是否在） |
| 电量/充电 | ~50 | 低频、需关联 |
| 蓝牙/外设 | ~30 | 低频 |
| 系统广播（时间变化/包安装/语言） | ~20 | 低频 |
| 用户输入（非语音） | ~20 | 低频、强相关 |
| **来电 / 短信** | **~5** | **低频、绝不可丢** |
| 合计 | **≈ 4 000** | |

其中**真正值得处理的是 3 件**：

- **A**：妈妈发来微信「明天来吃饭吗」（需要回应）
- **B**：电量 15% ∧ 未充电 ∧ 在回家路上（多源关联，见 `03` C5）
- **C**：一个下载完成（有 pending 任务正等着它）

**信噪比 ≈ 1 : 1300。** 这个数字决定了整个架构。

## 1. 结论先行

| # | 结论 |
|---|---|
| **R1** | **`02` 的"L0/L1a 必须是纯函数"过强，要收回。** 纯函数判不了"这条微信要不要回应"。正确约束是**每级的放大倍数上限**，不是"全部纯函数"。 |
| **R2** | 漏斗必须是 **4 级**：L0-a 结构（纯函数）→ **L0-b 廉价语义（有界速率，禁用主模型）** → L1a 任务增强 → L1b 编排唤醒。 |
| **R3** | **不可丢白名单（safety bypass）是一等机制。** 来电/短信/安全告警/支付类，即使不匹配任何订阅也必须进入摘要层。否则一次规则误配就是灾难。 |
| **R4** | **漏报必须可度量**：影子通道抽样 + 事后回收审计，产出 `miss_rate`。没有这个指标，常驻模式就是在赌过滤器永远正确。 |
| **R5** | **常驻模式的真正生死线是"打扰预算"，不是 token 预算。** 每天主动弹 20 次，用户三天就关了它。 |
| **R6** | **触发规则库是常驻模式的核心资产**（G-k）：规则命中是纯函数，模型只负责"填槽"，不负责"决定要不要建任务"。 |
| **R7** | 高频事件源必须**在源侧聚合**（G-l），SA 看到的应是"设备状态变化"而不是传感器流。 |

## 2. 漏斗结构（修正后的四层）

```
4 000 事件/夜
   │
   ├─[L0-a 结构过滤]  纯函数：类型/来源/速率/时间窗/去重
   │      丢弃 ≈ 3 940（98.5%）
   ↓
   60 条（白名单 20 + 结构候选 40）
   │
   ├─[L0-b 廉价语义]  小模型/分类器，**禁用主模型**，有界速率
   │      丢弃 ≈ 50
   ↓
   10 条
   │
   ├─[L1a 任务增强]   命中某任务订阅 → 写 inbox，**不唤醒**
   ↓
   ├─[L1b 编排唤醒]   需改图 → tick 队列，批量合并
   ↓
   3~5 次编排调用/夜
```

### 2.1 为什么要修正 `02` 的断言

`02` §4.5 写的是"L0/L1a 必须是纯函数，否则成本无法收敛"。C6 走下来发现这是**错误的教条**：

- 纯函数能判断"类型是通知且来源是微信"，**判断不了"这条微信要不要回应"**；
- 如果坚持纯函数，那么"要不要回应"就只能丢给 L1b（主模型）——而 60 条候选 × 主模型 = 180k token/夜，**成本反而失控**；
- 真正的解法是**在中间插一个廉价层**：用小模型/分类器做粗筛，把 60 压到 10。

**所以正确的约束不是"纯函数"，而是：**

> **每一级的输入量必须比上一级小一个数量级以上，且每一级的单位成本必须比上一级低一个数量级以上。**

这是"漏斗宽度约束"，它同时对成本和可解释性提出了要求：
纯函数不是目的，**"放大倍数有界"才是目的**。

### 2.2 L0-b 的三条硬约束

| 约束 | 理由 | 验收 |
|---|---|---|
| **禁用主模型** | 否则 60 条就吃掉与编排同级的预算 | 静态检查：L0-b 只允许小模型/分类器路由 |
| **有界速率** | 事件洪峰（如通知风暴）不能击穿 | 令牌桶 + 降级到"只走白名单" |
| **判断结果必须可解释** | 漏报要能归因 | 每条 L0-b 判定产出 `{reason, confidence, model_version}` |

## 3. 三个真事件各走哪条路

这是 C6 最有信息量的部分：**三个事件走了三条完全不同的路**。

### 3.1 A：妈妈的微信「明天来吃饭吗」

| 层 | 判断 | 结果 |
|---|---|---|
| L0-a | 类型=notification ∧ 来源=wechat ∧ **命中"人发来的消息"白名单** | ✅ 通过（白名单不过滤） |
| L0-b | 「是否需要用户回应」→ yes（问句 + 来自联系人） | ✅ 候选 |
| 触发规则 | 命中规则 `人问我问题 → 建 reply 任务` | ✅ **规则命中是纯函数** |
| L1b | 任务模板实例化需要填槽：目标 = "回应妈妈的晚饭问题" | ✅ 唤醒 1 次 |
| 结果 | 建任务 → SA 编排出 reply 图（可能是一个单节点融合图） | — |

**关键点：模型的工作是"填槽"，不是"决定要不要建任务"。** 后者由规则（纯函数）完成，模型只在规则命中后被调用一次。

### 3.2 B：电量 15% ∧ 归途

| 层 | 判断 | 结果 |
|---|---|---|
| L0-a | 电量事件 ✅、位置事件 ✅（都是结构化） | 通过 |
| **窗口聚合** | **确定性状态机**：key=`power_context`，window=15min，条件 `电量<20% ∧ 充电=false ∧ 位置∈归途` | ⚠️ 前两条到达时不触发 |
| 聚合达成 | 第三个条件到达 → 产出合成事件 `context.low_battery_commuting{...}` | ✅ |
| 触发规则 | 命中 `低电+归途 → 建议省电` | ✅ |
| L1b | 编排：一个融合节点（开省电 + 提示） | 1 次唤醒 |

**关键点：关联窗口必须是确定性的**。它有状态（记住刚才见过电量低），但那个状态是**有界缓存**，不是历史。如果关联判断需要模型，那 400 条位置事件就要 400 次调用——直接崩。

### 3.3 C：下载完成

| 层 | 判断 | 结果 |
|---|---|---|
| L0-a | 类型=`download.done` ∧ id 命中活跃任务的 `waits` | ✅ **精确匹配，零歧义** |
| L0-b | 跳过（不需要语义判断） | — |
| L1a | 写进该任务 inbox | 不唤醒 |
| L1b | 该任务需要改图（后续节点） | 1 次唤醒 |

**关键点：精确匹配的事件应该跳过 L0-b。** 否则白白花一次分类调用。
→ 需要 **bypass 通道**：命中活跃任务 `waits` 的事件直接进 L1a。

## 4. 不可丢白名单（safety bypass，R3）

某些事件**无论是否匹配任何规则都不能被静默丢弃**：

| 类别 | 例子 | 处置 |
|---|---|---|
| 人际通信 | 来电、短信、来自联系人的消息 | 必进摘要层（不唤醒也记 digest） |
| 安全 | 权限弹窗、系统错误、异常重启 | 必进摘要层 + 可能唤醒 |
| 财务 | 支付通知、订阅扣费 | 必进摘要层 |
| 健康 | 跌倒检测、心率异常 | 必唤醒 |

**为什么必须独立于订阅机制**：订阅是 SA 配的，SA 会配错。白名单由**平台/用户**定义，SA 无权修改。
这是"被编排者不能编辑编排者对自己的认知"的镜像：**编排者也不能编辑安全底线**。

## 5. 漏报审计（R4）

过滤器是唯一的静默丢弃点。要度量它错没错：

| 机制 | 做法 | 产出 |
|---|---|---|
| **影子通道** | 对被 L0-a 丢弃的事件按 0.5% 抽样（+ 白名单 100%），送 L0-b 复核 | 抽样 `miss` 计数 |
| **回收审计** | 每周回看：用户事后手动处理了哪些事？这些事当年有没有被过滤掉？ | `manual_after_miss` 列表 |
| **反向压测** | 用历史 L1b 唤醒记录，问"若过滤更严，会不会漏掉这条" | 规则边际收益 |
| **no-rule 桶监控** | 多少事件落入"结构通过但无规则命中" | 规则库覆盖率 |

指标：

```
miss_rate = 抽样发现该关注却被丢的事件数 / 抽样总数
阈值：miss_rate > 0.5% → 告警；> 2% → 自动放宽 L0-a
```

**成本上限**：影子通道的复核成本必须 ≤ 编排预算的 5%。抽样率因此是**由预算反推**的，不是拍脑袋。

## 6. 成本账

| 层 | 次数/夜 | 单位成本 | 合计 |
|---|---|---|---|
| L0-a 纯函数 | 4 000 | ≈ 0（微秒级 CPU） | ≈ 0 |
| L0-b 廉价语义 | 60 | ~200 token（小模型） | ~12k token |
| L1a 增强 | 10 | 0 | 0 |
| L1b 编排 | 4 | ~3k token | ~12k token |
| **合计** | | | **≈ 24k token / 夜** |

**反例**：若每条事件都问主模型 → 4 000 × 1.5k ≈ **6M token / 夜**。

> **差 250 倍。** 这就是"漏斗"的全部价值，也是常驻模式能不能上线的分界线。

## 7. 新缺口

### G-k｜触发规则库：常驻模式的核心资产

**问题**：规则从哪来？谁维护？如何演进？

- 规则命中是纯函数（好），但**规则本身是 SA 的产出** → 必须记账、版本化、灰发、可回滚；
- 规则错了的后果是**不对称的**：误报费钱（可接受），漏报丢事（不可接受）；
- 需要**覆盖率指标**：`no-rule 桶 / 总候选`，这个比值上升说明规则库落后于现实。

**建议形态**：

```yaml
rule:
  id: reply-to-question
  match: {type: notification, from: contact, intent: question}
  action: instantiate_template("reply", slots: [sender, topic])
  version: 3
  status: active | shadow | disabled     # 灰发
  stats: {hits, misses, false_positives}
```

**v1 建议**：规则库**只允许人写/审**，SA 可以**提议**新规则（走 patch 记账），但不能自动启用。

### G-l｜事件源侧聚合

若一夜 50 万事件（传感器全开 + 密集网络抖动），L0-a 本身会成为瓶颈。

**解法**：事件源必须声明自己的采样/聚合策略——**SA 看到的应该是"设备状态变化"，不是传感器流**。

```
传感器 → [源侧聚合: 1s 窗口 / 变化检测] → 状态事件（~2000 → ~50）
```

这条与 `02` 的"里程碑词汇表"是同一原则的下沉版本：**归约要尽量靠近源头**。

### G-m｜关联窗口的有界性

窗口状态必须有：key 空间上限、每 key TTL、窗口大小上限。否则"关联"会变成另一条无界历史。

### G-n｜"值得关注"缺可验收定义

常驻模式的验收标准目前是模糊的。建议用**双向指标**：

| 指标 | 定义 | 目标 |
|---|---|---|
| **precision** | 主动处理的事件中，用户认可的比例 | 高（否则烦） |
| **recall** | 该处理的事件中，被处理的比例 | 高（否则漏） |
| 打扰次数 | 每日主动触达用户次数 | 低 |
| `miss_rate` | 见 §5 | < 0.5% |

## 8. 常驻模式的真正生死线：打扰预算（R5）

这是本次推演最反直觉的发现。

**常驻 agent 的失败方式不是"太贵"，而是"太烦"。**

一夜 3 个真事件，如果 L0-b 误判出 20 条候选、每条都问用户，成本可能只有几毛钱，
但**用户三天就会关掉这个功能**。而一旦关了，前面所有架构都不再有意义。

**建议：把"打扰"当作一等资源，与 token 平级做预算。**

```yaml
interruption_budget:
  daily_max: 5            # 每天主动触达上限
  quiet_hours: [23:00-07:00]
  on_exhausted: silent_digest   # 超预算降级为静默记录 + 日报
  priority_override: safety     # 安全类不受限
```

配套：**打扰要计息**——同一件事重复提醒 N 次算 N 次预算；用户忽略过的类型要降权。

> 这条对 `主动智能/` 专题同样适用：主动智能的失败模式几乎都是"打扰过度"，而不是"漏报"。

## 9. 统一纪律：三道拒绝服务

C6 之后，系统里所有"拒绝服务"的点都齐了，纪律收敛为三条：

| # | 纪律 | 含义 |
|---|---|---|
| **D-a 分级** | 每级放大倍数有上限，单位成本递减一个数量级 | 漏斗宽度约束 |
| **D-b 可解释** | 每个丢弃都能回答"为什么丢"（规则 id + 版本 + 理由） | 静默丢弃是缺陷 |
| **D-c 有兜底** | 不可丢白名单 + 抽样复核 + 事后回收审计 | 过滤器可能错，要能发现 |

三处拒绝服务：

| 点 | 挡什么 | 失败方向 | 特有兜底 |
|---|---|---|---|
| **任务分诊**（`05`） | 不需要图的任务 | 多花钱 | fail-open 到多节点图 |
| **L0-a/L0-b**（本节） | 不需要上下文的事件 | **可能丢事** | 白名单 + 影子通道 + 回收审计 |
| **节点 `milestones` 词汇表**（`02`） | 节点内部细节 | 编排信息不足 | 词汇表按接口契约评审 |

**三者是同一个模式：归约（reduction）无处不在，而每次归约都是一次可能出错的丢弃。**

## 10. 验收口径

| # | 验收 | 方法 |
|---|---|---|
| V-1 | 4 000 事件的夜晚，编排调用 ≤ 5 | 计数 |
| V-2 | L0-b 不含主模型路由 | 静态检查 |
| V-3 | 白名单事件 100% 进入摘要层（即使未匹配订阅） | 注入测试 |
| V-4 | 影子通道 `miss_rate` 可计算且低于阈值 | 抽样统计 |

| V-8 | 每条丢弃记录含 `{rule_id, version, reason}` | 日志校验 |

## 12. 一句话

> **洪水不是靠更强的模型挡住，而是靠四个更窄的漏斗口挡住。**
> 每级只把上一级的输出砍掉一个数量级，且单位成本必须更低；
> 砍掉的每一条都要能解释，砍错了要有办法发现；
> 而真正决定这个功能能不能活的，是**用户还愿不愿意被它打扰**。
