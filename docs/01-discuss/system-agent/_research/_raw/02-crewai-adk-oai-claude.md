## CrewAI Flows (crewai 1.15.34；文档 docs.crewai.com/en/… 为 v1.15.34)
**来源**: https://docs.crewai.com/en/concepts/flows.md, https://docs.crewai.com/en/concepts/checkpointing.md, https://docs.crewai.com/en/guides/flows/mastering-flow-state.md, https://docs.crewai.com/en/learn/human-feedback-in-flows.md, https://docs.crewai.com/en/concepts/crews.md, https://docs.crewai.com/en/concepts/planning.md, https://docs.crewai.com/en/concepts/memory.md, https://docs.crewai.com/llms.txt

1. **控制流单元**: 装饰器标记的普通 Python 方法 + 事件发射驱动。`@start()` 标入口（可无参、可 `@start("method_or_label")` 门控、可传 callable 条件）；`@listen()` 挂到某个方法/路由器标签上，“will be executed when the specified task emits an output”（原话）；`@router()` 返回 `Literal[...]` 字符串标签来分支；`or_` / `and_` 做多源聚合（`or_`：`listen` 任一上游发射即触发）。文档明说 Flows 是 “structured, event-driven workflows”，“Built on an event-driven model”。无显式 `emit()` API —— 发射物是方法的返回值。
2. **工具/异步与“稍后回来”原语**: **有，但只服务于人类反馈**。`@human_feedback`（需 CrewAI ≥1.8.0）默认阻塞等控制台输入；用 `provider=` 传自定义 `HumanFeedbackProvider` 时，provider 里 `raise HumanFeedbackPending(context=..., callback_info=...)`，此时 “The flow framework **automatically persists state** when `HumanFeedbackPending` is raised”，`kickoff()` **返回** `HumanFeedbackPending` 对象而非抛异常；之后 `ReviewFlow.from_pending(flow_id)` → `flow.resume(feedback)` / `await flow.resume_async(feedback)` 续跑。相关类型：`HumanFeedbackPending`、`PendingFeedbackContext`（含 `flow_id`/`flow_class`/`method_name`/`method_output`/`emit`/`default_outcome`/`llm`/`requested_at`）、`ConsoleProvider`。**任意工具调用/AI 调用没有通用的 pending 原语**；异步只有 `kickoff_async`/`akickoff`（同一进程内并发，不是挂起后跨进程恢复）。
3. **持久化与重启恢复**: **两套互斥系统**。
   - `@persist`（`crewai.flow.persistence.persist`）：类级=每个方法执行后存；“Class-Level Persistence: … saves state after every method execution”。默认后端 `SQLiteFlowPersistence`。恢复二义明确区分：`kickoff(inputs={"id": <uuid>})` = **resume**（“load the latest snapshot … and continue writing under the same `flow_uuid`. The history extends”）；`kickoff(restore_from_state_id=<uuid>)` = **fork**（“hydrate the new run's state from it, and assign a fresh `state.id`”）。二者与 `from_checkpoint` 互斥（同时给 `ValueError`）。保存内容 = 你的 state（Pydantic `BaseModel` 或 dict）+ 自动 `id`；方法完成情况也有记录（state 指南：“During resume, listeners continue from prior checkpoints; cycle/router branches honor resumption flags”）。
   - **Checkpointing**（`crewai.CheckpointConfig`）：事件驱动快照，`crew.kickoff(from_checkpoint=...)` / `Crew.from_checkpoint(CheckpointConfig(restore_from="./.checkpoints/…json"))`。保存内容原话：“the full state of the crew, flow, or agent — configuration, agent memory and knowledge sources, task progress, intermediate outputs, internal state and attributes — alongside the kickoff inputs, the event history up to that point, and a lineage ID”。`on_events` 默认 `task_completed`（也可 `llm_call_completed`）；provider `JsonProvider`/`SqliteProvider`，`max_checkpoints` 裁剪。明确不恢复：lambda/闭包/bound method/`functools.partial`、callable guardrails、`@before_kickoff`/`@after_kickoff`（除非 `CREWAI_DESERIALIZE_CALLBACKS=1` 且是模块级函数点路径）。自动 checkpoint 写入 best-effort（失败只记日志），手动 `state.checkpoint()` 才 re-raise。
   - 另有统一 `Memory` 系统（LanceDB 落盘 `./.crewai/memory`，`StorageBackend` protocol 可换），与 flow 状态是不同层。
4. **关键路径上的 LLM 调用 / 确定性路径**: **确定性路径存在且是默认写法**。Flow 方法是普通 Python，不调 LLM 就只有你的代码（官方示例里 LLM 是用户自己 `litellm.completion(...)` 显式调用）。Crew 路径则必然过模型：`Crew(planning=True)` 会 “all Crew data is sent to an AgentPlanner that will plan the tasks and this plan will be added to each task description”；`PlanningConfig` 有 `"low"`（“A heuristic check with no extra LLM call”）/`"medium"`/`"high"` 三档，可调低以减 LLM 调用。所以：**Flow 编排 = 确定性；Crew kickoff = LLM 驱动；混合由开发者选择**，但框架不为你保证“编排层零模型调用”的抽象（因为你写的就是 Python）。
5. **谁管状态**: **框架托管，且在 Flow 对象上强绑定**：`self.state`（自动注入 UUID `id`，支持 `Flow[MyState]` 泛型 Pydantic 或 `Flow[dict]`），持久化默认 SQLite；Crew/Agent 侧由 Checkpointing 快照整个运行时对象图。模型不拥有状态，只看到被塞进 prompt 的文本。
6. **一句话定性 + 直接引文**: **“用户写的 Python 事件流 + 框架提供的状态容器与快照”，最成熟的‘稍后回来’是 human-feedback 通道，不是工具通道。** 引文：`@listen()` “will be executed when the specified task emits an output”；“The flow framework **automatically persists state** when `HumanFeedbackPending` is raised”；“`restore_from_state_id` … assign a fresh `state.id`”。
**未能证实**: `/concepts/persist.md`、`/concepts/human-feedback.md`、`/concepts/router.md` 三个路径不存在（HTTP 200 但返回的是文档首页内容，属站点 fallback，非真实页面）——相关内容在 `/concepts/flows.md` 与 `/learn/human-feedback-in-flows.md` 中；未找到任何“工具调用可中途返回并在任意后续事件恢复”的通用原语；未找到 Flow 级 `invocation`/`step checkpoint` 的公开 API 名称（只有 `state.checkpoint()`）。

## Google ADK (google-adk 2.13.0；docs 域名 adk.dev，google.github.io/adk-docs 重定向至 adk.dev)
**来源**: https://adk.dev/agents/workflow-agents/index.md, https://adk.dev/agents/workflow-agents/sequential-agents/index.md, https://adk.dev/agents/workflow-agents/loop-agents/index.md, https://adk.dev/runtime/resume/index.md, https://adk.dev/runtime/event-loop/index.md, https://adk.dev/events/index.md, https://adk.dev/sessions/index.md, https://adk.dev/sessions/session/index.md, https://adk.dev/sessions/state/index.md, https://adk.dev/tools-custom/function-tools/index.md, https://adk.dev/tools-custom/confirmation/index.md, https://adk.dev/llms.txt

1. **控制流单元**: 三类**模板工作流 Agent** —— `SequentialAgent`（`sub_agents=[...]` 顺序）、`ParallelAgent`（并行）、`LoopAgent`（`sub_agents=[...], max_iterations=5`，或由子 agent 发终止信号）。它们本身**不调模型**：“determine the execution sequence according to their type, such as sequential, parallel, or loop, **without consulting an AI model** for assistance with the orchestration”。子 agent 之间通过 state 的 **Output Key**（`output_key`）传值。**注意换代**：文档明写 “Starting in ADK 2.0 for Python and Go, template workflows have been superseded by … graph-based workflows (`/graphs/`) and dynamic workflows”，有 `/graphs/index.md`、`/graphs/human-input/`、`/graphs/routes/`。
2. **工具/异步与“稍后回来”原语**: **有，且是 ADK 的核心机制之一**。`LongRunningFunctionTool(func=...)`：模型调用后你的函数只做发起 + 可选返回 initial result（如 operation id），框架把它包进 `FunctionResponse` 回给模型，然后 “the agent run is ended / paused”；客户端轮询进度后把 intermediate/final response 发回，进入下一次 run。文档明确边界：“designed to help you start and *manage* long running tasks … but ***not perform*** the actual, long task”。工具级人工确认：`FunctionTool(reimburse, require_confirmation=True)`（Python/Go/Java）或 Kotlin `@Tool(requireConfirmation=true)`；确认请求走一个 `adk_request_confirmation` 的 `FunctionCall` 事件，resume 时把 `function_response` 里 `confirmed: true` 回给同一 `function_call_id`。事件循环本身是 `Runner` ↔ agent 的异步生成器 `async for event in agent.run_async(ctx)`，`Runner` 每拿到一个 event 就 `session_service.append_event` 提交再向上 yield。
3. **持久化与重启恢复**: **两层，都有一手支持**。
   - 常规：`SessionService` 持久化会话（event 历史 + `state`）。实现有 `InMemorySessionService`（“Persistence: None. **All conversation data is lost if the application restarts.**”）、`DatabaseSessionService(db_url="sqlite+aiosqlite:///./my_agent_data.db")`（需 `pip install google-adk[db]`，支持 PostgreSQL/MySQL/SQLite，Python/Go 标注 v0.1.0 起）、`VertexAiSessionService`（走 Agent Runtime）。
   - 崩溃恢复：`App(..., resumability_config=ResumabilityConfig(is_resumable=True))`，Python 自 v1.16.0 起。恢复靠 `invocation_id`：`runner.run_async(user_id=..., session_id=..., invocation_id='invocation-123')` 或 REST `POST /run_sse` 带 `invocation_id`。原理原话：“The Resume feature works by logging completed Agent workflow tasks, including incremental steps using Events and Event Actions”；各模板 agent 分别读 `current_sub_agent` / `times_looped` 决定从哪继续；**已成功返回的工具结果被重放，失败的重新执行**——“the Resume feature ensures that the Tools in an agent are run ***at least once***, and may run more than once”，故有副作用的工具需自己去重。限制：恢复前不要改工作流；Custom Agent 需自己实现 `BaseAgentState` 步骤 + `end_of_agent=True`；Web UI/CLI 不支持恢复。
4. **关键路径上的 LLM 调用 / 确定性路径**: **明确支持“确定性路径从不碰模型”**。三个模板 workflow 页逐页复述同一句：SequentialAgent / LoopAgent 的 “execution … is not controlled by an AI model, and is deterministic in how it executes its sub-agents. The sub-agents within the defined loop may or may not utilize AI models”。即：**编排层（Sequential/Parallel/Loop、graph）零模型调用；只有 `LlmAgent` 是模型路径**。
5. **谁管状态**: **框架（SessionService）托管，且分层作用域**。`Session.state` 是 key→value dict，前缀即作用域：无前缀=本 session、`user:`=跨该用户所有 session、`app:`=跨全应用、`temp:`=单次 invocation 内（父子 agent 共享同一 invocation）。写入通过 `EventActions.state_delta` 提交；`LlmAgent` 的 `output_key` 把模型输出写进 state；prompt 里用 `{key}` 模板注入。模型仍不直接拥有状态：它只看到被注入 instruction 的那部分。
6. **一句话定性 + 直接引文**: **event-loop 运行时 + 显式分区状态存储；“确定性编排 / 模型决策”分工最清楚，且唯一提供 `LongRunningFunctionTool` 这种官方“工具跑到一半就结束本次 run”原语的框架。** 引文：“without consulting an AI model for assistance with the orchestration. This approach results in deterministic and predictable execution patterns.”；“the agent run is ended / paused”；`ResumabilityConfig(is_resumable=True)`；`Runner` 侧 “Commits state/artifact deltas etc.”
**未能证实**: 旧路径 `/agents/workflow-agents/{sequential,parallel,loop}.md` 与 `/sessions/session-services.md` 均 HTTP 404（正确路径是 `*-agents/index.md`，session service 列表在 `/sessions/session/index.md`）；未找到 `ResumabilityConfig` 在中文/更细字段上的说明（只证实 `is_resumable` 一个字段）；未找到“工具中途返回后可无限期挂起跨天恢复”的保证（`LongRunningFunctionTool` 的暂停点是“本次 run 结束”，需客户端再次发起 run）。

## OpenAI Agents SDK (Python, openai-agents 0.24.0；文档 openai.github.io/openai-agents-python)
**来源**: https://openai.github.io/openai-agents-python/results/, https://openai.github.io/openai-agents-python/running_agents/, https://openai.github.io/openai-agents-python/human_in_the_loop/, https://openai.github.io/openai-agents-python/sessions/, https://openai.github.io/openai-agents-python/tools/, https://openai.github.io/openai-agents-python/llms.txt

1. **控制流单元**: **没有声明式控制流单元（无 `@start`/`@listen` 类，无 graph/DAG 原语）**。控制流 = 一个固定 agent loop + 三个分支事件：`final output` / `handoff` / `tool calls`。循环原话：“The runner then runs a loop: We call the LLM for the current agent… If the runner classifies the LLM's output as final output, the loop ends… If the LLM requests a handoff, we update the current agent and input, and re-run the loop. If the LLM produces tool calls, we run those tool calls, append the results, and re-run the loop.” 终局判定：“it produces text output with the desired type, and there are no tool calls”。超 `max_turns` 抛 `MaxTurnsExceeded`（`max_turns=None` 关闭）。多 agent 协作靠 `handoff`（换 agent 继续同一循环）与 `Agent.as_tool()`（嵌套 run）。
2. **工具/异步与“稍后回来”原语**: **有，而且是最完整的一档**。审批中断：工具声明 `needs_approval=True` 或给一个 async 判定函数（“The callable receives the run context, parsed tool parameters, and the tool call ID”；参数不可安全解析时 **fail closed** 走人工审批）。命中后 “execution pauses, and `RunResult.interruptions` (or `RunResultStreaming.interruptions`) contains `ToolApprovalItem` entries with details such as `agent.name`, `tool_name`, and `arguments`”。恢复：`result.to_state()` → `state.approve(interruption)` / `state.reject(...)` → `Runner.run(agent, state)`。可 sticky：`always_approve=True`/`always_reject=True`，且随 `RunState` 序列化存活。可混合多类型（function tool / hosted MCP 审批 / 嵌套 `Agent.as_tool()` 审批），部分批准后再跑，剩下的仍留在 `interruptions` 里继续暂停。另有 `RunState.add_input()` 在两次 model call 之间注入新用户输入。异步工具：`@tool(timeout=2.0, timeout_behavior="error_as_result"|"raise_exception")`（“Timeout configuration is supported only for async `@function_tool` handlers”），`failure_error_function` 控制错误回喂模型。另有 `Agent.as_tool(..., needs_approval=...)`、`ShellTool`、`ApplyPatchTool`、`MCPServerStdio/Sse/StreamableHttp(... require_approval=...)`、`HostedMCPTool(tool_config={"require_approval": "always"})`。
3. **持久化与重启恢复**: **有 `RunState`，可序列化、可跨进程恢复 —— 这是关键**。序列化：`state.to_json()` / `state.to_string()`，反序列化 `RunState.from_json(...)` / `RunState.from_string(...)`；文档强调 “RunState is designed to be durable. Use `state.to_json()` or `state.to_string()` to store pending work in a database or queue and recreate it later”。`RunState` 携带：审批决定、pending 工具调用与参数、sticky 决定（含 per-call scoping by call ID）、累积的 tool guardrail 结果、`pending_input`、选中的 agent（handoff 后）。带工具输出的 Pydantic/dataclass 会被结构化序列化（tuple 经 JSON 往返变成 list）。还有 “crash 后 Session 写失败” 的对账机制：用同一个 `RunState` + 原 `Session` backend/`session_id` 重试，SDK 会核对 history 尾巴，“does not execute completed tools, tool guardrails, hooks, or handoffs again”；不匹配则 `UserError` **fail closed**；若终局输出已被接受后才写盘失败，则标记 `RunState` 不可恢复，后续重试全部 `UserError`。安全边界明确：`from_json` “do not authenticate the snapshot”，只能从可信存储反序列化，浏览器侧只发不透明 id，快照留服务端。会话历史另有三套互斥机制：client-managed `Session`（`SQLiteSession` / `AsyncSQLiteSession` / `RedisSession` / `SQLAlchemySession`）、server-managed `conversation_id` / `previous_response_id` / `auto_previous_response_id`；`RunResult.last_response_id` 可回填 `previous_response_id` 续链。
4. **关键路径上的 LLM 调用 / 确定性路径**: **框架内没有确定性编排层**。llms.txt 全量索引中对 graph/DAG/workflow 编排原语检索为 0 命中；每次 `Runner.run` 都是 model→(tool|handoff)→model 循环，模型在环内。确定性只能由**应用代码**顺序多次调用 `Runner.run(...)`、或用 `Agent.as_tool()` 把子 agent 当函数调——即“确定性来自宿主程序，不来自 SDK 原语”。
5. **谁管状态**: **三层，边界最清楚**。① 应用上下文：`RunContextWrapper`（进程内，可 sticky 存审批决定）；② 会话历史：client-managed `Session`（SDK 落盘）或 server-managed（`conversation_id`/`previous_response_id`，OpenAI 侧保管）；③ 暂停中的执行：`RunState`（应用负责序列化与存储）。模型侧只有 Responses API 的 input items；`to_input_list()` / `to_input_list(mode="normalized")` 负责把 run 折叠成下一轮 input。
6. **一句话定性 + 直接引文**: **“固定 while 循环 + 可序列化 RunState”的极简主义：没有编排 DSL，但把“暂停—存盘—跨进程恢复—幂等对账”做成了第一等公民。** 引文：“The runner then runs a loop”（后接四条分支）；“`RunState` is designed to be durable. Use `state.to_json()` or `state.to_string()` to store pending work in a database or queue”；“`RunResult.interruptions` … contains `ToolApprovalItem` entries”；“do not authenticate the snapshot”。
**未能证实**: 未找到 `RunState` 的 schema/字段级完整清单（只能从行为描述归纳）；未找到“一个普通（非审批）工具调用可以中途返回、之后恢复”的机制——所有 pending 语义都绑定在**审批中断**与 `add_input()` 上，没有 ADK `LongRunningFunctionTool` 那样的“工具主动挂起”。`/sessions/` 页面 title 为 “Overview”，页面内 H1 为 Sessions（属站点版式，不影响内容）。

## Anthropic Claude Agent SDK (Python SDK 0.2.176；文档已迁至 code.claude.com/docs/en/agent-sdk/…)
**来源**: https://code.claude.com/docs/en/agent-sdk/overview.md, https://code.claude.com/docs/en/agent-sdk/agent-loop.md, https://code.claude.com/docs/en/agent-sdk/hooks.md, https://code.claude.com/docs/en/agent-sdk/sessions.md, https://code.claude.com/docs/en/agent-sdk/permissions.md, https://code.claude.com/docs/en/agent-sdk/subagents.md, https://code.claude.com/docs/en/agent-sdk/python.md, https://code.claude.com/docs/en/hooks.md

1. **控制流单元**: **没有声明式单元；控制流 = Claude Code 的 agentic loop 本体**。五步原话：“1. Receive prompt… 2. Evaluate and respond… 3. Execute tools… 4. Repeat. Steps 2 and 3 repeat as a cycle. Claude continues calling tools and processing results until it produces a response with no tool calls. 5. Return result.”。消息类型：`SystemMessage`(subtype `init`)、`AssistantMessage`、`UserMessage`、`ResultMessage`（含 `stop_reason`、`total_cost_usd`、`session_id`）。对 SDK 使用者的“控制流钩子”是 **hooks**，不是装饰器。可调旋钮：`max_turns`/budget、`effort`、`permission_mode`、`model`。并行：同一 turn 内多个工具调用，只读工具可并发，改状态的（`Edit`/`Write`/`Bash`）串行；自定义工具默认串行，靠 MCP 注解 `readOnlyHint` 才并发。
2. **工具/异步与“稍后回来”原语**: **有，而且是唯一提供“真的把工具调用留在 transcript 里、退出进程、之后 `--resume` 重放”的框架**。机制在 `PreToolUse` hook 的 `permissionDecision: "defer"`：“The tool doesn't execute. The turn ends with a result carrying `stop_reason: "tool_deferred"`, and the pending tool call stays in the transcript.”；SDK result 里带 `deferred_tool_use`（`id`/`name`/`input`）；调用方拿答案后 `claude -p --resume <session-id>` 重启，同一工具调用**再次触发** `PreToolUse`，这次返回 `"allow"` + `updatedInput` 携带答案，工具才执行。“There is no timeout or retry limit. The session remains on disk until you resume it”（仅 `cleanupPeriodDays` 30 天保留影响）。限制明确：**只在非交互 `-p` 模式生效**；**只在单个 turn 只有一个工具调用时生效**（批内多调用会被忽略并警告，理由：“resume can only re-run one tool”）；工具消失时 resume 首条 result 为 `stop_reason: "tool_deferred_unavailable"` + `is_error: true`。另一条权限通道 `can_use_tool`（Python `ClaudeAgentOptions(can_use_tool=...)`，TS `canUseTool`）：仅在权限流走到“需要询问”时被调用，`CanUseTool` 收到 `tool_use_id`；但它是**进程内异步回调**，不是持久挂起。
3. **持久化与重启恢复**: **会话级持久化极完备（进程重启可恢复），但工具级“半成品调用”的持久恢复只有 `defer` 这一条路**。会话：SDK 自动写盘，“Claude Code stores sessions under `~/.claude/projects/<encoded-cwd>/*.jsonl`”（非字母数字字符替换为 `-`；可用 `CLAUDE_CONFIG_DIR` / `CLAUDE_CODE_PROJECT_DIR_NAME` 改）。三种入口：`continue_conversation=True` / `continue: true`（取 cwd 下最近一个会话，无需 id）、`resume=<session_id>`（指定会话）、`fork_session(session_id, ...)` → `ForkSessionResult.session_id`（复制历史开新会话，原会话不变；fork 不含 file checkpoint，不能回退到 fork 前 checkpoint）。工具：`list_sessions()` / `get_session_messages()` / `rename_session()` / `tag_session()`。可关：TS `persistSession: false`；Python 用 `CLAUDE_CODE_SKIP_PROMPT_HISTORY`。跨机：`session_store`/`sessionStore` 适配器镜像 transcript，或直接搬 `.jsonl`。**明确边界**：“Sessions persist the **conversation**, not the filesystem”——要回滚文件得用 file checkpointing。
4. **关键路径上的 LLM 调用 / 确定性路径**: **编排层不存在，所以“确定性路径”= hooks + permissions 这两层，它们是纯代码、零模型调用；但主循环本身永远过模型**。hooks 是确定性回调解确切点位；权限判定是 6 步固定序列（hooks → deny 规则 → ask 规则 → permission mode → allow 规则 → `canUseTool`，文档给出完整顺序，并有 `CLAUDE_SDK_CAN_USE_TOOL_SHADOWED` 警告说明某些配置下回调根本不被调用）。多 agent 的确定性编排靠宿主程序/`Agent` 工具，不在 SDK 内核。
5. **谁管状态**: **SDK/CLI 进程拥有 transcript（磁盘 `~/.claude/projects/…/*.jsonl`），应用只持有 `session_id` 与可选 `session_store` 适配器**；上下文窗口管理（auto-compaction）也归 SDK（`PreCompact`/`PostCompact` hook 可介入）。模型侧上下文由 SDK 组装。文件系统状态**不在**会话里。
6. **一句话定性 + 直接引文**: **“把半个成熟 CLI 当作库”：主循环是模型驱动不可改，但用 hooks 在生命周期点位注入确定性代码，并用 `defer` 实现了别家都没有的‘工具调用级持久挂起’。** 引文：“`"defer"` ends the turn so the tool can be resumed later”；“The session remains on disk until you resume it”；“Sessions persist the **conversation**, not the filesystem”；hooks “By default, the agent waits for your hook to return before proceeding.”（异步输出 `{"async": true}` 则 agent 立即继续，“Async outputs can't block, modify, or inject context”）。
**未能证实**: `https://docs.claude.com/en/api/agent-sdk/overview` 等旧路径 HTTP 200 但 302 到 `code.claude.com/docs/en/agent-sdk/overview`（我按最终 URL 引用）；未找到 `hooks` 中除 `PreToolUse` 之外任何“可 pause 等外部事件”的机制——`can_use_tool` 是异步回调，`async: true` 的 hook 明确“can't block”；未找到“用户中途 kill 掉进行中的 Bash/Edit 后从该工具内部继续（保留部分副作用）”的能力，`defer` 是在工具**执行前**拦下；Python SDK 无 `SessionStart`/`SessionEnd` hook（文档标注 “Session hooks not available in Python”）。

## 横向对照（承载上面五问的差异点）

| 维度 | CrewAI | ADK | OpenAI Agents SDK | Claude Agent SDK |
|---|---|---|---|---|
| 控制流单元 | `@start`/`@listen`/`@router`/`or_`/`and_`（你自己的 Python 方法） | `SequentialAgent`/`ParallelAgent`/`LoopAgent`/graph | 无（单一 agent loop + handoff/tool 分支） | 无（Claude Code agent loop；hooks 是注入点） |
| 工具中途返回 | 仅 `@human_feedback` + `HumanFeedbackPending`/`from_pending`/`resume` | `LongRunningFunctionTool`：run 结束，客户端回 `function_response` | 仅审批中断：`needs_approval` → `interruptions` → `RunState` | `PreToolUse` 返回 `"defer"` → `stop_reason: tool_deferred` → `--resume` |
| 重启恢复 | `@persist` + `kickoff(inputs={"id"})` / `restore_from_state_id`；`CheckpointConfig`/`from_checkpoint` | `SessionService`（`DatabaseSessionService` 等）+ `ResumabilityConfig(is_resumable=True)` + `invocation_id` | `RunState.to_json/from_json`、`to_string/from_string` + `Session` | `~/.claude/projects/<cwd>/*.jsonl` + `resume`/`continue_conversation`/`fork_session` |
