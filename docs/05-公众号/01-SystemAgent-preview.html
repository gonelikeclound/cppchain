SYSTEM AGENT · 工程实践

让 984 条事件只唤醒系统 5 次

—— 一个 SystemAgent 从概念到落地的完整实践

这次聊聊一个叫 SystemAgent（系统代理） 的东西。

它研究的不是「让大模型处理一切」，而是一件更务实的事：大模型到底该在什么时候出现。

这是我在一个用 C++26 从零构建的 Agent 框架学习项目（简化复刻 langchain / langgraph，一切观点都要有可运行 demo 验证）里做的一个完整专题：二十余轮研讨、十余个里程碑、1113 个测试全绿，最终落地成一个既能「一句话生成编排图并执行」、又能「常驻系统处理事件洪峰」的系统级 Agent。

本文记录它从一句话概念到可运行验证的全过程——包括所有我们如实写下的「诚实边界」。

01｜夜里的四千条事件

先从一个数字说起。

一份终端设备的样本里，一个夜晚大约产生 4000 条事件：传感器读数、群消息、系统告警、媒体播放……其中真正需要系统（或人）回应和处理的，一只手数得过来。

假如你的「智能助手」真的做到了 7×24 常驻，并且对每一条事件都认认真真地调用一次主模型——

账是这样算的（参考推演）：一个夜晚上约 600 万 token。除了 250 倍的计算浪费，更致命的是注意力被稀释——你留给真正紧急事件的那个「注意力窗口」，被一大片噪声事件共用。告警疲劳，1:1300 的信噪比，就是这么来的。

所以真正的问题不是「大模型能不能处理一切」，而是：它该在什么时候出现。

这个问题的答案，就是 SystemAgent。

02｜把 LLM 请下「关键路径」

主流 Agent 长什么样？一个 ReAct 循环：观察 → 思考 → 行动 → 再观察。循环的每一步都可能调用模型——模型站在每一次状态跃迁的关键路径上，每动一下都要过一遍模型。

SystemAgent 提供的是另一种形状：

事件 → 状态跃迁 →（仅在声明的接缝处咨询模型）→ 新状态 → … → 终态

它与循环式 Agent 的核心差异，不是「事件驱动 vs 循环」——而是谁站在每次跃迁的关键路径上：

  • 确定性跃迁完全交给机器推进（状态机、规则、预编排 DAG）；
  • LLM 从「每次跃迁必经」的瓶颈，降级为「显式 gate 上被咨询的专家」。

打个比方：循环式 Agent 像一位接线员，每条连线都要经他手转；SystemAgent 像一位顾问——只在系统声明好的那几个「接缝」被请出来，问完就走，剩下的流程系统自己走完。

我们还给它立了两条硬约束：

  • SA 只编排，不执行——它的动作只作用于编排图本身，不直接染指领域执行（安全不变式 I1）；
  • LLM 只出现在声明的接缝——不在声明处，系统不该唤醒它，也不该让它隐形地介入。

03｜三个「空白原语」

带着这套思路去业界找底座，发现几乎找不到现成的原语。缺的是三样东西：

原语含义
显式迁移表把状态机的状态与转移显式写出来——确定、可预校验、可回放；
可记账的 LLM 咨询每次咨询模型都能记账：为什么问、花了多少 token、结果如何、发生在哪一步；
咨询期间进程可死等模型答复的那段时间里，正在跑的编排不能被卡死——要能挂起、恢复、甚至被杀掉重启。

一个很有意思的观察：业界方案普遍「三选二」——有显式迁移表的，通常没有真正可记账的模型咨询；能认真咨询模型的，又往往没有显式迁移表；至于「咨询等待期进程可死」，几乎没人做。

我们 v1 决定先走最小闭环：状态机（B）+ 咨询（D），先把「显式迁移表」和「可记账咨询」这两样打通。

04｜SystemAgent 不是一个 agent，而是一组 agent

开题第一轮就有一个重要拍板：SystemAgent 不是一个 agent，而是一组 agent。

事件 ─► 核心 agent（编排者）—— 分诊 / 选域 / 编排拓扑 / fallback
            │ handoff / Send / 子 workflow / 问人
    ┌───────┼───────┐
    ▼       ▼       ▼
 电话域    消息域    更多领域
 (能力+FSM) (能力+FSM)
    └───────┴──┬────┘
       工具都指向 mock 世界
  • 核心 agent：负责分诊、编排、跨域协调。它不做事，只决定「谁来做、怎么做、做不了怎么办」；
  • 领域 agents：各自持有一个领域的能力与状态机（电话域的拨号 FSM、消息域的发送……），像封闭的 ReAct 循环，只上报终态与里程碑；
  • 所有工具指向一个 mock 世界 libsamock.so（后面细说）。

这个形态让我们能直接复用项目里已有的多智能体原语：agent loop / subagent / Send / handoff / 子 workflow。整副骨架，两天之内就搭了出来。

05｜第一个可运行的闭环：mock 世界、假电话、语义层守门员

项目规矩是「问题 + demo 驱动」：每个论点都要有能跑的东西验证，不写空头方案。所以第一步，是把「世界」mock 出来。

mock 世界 libsamock.so，一个独立的动态库，装下三样东西：

  • 世界模型 + 三诚实度。世界台账只追加、绝不撒谎；但 agent 可以被做成「诚实的 / 撒谎的 / 半真半假的」三种——专门用来验证一件事：断言只看世界，不看 agent 的自述。agent 说「我做完了」不算，世界说算的才算；
  • 假电话 FSM。每次拨号是一个 Session，状态由剧本纯派生——没有后台线程、完全可回放、逐字节确定。里程碑事件（拨号 / 振铃 / 拒接 / 接通 / 挂断）在状态跳变时原子发一次；还留了一个控制平面 barge_in，专门注入用户的「改口」；
  • 虚拟钟。用工具推进的模拟钟，确定性从 0 起步——跑一段编排，不需要真的等 27 秒。

第一个完整故事（C7 简版）。给妈妈打电话：拨号被拒 → 自动重拨 → 接通 → 用户改口「去微信说」→ 核心把话改道到消息域 → 消息送达世界。24 条断言全绿，最得意的几条：

  • 世界终态正确（通话 ended、原因 user_redirected、消息已送达）；
  • 里程碑全序恰好 7 条；虚拟钟停在 27 秒（零真实等待）；
  • 最关键的一条：核心模型全程只被咨询了 2 次——拒接、振铃、自动重拨这些「容易被吵醒」的活儿，全由电话域自己的状态机悄悄地干完了。

语义层守门员（sa_guard）。接着是一条「不信任模型、只做校验」的路：把 SA 语义层做成纯函数校验器，七条不变式 I00–I07——未知 agent、幻觉工具、核心只读、分诊目标、里程碑词汇表、预算、任务断言。对撞面的效果很直接：

  • 单元自检：12 条坏编排（幻觉工具、越域、预算超限、循环迹象……）必须条条被拒；
  • 集成过检：S2 的真实轨迹走完整验证链，白名单取自实际部署注册表——防漂移；
  • 运行时对抗：给系统弹一把「幻觉工具」，看它会不会被拦住——ToolNode 既有的失败关闭机制把 unknown tool 错误顶回去：咨询不被中断，世界零污染。

这套分工后来一直沿用：「验证器负责审，ToolNode 负责挡。」

06｜让编排看得见：UI、浏览器触发、E2E

到这里，系统从「能跑」变成「能看」了。

SA 专用编排台。一个自包含的单文件页面：左右两栏，左边是任务列表（用户的话 + SA 的回传 + 用户补充），右边上半是 DAG 节点图、下半是消息流，中间分隔条可以拖。点一个节点，下方消息按它筛选——编排在哪儿、每一跳发生了什么，全部肉眼可见。

浏览器真触发。页面上的「▶ 运行 demo」不是假演示——它真的经过一个 CGI 薄壳去 spawn 一个 demo 进程、真跑一遍、把结果写回 JSON 历史。

「太快了，看不到执行过程」→ 真·慢放。mock 毫秒级跑完，是幸福的烦恼，但我自己都看不过来。于是做成后端真慢跑 + 前端轮询逐节点点亮：默认 300ms/步，约 6 秒走完整个编排——你能看到「用户 → 核心分诊 → 电话域拨号 → 拒接/重拨/接通 → 改口 → 消息域送达 → 世界断言」像心电图一样一路点亮。

E2E 闭合。再做三阶段端到端脚本：A 静态 HTTP（页面骨架 + 数据契约）/ B CGI 运行整路（真实回执 + 磁盘产物 + 确定性数值贯通）/ C headless Chrome 真实点击「运行 demo」按钮走到「运行完成」。顺带一个彩蛋级断言：生成的任务日志与内置样例逐字节等价——任何两次同源运行，多一个字节都不差。

07｜一句话，变成一张能跑的 DAG

做到第 6 轮，我原以为 SA 的活儿是「运行 DAG」。然后被自己纠正了：SA 的核心不是跑 DAG，而是生成 DAG——用户给一句话，系统吐出一张编排图，再把它跑起来。

于是规划层接上真机模型（deepseek-flash，这个项目「够用就不上大模型」）：

一句话 ─► Planner(LLM) ─► 受限 IR ─► P00–P29 静态校验 ─► 通用解释器执行
                │                    │  不合法 → 回喂重试 ≤3 → 仍不过拒跑
                └────────────────────┘  （fail-closed）
  • Planner 只产出受限 IR（角色、边类型都有白名单），解析还能容忍 ```json 围栏和前后解释文字；
  • P00–P29 纯函数静态校验：恰好 1 个 user / 1 个 world、域节点必须有核心的 dispatch、无环、所有节点都在 user→world 路径上……不合法就把问题回喂模型重试，三次仍不过直接拒跑——宁可不做，不做错的；
  • 校验通过后，一个通用解释器按拓扑序把图跑起来：电话域的 FSM 拨号 / 重拨 / barge_in、消息域的 send_message、world 节点的断言逐项查。

实测：「给妈妈打电话，拒接再打一次，改口就发微信」→ 模型吐出 6 节点/6 边的图 → 执行完成，16 条消息、7 个里程碑、虚拟钟 27 秒。换成「只发微信」，图缩成 4 节点直路。同一个确定性执行器，只换上面那张图，行为就跟着图的形状变了。

这一轮还顺带把「任务历史」做成了正经功能：留痕、持久删除、下载、单运行锁（两个标签页同时点运行，后者会明确拿到「已有一次运行在进行」）。

08｜会算数、会读文件、会看天气

规划出来的图要能「真的干活」，就得接真实工具。我们建了一个工具目录：默认 17 个只读工具——计算器、时间、文件五件套（读 / 列目录 / 搜索 / 抽样本 / 采样）、旅行数据库只读五件、天气、arXiv 检索、抓网页、读图；开启副作用开关后，再加上写文件、提交结果、执行命令，共 20 个。

几个实测瞬间：

  • 「算一下 (23*7+5)/2」→ 83（计算器真跑）；
  • 「读 README.md 开头」→ 真去仓库里读了文件；
  • 「北京今天天气」→ get_weather 返回真实天气数据；
  • 默认模式（只读）下，一个引用写文件工具的计划被静态校验直接拒绝——零产出。副作用默认是关的，开要服务端显式授权。

这轮还修了一个让我们惦记很久的 bug：工具结果按「字节」截断，会把 UTF-8 的中文字从中间劈开，JSON 一解析就炸（nlohmann 抛 type_error 316）。三处全部改成按字符安全截断——这个细节后来在别处又救了我一次。

09｜一段「诚实」工程的边界

如果说上一段是「把能力接进来」，这一段就是「把幻觉挡出去」。三个小故事：

① 只检索，不总结。

一句「查找最新的 super-agent 内容，并生成摘要」丢进去——系统只搜了，没总结，还宣告 Completed。

排查根因时发现一个结构性缺口：规划的 IR 里根本没有「综合」这种节点，模型把「写摘要」塞进了核心任务的描述里——而核心节点只负责分诊、不调用模型，自然没人去写摘要。修复不是打补丁，而是补齐缺失的节点类型：新增 synthesis 角色与 synthesize 边，解释器把上游检索结果收齐，真实调用 LLM 生成摘要，world 最后断言「摘要非空」。同时给 Planner 立了条规则：摘要 / 总结 / 报告，必须用 synthesis，不许塞进 core.task。

② 「这图看起来像模板。」

质疑永远是最好的测试，而这次人家说对了一半。我一度不服：图明明是模型现场生成的。一查根因发现真有问题——Planner 的 temperature 是 0，提示词里还躺着 4 个具象 few-shot 示例，模型干脆把示例的节点 id、形状原样抄了出来。

改法很朴素：去掉具象示例（只留字段示意图），temperature 提到 0.2。改完同一个问法连问两次，图的检索参数都会变；五条不同问法全部一次通过校验，节点名和结构开始「各长各的」。同时任务卡上加了「LLM 生成 / 脚本」徽标、详情里标了来源模型，还提供了「规划原文」视图——让「这张图到底是不是模型生成的」这件事变得可检验。诚实边界我们也如实写了：它仍是「受约束的生成」——校验器和解释器，就是那两堵墙。

③ 拒绝用模型记忆冒充阅读结果。

这是所有决定里我最喜欢的一个。任务：「下载歌德《少年维特之烦恼》，做 1000 字摘要，保存到文件」。

第一版翻车了——下载工具有 2 万字符上限，书有 26 万；更糟的是上游失败后，综合节点用模型的训练记忆编了一篇 1021 字的「摘要」——模型确实「读过」这本书，但那是它的记忆，不是本次任务真正抓到的文本。

修复分两半：

  • 新增 download_url 工具：全文落盘（默认上限 8MB），只回「路径 / 字节数 / 字符数」，不把正文塞进上下文；
  • synthesis 自动分片：20k 字符 × 12 片，逐片让 LLM 提取要点（map），再汇总成摘要（reduce）；
  • 最关键的一条：只要上游文件或结果为空、失败，synthesis 直接拒绝调用模型——「拒绝用模型记忆冒充阅读结果」，任务如实 Failed。

同一句话重跑：5 节点 user → core → download_url → synthesis → world，259k 字符 → 12 片 → 1344 字中文摘要 → 成功保存到本地文件。另外我们也照实记了一笔：模型抓到的是 Gutenberg 的英译本，不是德文原版——摘要基于实际抓到的文本，边界写得清清楚楚。

10｜常驻守护：SAD，和它的漏斗

对话层面跑顺之后，「SystemAgent」还有另一半没落地——不只是「用户问它然后它答」，而是常驻在系统里，自己看着系统。这一轮它有了名字：SAD（system agent daemon，常驻系统代理）。

设计主张是「预编排 + 多重拦截门」：

  • DAG 全部预编排，不在热路径运行时生成——加载期就能做静态校验、版本化、回滚；
  • 稳态事件 8~9 成走预编排 DAG；未匹配 / 高危 / 连续失败的，走受控升级（待归类队列、低频规划 gate、人审、诊断 DAG）——这里被我们自己纠正过：绝不搞「完全不生成」，否则新故障会「无图可用」；
  • 事件洪峰被一层层的门拦住：正常噪声，绝不允许唤醒编排。

L0–L4 门流水线：

事件源 → L0 规范化 → L1 去重合并 → L2 限流分级 → L3 准入 → L4 咨询门 → DAG 运行
                                                           │
                         未匹配 / 高危 → 升级队列（规划 / 人审 / 诊断 DAG）
                         全程：唤醒账 + 审计 + Reaper

每一道门都有明确的语义、配置、指标和失败策略；被丢弃的事件进 dead-letter，再按比例采样回放以量化漏报率——防「过度过滤把真故障也藏掉」。

先验机制，优先用离线 mock 验证（「世界先 mock」的路线在这里又一次兑现）：

984 条事件 → 候选被筛到 13 条 → 最终只唤醒编排 5 次 → 5 个预编排 DAG 全部执行。

其中 900 条是纯噪声、21 条去重、45 条限流；白名单事件 100% 进摘要层；影子审计测出漏报率 miss_rate = 0.412%。全程 1107/1107 测试全绿。

这套漏斗里还有几个「一等机制」——刻意不做成可开关的锦上添花：

  • 不可丢白名单（来电 / 短信 / 安全 / 财务 / 健康类）：无论是否匹配订阅都进摘要层；白名单由平台 / 用户定义，SA 无权修改；
  • 打扰预算：每天唤醒上限（例：5 次）、静默时段、超预算自动转静默摘要——预算是一等资源，不是可选项；
  • 漏报审计：影子抽样 + 事后检查「用户事后手动处理了哪些事」+ 监控 no-rule 桶，产出 miss_rate；
  • 每次丢弃可解释：每条被丢的事件都带 {rule_id, version, reason}，能回答「为什么丢」。

一句话概括分层哲学：规则决定「要不要建任务」，模型只负责「填槽」——规则库由人写、人审，可版本化、可回滚，SA 只提议。升级也是有界的：最多 1 次拓扑升级，交接包带着「已完成动作 + 剩余预算」，预算不重置，不可逆动作不重复执行。

再往后一轮，分层又被我（用户视角）自己纠正了一次：SAD 不该把每件事都接进来。它是最上层的粗略固定循环——事件 → 理解（LLM）→ 任务规格 → 提交 → 监控 → 关闭；只有需要全局协调的事件才进 SAD，其余直接下发给 Task Manager（零 LLM）。理解层输出的任务规格 JSON 里有一条很关键的规定：目标模板必须从预编排清单里选——理解层没有为任何具体事件写特例，换个新场景，不需要动理解代码。

11｜换到个人设备的最后一跃

云运维场景 demo 顺了，但更贴身的场景还没试过。于是把 mock 事件从数据中心切到每天揣在口袋里的那台机子：通知 / 电量 / 日历 / 安全 / 健康 / 下载 / 媒体 / 传感器。

常驻 SAD 处理起这些事：

  • 「妈妈微信提问」 → 读消息 → 草拟回复 → 发送 → 查日历 → 建提醒（一条跨消息 + 日历的任务）；
  • 「电量 15%，正在回家路上」 → 自动进入省电：降亮度、省电模式、精简通知；
  • 「会议 10 分钟后开始，但通勤要 25 分钟」 → 查路线、提醒出发、设闹钟；
  • 「异常登录（安全 crit）」 → 锁定屏幕、撤销会话、通知本人；
  • 「心率 150（健康 crit）」 → 核查、联系紧急联系人、告警。

而另一类事件被设计成根本不进 SAD：下载完成 → 通知、非归途低电 → 省电、好友消息 → inbox、媒体播放 → 摘要——本地事件直达任务层，零 LLM。

985 条 mock 事件分完账：全局 5 条进 SAD（5 次 LLM 理解），本地 4 条直达任务，总共 7 个任务。首跑 17.4 秒，缓存命中后 0.07 秒。

这里有个我反复玩味的数字：全程 985 条事件里，真正站上「LLM 关键路径」的，只有 5 个。

12｜业界的另一半

调研时顺手把业界拉了一份对照，结论有点扎心：大多数方案只做了一半。

  • Alertmanager / StackStorm / PagerDuty 这类：确定性工具（去重、规则、runbook）非常成熟——但没有智能，不会诊断、不会填槽；
  • AI SRE agents（Azure SRE Agent / AWS DevOps Agent / Datadog Bits AI SRE / HolmesGPT / K8sGPT）这类：有智能——但普遍缺严格漏斗、打扰预算、静态 DAG 审计，模型一旦被放进来，就忘了它该在哪一层出现；
  • LangGraph / AutoGen / CrewAI 这类编排框架：编排能力很强——但没有事件接入、过滤、预算、审计这一整套「系统侧」机制。

而 SAD 想占的位置，恰好是没人坐满的那个空位：确定性漏斗 + 静态 DAG + LLM gate + 唤醒账 / 审计。

它既不上头到「把所有事件交给模型」，也不死板到「一切靠人手写规则」——规则决定建不建任务，模型只在命中的规则上填槽。

附｜不写进宣传手册的纪律

几句话，是让我们敢写「全过」二字的底气。它们不性感，但缺一不可：

  1. 问题 + demo 驱动：每个论点必须有一个能跑的东西验证，拒绝空头方案。
  2. 真机模型不进 CI：所有带真实模型的验证环节手工跑，CI 里只有纯函数与离线 fixture——测试要快、要稳、要可重复，两者物理分开。
  3. 数字一致是硬要求：文档、报告、测试三处的数字必须对得上。从本专题 S7 的 1092 一路走到 S10c 的 1113，全仓串行全绿，才写「验收」二字。
  4. 诚实边界写进交付物：抓到了英译本照实记；上游失败只报 Failed 不编造；「受约束的生成」如实标注。这不是宣传时回避的东西，而是我们自己最在意的注脚。

✓结语

二十几轮研讨、两天多的密集迭代，把一个一句话概念，走到 1113 个测试全绿、两个 WebUI 编排台、一个离线全过的常驻 SAD 雏形。

这件事给我的答案，不是「用更大的模型」，而是：先想清楚模型该站在哪儿，再去想它该怎么站。

画工程边界，有时比堆参数更重要。

而 SystemAgent 最好的注脚，或许就是那个决定——上游失败时，综合节点拒绝调用模型：

你没有读到，就是没有读到。
