SystemAgent：从「一问一答」到「画图执行」

一个从清华 AURA OS 启发的想法，和那通打给妈妈的电话

这篇文章想聊的，是我给一类问题找到的解法——SystemAgent。它是什么、为什么值得做、以及它怎么变成一张能跑的图、一通能打完的电话。

简单说，它把 Agent 的「问一句、做一步、必须干等」，改成「画一张图、照着跑、有事才叫醒」。

先从一个名字说起。

01｜这个名字，是从清华 AURA OS 借来的

我最开始的灵感，是清华的 AURA OS（论文：《Blind Gods and Broken Screens: Architecting a Secure, Intent-Centric Mobile Agent Operating System》）里的 SystemAgent。那会儿我刚好一直在琢磨一个问题：一个 AI 系统里，「统筹全局」的角色，到底应该长什么样？

正好，我想做的是一个 AI 系统里的控制中枢——于是把「SystemAgent」这个名字借了过来。

说明一下：这只是借名。AURA OS 里的 SystemAgent，是那个操作系统里的一个组件；我做的这个，概念上并不是同一回事。

名字是借的，想法是自己的。这不影响故事往下讲。

02｜一句话，说清楚我在做什么

把一种循环，换成另一种循环。

原来的循环是这样的：

请求来了 → 想一想 → 调一个工具 → 等结果
      → 再想一想 → 再调一个工具 → …… → 得出结论

这个循环有个行话名字，叫 AgentLoop（也叫 ReAct，其实就是反复地「思考 → 行动 → 思考」）。它很好用，但有个很小又很致命的问题：中间那个「等结果」，是堵着的。

SystemAgent 想换成的循环长这样：

理解 → 画一张执行图 → 图上的节点各自执行
    → 做完了就上报 → 主流程接着处理 → …… → 得出结论

区别只有一句话：原来的循环是「边想、边做，不走完不停」；新的循环，是一套有状态的流程——每一步做没做、做到哪儿了，心里有数。

两种循环的差别，就是把「问一句、做一步、必须干等」的 Agent，改成「画一张图、照着跑、有事才叫醒」的状态机。

03｜最大的不同：从「干等」到「被叫醒」

传统 AgentLoop 和 SystemAgent 的本质差别，不在「循环还是状态机」这种表面形式，而在于：等一个慢结果的时候，它们在干什么。

原来的做法：调出一个工具，就傻等着它返回，期间什么都干不了。这就是「线性阻塞」。

SystemAgent 的做法：工具调用被拆成执行图上的一个个节点，节点跑节点的，主流程不用等。节点做完一件事，会主动把「事件」报上来，把主流程唤醒；主流程看一眼，再决定下一步。这就是「事件驱动 + 异步」。

打个比方：

  • 传统 Agent 像个接线员：每通电话都要经他转接，他得一直守着，接完一个才能接下一个；
  • SystemAgent 像个顾问：只在需要拿主意的时候被请出来，问完就走，活你自己接着干。

04｜为什么要改：现实不是「一问一答」的

现实里的任务，几乎都不是一次工具调用能做完的。举几个例子：

  • 下载一个很长的文件、甚至一整本书——工具可能要跑好几分钟；
  • 一个「操作界面」类的 Agent，在等页面上的某个按钮出现——它根本不知道要等多久；
  • 搜索、连接周围的设备——扫描、握手、授权，一长串步骤。

这些在传统 AgentLoop 里都很难办：只能先调工具，然后等。等也就算了，更麻烦的是——中途用户取消、工具出错，你就得回头收拾一大堆复杂的情况，特别容易翻车。

还有个更普遍的麻烦：用户跟 Agent 的交互是随时在变的。他可能中途打断你、补一句话、改一个要求——比如「别打电话了，还是发微信吧」。在一个「必须等结果才能继续」的循环里，这种善变的用户，几乎伺候不了。

所以我想：与其让一条循环把每一步都堵着，不如把每一步拆开、让它们各自独立，谁有进展谁说话。

05｜新的玩法：一张图，一个在后台听令的 Agent

新流程是这样的：

  1. 用户一句话进来，先由大模型把它理解清楚；
  2. 大模型把它变成一张执行图——图上的每个节点是一步要做的事，节点之间的连线是先后顺序；
  3. 执行交给执行引擎：它照着图一步、一步地跑；
  4. 这期间主 Agent 退到后台，不去盯每个节点，只「听」事件——节点做完了会主动上报；
  5. 主 Agent 被唤醒后做选择：
    • 一切顺利 → 让引擎继续往下跑；
    • 出了岔子（拒接、改口）→ 改一下这张图：换条边、加个节点、把任务改道，再让引擎接着跑。

图上的节点是什么？它可以是一次工具调用，也可以干脆是另一个子 Agent。都是由 SystemAgent 根据用户的需求，当下创建、当场分配的。

06｜抽出来看：它其实是「先计划、后执行」+ 异步

再抽象一层，SystemAgent 的思路其实不新，反而很古典——先有计划，再执行：

  • 先计划：把用户的话，先变成一张执行图；
  • 后执行：执行不再由 SystemAgent 亲自盯着，而是交给执行引擎按图来跑；
  • 异步：SystemAgent 只在「用得上」的时候才被唤醒——跑完一步，才被叫出来处理一步。

所以它本质上是更高级的「先计划、后执行」+「异步路由」的结合体：它不亲自干活，它只负责把活分下去、看着进度、随时调整。

07｜它解决了三个挠头的问题

① 任务能真正「停下来，再接着跑」。
执行图本身可以存盘，每个节点做到哪一步、状态也能存。所以任务随时可以被中断——比如关机、断电；重启之后检查一遍各节点的状态，就知道该从哪儿接着跑，不用从头再来。

② 任务能「边跑边调」。
用户随时可以打断、补充问题、看进度；路线不对，改一条边、换一个节点，都是实时的。

③ 它天生适合当系统的「底座 Agent」。
系统里每天产生海量事件（来消息、电量低、进程出错……），也有大量任务、进程、环境要处理。SystemAgent 可以当那个常驻的中枢：它不亲自调每个具体工具，只做协调、安排、调整——因此能实时响应，不会被某一件事拖住。

不亲自干活，所以能实时响应。

08｜先别急着上真机：这出戏是 mock 的

话题很深，所以先做减法：先用假数据，把整套流程测通，再谈真东西。

为此，我要讲一个我很喜欢的故事：给妈妈打电话。

拨号本身是个很成熟的功能，但它不是「调一次命令就完」的——它是一套状态机：

  • 正常流程：拨号 → 振铃 → 接通 → 通话 → 结束；
  • 意外流程：拒接、无人接听、中途挂断……

一个普通 AgentLoop，一次工具调用根本打不完这通电话。这里就得靠 SystemAgent：它启动一个「打电话」的状态机，随时接收状态机回传的消息，随时做调整。

为了把「复杂情况」演出来，我们用 mock 数据排了这么一出戏：

拨号被拒 → 自动重拨 → 接通 → 用户临时改口「去微信说」→ 核心把话改道到消息域 → 消息送达

09｜这出戏里：那张图，和那些消息

① 执行图

（此处放一张 demo 截图）
核心分诊 → 电话域拨号 → 拒接重拨 → 接通 → 改口改道 → 消息域送达

用文字还原，大概是这个形状：

你：「给妈妈打电话，没接就再打一次，打不通就发微信」
  │
  ▼
核心（听懂需求，拆成一张执行图）
  ├─ 电话域：先拨号 —— 这一步本身就是个状态机：
  │        拨号 → 振铃 → 接通 → 通话 → 挂断
  │        以及意外：拒接 / 无人接 / 中断
  ├─ 状态一变就上报：拨了、被拒了、通了……核心在后台等着
  ├─ 核心相机而动：
  │     · 被拒 → 让电话域「自动重拨」
  │     · 你改口「去微信说」→ 核心把话改道 → 交给消息域
  └─ 消息域：发微信，并让世界确认「已送达」

② 消息是怎么走的

按时间顺序，这场戏里最核心的几条消息：

你            ：给妈妈打电话
核心 → 电话域  ：发起拨号
电话域 → 核心  ：已拨号 / 振铃 / 被拒
核心 → 电话域  ：自动重拨
电话域 → 核心  ：接通，正在通话
你（插话）      ：别打了，去微信说
核心 → 消息域  ：改走消息域，把这套话说给妈妈
消息域 → 世界  ：消息已送达 ✓

③ 两个我最得意的细节

  • 全程核心（大模型）只被叫起来 2 次：一次决定自动重拨，一次决定改道。至于拒接、重拨、状态流转这些「看起来很忙」的活儿，全是电话域自己的状态机在后台悄悄干完的——能不吵醒大模型，就绝不吵醒。
  • 全程走的是一个「虚拟时钟」，27 秒跑完整出戏，没有一秒是真等：跑得快，每次结果还一模一样。

10｜接上真工具：它确实能真干活

到此为止都是 mock。SystemAgent 说白了，是一种更高级的「先计划、后执行 + 异步路由」。光讲故事不够，得接真工具验证。

我们建了一个工具目录，分两种模式：

  • 默认：17 个「只读」工具——只能看，不能改：计算器、时间、文件（读 / 列目录 / 搜索 / 抽样 / 采样）、旅行数据库（只读查询）、天气、论文检索、抓网页、读图片等；
  • 打开「副作用」开关后：再补上写文件、提交结果、执行命令，一共 20 个。

几个实测瞬间：

  • 「算一下 (23×7+5)÷2」→ 83。计算器真跑出来的，不是背的答案。
  • 「读 README.md 的开头」→ 真去仓库里把文件读回来了。
  • 「北京今天天气」→ 返回的是真实的北京天气数据。
  • 最值得说的一条：在默认只读模式下，一个计划里若偷偷引用了一个「写文件」的工具，会在跑起来之前就被静态校验拦下来——什么都不会发生，零产出。副作用开关默认是关的，要打开，得服务端显式授权。

一句话总结：它能干的活，是设计好的；它不能干的活，默认就干不了。
